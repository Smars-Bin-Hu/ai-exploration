# Basic 01 · 中文初稿（AI 写，供你改写）

按你的骨架和 brainstorm 定下的五处写成口语稿，约 2,300 字，讲下来 8–9 分钟。每段标了场景号，方便之后切分。括号里的〔画面〕是给自己看的提示，不念。

## 0 Hook

假设你今天要用 AI 开发一个功能。

你会怎么做？大概是这样：先把你觉得相关的代码文件一个个找出来，传给聊天框；再写一大段解释，告诉它这些代码是干什么的、怎么串起来的；然后把需求贴进去；最后再写满一屏的"要做这个""要加那个""千万别动那个"。

AI 还一行代码都没写，你已经忙了半个小时。然后你按下回车，期待它给你一个正确的结果。

〔画面：一长串 prompt〕

这个视频想讲清楚三件事：这种用法哪里出了问题，问题的根子在哪里，以及我们缺的那块东西叫什么。

## 1 你的痛点

如果你这样用过 AI，下面这几件事你应该都碰到过。

第一，它不知道你的项目。每一次，都要你去找代码、贴代码、解释代码。

第二，它会丢记忆。新开一个对话框，前面讲过的全都没了，你得从头再说一遍。而且你会发现，同一个对话聊得越久，它的表现好像越差，前面说好的事情，后面就忘了。

第三，你说了很多要做什么、不要做什么，它不一定照做。大多数时候它听话，可总有那么几次，偏偏跳过了你最在意的那一步。

第四，它检查自己的时候总是很自信。"已经完成了，测试全部通过。"等你拿到手一看，还有一堆错。

第五，你看不到它到底做了什么。它改了哪些文件、跑了哪些命令、为什么这么改，事后很难说清楚。

〔画面：一个痛点一张图〕

## 2 根因

这是不是你现在用 AI 的方式？

其实这就是 2024 年用 AI 的方式：把它当成一个聊天机器人。

问题不在 AI 不够聪明。问题在于，它周围本该由程序做的事，现在全压在你身上：找代码、记住上下文、盯着它按流程走、检查它的结果，全靠你手工去做。人一累就会漏，所以又累，又靠不住。

## 3 什么是 agent

那 agent 又是什么？

你平时和 AI 聊天，其实是在直接和大模型，也就是 LLM 对话：它思考，然后写一段文字回答你。

agent 是在 LLM 上加了 tool calling，也就是调用工具的能力。你可以把工具理解成它的手：想清楚以后，它可以自己去改你本地的代码文件、跑命令、上网搜索、打开浏览器。

但光有手还不够，关键是它会循环：调用一个工具，看一眼结果，再决定下一步做什么；再调用，再看，一直做到把活干完。

有了手，又会自己循环，agent 就诞生了。它不再只是回答你，而是能自己把一件事做完。

〔画面：LLM → 工具 → 结果 → 下一步，一个圈〕

## 4 什么是 harness

agent 能自己干活了，新问题也就来了。

回头看这几年：2024 年，大家研究的是怎么把 prompt 写好；2025 年，大家发现要做好 context engineering，管好 AI 的上下文，它才能发挥得稳定；到了 2026 年，coding agent 已经能真正帮你干活，比如 Claude Code、Codex、GitHub Copilot。能干活，也就意味着它可能做危险的事。怎么让 agent 干得又稳又好，这门功夫，就叫 harness engineering。

有一个公式：Agent = Model + Harness。模型之外的那些东西，都是 harness。

对照刚才那五个痛点，harness 要管的正好是五件事：

- 它不知道项目、会丢记忆，靠的是上下文管理；
- 它不一定照做，靠的是工作流和批准；
- 它可能做危险的事，靠的是拦住危险操作；
- 它自查太自信，靠的是让另一个 agent 来检查；
- 它是个黑盒，靠的是事后能审计它做了什么。

这些事以前都靠你在 prompt 里叮嘱，现在交给程序来做。

〔画面：Agent = Model + Harness，五件事围着模型〕

## 5 我的 harness

我自己开发了一个 harness 框架，它基于 VS Code 里的 GitHub Copilot。

如果你的团队是微软的客户，大概率同时在用两个 Copilot：M365 Copilot 和 GitHub Copilot。其中 GitHub Copilot 就是我们说的 coding agent，和大名鼎鼎的 Claude Code、Codex 是一类东西。我的 harness，就是帮你更好地驾驭 GitHub Copilot。

还是对着那五件事，看看在我的 harness 里分别是什么样子。

第一，记忆。每个任务都有自己的文件夹，需求、计划、进度都写在里面。聊天关了没关系，新开一个聊天，它从文件夹接着干。团队还可以有一个知识库，把项目的结构和坑写下来，agent 每次开工前先读。

〔画面：任务文件夹；新聊天接着干〕

第二，流程。一个开发任务一定是：先确认需求，再批准计划，最后批准写回。每一步都要你在看板上亲手输一串码，agent 跳不过去，也替你按不了。

〔画面：三个批准，输码的窗口〕

第三，边界。agent 只改代码的副本，碰不到你的仓库。它想 `git push`，会被一个叫 gate 的检查当场拦下，还会告诉它为什么。

〔画面：被拦下的命令和原因〕

第四，检查。你可以让另一个 agent 独立检查它的工作，没过就打回去改，过了才能写回。

〔画面：独立检查发现问题〕

第五，审计。它做过的每一步、被拦下的每一次、花了多少时间，都记在看板上，事后一目了然。

〔画面：看板的 Records 和任务报告〕

## 6 总结

所以，AI 并没有变笨，是我们的用法还停在 2024 年：把它当聊天机器人，人来做搬运、盯流程、做检查。

agent 把搬运交给了程序，harness 把流程、检查和边界也交给了程序。人终于可以退回来，只做判断和把关。

如果你在团队里推 AI，先别急着问"换哪个更强的模型"，先问一句："我们的 AI 周围，缺了什么？"
