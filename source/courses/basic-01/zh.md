# Basic 01 · 中文中文稿

## 0 Hook

2026年，很多团队都希望AI能落地到团队的开发中，很多公司给员工订阅了AI 聊天服务或者coding agent，比如Claude Code，CodeX，或者GitHub Copilot。然而在实践过程中，我们发现很多团队依然只是用AI完成它们日常工作中很小的一部分工作，甚至很多人使用AI的方式依旧是一问一答的聊天。

（画面：Claude Code，CodeX，和 GitHub Copilot 要出现）

打个比方，你是一个Software Engineer，现在手上有一个很庞大的老系统，你拿到业务方给你的一个需求，这个需求你之前已经做过很多类似的功能了，你清楚地知道最佳solution是什么，比如你要去改哪些代码，怎么测试，代码前后的依赖，影响面，你都有经验。现在强行就是让你用AI来完成，你会怎么做？

大概是这样：先把你觉得相关的代码文件一个个找出来，传给聊天框；再写一大段解释，告诉它这些代码是干什么的、怎么串起来的；然后把需求贴进去；最后再写满一屏的"要做这个""要加那个""千万别动那个"。

AI 还一行代码都没写，你已经忙了半个小时。然后你按下回车，期待它给你一个正确的结果。
可最后的结果往往是，AI 大概率给你80%～90%满意度的回答， 你把它给你写好的code粘贴回去，自己跑测试、自己验证结果...结果发现还是有一些地方是错的，你又花了更多时间来审查代码...最后你觉得，用AI还不如自己写来的快，AI理解不了你们的复杂系统，看不到你们的坑。

〔画面：一长串 prompt，AI的答案，奔溃的你〕

这个视频想讲清楚三件事：这种用法哪里出了问题，为什么开发团队很难让AI落地，以及我们缺的那块东西叫什么。

## 1 你的痛点

如果你这样用过 AI，下面这几件事你应该都碰到过。

第一，它不知道你的项目。每一次，都要你去找代码、贴代码、解释代码。

第二，它会丢记忆。新开一个对话框，前面讲过的全都没了，你得从头再说一遍。而且你会发现，同一个对话聊得越久，它的表现好像越差，前面说好的事情，后面就忘了。

第三，你说了很多要做什么、不要做什么，它不一定照做。大多数时候它听话，可总有那么几次，偏偏跳过了你最在意的那一步。尤其聊天越久，历史对话越多，AI的注意力越飘逸，老的内容越不记得。

第四，它检查自己的时候总是很自信。"已经完成了，测试全部通过。"等你拿到手一看，还有一堆错。

第五，你看不到它到底做了什么。它改了哪些文件、跑了哪些命令、为什么这么改，事后很难说清楚。

〔画面：一个痛点一张图〕

## 2 根因

这是不是你现在用 AI 的方式？

其实这就是 2024 年用 AI 的方式：把它当成一个聊天机器人。

2024年，大部分人仍然在研究怎么写好一个prompt，AI才能表现得更好，于是大家叫这个所谓 Prompt Engineering。但问题是，AI大模型即使足够聪明，你依然把AI当成一个回答问题的人，你没有让它上手干活。除了回答你的问题，其他任务，依然全压在你身上：找代码、整理需求、跑测试、记住上下文、盯着它按流程走、检查它的结果，全靠你手工去做。

最后很容易就会听到一种论调：AI不可靠，AI会犯错，AI只能帮我一部分工作...

## 3 什么是 agent

这里，就必须讲讲什么是AI Agent。

你平时和 AI 聊天，其实是在直接和大模型，也就是 LLM 对话：它思考，然后写一段文字回答你。agent 是在 LLM 上加了 tool calling，也就是调用工具的能力。你可以把工具理解成它的手：想清楚以后，它可以自己去改你本地的代码文件、跑命令、上网搜索、打开浏览器。但光有手还不够，关键是它会循环：调用一个工具，看一眼结果，再决定下一步做什么；再调用，再看，一直做到把活干完。

有了手，又会自己循环，agent 就诞生了。它不再只是回答你，而是能自己把一件事做完。

〔画面：LLM → 工具 → 结果 → 下一步，一个圈〕

## 4 什么是 harness

agent 能自己干活了，新问题也就来了。

回头看这几年：2024 年，大家研究的是怎么把 prompt 写好；2025 年，大家发现要做好 context engineering，管好 AI 的上下文，它才能发挥得稳定；到了 2026 年，coding agent 已经能真正帮你干活，比如 Claude Code、Codex、GitHub Copilot。能干活，也就意味着带来了新的问题。

企业发现，Agent落地需要解决这些问题：

- 它不知道你们的系统项目，每次还是需要人来介绍；
- 跨会话的记忆怎么保存？一个session断了，另一个session如何接着做任务？
- 人只拿agent来改代码，剩下的跑测试、CI/CD pipeline、更新工单还是人来做；
- 约定好的规则，它不一定照做；
- 不敢开放Server给它，因为它可能做危险的事（比如删表）；
- 它做完一个任务，它倾向于自信地认为自己的结果是正确的；
- 钱和时间都花哪里了，怎么优化；任务过程的计划、日志、痕迹统统没记录；
- 人的注意力最多管理5个会话，人的注意力变成了Agent干活的瓶颈；
- 一个长任务、复杂任务，agent 总是会停下来；

问题太多太多了。怎么让 agent 干得又稳又好，这门功夫，就叫 harness engineering。

有一个公式：Agent = Model + Harness。模型之外的那些东西，都是 harness。

这些事以前都靠你在 prompt 里叮嘱，现在交给程序来做。因为程序是确定性的，不花token，不靠模型自觉，我们把确定性的任务交给程序，需要判断和思考的事情交给Agent。

〔画面：Agent = Model + Harness，五件事围着模型〕

## 5 我的 harness

我自己开发了一个 harness 框架，它基于 VS Code 里的 GitHub Copilot。

如果你的团队是微软的客户，大概率同时在用两个 Copilot：M365 Copilot 和 GitHub Copilot。其中 GitHub Copilot 就是我们说的 coding agent，我的 harness，就是帮你更好地驾驭 GitHub Copilot。

还是对着那些缺口，看看在我的 harness 里分别是什么样子。

- 它不知道你们的系统项目，每次还是需要人来介绍；

我打造了一个标准代码库转知识库框架，通过一套工具来学习你的代码库，找到文件之间潜在的依赖关系，形成卡片，最后完成学习后生成总结文件和目录。Agent每次不需要重新读代码，只需要加载总结文件和部分卡片，就能大概了解你们的代码库，如果有需要，它能直接通过目录找到对应的文件。 

- 跨会话的记忆怎么保存？一个session断了，另一个session如何接着做任务？

每个任务是一个folder，里面存放了整个任务全生命周期的文件，包括任务计划、历史日志、状态，需求文档、测试脚本、改动的代码、以及任何agent在工作中产生的结果，都会保存在里面，这样即使一个会话死掉了，另一个会话只需要扫描这个任务目录，就能马上接着做。

- 人只拿agent来改代码，剩下的跑测试、CI/CD pipeline、更新工单还是人来做；不敢开放Server给它，因为它可能做危险的事（比如删表）；

给Agent访问开发环境和测试环境的权限，agent可以自己开发、自己写测试脚本、自己执行并自己改。对于安全性，我是这么来做的：通过提供标准的 Toolpack，给Agent开放了访问 lower enviornment 的只读权限，对于写和执行权限，必须经过人来审批，比如微软的SQL Server，我的harness前后跑了几千种危险命令的注入情况，通过黑名单、白名单和给人决策，以及账号本身的权限，保证了Agent的安全访问。

- 它做完一个任务，它倾向于自信地认为自己的结果是正确的；

通过引入独立的revier 作为subagent，让subagent来review agent的全部任务，并且给出测试判定。实战表明，reviewer能发现大量主agent没有考虑到的情况。

- 钱和时间都花哪里了，怎么优化；任务过程的计划、日志、痕迹统统没记录；

建立一套task report面板，专门来看整个任务的统计信息，时间花哪了，钱花哪了，哪些tool calling失败了，所有结论一目了然

- 还有很多别的，在这里由于时间问题，就不再一一列举。

## 6 总结

所以，AI 并没有变笨，是我们的用法还停在 2024 年：把它当聊天机器人，人来做搬运、盯流程、做检查。

agent 把搬运交给了程序，harness 把流程、检查和边界也交给了程序。人终于可以退回来，只做判断和把关。

如果你在团队里推 AI，先别急着问"换哪个更强的模型"，先问一句："我们的 AI 周围，缺了什么？"
