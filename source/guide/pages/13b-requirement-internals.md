This file holds the code-level detail behind the feature file 13 Requirement and intake: the digest of `REQ.md`, the confirmation line, `confirm-req` and `approve-plan --with-req` step by step, the gate's person-only folders, the intake commands and the Intake tab, the Word and Excel converter and its report, and the code that reads the "Done when" items. It is for "how does it work" and "where in the code" questions; what the requirement is for, and how a person uses it, is in the feature file.

## Requirement internals: the file `REQ.md` and who writes it

`REQ.md` is a Markdown file at the root of the task folder, made by `task new` for the tiers `medium` and `full` from the template `.harness/contracts/templates/task/<language>/REQ.md`, with `{name}` filled in. The template is read from the language of the run, then from a template placed directly in `templates/task/`, then from the default language; if none is found a one-line fallback is used, so a task never fails to start over a template {src:.harness/engine/modules/task/tasklife.py#L86-L123}. The template has a "User confirmed" line (`<not yet / confirmed yyyy-mm-dd>`) and the sections What to do, What not to do, Done when (three sub-headings: shown by the task files, shown by a run before the promote, shown after the promote), Source, Not clear yet, Changes {src:.harness/contracts/templates/task/en/REQ.md#L1-L42}.

The agent writes the content, with its edit tools, told by text (the skill `harness-my-task` and the hook reminder); no code writes or judges what the requirement says {src:.github/skills/harness-my-task/SKILL.md#L60-L110}. The code fills one thing in the file: the confirmation line, after the person's code (see the section "Requirement internals: `confirm-req` step by step"). The agent's edit tools are not refused on `REQ.md`: it sits at the root of the task folder, not in a person's folder, and the gate only keeps the agent inside the task folder {src:.harness/engine/modules/gate/handler.py#L64-L94}.

The reviewer judges against `REQ.md`. The review package, which `task review start` writes for the independent check, lists `REQ.md`, `PLAN.md` and `REQ/` under "Where the requirement is"; the reviewer's instructions say to check against what `REQ.md` says now, and the hook tells the agent that a check goes by `REQ.md` only {src:.harness/engine/modules/task/taskreview.py#L283-L298} {src:.github/agents/reviewer.agent.md#L44-L49}.

## Requirement internals: how the digest `req_digest` is computed

`req_digest(root, task)` in `core/tasks.py` is the sha256 (hex) of what `REQ.md` asks for; it returns an empty string when there is no `REQ.md`. `req_digest_of(text)` does the work for a text, so that a rewind can judge a file as it was then {src:.harness/engine/core/tasks.py#L117-L149}.

The rule: the file is read line by line. A line that matches a heading (`#` to `######`, optional space, then the title) switches a flag. The flag is on when the title, stripped of `*`, `_` and spaces and lower-cased, is exactly one of `what to do`, `what not to do`, `done when`, `要做什么`, `不做什么`, `做完的标准`. Heading lines themselves are not hashed. Non-empty lines under a flagged heading are kept, each with its whitespace collapsed to single spaces, and joined with one space, so a paragraph wrapped in another way gives the same digest {src:.harness/engine/core/tasks.py#L117-L149}.

Four consequences follow from that code. First, the match is exact: a section renamed ("Scope", "What to build") is not counted, and the Chinese names count only as written above. Second, a section the digest does not count (Source, Not clear yet, Changes, the confirmation line) can change freely without undoing a confirmation or an approval. Third, any heading, of any level, ends the counted region, because the flag is reset at every heading. The template puts the "Done when" items under three `###` sub-headings; read literally, only text directly under `## Done when`, before its first sub-heading, is counted, so a change to an item under a sub-heading does not change the digest. This is the code as read at 1.8.3; the reviewer's own parser of "Done when" (the section "Requirement internals: how `[T]`, `[R]` and `[A]` items are read") does include the sub-headings. Fourth, if the file has none of the three counted headings, the whole text counts, except lines that contain the confirmation words `用户确认` or `user confirmed` {src:.harness/engine/core/tasks.py#L117-L149}.

Two stored digests use it. `.task/task.json` holds `req.confirmed_sha256` (written by `confirm-req`) and `plan.req_sha256` (written by `approve-plan`), both from `req_digest` {src:.harness/engine/modules/task/task.py#L601-L612} {src:.harness/engine/modules/task/task.py#L469}. The code the person types is a different hash: the first six characters, upper-cased, of the sha256 of the whole `REQ.md` text (for `confirm-req`) or of the hash of both files (for `approve-plan --with-req`) {src:.harness/engine/core/approval.py#L17-L25}.

## Requirement internals: the confirmation line and the five values of `req_state`

`req_state(root, task)` in `modules/task/task.py` returns one of five strings, and every other part of the harness asks it: the board, the task page, the stage list, the next-step text and `approve-plan` {src:.harness/engine/modules/task/task.py#L551-L567}.

- `none`: there is no `REQ.md`, or it has no confirmation line.
- `unwritten`: the line exists, is not filled, and the text still holds the template's own first words (`<One or two paragraphs` or `<一两段`).
- `open`: written, not confirmed.
- `changed`: the person confirmed once (a digest is on record) and what the requirement asks is different now.
- `confirmed`: the line is filled and no change is on record.

The order of the checks is fixed: `taskreview.req_confirmed` first (None gives `none`, True gives `confirmed`), then `req_changed` (gives `changed`), then the read of the file for the unwritten marks {src:.harness/engine/modules/task/task.py#L551-L567}.

The regular expressions that decide whether the confirmation line is filled are in `taskreview.py`. The label is found by search, in any language: `用户确认` or `user confirmed`, case-insensitive. The first line that has the label is the line. What follows the label, lower-cased, counts as filled when it matches `已确认`, `confirmed` or a date of the form `dddd-dd-dd`, and does not match `还没确认`, `not yet`, `not confirmed` or `yyyy-mm-dd`; the template's own value contains both a confirmed word and "not yet", so it is not filled {src:.harness/engine/modules/task/taskreview.py#L45-L47} {src:.harness/engine/modules/task/taskreview.py#L88-L110}. `req_confirmed` returns the line's state and false when `req_changed` is true; `req_changed` is true when a digest is on record (`req.confirmed_sha256`) and the current `req_digest` differs from it {src:.harness/engine/modules/task/taskreview.py#L113-L116}.

Who writes the line is not checked. The code reads text. A line the agent writes as "confirmed 2026-11-19" counts as `confirmed` while no confirmation by the person is on record. Once a person has confirmed, a digest is on record, and a later change to the counted sections makes the state `changed` whatever the line says. The agent is told by text never to touch the line {src:AGENTS.md#L51}. Even a line faked by the agent leaves `DEV/` closed: `DEV/` opens only when the plan is approved, and the approval needs the person's typed code and is written only by `approve-plan` into `.task/task.json`, which the agent's edit tools cannot write {src:.harness/engine/modules/gate/handler.py#L64-L94} {src:.harness/engine/modules/task/task.py#L428-L475}.

## Requirement internals: `confirm-req` step by step

`task confirm-req` (`confirm_req` in `modules/task/task.py`) is the person's command. In order {src:.harness/engine/modules/task/task.py#L570-L612}:

1. `person("confirm-req", ...)` asks `approval.require_person`: stdin and stdout must be a terminal, or the board's Terminal window must hold a one-time code (the next section). Otherwise the command stops with the message that only the user can run it.
2. It picks the task (the one open task, or `--task`), requires the task open, and reads `req_state`. State `none` or `unwritten` is refused ("not written yet, or has no confirmation line"); state `confirmed` is refused ("confirmed already").
3. It reads `REQ.md`, takes the sha256 of the whole text as `digest`, prints a short screen (the file name, its number of lines) and asks the person to type the code, which is the first six characters of `digest`, upper-cased. A wrong answer is a refusal; the person may type it in lower case, because the comparison upper-cases the answer {src:.harness/engine/core/approval.py#L50-L58}. If there is no keyboard (the board's Terminal window), the command says to use the board button or a terminal of one's own.
4. Under the task's lock it reads the file again. If the hash is not the one the code was made for, the command stops: "the requirement changed while you were confirming".
5. `fill_confirmation` rewrites the line and records the digest. It looks for a line of the form list mark, optional bold, `用户确认` or `User confirmed`, optional bold, a colon (ASCII or full-width), then the value; it replaces the value with `confirmed` and today's date (`已确认` when the label is Chinese). A line not of that form is left as it is, but the digest is recorded all the same. It writes `req.confirmed_sha256` (the digest of the counted sections, not the code's hash) and `req.confirmed_at`, and adds a history line `confirm-req` carrying the first twelve characters of the whole-file hash {src:.harness/engine/modules/task/task.py#L601-L612}.
6. If the task has no plan yet and is not delivered, it sets `waiting` to `go-req`, so the board and the task page offer the message that tells the agent to go on; a delivered task waiting for acceptance is not given that mark {src:.harness/engine/modules/task/task.py#L596-L598}.

The page and the board do not offer **Confirm requirement** while any line of `REQ.md` is still the template's `<...>`: `req_placeholders` counts such lines, and the board and the task page drop the action when it is above zero {src:.harness/engine/modules/task/taskboard.py#L265-L266} {src:.harness/engine/modules/task/taskdesk.py#L538-L548}. A placeholder line is one that is only `<...>` after an optional list mark and item number (`- [R1] <ENV>: <...>` counts); real text that holds an angle bracket does not {src:.harness/engine/modules/task/task.py#L484-L508}.

## Requirement internals: `approve-plan` and `--with-req` step by step

`approve_plan` in `modules/task/task.py` approves `PLAN.md` for the requirement as it is now. A plan stands on a confirmed requirement (since 1.5.30). The steps {src:.harness/engine/modules/task/task.py#L428-L475}:

1. `person("approve-plan", ...)` requires a person (terminal, or the board's vouched Terminal window or button). The command line in `commands.py` is wrapped by `guarded`, which stops a person's command while the agent is in the middle of a turn, unless `--force` is given {src:.harness/engine/modules/task/commands.py#L106-L117} {src:.harness/engine/modules/task/commands.py#L258-L260}.
2. It requires the task open and a `PLAN.md` that is not empty (`plan.missing`).
3. It reads `req_state`. `unwritten` is refused outright with `plan.req.unwritten` ("the requirement is not written yet"), whether or not `--with-req` is given. `open` or `changed` without `--with-req` is refused with `plan.req.unconfirmed`, which names the command `approve-plan --with-req` and the alternative `confirm-req` {src:.harness/engine/core/messages.en.json#L2040-L2041}. State `none` (no `REQ.md`, or no confirmation line) and `confirmed` pass, and `--with-req` has no effect on them: the plan is approved alone.
4. With `--with-req` on an unconfirmed requirement, the code to type belongs to both files: `plan_digest_with(req_text, plan_digest)` is the sha256 of the hex hash of the requirement text followed by the hex hash of the plan; the code is its first six characters, upper-cased {src:.harness/engine/modules/task/task.py#L423-L425}. Without it the code is the first six characters of the plan's hash alone. The screen names both files and the folder `DEV/`.
5. Under the lock it reads again. The plan changed meanwhile: refused (`plan.changed`). The requirement changed meanwhile: refused (`req.changed`).
6. It fills the confirmation line (`fill_confirmation`, as for `confirm-req`), so one code leaves two records: the line and `req.confirmed_sha256`.
7. It writes `plan.approved_sha256`, `plan.approved_at` and `plan.req_sha256` (the digest of the requirement it was approved for), adds the history line `approve-plan`, sets `waiting` to `go-plan` (nobody told the agent: the board says so until the next prompt) and takes a snapshot of the task folder named `plan` {src:.harness/engine/modules/task/task.py#L460-L475}. A `--with-req` approval therefore leaves two history lines, `confirm-req` and `approve-plan`.

The code is uppercase hexadecimal: its characters are the digits 0 to 9 and the letters A to F, so it contains digits as well as capitals. Before 1.7.38 the requirement's code was eight small characters; it is not accepted any more {src:.harness/engine/core/approval.py#L17} {src:.harness/engine/core/approval.py#L57}.

On the board and on the task page the person does not choose `--with-req`. `web/serve.js` sets `with_req` itself when the action is `approve-plan` and the row carries `req_unconfirmed`, and the Approve plan window shows one code for both files; the server then calls `approve_plan(with_req=True, interactive=True)` with the code the person typed in the page {src:.harness/engine/modules/task/web/serve.js#L292-L295} {src:.harness/engine/modules/task/boardserve.py#L809-L812} {src:.harness/engine/modules/task/boardserve.py#L829-L830}. `req_unconfirmed` is set on a board row when the task is open and `req_state` is `open` or `changed`; on the task page it is further limited to the tier `full` {src:.harness/engine/modules/task/taskboard.py#L267} {src:.harness/engine/modules/task/taskdesk.py#L575}. When a plan is written but not approved and the requirement is `open` or `changed`, the agent's next-step text is the `task.step.approve_req` message, which tells the user to read both files and press Approve plan, so that one ask is made, not two that say different things {src:.harness/engine/modules/task/task.py#L290-L295}.

## Requirement internals: why only a person can confirm or approve

Three layers hold, and none is the agent's choice. First, `approval.require_person` accepts a command only when stdin and stdout are a terminal, or when the board's Terminal window has vouched for it. The board makes a one-time code per command typed in its Terminal window, keeps only the code's fingerprint in a folder of the guardrail lists that the agent's file tools cannot write, and the command uses it once; a code not used expires after 600 seconds {src:.harness/engine/core/approval.py#L28-L42} {src:.harness/engine/core/boardperson.py#L1-L24}. An agent has no paired browser, so the board makes no code for it. The module says this raises the bar and is not a sandbox: a process of the same user that builds the path at run time can still reach the folder {src:.harness/engine/core/boardperson.py#L1-L24}. Second, the gate refuses the command on the agent's command line: the pattern in `gate.json` names `task approve-plan` and `task confirm-req` (the `--with-req` form is the same command) among the commands only the user may run {src:.harness/policies/gate.json#L131-L137}. Third, the code itself is bound to the file contents (the digest above), so a code cannot be used for another version {src:.harness/engine/core/approval.py#L1-L8}. The board's buttons go through `/api/act`, which needs the browser to be paired and the code the person typed {src:.harness/engine/modules/task/boardserve.py#L809-L830}.

## Requirement internals: what happens when the requirement changes after the plan was approved

`plan_approved` in `core/tasks.py` is true only when `plan.approved_sha256` equals the current hash of `PLAN.md` and `plan_req_changed` is false. `plan_req_changed` is true when `plan.req_sha256` is set and differs from the current `req_digest` {src:.harness/engine/core/tasks.py#L152-L164}. So a change to the counted sections of `REQ.md` (see the digest section above) undoes the approval, with no action by anyone.

An approval stored before `req_sha256` existed has an empty value there; `bool(kept)` is false, so there is nothing to compare and the plan stays approved {src:.harness/engine/core/tasks.py#L152-L156}. The same holds when the plan was approved while `REQ.md` did not exist (the digest was an empty string).

Effects of an unapproved plan: for the chat that holds the task, the gate's `check_task_write` denies any edit-tool write under `DEV/`. When the plan was approved before and only the requirement changed, it uses the dedicated reason `gate.task.plan_req`, not the plain "approve the plan first" one. That message tells the agent to check that `PLAN.md` still fits the requirement (and change it if not), stop and tell the user to read both again and confirm and approve on the task page, go on when the user says it is approved, and meanwhile write only notes, RCA, design and read-only queries at the root of the task folder (code waits, code run by hand too) {src:.harness/engine/modules/gate/handler.py#L73-L90} {src:.harness/engine/core/messages.en.json#L427}. The promote command (the dry run and the write-back both go through `require_plan`) and autorun (the board does not offer `autorun on` without an approved plan) check `plan_approved` too, and the stage falls back to the requirement {src:.harness/engine/modules/task/task.py#L404-L406} {src:.harness/engine/modules/task/task.py#L911-L915} {src:.harness/engine/modules/task/taskboard.py#L263-L264} {src:.harness/engine/modules/task/taskstages.py#L56-L67}. Work already in `DEV/` stays; only new writes by the edit tools are refused. Nothing in the gate covers a shell command writing to `DEV/`.

`task approve-plan` alone is refused when `req_state` is `changed` (the message `plan.req.unconfirmed`); the person approves again with `--with-req`, which confirms the changed requirement and the plan with one code {src:.harness/engine/modules/task/task.py#L443-L451}. When the person's old confirmation lapses, `req_confirmed` returns false (it requires `not req_changed`), so the line in the file may still read "confirmed" while the state is `changed` {src:.harness/engine/modules/task/taskreview.py#L88-L100}.

A rewind restores a file as it was; `rewind.req_after` reports `lost` when the requirement is confirmed now and the restored `REQ.md` has no filled line or a different digest, so the requirement waits for the person again. `REQ/`, `REF/` and `INBOX/` are skipped by rewind and by snapshots (`PERSON_DIRS`), so a rewind or a snapshot never touches the person's documents {src:.harness/engine/modules/task/rewind.py#L36} {src:.harness/engine/modules/task/rewind.py#L287-L303} {src:.harness/engine/modules/task/tasksnap.py#L31}.

## Requirement internals: the reminder `task.inject.req` at every prompt

The hook handler builds the text it injects at session start and with every user prompt: `prompt_text` calls `task_text` for a session that holds an open task. `task_text` adds the message `task.inject.req` whenever the task folder has a `REQ.md` {src:.harness/engine/modules/task/handler.py#L93-L108} {src:.harness/engine/modules/task/handler.py#L162-L170}. The text says: when what the user asks in this prompt differs from `REQ.md` or adds a new condition, change `REQ.md` first and add a line to its change record, then touch the work; a direct instruction ("write it as ...") is a change of the requirement too; an independent check goes by `REQ.md` only {src:.harness/engine/core/messages.en.json#L108}. It is not sent to an admin session or to a session with no task, and it is sent whatever the prompt says. Whether the prompt conflicts with `REQ.md` is decided by the model reading the reminder; no code compares the prompt with the file. What code does is the digest above: if the agent does change the three sections, the confirmation, the plan's approval and `DEV/` lapse; if it does not, nothing does.

## Requirement internals: the person's folders `REQ/`, `REF/` and `INBOX/` and how the gate keeps the agent out

`tasks.PERSON_DIRS = ("req", "ref", "inbox")` is the list of the person's folders, in lower case because the gate compares without regard to case {src:.harness/engine/core/tasks.py#L37}. In `check_task_write` the gate takes the first folder of the written path under the task, lower-cases it, and denies the write when it is in the list, with the reason `gate.task.person_files` (these folders hold what the user gave and are read only; write notes and results at the root of the task folder) {src:.harness/engine/modules/gate/handler.py#L91-L93} {src:.harness/engine/core/messages.en.json#L431}. The earlier checks of the same function decide first: a path outside the task folder, or the task folder itself, is `task_outside`; under `DEV/` the plan rule applies; the person's-folder rule is the last {src:.harness/engine/modules/gate/handler.py#L77-L94}.

The rule binds only a session that holds an open task. `check_task_write` returns no decision when the session has no `active_task`, or the task is gone or closed {src:.harness/engine/modules/gate/handler.py#L67-L72}. It applies to the agent's edit and create tools; the terminal checks do not know `PERSON_DIRS`, so a shell command that writes into `REQ/`, `REF/` or `INBOX/` is not refused by this rule {src:.harness/engine/modules/gate/handler.py#L117-L139}. When the gate's own policy file cannot be read, the handler runs on a built-in copy of the shipped policy and `fallback.refine` adds a stricter net: a write tool passes only inside the open task's folder, a git write is refused, and a shell command that writes a file outside that folder is refused. Writes inside the task folder, including `REQ/`, are not covered by that net; the edit tools' person's-folder rule still runs on top {src:.harness/engine/modules/gate/handler.py#L796-L803} {src:.harness/engine/modules/gate/fallback.py#L1-L14} {src:.harness/engine/modules/gate/fallback.py#L141-L158}.

The design reason: these folders hold what the person brought, and evidence the agent could edit would not be evidence. The person's page and commands write them; the agent records the result of a run through a command that judges it (`task run record`, `task test record`, into `RUNS/`) {src:docs/05-design.md#L208-L210}. `REQ/` is a different thing from `REQ.md`: `REQ.md` is at the task root and the agent writes it; `REQ/` holds the documents, the converted files, the pasted tables, `INTAKE.md`, `originals/`, `media/` and the tool-made `.pristine/` copies {src:.harness/engine/modules/task/intake.py#L1-L11}. `REF/` holds reference material: files the person adds on the Files tab, `REF/from-<old>/` copied by `task fork`, and a hand edit kept by `task recover`; it is not written back {src:.harness/engine/modules/task/taskfork.py#L1-L10}.

## Requirement internals: what `INBOX/` holds and who names its files

`INBOX/` (since 1.5.42) holds what the person gives the task on its page, written by the board server. For an environment the person ran something in, the server writes `INBOX/<ENV>/<time>/` with `given.txt` (the output), `ran.txt` (the commands, when given) and `image-N.<type>`. A command the person runs from the page leaves the same two files under `INBOX/BOARD/<time>/` {src:.harness/engine/modules/task/taskinbox.py#L1-L11}.

The server picks every name and caps every size. The environment name must match a letter followed by up to eleven letters, digits, `_` or `-`, and is stored upper-case. The folder is `<time>` as `YYYYmmdd-HHMMSS` (UTC); two in one second get `-2`, `-3`. Limits: text 400,000 bytes, commands 100,000 bytes, at most 10 pictures, each at most 8 MB. A picture is accepted by what its first bytes say it is (PNG, JPEG, GIF, WebP), not by its name or the browser's claimed type; SVG is refused because it can carry a script. Nothing is written without text or a picture, and the task must be open {src:.harness/engine/modules/task/taskinbox.py#L27-L94}. After the write the server adds a history line `inbox` and returns the message that tells the agent to read the newest folder of the environment and record it with `task test record` (test tasks) or `task run record` (all others) {src:.harness/engine/modules/task/taskinbox.py#L89-L94}. The agent's tools cannot write there, so what is in `INBOX/` is what the person gave.

## Requirement internals: the intake commands `convert`, `paste`, `init`, `setup`

`harness task intake` has four subcommands, defined in `commands.py`; the Intake tab calls the same functions in `intake.py` {src:.harness/engine/modules/task/commands.py#L318-L336}. None of them is person-only: the gate's list of person-only commands does not name `task intake`, so a command the agent runs is not refused {src:.harness/policies/gate.json#L133-L136}.

`convert` (`intake.add_file`): the task must be open. An empty file is refused (`intake.empty`). A file over 60 MB (`MAX_FILE_BYTES`) is refused (`intake.big`). The file name is cleaned (`safe_name`: letters of any language, digits and `._-`; spaces, slashes, quotes, brackets and shell marks become one `-`; at most 100 characters for the name, 60 for the stem). The stem is made unique in `REQ/` and `REQ/originals/` by `unique_stem`: a taken name gets `-2`, `-3` and so on {src:.harness/engine/modules/task/intake.py#L232-L243}. By the suffix it chooses: `.docx` and `.docm` to the docx converter; `.xlsx` and `.xlsm` to the xlsx converter (with `--include-hidden` to read hidden sheets, rows and columns); `.xls` needs `xlrd`; `.pdf` needs `pypdf`; a text type (`.md .txt .csv .tsv .json .sql .yml .yaml .xml .log .py .sh .ps1`) or a picture (`.png .jpg .jpeg .gif .webp`) is its own original, copied into `REQ/` with no report; `.doc .ppt .pptx .rtf .odt .ods` and any other type are kept as originals only, with a note saying to save as `.docx` or `.xlsx` or to paste the text {src:.harness/engine/modules/task/intake.py#L34-L44} {src:.harness/engine/modules/task/intake.py#L278-L332}.

What `convert` writes: the original into `REQ/originals/<stem><suffix>` (not for a text file or a picture); each converted file into `REQ/`; a copy of every text-type converted file into `REQ/.pristine/` (images, `originals/` and the report get none); and `<stem>.convert.md`, the report. It adds a history line `intake`, `<original>: N file(s)`. A conversion error becomes a `CommandError` with the file name. A scanned PDF (almost no text: fewer than 20 characters per page) gives no text file and a note saying it needs OCR; the person must type or paste the content {src:.harness/engine/modules/task/intake.py#L209-L226} {src:.harness/engine/modules/task/intake.py#L317-L332}. A PDF that is password-protected is refused; a PDF with text gets one `.md` with a heading per page and a note that the order of text and tables may be broken {src:.harness/engine/modules/task/intake.py#L209-L226}. A `.xls` keeps formatting information so merged cells and hidden rows and columns are known {src:.harness/engine/modules/task/intake.py#L138-L206}.

The optional readers: `xlrd` and `pypdf` are listed in the policy `tools` as `optional_packages`; a missing one raises an error with the install command from `python.install_command` (with `{package}` filled in), or a message that no command is set. The harness never runs an install; the policy text says the gate refuses package installs by the agent {src:.harness/policies/tools.json#L3} {src:.harness/policies/tools.json#L8-L11} {src:.harness/engine/modules/task/intake.py#L58-L80}. `task intake setup` lists which optional readers are installed (it checks with `importlib.util.find_spec`), says that Word, Excel, text and picture files need nothing, warns when the install command names a different Python from the one the harness runs on, and prints one install command for everything missing {src:.harness/engine/modules/task/intake.py#L120-L132}.

`paste` (`intake.paste`): saves text the person copied as `REQ/<name>.<ext>`. `--kind` is `csv`, `md`, `doc` or `txt` (default `csv`); any other value is refused. Empty text is refused; more than 2,000,000 bytes (`MAX_PASTE_BYTES`) is refused. For `csv` and `md`, the first line decides the delimiter: a tab in it means tab-separated (cells copied out of Excel), otherwise commas; rows are padded to the widest row and trailing empty rows are dropped; `csv` writes a CSV, `md` writes a Markdown table (cells cut as needed, `|` escaped). `doc` and `txt` are kept as typed (line endings normalised); `doc` is stored as a `.md` file. The file name gets the same unique-stem rule, and a copy goes into `REQ/.pristine/` {src:.harness/engine/modules/task/intake.py#L335-L371}.

`init` (`intake.init`) makes `REQ/INTAKE.md`; its template and domain rules are in the section "Requirement internals: `INTAKE.md` and the knowledge base domain". `setup` is as above.

## Requirement internals: the Intake tab

The tab belongs to an open task that has a `REQ.md`; `intake_view` returns nothing otherwise {src:.harness/engine/modules/task/taskdesk.py#L509-L516}. It lists the files of `REQ/` (at most 500, the tool-made `.pristine` and any path with a part starting with `.` are left out), `INTAKE.md` first, and for each file whether it is editable, whether it has a pristine copy, whether it is an original, whether it is a report; it also lists originals that gave no text file (a scanned PDF, a `.doc`) so the person can see the agent cannot read them {src:.harness/engine/modules/task/intake.py#L463-L482} {src:.harness/engine/modules/task/taskdesk.py#L519-L530}.

The page posts to `/api/intake` with an `action`: `upload`, `paste`, `init`, `read`, `save`, `reset`, `delete`, `rename`, `delete_many`. Every action except `read` needs a paired browser (otherwise 403); a refusal comes back as a 409 with the message {src:.harness/engine/modules/task/boardserve.py#L2185-L2198} {src:.harness/engine/modules/task/boardserve.py#L640-L668}. Upload sends the file as base64; the browser refuses a file over 28 MB itself (`limit_mb` in the view), because the request body is capped at 40 MB, and the server's own limit is the 60 MB of `add_file` {src:.harness/engine/modules/task/boardserve.py#L87} {src:.harness/engine/modules/task/taskdesk.py#L516}.

Path safety: every path comes from a page and is never trusted. `clean_relative` refuses an empty path, a NUL byte, an absolute or drive path, and any part that is empty, `.`, `..` or starts with a dot; `req_file` also refuses a symbolic link on the way {src:.harness/engine/modules/task/intake.py#L436-L456}. Edit rules: a file is editable when it is not under `originals/` and its type is a text type; the page reads a file for edit up to 400,000 bytes (`EDIT_BYTES`); a save over 2,000,000 bytes is refused. An original is never edited and never renamed, because the report and the files made from it name it. `reset` puts a converted file back from `REQ/.pristine/`, and fails when there is no pristine copy. `rename` keeps the type unless both types are text types, refuses a name already taken, and moves the pristine copy with it. `delete` removes the file and its pristine copy and, unlike the other actions, may delete an original: the person decides. `delete_many` checks every path first, so one bad path deletes nothing {src:.harness/engine/modules/task/intake.py#L459-L592}. Each action adds an `intake` history line.

## Requirement internals: `INTAKE.md` and the knowledge base domain

`INTAKE.md` is made from the template `.harness/contracts/templates/task/<language>/INTAKE.md` (the English one if the language has none), with `{name}`, `{type}` and `{domain}` replaced {src:.harness/engine/modules/task/intake.py#L400-L428}. The template: a title `# Intake: {name}`; a note that the business documents go in `REQ/` and that the agent reads this file first, then the converted files, not the originals; a Goal section of three numbered items (this is `{type}` task and read the intake files and understand the requirement; ask the human about what is unclear using the skill `generic-grill-me`, but ask only where the documents contradict each other, are wrong, or do not match the knowledge base or the code; "Human adds:" followed by a placeholder for the person's own lines); and a Knowledge base section holding `{domain}` {src:.harness/contracts/templates/task/en/INTAKE.md#L1-L15}. `{type}` comes from the task's kind: `rca` gives "an RCA", `dev` "a development", `test` "a test", `design` "a design", `kb` "a knowledge base update", and `other` and `qa` "a general" {src:.harness/engine/modules/task/intake.py#L374-L376}.

`init` never overwrites: if `REQ/INTAKE.md` exists it stops with `intake.init.exists` and says to edit it. It does not set the task's domain; it only writes text. The `{domain}` block comes from `domain_block(chosen, offered)`, three cases {src:.harness/engine/modules/task/intake.py#L379-L387}:

- A domain is chosen: the block tells the agent to scan `knowledge-base/domains/<d>/`, read its map and the cards of the objects the requirement names, run `harness task set-domain <first>` first so the domain's skills are loaded, and write `REQ.md` from the intake files and what it found, with every item's source, the objects and code it affects and what does not fit {src:.harness/engine/core/messages.en.json#L839}.
- No domain is chosen but the knowledge base has domains: the block tells the agent to ask the human which domain, listing the names (or none), then scan it as above {src:.harness/engine/core/messages.en.json#L840}.
- `none` was chosen, or there are no domains: the block says not to scan the knowledge base, to write `REQ.md` from the intake files and to check what it touches with `harness target refs <name>` {src:.harness/engine/core/messages.en.json#L841}.

How the chosen names are resolved: if `--domain` (or the page's choice) is given, a name counts unless it is `none`, `other` or empty and not a real folder (a folder called `Other` is a domain); the rest are checked by `known_domains`, which matches in any case and refuses an unknown name with the list of the domains the knowledge base has (`domain.unknown`). If nothing is given, the task's own domains are used; if the task has none and the knowledge base has domains, the block says to ask. A `none` choice made on purpose leaves nothing to ask {src:.harness/engine/modules/task/intake.py#L400-L428} {src:.harness/engine/modules/task/tasklife.py#L237-L252}. The agent follows the block by text: the skill `generic-req-review` repeats the three cases {src:.github/skills/generic-req-review/SKILL.md#L24-L25}.

## Requirement internals: why a program converts Word and Excel, and the limits it sets

The design reason: a Word or Excel file is mostly layout, and a model reading it directly spends tokens on that and may drop a part without saying so; a program writes Markdown and CSV, keeps the original and lists what it left out {src:docs/05-design.md#L204-L206}. The intake guide adds two reasons: a Word paper's cover page, revision history, comments and disclaimers and an Excel file's hidden sheets, helper columns and colours cost context, and the agent may take the noise for requirements; and the person's confirmation of `REQ.md` is the real check, which is much easier on a short, clean input {src:docs/09-intake.md#L19-L21}. The converted values are also written as a person reads them: Word's automatic numbers as text (`3.2`), dates and percentages formatted, a formula as the value Excel last saved {src:.harness/engine/modules/task/intakeconvert.py#L1-L16}.

`intakeconvert.py` uses the standard library only (`zipfile`, `xml.etree`), so it costs no tokens and a conversion is deterministic {src:.harness/engine/modules/task/intakeconvert.py#L1-L16}. Safety limits {src:.harness/engine/modules/task/intakeconvert.py#L39-L47}:

- A zip that unpacks to more than 200 MB in total is refused (`MAX_ZIP_BYTES`), as a defence against a zip bomb.
- A single part larger than 80 MB (`MAX_PART_BYTES`) is treated as missing: `read_part` returns nothing, so a sheet or a picture of that size is silently not read.
- A sheet is read for at most the first 100,000 rows (`MAX_ROWS`); the report says "only the first 100000 rows are read".
- A sheet is read for at most 500 columns (`MAX_COLUMNS`); cells past column 500 are skipped with no note in the report.

A file that is not a zip raises the error "not an Office Open XML file (it is not a zip): an old .doc or .xls, or a damaged file; save it as .docx or .xlsx and try again" {src:.harness/engine/modules/task/intakeconvert.py#L66-L73}. An Office file protected by a password is not a zip either, so it fails with this same message; the code has no separate password message for Word or Excel (only the PDF reader has one). A file with no `word/document.xml` is "not a Word document"; no `xl/workbook.xml` is "not a workbook" {src:.harness/engine/modules/task/intakeconvert.py#L392-L398} {src:.harness/engine/modules/task/intakeconvert.py#L543-L549}.

## Requirement internals: how a `.docx` becomes Markdown

`convert_docx(data, stem)` builds the Markdown in `Docx.convert`. What it carries, and what it does with the rest {src:.harness/engine/modules/task/intakeconvert.py#L543-L918}:

- Headings: paragraph styles named Heading, Überschrift or 标题 (also `Title`) give `#` to `######`, found through the style chain; Word's own numbering is written before the heading text.
- Lists and Word numbers: `Numbering` works out the automatic numbers (decimal, letters, Roman, `decimalZero`, and multi-level like `3.2`) from `numbering.xml`, so `3.2 Scope` does not come out as `Scope`. A bullet becomes `- `, a numbered item gets its number as text, indented by level.
- Formatting: only bold is kept (`**text**`). Italics, underline, colours, fonts and highlighting are dropped with no note.
- Tables: cells become a Markdown table; merged cells (horizontal and vertical) repeat their text, and the report counts them; a nested table (to depth 3) is flattened into the cell. A table with more than 30 rows (`BIG_TABLE_ROWS`) or more than 8 columns (`BIG_TABLE_COLUMNS`) goes whole into its own `<stem>--table-N.csv`, and the text keeps a note line and the first rows (a header and four); the report names the file.
- Links: a hyperlink is kept as `[text](target)` only for an external `http` or `mailto` target; any other link keeps its text only.
- Footnotes: numbered from 1 in the order used, listed at the end of the file as numbered footnote entries. Endnotes are not read and are dropped with no note.
- Pictures: each is copied to `REQ/media/<stem>-image-N.<ext>` with a Markdown image; the report counts them and says a number that is only in a picture must be given as text. A picture in a type a browser cannot show (EMF, WMF, BMP, TIFF) is linked, not shown, and the report says to paste a screenshot instead.
- Text boxes: written in the text as `[text box: ...]`, and the report counts them.
- Tracked changes: insertions are kept as text and deletions are left out; the report gives both counts.
- Comments: written to a file of their own, `<stem>--comments.md` (author, date, text), with a note saying to delete it when not needed.
- Embedded objects: an embedded `.xlsx` or `.xlsm` is converted like any workbook (files named `<stem>--embedded-N--<sheet>.csv`) and its notes are copied into the report; any other embedded Office object (OLE) cannot be read, is kept as `REQ/originals/<stem>--embedded-N<suffix>` and noted; a link to a file outside the document is noted as not read.
- Left out with a report note: headers and footers (counted), the table of contents (counted).
- Left out with no report note: endnotes, equations, charts and SmartArt (a drawing with no picture inside gives nothing), and all formatting except bold. A drawing's text box is kept; its other shapes are not {src:.harness/engine/modules/task/intakeconvert.py#L711-L760}.

## Requirement internals: how an `.xlsx` becomes CSV

`convert_xlsx(data, stem, include_hidden, prefix)` writes one CSV per visible worksheet, named `<stem>--<sheet name>.csv` (sheet name cleaned by `safe_name`, a repeat gets `-2`) {src:.harness/engine/modules/task/intakeconvert.py#L392-L469}. The rules, in the order the code applies them:

- Sheets: a chart sheet or a macro sheet (target not under `worksheets`) is not converted and noted. A hidden or very hidden sheet is not converted unless `--include-hidden` is given, and noted. An empty sheet gives no file and a note.
- Hidden rows and columns are skipped unless `--include-hidden`; the skipped rows are not blank rows, they are left out; the report gives the counts.
- Values: shared and inline strings are resolved; booleans become `TRUE` or `FALSE`; a formula gives the value Excel last saved (the report counts formulas; formulas with no saved value, from a file not written by Excel, leave the cell empty and are counted); numbers go through the cell's format: a date format gives `YYYY-MM-DD` (with time when there is one; the 1904 date base is honoured), a plain number format keeps the zeros it pads (`00123`, `3.10`) and a percent sign, and thousands separators are not written because they would be read as column breaks; a fraction, scientific or text format gives the number as stored {src:.harness/engine/modules/task/intakeconvert.py#L145-L212}.
- Merged cells: a range is filled with the text of its first cell (the report counts them). A block over several rows and columns, or a banner across the whole used width, stays in its first cell only, and the report counts such blocks. A range over 5,000 cells is ignored.
- Colours: a cell with a solid non-white fill is counted; the colour is not carried over and the report says to say what it means in words in `INTAKE.md`, or add a column.
- Empty cells: `trim_grid` cuts every column with nothing in it, not only those at the edges, and every empty row after the last used one; the report says how many empty columns were cut.
- Charts, pictures and cell comments are not converted; the report says so per sheet. A workbook with macros (`xl/vbaProject.bin`) is noted as not read.
- A sheet of more than 200 rows is noted: the agent should read its header and a sample, not all of it. Beyond 100,000 rows only the first 100,000 are read, with a note.

## Requirement internals: the conversion report `<stem>.convert.md`

Every conversion that is not a pass-through writes `REQ/<stem>.convert.md` with `report_text` {src:.harness/engine/modules/task/intake.py#L260-L275}. It holds, in order: the title with the original name; one line saying when it was converted by `task intake convert` and that no AI was used; the original's path under `originals/`, its size in bytes and the first 16 characters of its sha256, kept as given; a line saying the agent reads the files below, not the original; a Files list (or "none"); when sheets were read, a Sheets table (sheet, state, rows by columns, and the file or the reason it was skipped) and, for each sheet that gave a file, the first rows as a table, with each cell cut to 40 characters; and a section "Not carried over, or to check" with one bullet per note.

The notes that can appear, as the code writes them {src:.harness/engine/modules/task/intakeconvert.py#L392-L469} {src:.harness/engine/modules/task/intakeconvert.py#L872-L918}:

- Worksheet notes: sheet is a chart or macro sheet; sheet is hidden (or very hidden); sheet is empty; hidden rows and columns skipped; merged ranges (value repeated); formulas (last saved value used); merged blocks (text in the first cell only); cells with a fill colour; more than 200 rows (read a header and a sample); formulas with no saved value (cells empty); empty columns cut; cell comments not converted; charts or pictures not converted; only the first 100,000 rows read; the workbook has macros.
- Word notes: a table moved to its own CSV; embedded workbook notes and embedded objects kept as originals; a link to an outside file; a picture type a browser cannot show; the comments file; tracked-change counts; merged table cells; the table of contents left out; text boxes written inline; headers and footers left out; the count of pictures in `media/`.

The report is a person's and the agent's guide: the agent is told by text to read the reports first (`REQ/*.convert.md`), then the converted files, and to say so when what it needs was left out, not to guess {src:.github/skills/generic-req-review/SKILL.md#L24-L25}. The items that are dropped with no note (endnotes, equations, charts and SmartArt, formatting other than bold, columns past 500) never reach the report; a person who needs them must look at the original or paste the content. The gate stops the agent's edit tools from writing in `REQ/`; each converted `.md` or `.csv` has a pristine copy for the person to restore it {src:.harness/engine/modules/task/intake.py#L246-L253}.

## Requirement internals: how the `[T]`, `[R]` and `[A]` items are read

`reviewcheck.done_items(root, task)` reads the "Done when" section of `REQ.md`. It scans headings: the section starts at a heading whose title (stripped of `*` and `_`, lower-cased) is `done when` or `做完的标准`, and ends at the next heading of the same depth or a shallower one, so the `###` sub-headings are inside it. Inside, a line that holds `[T1]`, `[R2]`, `[A3]` (a letter and one to three digits in brackets) is an item; the first line of an item gives its text; a line that is still the template's (`[T1] <...>`) is skipped. For an R item the environment is read from `[R1] DEV:` or `[R1] \`DEV\`:` (a letter, then up to 39 letters, digits, `_` or `-`, then a colon), and stored in upper case {src:.harness/engine/modules/task/reviewcheck.py#L21-L61}.

The division is made by text and by the code at two places. By text: the review package tells the reviewer to check `[T…]` by the task files, to judge `[R…]` only by the result saved in `RUNS/`, and not to judge `[A…]` (those are shown after the promote; they are not findings), and to name the item in the basis of each finding {src:.harness/engine/core/messages.en.json#L77}. By code: `task review start` is refused when an R environment has no result, and a finding is dropped by form (the next two sections). The T, R and A division is not enforced beyond that: the reviewer is a model and the code does not check what it judged.

## Requirement internals: `task review start` and the run results in `RUNS/`

`review start` (the agent's command, in `taskreview.start`) checks in this order, and each refusal uses no check {src:.harness/engine/modules/task/taskreview.py#L359-L373}:

1. The task is open.
2. The number of checks the person asked for (`review.n`) is not 0: with checks off it stops with `review.off`.
3. There is a result to check (`has_something`): for a development or knowledge base task, a file in `DEV/`; for a test task, a results file; for any other kind, a file other than `REQ.md` {src:.harness/engine/modules/task/taskreview.py#L170-L177}.
4. `not_ready`: first, an open handoff to the person (`review.handoff_open`: "their result is not back, so there is nothing to check yet"); second, `reviewcheck.missing_runs` is not empty (`review.runs_missing`): an R item names an environment with no file anywhere under `RUNS/<ENV>/` (the folder is matched in any case; a file counts when it is a real file and not a link), or an R item names no environment and `RUNS/` has no file at all {src:.harness/engine/modules/task/taskreview.py#L320-L329} {src:.harness/engine/modules/task/reviewcheck.py#L64-L90}.
5. Only after that: the check count is not already enough (`review.enough`) and the check limit is not reached (`review.limit`).

On the refusal for a missing run, if no handoff is open yet, the harness marks the task as waiting for the person's run itself: `mark_run` writes a `handoff` of kind `run` for the first environment that has no result (an environment named by an R item, never the unnamed `RUNS/` case), with the words of that environment's R items as the detail (cut to 200 characters), `by: harness`, and a history line `handoff`. The board then shows the task as waiting for the person, whether or not the agent runs `task handoff run` {src:.harness/engine/modules/task/taskreview.py#L338-L356}.

The agent cannot clear that handoff by itself while `RUNS/<ENV>/` is empty: `task handoff clear` (`handoff_clear`) for a run refuses with `task.handoff.clear_no_result` when `reviewcheck.has_run` finds no file under `RUNS/<ENV>/`; the result must be saved first {src:.harness/engine/modules/task/tasklife.py#L650-L665}. The person's result is saved by `task run record --env <ENV>`, which writes a `## Run N` section into `RUNS/<ENV>/results.md` (what was run, what the person gave in a code block, the screenshots copied into `RUNS/<ENV>/evidence/`), and removes the handoff of that environment {src:.harness/engine/modules/task/runrecord.py#L33-L81}. The person's input comes from `INBOX/<ENV>/` or the chat.

A caveat: all of this is inside `review start`. With checks off (`review.n` is 0) or waived, nothing in code requires a file in `RUNS/` before the dry run or the write-back; `task promote --dry-run` asks only that the passes are there or waived {src:.harness/engine/modules/task/taskreview.py#L260-L262} {src:.harness/engine/modules/task/taskreview.py#L563-L568}. Whether the person ran the R items at all, with checks off, is left to the person and to the agent's text.

## Requirement internals: what the code checks of a reviewer's findings

The reviewer is a model; the code looks only at the form of a FAIL. When the reviewer's call finishes, `taskreview.record` stores the answer in the round folder and, for a FAIL, runs `reviewcheck.check` {src:.harness/engine/modules/task/taskreview.py#L412-L436}. A finding is a bullet that carries a `| basis:` part; the text before it must start with `file:line` (markdown marks allowed). Each finding is dropped, with its reason, when {src:.harness/engine/modules/task/reviewcheck.py#L93-L116} {src:.harness/engine/modules/task/reviewcheck.py#L164-L186}:

- its basis names only `[A…]` items (reason `after`: those are checked after the promote);
- it names no `file:line` (`no_place`);
- the file is not found (`no_file`): looked for from the repository root, the task folder, the target repositories and the knowledge base, then as the end of a path inside the task folder;
- the line is below 1 or past the file's last line (`no_line`; a file over 20 MB counts as having any line).

A finding whose basis names no item at all is not dropped for that; the code does not require a basis to cite an item, and a finding that names both an A item and a T or R item is kept. When every finding is dropped (none kept), the FAIL is invalid: the check is given back (`refunded`) for up to `free_invalid` times (default 2), and the next package lists why each finding was dropped {src:.harness/engine/modules/task/taskreview.py#L40} {src:.harness/engine/modules/task/taskreview.py#L307-L312}. A `REQ.md` with no numbered items is checked as before: only `file:line` is looked at. The code never judges whether the finding is right.

The reviewer is also told that a confirmation line that is not filled in is not a finding: the package adds the sentence that only the user can change that line, so the author cannot fix it and it must not cost a check {src:.harness/engine/modules/task/taskreview.py#L293-L294}.

## Requirement internals: what code does not do

- The code never judges whether `REQ.md` says what the person meant; only the person, by reading it.
- The confirmation line is read as text; who wrote it is not checked. The digest and the typed code are what bind a confirmation to a version.
- The person's-folder rule covers the agent's edit tools in a session that holds an open task. A shell command writing into `REQ/`, `REF/` or `INBOX/`, and `harness task intake convert` run by the agent, are not refused by it.
- Not reading `REQ/originals/` is an instruction in text; nothing stops a read.
- The digest counts only what is directly under the six named headings; a section renamed, and items under a sub-heading of "Done when", are outside it (see the digest section).
- A task of the tier `medium` has `REQ.md`, but only a `full` task waits for its confirmation; the hard check is `approve-plan`, in any tier, when `REQ.md` has a confirmation line {src:.harness/engine/modules/task/taskdesk.py#L533-L535} {src:.harness/engine/modules/task/task.py#L443-L451}.
- Nothing in the Word and Excel converter reads macros, charts, equations or colours; it is a flat copy and does not decide what matters.
