This file holds the code-level detail behind the feature file 22 Cost and usage: the three parts of cost and the rule the harness follows, the jobs code does instead of the model, what code pushes into the model's context, what the harness's own log keeps, where Credits and times come from and what the report does without Copilot's record, the cards of the task analysis page, the three layers of Agent Performance Review, the gate review and its eval samples, the one measurement made at version 1.0, and the "fixed schema" rule. ## Cost and usage internals: the three parts of cost and the overall rule

The harness's cost guide says cost has three parts: the number of model calls, the tokens each call reads and writes, and the time people spend waiting and stepping in. Its one rule is to do things in the cheapest way that is enough, not to let the model do what code can do, and to have every model call read less, write less and redo less {src:docs/06-cost-optimization.md#L3}. What it saves is the cost of rework and incidents, not the lowest price of one call, and each saving is "saved by design", not a bill {src:docs/06-cost-optimization.md#L5} {src:docs/06-cost-optimization.md#L78}. No code measures a saving: the harness's own log holds no token counts, and the task analysis page shows only what Copilot says a task used {src:.harness/engine/core/callrecord.py#L1-L10}.

**Calls.** Hooks, the gate, task commands, conversion, knowledge base checks and eval checks are code and call no model {src:docs/06-cost-optimization.md#L9-L13}. Code: the reviewer subagent may be called only by a session that holds a task, when checks are on (`review.n` above 0; default 0) and after `task review start` opened a round; any other call is refused {src:.harness/engine/modules/task/handler.py#L286-L299} {src:.harness/engine/modules/task/taskreview.py#L120-L128}. The checks allowed are `n + extra_checks (2) +` what the person added, and `n` is capped at `max_n` (5) {src:.harness/engine/modules/task/taskreview.py#L151-L165}. A person switches on the other subagents (autorun with its spend limit; `/generic-mapreduce`, at most 4 mappers in the policy window) and picks the model {src:.harness/policies/task.json#L3}.

**Tokens.** Code decides what the hook injects with each prompt; text asks the model to read `TASK.md` first, the reviewer to read the diff first and the call message to be one sentence; Copilot decides when a skill's text or an `applyTo` file is loaded (see step-by-step disclosure below) {src:.harness/engine/modules/task/handler.py#L93-L126} {src:.harness/engine/core/messages.en.json#L49-L59}.

**People's time.** Code: the plan and diff are files read in an editor, approval is bound to the content by a code, the board reads state files, and the report is written at close {src:docs/06-cost-optimization.md#L57} {src:.harness/engine/modules/task/task.py#L395}.

## Cost and usage internals: jobs done by code and not by the model

**Task folders.** `tasklife.new` makes the folder from the shipped templates in `.harness/contracts/templates/task/<language>/` and replaces only the known `{names}` {src:.harness/engine/modules/task/tasklife.py#L86-L122}. `task upgrade` adds the files of a higher tier and leaves existing ones; `task fork` copies an old task's context to `REF/from-<old>/`, never its state; `task archive` moves only closed tasks; `task list` reads `.task/task.json`, not Markdown {src:.harness/engine/modules/task/tasklife.py#L1-L12} {src:.harness/engine/modules/task/taskfork.py#L1-L12}. `task fetch` copies a file as the target repository's base branch has it to `DEV/<repo>/<path>` and keeps the same bytes under `.task/base/`, so a diff needs no look into the repository; one fetch copies at most `fetch.max_files` (200) files {src:.harness/engine/modules/task/task.py#L1-L14} {src:.harness/engine/modules/task/task.py#L618-L632} {src:.harness/policies/task.json#L4-L6}.

**Diffs.** `changes` in `task.py` compares each file under `DEV/` with its base copy using `difflib.unified_diff` (3 lines of context); a new file shows against `/dev/null`, a non-UTF-8 file only as binary; `task diff` writes `CHANGES.diff` {src:.harness/engine/modules/task/task.py#L793-L835}. `task promote --dry-run` writes the whole patch to `PROMOTE-PLAN.diff` and gives the agent only the files and counts {src:.harness/engine/modules/task/task.py#L905-L910}.

**Snapshots.** `tasksnap.take` copies the task's result files to `SNAPSHOT/<gate>-<time>/files/` and writes `manifest.json` with the sha256 of each file and one `digest` of the whole. It runs at the plan approval (`plan`), each independent check (`review-NNN`) and each promote dry run (`promote`) {src:.harness/engine/modules/task/tasksnap.py#L97-L118} {src:.harness/engine/modules/task/task.py#L474} {src:.harness/engine/modules/task/taskreview.py#L394}. A file over `max_file_mb` (5) is listed but not copied; each new snapshot prunes those older than `keep_days` (14) {src:.harness/engine/modules/task/tasksnap.py#L27} {src:.harness/engine/modules/task/tasksnap.py#L137-L148}. The state folder, the person's folders, `TASK.md`, `TODO.md`, `LOG.md`, `READ/`, `OUT/` and earlier rounds are not part of a snapshot or digest {src:.harness/engine/modules/task/tasksnap.py#L28-L55}.

**Reports.** `task_report.generate` writes `report.md` (facts only) and `report.html` into `.workspace/reports/tasks/<task>/`; `task close` and `harness task report` call it {src:.harness/engine/modules/task/task_report.py#L133-L158} {src:.harness/engine/modules/task/task.py#L395}.

**Intake.** `task intake convert` keeps the original unchanged in `REQ/originals/` and writes its text (Markdown or CSV) into `REQ/` with a report of what was left out; a file over 60 MB is refused {src:.harness/engine/modules/task/intake.py#L1-L12} {src:.harness/engine/modules/task/intake.py#L37}. No model and no install: a docx or xlsx is a zip of XML read with the standard library. A docx becomes Markdown (Word's list numbers written as text, a table over 30 rows or 8 columns as a CSV of its own, tracked insertions kept and deletions dropped; headers, footers and the contents table dropped); an xlsx becomes one CSV per sheet, hidden parts skipped unless asked, a formula's last saved value {src:.harness/engine/modules/task/intakeconvert.py#L1-L48}. `task intake setup` only lists which optional readers are installed and the install command; the harness never runs it {src:.harness/engine/modules/task/intake.py#L1-L8}.

**Eval checks.** A scenario is `.harness/eval/scenarios/<id>/` with `scenario.md` and `expect.json`; `eval check` reads the session log and the files left behind and gives yes or no with a reason per rule; no model. Rule types: `calls`, `order`, `files` and `json` {src:.harness/engine/modules/evalcheck/scenario.py#L1-L52}. **Knowledge base**: `kb check` validates the form and `kb stale` compares git blob shas (see the section on the fixed schema) {src:.harness/engine/core/kbstd.py#L189-L260}. What stays with the model or a person: what a change means, what to write in a card, every approval.

## Cost and usage internals: step-by-step disclosure, what code pushes and what does not

**The one block code injects.** At session start and with every prompt, `prompt_text` gives the model: with no task, the session id, the language, the rule to open a task before producing files and the open tasks; with a task (`task_text`), the task, kind, tier and round with "a new session reads `TASK.md` first, then what it points to; update it before you stop", the next step, a line on `REQ.md`, the review line, what the edit tools may write, the task page URL, the names of the task's domain skills and an autorun line {src:.harness/engine/modules/task/handler.py#L93-L126} {src:.harness/engine/modules/task/handler.py#L162-L176}. This block is the one place where code decides what enters the context every turn. Domain skills live in the knowledge base, are not in Copilot's menu, and the hook gives only their names (one line per prompt); the agent reads a `SKILL.md` when its description fits {src:.harness/engine/modules/task/tasklife.py#L255-L263}.

**The `TASK.md` habit is pushed by code; its length by none.** `task new` and `task open` return `read_first`, the injected head says to read it first, and a Stop reminder blocks once per prompt when task files were written but `TASK.md` was not. The limit "within one screen" is only a sentence in the template; no code measures length {src:.harness/engine/modules/task/tasklife.py#L155-L160} {src:.harness/contracts/templates/task/en/TASK.md#L3}.

**The Stop reminder, exactly.** `task_file_stop` returns a block (the hook will not let the turn end and feeds the reason back) only when all hold: policy `task_file_reminder` is true (default); the task's `TASK.md` exists; no `deliver` state is pending; this prompt wrote a file inside the task folder with an edit or create tool (`on_task_write` sets `wrote`; a terminal write does not); none of those writes was `TASK.md`; and the prompt was not reminded yet. It sets `reminded`, and the reason says to update `TASK.md` only, then end. A new prompt resets the marks, so it blocks at most once per prompt, and the second Stop of a block passes; it is joined with the check and write-back reminders into one reason. A broken policy raises inside the reminder, the hook logs it and the reminder does not run {src:.harness/engine/modules/task/handler.py#L350-L373} {src:.harness/engine/modules/task/handler.py#L423-L435} {src:.harness/engine/modules/task/handler.py#L599-L625}. It checks that `TASK.md` was written, not that it is right.

**What is Copilot's, and what the harness only checks.** That Copilot reads only a skill's name and description at first and loads the rest, or an `applyTo` file, when needed is Copilot's behaviour, stated in the harness's guide; no harness code does the loading {src:docs/06-cost-optimization.md#L26}. `skillcheck` errors on a description under 10 or over 1,024 characters, a body over 500 lines or a dead link, and warns on a description over 600 characters, a body over 200 lines, no "Gotchas" heading, an orphan file or a description that does not say when to use the skill {src:.harness/engine/core/skillcheck.py#L22-L23} {src:.harness/engine/core/skillcheck.py#L160-L222}. `doctor` counts a knowledge base instruction file as loaded on its own only when its `applyTo` is `**`, `**/*`, `*` or `**/**`, or `AGENTS.md` or `copilot-instructions.md` names it; a narrower `applyTo` such as `knowledge-base/**` gets the warning "not loaded" {src:.harness/engine/doctor.py#L32} {src:.harness/engine/doctor.py#L490-L499}. `AGENTS.md` has 64 lines and no code limits it.

**Knowledge base limits are warnings; reads are logged.** `kb check` warns when `architecture.md` has over 300 lines or a card over 120 lines {src:.harness/engine/core/kbstd.py#L36-L37} {src:.harness/engine/core/kbstd.py#L165-L186}. The hook logs the names (never the content) of knowledge base files a finished read, search or terminal call named, up to 20 per call, unless policy `knowledge_base_reads` is false {src:.harness/engine/core/kbreads.py#L1-L24}.

## Cost and usage internals: the harness's own log

The log is one JSONL line per hook call in `.harness/runtime/logs/<surface>/<session id>.jsonl`, written by the observe module after the decision is merged, so a line holds the final decision and the hook's milliseconds; the module has no opinion and never changes a call {src:.harness/engine/modules/observe/handler.py#L1-L6}. `callrecord.build` writes the surface, event, session id, tool name and kind, agent type, the modules that ran and the decision; for a refusal, confirmation or Stop block also `judge`, `by` and `reason`; and the facts `kind`, `verdict`, `task` and `external` (an outside call's system, environment, verb and target, never its result). A UserPromptSubmit line has the event, the decision and the task fact, and no prompt text {src:.harness/engine/core/callrecord.py#L43-L98}.

**The exceptions, all of them.** Beyond that a line may hold: the error text of a failed call; for a refused or confirmed call (`PreToolUse` deny or ask) its paths (up to 5) and its command; for a finished call up to 5 paths it touched, never the command; for a terminal call a 10-character hash of the command; a loaded skill's name; the knowledge base file names above; at `SessionStart` and subagent start and stop, the transcript path and model name {src:.harness/engine/core/callrecord.py#L68-L97}. It holds no tokens and no Credits {src:docs/06-cost-optimization.md#L5}.

**Cutting and redaction.** `clip_record` runs `redact.text` on `reason`, `error` and the command and cuts them to `max_text_chars` (default 300), except `reason`, cut at 1,500 so the right way at its end survives; paths are cut but not redacted {src:.harness/engine/modules/observe/handler.py#L41-L61}. `core/redact.py` masks only the value as `***` and keeps the shape of the text: Bearer and Basic tokens, values of keys named like password, secret, token, api key or credential, `--password x`, `user:password@host`, common token shapes (GitHub, OpenAI, AWS, Slack, JWT), private key blocks and runs of 40 or more characters with no space that do not read as a path or a name of code; and a home folder becomes `~`. Its header calls it a net with wide holes {src:.harness/engine/core/redact.py#L1-L5} {src:.harness/engine/core/redact.py#L45-L95}.

**A failing log never stops the hook.** `_append` swallows every error; a failure building the record goes to `hook-errors.jsonl` as `hook:record:<event>` and the hook answers as decided; a failure of the observe step is logged as `observe`; a broken `observe.json` falls back to defaults; a call with no session id appears only in `hook-errors.jsonl` {src:.harness/engine/core/logs.py#L20-L27} {src:.harness/engine/hook.py#L139-L165}. `hook-errors.jsonl` is where raw input can land: when the hook itself fails it keeps the error, the last 2,000 characters of the traceback and the first 1,500 characters of the raw input (`sample`), not redacted {src:.harness/engine/core/logs.py#L39-L50}. Optional `capture` (policy `observe.capture.enabled`, off by default) writes for every call the whole raw input, the hook's output, the working folder and the names (not values) of environment variables to `.harness/runtime/capture/`, unredacted; the policy says to leave it off because the input holds code {src:.harness/engine/modules/observe/handler.py#L64-L92} {src:.harness/policies/observe.json#L1-L9}. `unseen-tools.jsonl`, for `doctor` only, records an unknown tool or an unreadable call by surface, tool, kind and the key names of its input, never a value, at most 200 lines {src:.harness/engine/core/unseen.py#L1-L56}.

**The stated reason is spread over three files.** The policy says capture is off because the input holds code; `redact.py` says redaction has holes; the Copilot reader says numbers and times come from Copilot's record at report time {src:.harness/policies/observe.json#L1-L9} {src:.harness/engine/core/redact.py#L1-L5} {src:.harness/engine/core/copilot_events.py#L1-L11}. So the log keeps facts that need no text, and what needs text is read later from Copilot's record on this computer.

## Cost and usage internals: where Credits and times come from, and the fallback

`copilot_events.events_path(session_id, hint)` tries first the transcript path the hook logged for the session (`hint`), then `<COPILOT_HOME or ~/.copilot>/session-state/<session id>/events.jsonl`; a session id containing `/`, `\` or `..` is not used to build that second path; a candidate counts only if it is a file of at most 300 MB {src:.harness/engine/core/copilot_events.py#L26-L58}. Policy `report.copilot_events` (default true) switches the reading off. The reader never raises and returns nothing when it finds no prompt. It keeps no tool result or argument, though it reads arguments to notice a wait for a person and a write of `REQ.md` or `PLAN.md` {src:.harness/engine/core/copilot_events.py#L108-L133}.

**Times.** Each `user.message` starts a prompt; a subagent's own rows (with an `agentId`) are skipped, and `subagent.completed` adds its `durationMs`. The prompt ends at its last `assistant.*` or `tool.*` row. Model time is each turn's start to its first message less a permission wait; a tool's time is its start to completion less a permission wait; a tool that only waits for a person (`ask_user`, `harness wait --approval`) and a permission wait the host did not answer by policy count as approval time {src:.harness/engine/core/copilot_events.py#L287-L444}. `split` then makes the parts add up: active time is prompt end minus start; turns are capped at it, model time at the turns, approval at what is left, subagents at what is left after that; **tool time is the remainder of the turns**, not a sum of tool rows; time outside any turn is "other". So active = model + tools + subagents + approval wait + other {src:.harness/engine/modules/task/taskinsight.py#L458-L469}.

**Waiting for you** is the time from a prompt's end to the start of the task's next prompt in any session, minus time the task was paused; the last prompt has none, and a wait under 1 second is dropped. `add_open_wait` adds the wait still going on {src:.harness/engine/modules/task/taskinsight.py#L603-L606} {src:.harness/engine/modules/task/taskinsight.py#L755-L783}.

**Credits, premium requests, tokens, context.** Each `session.usage_record` adds its `totalNanoAiu` (divided by a billion) and its input and output tokens to the prompt running when it was recorded; each `session.usage_checkpoint` adds the part of its running total the calls have not counted (the "rest", only if above 0.001) to the prompt running then; premium requests are the checkpoint's `totalPremiumRequests` minus the last total; context size is the largest `prompt_tokens` in a checkpoint {src:.harness/engine/core/copilot_events.py#L153-L215} {src:.harness/engine/core/copilot_events.py#L413-L442}. A Copilot prompt matching no hook-log prompt (30 s before to 5 s after) joins the prompt before it {src:.harness/engine/modules/task/taskinsight.py#L162-L190}.

**The fallback when `events.jsonl` is missing** (per session; also when the policy is off or the file gives no prompt): if the hook log has user prompts, `from_hook_log` is used. Each prompt runs until the last hook row before the next; model and turn time are `None`; a tool's time is the gap between its `PreToolUse` and `PostToolUse` rows (a call refused or with no end counts 0); there are no Credits, premium requests, tokens, turns, context size, cache, compactions or subagent times. The session's `source` is `hook-log` (`none` with no hook prompts); mixed sessions give `mixed` {src:.harness/engine/modules/task/taskinsight.py#L193-L245} {src:.harness/engine/modules/task/taskinsight.py#L734-L738}. On the page: Credits and premium requests show `-`, the bar that splits working time is not drawn, the Credits columns are left out, the footer says "the hook log only (no usage, and model time cannot be told from tool time)", a key point says Copilot's record was not found for some sessions, and with no prompt at all the page says "No session record was found for this task" {src:.harness/engine/modules/task/web/task.js#L18-L25} {src:.harness/engine/modules/task/web/task.js#L90-L93} {src:.harness/engine/core/messages.en.json#L306-L309}.

## Cost and usage internals: the task analysis page, card by card

`web/task.js` draws the page from `taskinsight.build`. Cards, in order, each left out when it has nothing to show: **key points** (at most 8, largest first), the **Agent Performance Review box**, **where the time went**, **gate blocks**, **every prompt** with its stage tag, the **stage table**, the **context-growth chart**, **cache**, the **tools table**, **independent checks**, and a footer with the data source {src:.harness/engine/modules/task/web/task.js#L352-L360}.

**Where the time went**: one bar of working against waiting with percentages, and, only with model time, a second bar splitting working time into thinking, tools, subagents, waiting for the person's answer or approval, and other {src:.harness/engine/modules/task/web/task.js#L99-L113}. **Every prompt**: stage tag, time bar, Credits, turns, tool calls, tags for refused, held, blocked Stop, failed and compacted, the first 300 characters of what the person typed (`report.prompt_chars`), and a "⏸" line after a wait of 60 seconds or more {src:.harness/engine/modules/task/web/task.js#L129-L155}. **Stage table**: left out when the task has only the stage "doing" {src:.harness/engine/modules/task/web/task.js#L157-L179}. **Context growth**: a line over the prompts, one dot per prompt, a hollow dot where Copilot compacted; it needs two points; its key point fires when the largest context is at least 1.5 times the first and at least 10,000 tokens more {src:.harness/engine/modules/task/web/task.js#L181-L227}. **Cache**: a column per model call, with a red mark where the cache had run out. **Tools table**: the 15 tools that took the most time, with calls, total time, longest, failed calls and result tokens {src:.harness/engine/modules/task/web/task.js#L260-L271}. **Subagents have no card of their own**: they appear as a slice of the time bar, a column of the stage table and rows of the checks table. **Gate blocks** are described in the gate review section.

**Which copy has the Agent Performance Review box.** The box draws only when `info.perf` is set, and only `report_info` in the board server sets it. So it is on the page the board serves and on copies saved from it, and not in the `report.html` that `task close` or `harness task report` writes: `write_task_page` sets the gate section but no perf, and `PERF.section` returns nothing without it {src:.harness/engine/modules/task/boardserve.py#L580-L606} {src:.harness/engine/modules/task/taskboard.py#L94-L106} {src:.harness/engine/modules/task/web/perf.js#L14-L16}. The disk file is a snapshot (written again when a verdict changes, shown without buttons); a served page recomputes at each request {src:.harness/engine/modules/task/taskboard.py#L108-L115}.

## Cost and usage internals: Agent Performance Review, free and paid

**Free and paid.** The free part is code on this computer: the box on the served task page, built by `perfreview.summary_view`, with tiles for trouble (failed, refused, held), tries again (retry, repeat), the person's interventions and, with a review, the waste share; a "quiet" line; the prompts worth reading; a link to `/tasks/<task>/performance`; and the button that starts the paid part {src:.harness/engine/modules/task/perfreview.py#L530-L545} {src:.harness/engine/modules/task/web/perf.js#L14-L56}. The paid part is a model in an `rca` task `apr-<task>` that reasons over what code picked. **Facts** (`perfdata.facts`): `failed`, `refused`, `held`, `retry` (the same tool with similar words within 3 calls after a failure), `repeat` (the same read again with no write between), `person`, `slow` (120 s or more), `cold`, `compaction`, `intervention`. A task is **quiet** when none of failed, refused, held, retry, repeat or cold happened and the person did not step in {src:.harness/engine/modules/task/perfdata.py#L506-L571} {src:.harness/engine/modules/task/perfdata.py#L686-L706}.

**What the free layer reads.** `perfdata.collect` reads, per session that picked the task up, Copilot's record (every model call with its exact Credits, tool calls with arguments and results, thinking summaries, compactions, subagents), the hook log (what the gate decided per call), `.task/sent.jsonl` (what the board sent, to tell a prompt's origin) and the person's decisions in `task.json` {src:.harness/engine/modules/task/perfdata.py#L1-L26} {src:.harness/engine/modules/task/perfdata.py#L708-L765}. Without Copilot's record the evidence is the hook log alone: source `hook-log`, no cost, thinking or results. With no call and no cost at all `collect` raises "No tool call of the task was found": the review command errors and the box shows nothing, or "no record" on a served page {src:.harness/engine/modules/task/perfdata.py#L753-L756}. Texts kept are redacted and cut: arguments 600 characters, results 400, thinking 2,000 {src:.harness/engine/modules/task/perfdata.py#L38-L50}.

**"Worth reading" is at most 8 prompts** (`WORTH_MAX`): the three dearest that each hold 10% or more of the Credits, prompts with trouble weight 2 or more (retry and repeat weigh 2), prompts before an intervention, and prompts with a cold cache or a compaction {src:.harness/engine/modules/task/perfdata.py#L651-L683}. **Context makeup**: what every call carried before any work, by part (tools, the platform's instructions, the harness's instructions, what the harness added, skills). Tools and system parts come from Copilot's record; harness-added text and skills are estimated at 4 characters a token and scaled down to the real prompt size when they would exceed it; subagent calls are left out {src:.harness/engine/modules/task/perfdata.py#L586-L648}.

**The three layers and where each lives.** Layer 1, accounts and facts (code, free): `perfdata.py`. Layer 2, lookups (code): the command in `perfreview.py`; `harness task performance <task> --task <review task>` collects, writes `EVIDENCE.json` into the review task's folder and sets `reviews: <task>` in its state; `--overview`, `--prompt`, `--span`, `--find`, `--call` and `--check` read the stored evidence {src:.harness/engine/modules/task/perfreview.py#L1-L26} {src:.harness/engine/modules/task/perfreview.py#L299-L328}. **Layer 3, reasoning and blame, is not a Python file: it is a model following the skill `harness-agent-performance-review`**, reading only the prompts layer 1 picked {src:.github/skills/harness-agent-performance-review/SKILL.md#L36-L48}. `perfroll.py` does the same across tasks (`--all`, `--days N`) with a free layer over every task with a record (review tasks left out; tasks with no record counted as `no_record`) and a reviewed layer over review tasks whose `FINDINGS.json` passes `check_findings`; the others go to `not_checked` {src:.harness/engine/modules/task/perfroll.py#L1-L22}.

**Guards in code.** `perfreview.run` refuses unless the review task is open and of kind `rca`; a task cannot review itself; lookups and `--check` refuse unless `EVIDENCE.json` exists with the version the code writes (`VERSION` 2) {src:.harness/engine/modules/task/perfreview.py#L275-L297} {src:.harness/engine/modules/task/perfdata.py#L37}. **It does not check who started the review**: only the skill's text, its `disable-model-invocation: true` and the board's button keep a review user-started {src:.github/skills/harness-agent-performance-review/SKILL.md#L5} {src:.github/skills/harness-agent-performance-review/SKILL.md#L21-L24}.

**Why code, not the model, counts the waste.** `FINDINGS.json` has no cost field: segments carry an id, calls (`c10..c14`) or a prompt, a verdict `waste`, `needed` or `cold`, and words; findings carry segments, owner, confidence, title, why and evidence ids {src:.github/skills/harness-agent-performance-review/templates/FINDINGS.json#L1-L24}. `check_findings` computes the cost: a `waste` segment costs all the time and Credits of its calls (`span`); a `cold` segment only the extra its cold caches cost and no time (`cold_extra`); a segment with several owners is split evenly, each owner counted once; the waste's share of the task total is returned. The review page recomputes the same {src:.harness/engine/modules/task/perfreview.py#L431-L465}. The check also refuses an owner, confidence or verdict outside the lists, an unknown id, a waste segment with no owner, a `model` or `harness` finding with no evidence unless `unsure`, and a `certain` model finding that does not cite where the right way was in the agent's context {src:.harness/engine/modules/task/perfreview.py#L349-L429}. **`--check` verifies shape and arithmetic only**; it cannot tell whether a verdict is right, and a `person` finding needs no evidence by code.

**The review's own cost** is read like any task's and shown beside the review; since its state has `reviews: <task>`, the board leaves it out of the cost median and compares it with no other task {src:.harness/engine/modules/task/health.py#L141-L148} {src:.harness/engine/modules/task/taskboard.py#L292}. For a quiet task the skill says to write a summary saying so, with no segments, run `--check` and deliver {src:.github/skills/harness-agent-performance-review/SKILL.md#L38}.

## Cost and usage internals: the gate review and the eval export

The gate review is the section of the task analysis page that lists the gate's blocks and lets the person judge each: "Right to block", "Wrong block", "Not sure". Blocks are the `PreToolUse` lines with decision `deny` in the hook log of the task's session and its subagents' sessions; a call the gate held for the person is not a block and is counted apart as "held". Each has an id (12 characters of a sha1 over time, tool, command, paths and reason) and a rule name (the reported `kind`, else module and tool); the page shows the newest 200 {src:.harness/engine/modules/task/gatereview.py#L1-L10} {src:.harness/engine/modules/task/gatereview.py#L26-L87}.

**Who sets a verdict.** Only the paired browser, by `POST /api/verdict`; no command sets it. `set_verdict` accepts `right`, `wrong`, `unsure` or empty (taking it back), only for a block in the log, also on a closed task. It is kept in `task.json` as `gate_verdicts`, and `.task/**` is a path only the command line writes, so the agent's tools are refused there. The server then writes the disk report again {src:.harness/engine/modules/task/gatereview.py#L90-L108} {src:.harness/engine/modules/task/boardserve.py#L609-L622} {src:.harness/policies/gate.json#L24-L34}.

**The export.** `POST /api/export` writes, for each block judged wrong, `.harness/eval/fixtures/gate/<rule>/<id>.json` with the fields `schema` (1), `kind` (`gate-false-block`), `id`, `rule`, `tool`, `command`, `paths`, `reason`, `expect` (`allow`) and the harness version; no task, session or time. Text goes through `redact` again and is cut to 600 characters. Exporting twice writes the same file; a verdict taken back or changed exports nothing. The folder is gitignored because samples hold the person's commands {src:.harness/engine/modules/task/gatereview.py#L111-L137} {src:.gitignore#L7-L8}. `redact` keeps the shape and masks only the value. **No code in 1.8.3 replays these samples against the gate**; the docs say only that a later gate change "can be tested on" them {src:docs/02-features.md#L85}.

## Cost and usage internals: the 1.0 measurement and what 1.1 kept

At version 1.0 one comparison was made on a simulated data engineering repository (5 domains, 93 files, not runnable) with four tasks: adding a pipeline, adding a field across domains, renaming a pipeline with deletions, fixing a formula where the requirement also asked for a change to a protected path. Each was done once by the three-role setup (orchestrator, builder, reviewer, with a knowledge base plugged in) and once by one top-model agent with no harness; one static check script scored all {src:docs/06-cost-optimization.md#L80-L88}. **Result**: both passed 4 of 4 in one round, so the extra roles bought no quality; usage was about 456 AI credits against about 101 (4.5 times) and time about 16 minutes against about 3 {src:docs/06-cost-optimization.md#L90-L98}. The extra cost bought mainly the independent check: once the builder missed two cross-domain references and the reviewer sent the work back {src:docs/06-cost-optimization.md#L99}. **Caveats**: one run per task, so order of magnitude only; vague requirements in very large repositories were not measured; the effect of `[review]` 0, 1 or 2 on real tasks was not measured; and the knowledge base was in the three-role arm only, which the comparison does not separate from the roles {src:docs/06-cost-optimization.md#L87} {src:docs/06-cost-optimization.md#L101}.

**What 1.1 kept.** 1.1.0 removed the Levels, the multi-agent flow and the verifier, and kept the independent check as `[review]=n`, switched on when wanted, with one agent doing the work; a person's approval before anything is written to a repository, and a record that can be looked up, stay with every task {src:docs/06-cost-optimization.md#L100} {src:docs/07-release-notes.md#L3586-L3601}. The reasons are in {src:docs/05-design.md#L57-L68}.

## Cost and usage internals: the "fixed schema" rule and three places that follow it

The rule is in the harness's cost guide, in the knowledge base bullet, in these words: "where a question has one right answer that a program can compute, put the data in a fixed schema and let a program compute it", then "the model is kept for what needs judgment: what a change means, what to write in a card" {src:docs/06-cost-optimization.md#L15}. Only the knowledge base example is tied to the sentence there; the two others apply the same rule.

**Place 1, the knowledge base.** Every domain has the same files and fields: `domain.yaml`, `architecture.md`, `objects/index.jsonl` (one line per object with `id`, `type`, `repo`, `sources` each with `path` and `sha`, `card`, `level`) and cards, one `## <id>` section per object. `kb check` validates the form (fields, id pattern, no duplicate object, level from a list, card present, no path of one computer); `kb stale` asks git for the blob sha of each source path on the base branch (`git ls-tree -r -l`) and compares it with the stored `sha`, marking a source missing as gone and one with no sha as unstamped. No model reads anything and the answer is the same every time {src:.harness/engine/core/kbstd.py#L1-L30} {src:.harness/engine/core/kbstd.py#L91-L188} {src:.harness/engine/core/kbstd.py#L207-L260}.

**Place 2, independent checks.** The state is a fixed structure in `task.json`; each round holds the sha256 `digest` of the result, and the number of passes is recomputed from the rounds and the digest of the work now: it counts back from the last counted check and stops at a non-PASS or a different digest {src:.harness/engine/modules/task/taskreview.py#L120-L169} {src:.harness/engine/modules/task/tasksnap.py#L81-L95}. The reviewer's answer has a fixed form a script validates: `parse_verdict` reads `PASS` or `FAIL` from the verdict line among the first non-empty lines (else `unknown`), and for a `FAIL` `reviewcheck.check` drops each finding whose `file:line` does not exist or whose basis is only items checked after the write-back; a FAIL with none left is invalid and given back, up to `free_invalid` (2) times {src:.harness/engine/modules/task/taskreview.py#L69-L90} {src:.harness/engine/modules/task/reviewcheck.py#L164-L187}. The judgment is the model's; only its form is code's.

**Place 3, cost and usage.** Time and Credits are computed by code from Copilot's record of known row types and fields, and a review's findings are a fixed JSON form in which the model gives ids and verdicts and code computes the cost {src:.harness/engine/core/copilot_events.py#L153-L215} {src:.harness/engine/modules/task/perfreview.py#L349-L465}.
