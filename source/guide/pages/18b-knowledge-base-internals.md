This file holds the code-level detail behind the feature file 18 Knowledge base: why the harness ships no knowledge base and where one plugs in, the cost rule and what the code holds of it, the files of a domain in the standard form, what `kb check` and `kb stale` do, how `kb map` and the toolkit work, how `kbmap.py` caches per file by git blob, how `kbextract.py` isolates extractors, how `kb audit`, `kb status`, `kb order` and `kb cardcheck` compute their answers, who approves which step, the uses the map cannot see, how the knowledge base is kept true, `company/` and `company sync`, and where scripts end and the model begins. It is for "how does it work" and "where in the code" questions. Code locations are at harness version 1.8.3.

## Knowledge base internals: shipped empty, and how the code tells empty from content

The harness ships without a knowledge base: in 1.8.3 the folder `knowledge-base/` is not in the package and is made when a team imports its own. The rule for agents that change the harness itself is that `knowledge-base/` stays empty when shipped, and that business knowledge is not put, faked or wired in {src:AGENTS.md#L11-L15}. The reason is upgrade safety: unpacking a new harness over a copy never writes the team's knowledge base {src:docs/03-configure.md#L116}. `harness reinstall --from <old copy>` (applied only by a person at a terminal) carries the old `knowledge-base/` over only when the old one has team content and the new one is a placeholder {src:.harness/engine/core/reinstall.py#L182-L189}. The target policy also ships empty (`repos_root` empty, `repos` empty, `base_ref` `main`); a team's values, including the entry with `knowledge_base: true`, go in `target.override.json` {src:.harness/policies/target.json#L1-L9}.

`targets.knowledge_base_content(folder)` decides what counts as content: nothing when the folder is missing, otherwise every item except `README.md`, `.gitkeep`, `.gitignore`, `.DS_Store` and names starting with a dot {src:.harness/engine/core/targets.py#L170-L179}. `doctor`, Get ready, the setup status, `target init-kb` and `reinstall` all ask this one function. `doctor` passes the empty folder, and with content it only warns (no README, broken README links, an unregistered git repository, form errors, no instruction file Copilot would load) {src:.harness/engine/doctor.py#L522-L556}.

## Knowledge base internals: where it plugs in

A knowledge base plugs in at four places. The folder `knowledge-base/`, or a repository registered with `knowledge_base: true` {src:.harness/engine/core/targets.py#L1-L10}. The instruction file `.github/instructions/knowledgebase.instructions.md`: its `applyTo: 'knowledge-base/**'` fires only when the agent touches a file there, so `copilot-instructions.md` links it to make it count for every read {src:.github/instructions/knowledgebase.instructions.md#L1-L4} {src:.github/copilot-instructions.md#L6}; `doctor` passes it only when its `applyTo` is a broad pattern or `AGENTS.md` or `copilot-instructions.md` names it {src:.harness/engine/doctor.py#L490-L499}. The `company/` folder, whose copies `harness company sync` makes (see the section on `company/`). And the hook `kb_offer_stop` (see the section on keeping it true) {src:.harness/engine/modules/task/handler.py#L462-L483}.

Docs and code disagree on one point: `docs/03-configure.md` calls `knowledgebase.instructions.md` an empty placeholder when shipped {src:docs/03-configure.md#L116}, but at 1.8.3 it ships with its full text. It is a text instruction to the model; no code forces the agent to follow it {src:.github/instructions/knowledgebase.instructions.md#L1-L41}.

## Knowledge base internals: the cost rule and what follows

The standard states one test for every rule in it: reading the knowledge must cost less than reading the code it describes and give a better answer; a card longer than the code, a list kept in three places and a fact with no source each break it {src:.harness/contracts/kb/README.md#L5-L5}. It is a design test: no code measures what a read costs, and no check compares a card with its code except the long-object limit below. Where the knowledge base and the code disagree, the code wins, and the instruction file tells the agent to treat the page as the problem {src:docs/08-knowledge-base.md#L11-L11} {src:.github/instructions/knowledgebase.instructions.md#L8-L8}.

What follows is form, and part of it is checked. Each object is listed once, in `objects/index.jsonl`; `domain.yaml` lists no objects; a card is reached by a pointer `objects/<type>.md#<id>` {src:.harness/contracts/kb/README.md#L65-L80}. The limits are `CARD_MAX_LINES` 120 and `ARCHITECTURE_MAX_LINES` 300; `kb check` reports an overlong card or `architecture.md` as a warning, never an error. A card's length is the lines under its `##` heading; when its index line has `lines` the limit is the larger of 120 and one line per 10 lines of its code {src:.harness/engine/core/kbstd.py#L36-L144}. "A list in three places" is checked only as an id twice in one domain's index (an error) and object-list keys in `domain.yaml` (a warning); nothing compares across domains.

## Knowledge base internals: a domain in the standard form

One folder per domain, `<knowledge base>/domains/<domain>/` {src:.harness/contracts/kb/README.md#L7-L26}. `architecture.md` has fixed sections in this order, at most 300 lines: Purpose, Flows, Key data, Where to start, Traps, Limits; nothing checks the order. Empty templates are in `.harness/contracts/kb/templates/`.

`domain.yaml`: required by code are `schema_version` (1), `domain` (the folder name), `description`, `sources` (each with `repo` and `commit`) and `entry_points`; other known keys are `updated`, `generated_by`, `boundaries`, `shared`, `excluded`, `systems`, `files` (each path must exist), `open_questions`, `environment`; any other key is a warning {src:.harness/engine/core/kbstd.py#L24-L31} {src:.harness/contracts/kb/README.md#L33-L63}.

`objects/index.jsonl`: one JSON object per line, written by scripts (`kb index`, `kb stamp`). Required: `id` (`<type>:<name>`), `type`, `card`, `level` (`verified`, `supported`, `inferred`, `unknown`, `conflict`), and with a source `repo` and `sources` (`{path, sha}`, the git blob of the source when the card was written). Optional: `lines`, `source_missing` (`{seen_in, last_in_git}`), `family`, `name`, `classification` {src:.harness/contracts/kb/README.md#L67-L83}.

A card is a `## <id>` section in `objects/<type>.md`: a What line; a relations line Reads, Writes, Called by, Calls (the map's, not the model's); a Level line naming the repository and commit it was read at; the logic, each rule citing its lines as `L120-L145`; and Traps {src:.harness/contracts/kb/README.md#L118-L134}. `kb cardcheck`, not `kb check`, tests the relations against the map and the cited lines against the object's code.

`environment.md` is one table, newest first; `Code then` is the object's index sha on the day the fact was seen {src:.harness/contracts/kb/README.md#L89-L116}. `requests.md` is one table: Id, Object, Kind (`code`, `runtime`, `history`, `decision`), Why, How to get it, Status (`open`, `answered <date> by <who>: <where it went>`, `declined <date>: <why>`, never asked again); one row per object and kind. Code reads inside neither table except that `kb status` counts `requests.md` rows whose last cell starts with `open` {src:.harness/engine/core/kbstatus.py#L88-L93}.

## Knowledge base internals: what `kb check` verifies

`kb check` runs `check_domain` on every domain of every knowledge base, or on those named with `--domain`; no model reads anything {src:.harness/engine/core/kbstd.py#L91-L204}. Errors: in `domain.yaml`, missing or unreadable, `schema_version` not 1, a missing required key, `domain` not the folder name, a source without `repo` or `commit`, a `files` path that is missing; in the index, missing, a line that is not one JSON object, a missing `id`, `type`, `card` or `level`, a bad or repeated id, a level outside the five, a bad `source_missing`, sources without `repo`, a card file or heading that does not exist; an entry point not in the index; and the local-path scan, which reads every `.md`, `.yaml`, `.yml`, `.json` and `.jsonl` file in the domain folder for a path of one computer (`C:\Users\`, `/Users/<name>/`, `/home/<name>/`, `%LOCALAPPDATA%`, `%USERPROFILE%`, `~/`). Warnings: object lists or unknown keys in `domain.yaml`, a gap line at the wrong level, a line without usable sources, a card without an anchor, an overlong card, no `architecture.md`, one over 300 lines.

The exit code is 1 on any error or a `--domain` name that is no domain; warnings never change it. `kb check --path <folder>` checks one folder anywhere (a migration in a task's `DEV/`) {src:.harness/engine/core/kbstd.py#L198-L312}. Not checked: the order of the `architecture.md` sections, what a card says, the inside of `environment.md` and `requests.md`, the index's sort order, whether any `sha` is right. `doctor` turns the errors into one warning; Pack for colleagues refuses on them {src:.harness/engine/doctor.py#L559-L571} {src:.harness/engine/core/company.py#L529-L542}.

## Knowledge base internals: how `kb stale` finds out-of-date cards

`kb stale --domain <d> [--diff]` compares, for each source of each index line, the git blob sha stored when the card was written with the blob sha of the same file on the repository's base branch now {src:.harness/engine/core/kbstd.py#L207-L252}. The card's "as of" commit is a note for readers and is not used. It groups the pairs by the line's `repo`, asks git for the blob shas with `git ls-tree -r -l -z --full-tree <base_ref> -- <paths>` in chunks of 200 paths and compares {src:.harness/engine/core/gitread.py#L19-L70}. The `base_ref` is the repository's own in the target policy, default `main`; only committed content on it is seen.

Each source falls in one class {src:.harness/engine/core/kbstd.py#L233-L247}: `gone` (path not on the base branch); `unstamped` (path there, no `sha`); `changed` (the recorded sha, 12 characters, is not a prefix of the current blob sha); otherwise fresh. Also listed: `unknown_repos` and, only when git failed, `unreadable_repos`. Lines with `source_missing` and `family` lines have no sources and are not judged. Blobs, not commits: another file changing in the same commit does not make a card stale. A git failure is never read as "everything gone": `gitread.run` raises `GitError` (git missing, 30 seconds, failure), and `kb stale` lists the repository in `unreadable_repos` and judges none of its cards {src:.harness/engine/core/gitread.py#L36-L49}. With `--diff`, each `changed` entry gets the `git diff -U2` between the old and current blob, at most 120 lines (`diff_cut: true` when cut); when git no longer has the old blob the diff is empty with a note. Staleness never sets the exit code; an unknown domain, or one with no index file, exits 1 {src:.harness/engine/modules/observe/commands.py#L48-L52}.

The same computation is used by `task fetch`, by the board's book button (`changed` plus `gone` over all domains, about every ten minutes), and by `kb stamp`, in a task's `DEV/` only, which sets the named objects' source shas (all by default) to the first 12 characters of the current base-branch blob and refuses to stamp from a git answer it did not get {src:.harness/engine/core/kbdetail.py#L17-L47} {src:.harness/engine/core/kbstd.py#L315-L367}.

## Knowledge base internals: the repository map, `kb map` and `kb survey`

`kb map` builds the map of every object and every use in the target repositories, by script. It reads each repository's committed base branch (`rev-parse --verify <base_ref>`, then `ls-tree` of that commit), not the working tree; by default it maps every target repository except the knowledge base, and `--repo` names others {src:.harness/engine/core/kbmap.py#L194-L311}. A repository with no such branch gets a note and is not mapped; one git cannot read gets the git error as its note and the others are still mapped {src:.harness/engine/core/kbmap.py#L320-L335}. Without a toolkit, `kb map` refuses and points to `/generic-kb-toolkit-design`; `kb survey` needs none: per repository it lists the kinds of file by suffix, the busiest folders and a few sample files of each kind (`--samples`, 1 to 10), and is the start of the design {src:.harness/engine/core/kbmap.py#L320-L382}.

A run reports, per repository, `files`, `read`, `objects`, `empty`, `failed`, `skipped`; and over the graph the objects by type, the uses by kind, the entry points, `unused`, `dynamic`, `missing`, `external`, `unresolved` and `obsolete_used` {src:.harness/engine/core/kbgraph.py#L319-L343}. It then checks `facts.jsonl` on every run and lists each fact not found as `missing`, and then adds the `declared.jsonl` uses (see the section on uses the map cannot see); a declared use never makes a fact pass {src:.harness/engine/core/kbmap.py#L249-L348}.

`kb map` is a plain command with no task and no approval of its own. Its cache is under `.harness/runtime/`, which the gate lists as admin-locked, and is not knowledge {src:.harness/engine/modules/observe/commands.py#L94-L99} {src:.harness/policies/gate.json#L19-L22}. `--toolkit <folder>` tries a toolkit being built: the folder must be inside `.workspace/sandbox/tasks/`, else the command stops, and the trial's map replaces the cached map until `kb map` runs again without it {src:.harness/engine/core/kbmap.py#L151-L160} {src:.github/skills/generic-kb-toolkit-build/SKILL.md#L51-L51}.

## Knowledge base internals: the toolkit and the extractor contract

The toolkit lives in the knowledge base at `toolkit/`: `toolkit.json`, the `extract_*.py` extractors, `facts.jsonl`, `declared.jsonl`, `inventory/` (the read-only query a person runs on production, used by `kb gaps --inventory`) and `DESIGN.md` {src:.harness/contracts/kb/map.md#L5-L19}. `toolkit.json` requires `schema_version`, `name` and `extractors`; optional are `repos`, `ignore`, `obsolete`, `markers`, `names` (`sql` or `plain`), `entry_types`, `executable_types`, `stop_words`, `shared_min`. Each extractor rule has a `glob` and either `file` (inside the toolkit folder) with `function` (default `extract`), or `builtin: regex` with `node` and `edges` patterns; `ignore` is tested first and the first matching rule wins {src:.harness/engine/core/kbmap.py#L59-L131}.

An extractor is `def f(text, context)`, standard library only, no import of the harness. `context` holds `path`, `stem`, `folder`, `repo`, `rule` and the markers. It returns objects with `id` (`<type>:<name>`), `type`, `name`, `line`, `dynamic` and `refs` (`kind`, `name`, optionally `as`) {src:.harness/contracts/kb/map.md#L19-L59}. The harness ships no toolkit, one builtin extractor (`regex`), and two samples in `.harness/examples/kb-toolkits/` {src:.harness/engine/core/kbextract.py#L81-L110}. An extractor is Python the harness runs; the claim is that a person read it in the approved write-back, but there is no sandbox and no code review step, and a trial toolkit runs before anyone reviewed it.

## Knowledge base internals: `kbmap.py` caches per file by git blob

`build_one` maps one repository and re-reads only files whose blob changed {src:.harness/engine/core/kbmap.py#L194-L242}. The cache is `.harness/runtime/kbmap/<repo>.json`, with `schema_version` 4 (missing, unparsable or another version counts as empty), the commit, toolkit name and signature, and per file `sha`, `lines`, `objects` and any `error` {src:.harness/engine/core/kbgraph.py#L22-L101}. `git ls-tree` of the base commit gives every file; the toolkit's rules choose which are mapped; a file is read when its cached sha differs from the current one; files over 5,000,000 bytes are listed under `skipped`; blobs come from `git cat-file --batch`, 400 per call; a sha git does not return counts as failed and is tried again next run; a file that errored is cached with its error and not retried until its blob or the signature changes; the record is written atomically {src:.harness/engine/core/gitread.py#L73-L89} {src:.harness/engine/core/state.py#L129-L144}.

The toolkit signature is the first 16 hex characters of a sha256 over `toolkit.json` and, sorted, each extractor file it names; `facts.jsonl` and `declared.jsonl` are not in it. When the cached signature differs, nothing cached is kept and every file is read again; `--fresh` does the same {src:.harness/engine/core/kbmap.py#L134-L203}.

## Knowledge base internals: `kbextract.py` isolates each extractor call

`kbextract.run` calls the extractor on one decoded file inside `try/except Exception`: an exception becomes the file's error string and it gets no objects; a return that is not a list becomes an error; items without an `id` and a `type`, and refs without a `kind` and a `name`, are dropped {src:.harness/engine/core/kbextract.py#L24-L74}. One failing file is counted under `failed` and the map goes on. `kbextract.load` imports the extractor under a unique module name (`kbtoolkit_` plus 12 hex characters of the sha256 of its path) with bytecode writing off, so no `__pycache__` appears in the knowledge base. A file that is missing, cannot load or lacks the named function raises `ToolkitError`, which stops the whole map on purpose; the extractor loads when the first file needing it is read {src:.harness/engine/core/kbmap.py#L64-L73}. `decode` never raises: UTF-16 with a byte order mark, then UTF-8, then cp1252.

## Knowledge base internals: `kb audit`, how the sample is drawn and what blind means

`kb audit` without `--answers` draws the sample by script and gives, for each object, where its code is (`id`, `type`, `repo`, `path`, `line`, `lines`, `dynamic` when set) and never what it uses {src:.harness/engine/core/kbaudit.py#L33-L62}. The types are those named with `--type`, else every type whose objects have an outgoing use in the map, so a type that uses nothing is left out. Per type, the live objects (not `obsolete`) are sorted by size and cut into `--per-type` equal slices (default 5, fewer when the type is smaller), and one object per slice is picked by a random generator seeded with `--seed` (default 1): the same map and seed give the same sample, another seed another one.

The blind reading is text, not code. The sample's `next` line and the skill `generic-kb-toolkit-audit` tell the agent to read each object's lines with `task fetch --read`, write one JSON line per use, and not to run `kb near` or `kb order` or look at the map or a card for these objects first {src:.harness/engine/core/messages.en.json#L1235-L1235} {src:.github/skills/generic-kb-toolkit-audit/SKILL.md#L37-L37}. Nothing in code enforces it: the map stays open to the agent, and no code checks which commands ran before the readings {src:.harness/engine/modules/observe/commands.py#L120-L126}.

## Knowledge base internals: `kb audit`, recall, precision and the bar

`kb audit --answers <file>` scores the readings per type {src:.harness/engine/core/kbaudit.py#L65-L179}. A reading is `{from, to, kind, line}`, or `{from, none: true}` for an object that uses nothing; a line that is not JSON, has no `from`, or has neither `to` nor `none` goes to `bad_lines`. A reading marked `dynamic` is skipped. When a `to` fits several objects (the same `schema.name` in two databases) the reading goes to `ambiguous`, and neither it nor the map's matching uses are scored. A reading of a name the map holds as missing or outside matches that use. Kinds do not enter the score; a different kind is listed in `kind_differs`.

Recall of a type is the share of its read uses the map has; precision is the share of its map uses that were read; a side with nothing scores 1.0. A type passes when both reach the bar, `--min`, default 0.95. The audit passes only when there is at least one type, every type passes, and `bad_lines` and `ambiguous` are empty: an ambiguous or bad line blocks passing whatever the numbers are {src:.harness/engine/core/kbaudit.py#L170-L179}. `not_in_map` (a `from` that is no object of the map) and `kind_differs` are listed and do not block; `map_misses` and `map_only` list each difference, up to 100. The exit code is 0 on a pass and 1 otherwise. The code does not check that every sampled object was read: one with no lines in the answers is not scored. That each difference is looked up again at its line, and the answers corrected, before the final score is step 4 of the skill (text) {src:.github/skills/generic-kb-toolkit-audit/SKILL.md#L42-L45}.

## Knowledge base internals: `kb audit`, the result file, `kb status` and a fail

The result is a file the agent writes: `AUDIT.md` in the task, from a template with a `Result:` line and the toolkit's signature; after a pass the write-back puts it at `<knowledge base>/toolkit/audit.md` {src:.github/skills/generic-kb-toolkit-audit/SKILL.md#L46-L47}. `kb status` reads that file, not the score: the audit step is done when the file has a line starting `Result:` then `pass` (case ignored, bold marks allowed) and holds the current toolkit's signature; without it the step stays open with a note that the toolkit changed {src:.harness/engine/core/kbstatus.py#L21-L22} {src:.harness/engine/core/kbstatus.py#L190-L196}. The signature leaves out `facts.jsonl` and `declared.jsonl`. Nothing checks the numbers in the file or that it came from a real run; a person approves the write-back.

On a fail, code does nothing: nothing records it, the audit step stays not done, and `kb status` names it as the next step. The skill tells the agent to name the failing types and the patterns of the misses, fix the toolkit with `/generic-kb-toolkit-build`, and audit again with another `--seed` {src:.github/skills/generic-kb-toolkit-audit/SKILL.md#L47-L47}. The audit is not a gate for learning: `kb order`, `kb index` and learn tasks do not read it. The learn-plan skill offers the audit first, lets the user go on without it, and then says so in the plan's first line {src:.github/skills/generic-kb-learn-plan/SKILL.md#L33-L33}.

## Knowledge base internals: the steps of building as `kb status` computes them

`kb status` works out eight steps from files alone: `targets`, `kb_repo`, `toolkit`, `map`, `audit`, `domains`, `learn`, `maintain`. The stage is the first step not done; `maintain` is done only when the seven before it are {src:.harness/engine/core/kbstatus.py#L157-L217}. Plan, batches and synthesize all sit inside `learn`. `toolkit` is done when `toolkit/toolkit.json` loads; `map` when every code repository the toolkit covers has a cache of the current schema version and, in the full mode, every fact is found and at least one was checked; `domains` when at least one domain exists, as a folder, as a row of the README table (header with `Domain` and `Status`; a row with no folder counts as not started) or as an open `kb` task naming it; `learn` when every domain is done.

A domain is done when `discovery/learn-plan.md` holds a `harness kb order --entry <id>` command with no `<` placeholder, `architecture.md` has a Flows line with an arrow between backticked ids, and that command, run with `--path` on the domain folder, leaves nothing to learn. A domain with cards and an `architecture.md` but no plan counts as done (learned before plans). A domain an open `kb` task learns is judged by its copy in that task's `DEV/` and is not done until written back {src:.harness/engine/core/kbstatus.py#L54-L109}.

## Knowledge base internals: who approves what while a knowledge base is built

Two approvals are enforced by code, for every task and so for every `kb` task. The plan: `task approve-plan` needs a terminal a person types in (or the board's Terminal window) and a six-character code from the sha256 of `PLAN.md` {src:.harness/engine/core/approval.py#L1-L26}; the gate denies an agent that tries to run it {src:.harness/engine/modules/gate/builtin.py#L148-L151}; until it is given, and again after `PLAN.md` or the requirement changes, the gate refuses writes into the task's `DEV/` {src:.harness/engine/modules/gate/handler.py#L64-L88}. The write-back: `task promote` runs only after `task approve-promote` approved the dry run's plan, in the same way {src:.harness/engine/modules/task/task.py#L941-L944}. Everything else is text in a skill, which no code checks.

Toolkit design is an offer; the person approves `TOOLKIT-DESIGN.md` (text) {src:.github/skills/generic-kb-toolkit-design/SKILL.md#L41-L41}. `generic-kb-toolkit-build` carries `disable-model-invocation: true` and says user-only, so the person types it; the harness code only reads that flag to decide how the board starts a skill, and has no check of its own that refuses an agent loading it; its plan and write-back need the two approvals {src:.harness/engine/modules/task/skillsend.py#L30-L36}. `kb map` needs none. The audit is an offer the person may decline; `toolkit/audit.md` is written back with the two approvals. The person confirms the cut of domains once, on `DOMAINS.md` (text); the list goes into the README table through that task's plan and write-back {src:.github/skills/generic-kb-domains/SKILL.md#L42-L43}. The learn plan is approved once per domain with `approve-plan`, and a copy goes to `discovery/learn-plan.md`. Batches need no approval and no write-back: they run inside the approved task and their cards stay in `DEV/`. Synthesize writes `architecture.md`, sets the README status and fills `domain.yaml`, and the whole domain is then written back once with `approve-promote` {src:.github/skills/generic-kb-learn-plan/SKILL.md#L58-L62} {src:.github/skills/generic-kb-learn-synthesize/SKILL.md#L34-L40}.

## Knowledge base internals: `kb order`, how bottom-up is computed

`kb order --entry <id or name> ...` works out by script what to learn for the named entry points and in what order {src:.harness/engine/core/kblearn.py#L54-L194}. Each `--entry` and `--stop` must name exactly one object. Shared objects: the map's own entry points plus the chosen ones each reach a set of objects; an object reached from at least `--shared-min` of them (default the toolkit's `shared_min`, 3), at least one not chosen, is shared and left for `shared/`; an object only the chosen entry points reach stays in the domain however many of them reach it. The closure follows uses from the chosen entry points without entering a shared or `--stop` object; those met are listed as `shared` and `stopped_at` and not learned.

Bottom up is computed inside the closure: objects that use each other (strongly connected, found with Tarjan's algorithm) are collapsed into one part; a part has height 0 when it uses nothing else in the closure, otherwise one more than the highest part it uses; objects not already in the `--path` index are sorted by height, then type, then id {src:.harness/engine/core/kblearn.py#L83-L180}. Why: when what an object uses is learned first, its card can name the cards below it instead of reading that code again {src:docs/08-knowledge-base.md#L66-L66} {src:.github/skills/generic-kb-learn-batch/SKILL.md#L40-L40}.

## Knowledge base internals: `kb order`, batches, options and outputs

A batch is objects of one type. Each object, in the sorted order, goes into the first batch of the same type and the same `dynamic` flag that comes no earlier than the batches of what it uses and has room: fewer than `--batch` objects (default 20) and lines within `--lines` (default 1500). An empty batch always has room, so an object longer than the budget is a batch alone, and `dynamic` objects are never mixed with others {src:.harness/engine/core/kblearn.py#L24-L156}. What an object uses therefore sits in an earlier batch or earlier in the same one, except in a cycle: `cycles` lists them, and code does not put a cycle in one batch (members of two types land in two batches, and the limits can split one type). That a cycle is learned in one batch is the skill's text {src:.github/skills/generic-kb-learn-plan/SKILL.md#L49-L49}.

The answer has `to_learn`, `batches` (`batch`, `type`, `card_file`, `lines`, `dynamic`, `objects`), `large` (objects of 400 lines or more, longest first, read in parts), `shared`, `stopped_at`, `cycles`, `dynamic`, `obsolete`, `missing` and `outside` {src:.harness/engine/core/kblearn.py#L182-L193}. Options are `--batch`, `--lines`, `--shared-min`, repeatable `--stop`, and `--path <domain folder>`, which leaves out objects already in its index, so batch numbers change as batches are learned; {src:.harness/engine/modules/observe/commands.py#L128-L135}.

## Knowledge base internals: `kb cardcheck`, errors, warnings and what it does not check

`kb cardcheck --path <domain folder>` compares the relations that cards and `architecture.md` write with the uses in the map, with no model {src:.harness/engine/core/kblearn.py#L406-L428}. It reads each `## <type>:<name>` section of `objects/*.md` and pulls Reads, Writes, Calls and Called by out of the card's text by regular expression; only ids count. The expected sets come from the map: an outgoing use of kind `reads` or `writes` goes under Reads or Writes, every other kind under Calls, and Called by is every object with a use into this one; declared uses are in the map and so expected {src:.harness/engine/core/kblearn.py#L276-L310}.

Errors, which give exit code 1: a card names a relation the map lacks or has under another field; a card leaves out a Reads, Writes or Calls use of the map (unless declared); a cited range (`L120-L145`) is reversed or outside the object's own code on the base branch; a card of an object of 400 lines or more cites no line; and in the Flows section of `architecture.md`, a line with an arrow whose neighbouring ids are not linked in the map, either direction, within three steps {src:.harness/engine/core/kblearn.py#L313-L403}. Only warnings: a Called by or a declared use left out; an extra relation on a `dynamic` object that the map has under no field; no cite on a card of an object of 50 to 399 lines; and a card stamped against older code, whose cites are then not checked.

Not refused: an id that is not in the map is listed as `not_in_map` (silently when its index line has `source_missing`), so a made-up object is not an error. It does not read the card's prose, check that a rule fits the lines it cites, or check that every object has a card. It is not a gate in code: no promote, hook or `kb check` runs it; the batch and synthesize skills tell the agent to run it after each batch and after `architecture.md` {src:.github/skills/generic-kb-learn-batch/SKILL.md#L43-L43} {src:.github/skills/generic-kb-learn-synthesize/SKILL.md#L39-L39}.

## Knowledge base internals: uses the map cannot see (`by_name`, `declared.jsonl`, `hidden-uses.jsonl`, `dynamic`, `outside`, `missing`)

Teach the extractor first; a declared line is for what no rule can read {src:.harness/contracts/kb/map.md#L66-L74}. `by_name` is a setting in an extractor's rule in `toolkit.json`, read by the sample SQL Server extractor and not by the harness: each entry names a wrapper that starts a job or package by a literal name (`call`, `param` or `position`, `as`, `kind`). A literal name becomes a real use; a variable marks the calling object `dynamic`. The extractor has `sp_start_job` built in; the sample `toolkit.json` has no entry. It is not the toolkit key `names` (`sql` or `plain`), which sets how names resolve. {src:.harness/examples/kb-toolkits/sqlserver/extract_sqlserver.py#L62-L65} {src:.harness/examples/kb-toolkits/sqlserver/extract_sqlserver.py#L202-L240}.

`declared.jsonl` holds one use per line: `from`, `kind`, `to`, `how` and `evidence` (`repo`, `path`, `line`, `text`); a line without a complete form is `bad_lines`, and `how` is not checked {src:.harness/engine/core/kbmap.py#L90-L112}. It is processed only when `kb map` runs: the evidence text must be found within 5 lines of its line on the base branch, else the use is `stale` and left out; an end not in the map is `not_in_map`; a use the toolkit finds itself is `already_mapped`. The uses that hold are saved to `.harness/runtime/kbmap-declared.json`, which `kb near`, `kb order`, `kb flows`, the audit and `kb cardcheck` read, so editing the file changes nothing until the next `kb map`; a card that omits such a use gets a warning {src:.harness/engine/core/kbmap.py#L249-L301}. `hidden-uses.jsonl` is different: in a learn batch the agent writes it into the domain's `discovery/`, in the same form, for a use the code shows and the map lacks. It never goes on a card, no code reads it (`kb check` only scans it for local paths), the synthesize skill lists it under Limits of `architecture.md`, and the toolkit build is told to take those lines first {src:.github/skills/generic-kb-learn-batch/SKILL.md#L48-L48} {src:.github/skills/generic-kb-toolkit-build/SKILL.md#L36-L36}.

`dynamic` is set by the extractor on an object whose uses are incomplete. It gives such objects batches of their own in `kb order`, leaves readings marked dynamic out of the audit score, and turns a card's extra relation on them into a warning; the plan skill asks one `runtime` request for each {src:.harness/engine/core/kbaudit.py#L137-L138} {src:.github/skills/generic-kb-learn-plan/SKILL.md#L44-L47}. A use that resolves to no object is `missing` when its name looks like this system's, and `external` when it names another system (SQL names: a database the map has no objects of); `kb order` and `kb near` show the latter as `outside` {src:.harness/engine/core/kbgraph.py#L254-L275}. `outside` is a boundary, not a request: the plan skill gives it, like `stopped_at`, a line in `boundaries` of `domain.yaml`. `missing` is a gap and becomes a `code` request; `kb gaps` says whether git ever had the file. Neither is an object of the map, so neither can be named on a card.

## Knowledge base internals: keeping a knowledge base true in daily work

By text, the agent runs `kb stale --domain <d>` once at the start of a task that will change code or relies on cards, treats a `changed` or `gone` card as history, notes wrong, stale or missing knowledge in `LOG.md` with the id and evidence without stopping the task, asks at the next natural stop in two or three lines, and after a no does not ask again in that task {src:.github/instructions/knowledgebase.instructions.md#L21-L34}. Code adds one flag: `task fetch` and `task fetch --read` answer with `kb_cards` for the files just fetched, each `stale` when its index source has a sha and the base-branch blob does not start with it. An unstamped card is never flagged; on a git error no cards are given; `gone` exists only in `kb stale`, since a fetch handles files that exist {src:.harness/engine/core/kbstd.py#L275-L302} {src:.harness/engine/modules/task/task.py#L666-L702}.

`generic-kb-refresh` is an offer, in a `kb` task for one domain, at most about 20 cards per task; the plan goes to the person in the terminal; the agent changes only the lines a diff touches; a `gone` source is handled by a rename or by asking the person whether to drop the object or keep it as `source_missing` with level `unknown`; it stamps only cards it checked, never the whole domain; and it checks the form with `kb check --path`, not `kb cardcheck`, so relations are not re-verified {src:.github/skills/generic-kb-refresh/SKILL.md#L30-L49}. `generic-capture-knowledge` is an offer at the end of a task and writes only `KB-DRAFT.md`; it keeps a candidate only when four tests hold (a future agent would get it wrong, the task holds the evidence, it is not in the knowledge base yet, it is still true next month), and "nothing" is the default answer. Each kept fact goes to a card, to `architecture.md` or to a domain skill's gotcha; values, names and secrets are never copied; putting it in is a separate `kb` task {src:.github/skills/generic-capture-knowledge/SKILL.md#L16-L48}.

`kb_offer` is not part of this loop. `kb_offer_stop` is skipped when `kb_offer` is false, for a `kb` task, in autorun, once it fired in the session, when the stage is `targets`, `kb_repo` or `maintain`, and as soon as any domain is done; it runs only when no other stop block (review, task file, write-back) is open. It offers the next building step while the knowledge base is not built, and never fires once a domain is done {src:.harness/engine/modules/task/handler.py#L462-L483} {src:.harness/engine/modules/task/handler.py#L618-L621}.

## Knowledge base internals: the `company/` folder and `company sync`

`<knowledge base>/company/` holds the company's own content, so a copy of the harness stays clean; the first registered knowledge base that has a `company/` is used {src:.harness/engine/core/company.py#L1-L19} {src:.harness/engine/core/targets.py#L191-L193}. In it: `company.json` with `skill_prefix`, read in place; `standards/code-standards.md`, read where it lies in place of `.harness/standards/code-standards.md`; `skills/` (`<prefix>-<name>` folders); `instructions/` (`<name>.instructions.md`); `tools/packs.json` (the factory tool packs that are on), `tools/packs/<name>/` (packs the company wrote, always on), `tools/connections.json` and `tools/computer.json` (a recipe per computer: CA bundle host and proxy, hints for tool folders); and `manifest.json`, made by `pack` {src:.harness/engine/core/standards.py#L22-L24}. No secrets in it is a text rule {src:.github/instructions/knowledgebase.instructions.md#L40-L40}.

`harness company sync` copies and touches no other file {src:.harness/engine/core/company.py#L164-L307}. Each skill folder whose name starts with the prefix and passes the skill checks is copied whole to `.github/skills/`, replacing the copy when it differs; others are listed as `refused` and the exit code is 1. Each instruction file goes to `.github/instructions/<prefix>-<name>.instructions.md` (the prefix is not added twice), except `knowledgebase.instructions.md`, which keeps its name and replaces the harness's. `tools/connections.json` goes to `.harness/policies/connections.company.json` and `tools/computer.json` to `computer.company.json`. Then the skills of every active tool pack are put into `.github/skills/` as `<prefix>-<skill name>`, and those of packs turned off are taken back {src:.harness/engine/core/toolpacks.py#L869-L951}. Edit `company/`, not the copies: each sync overwrites them.

The prefix lives in `company.json`, and the sync also needs the person's `user` policy to hold the same word: if the company has skills or other instruction files and the policy has no `skill_prefix`, or both are set and the words differ (ignoring case), the sync stops before copying anything; the board's prefix button writes the company's word into the person's override and then syncs. A company pack with the name of a factory pack, or an unreadable `packs.json`, also stops the whole sync with nothing changed {src:.harness/engine/core/company.py#L164-L172} {src:.harness/engine/modules/task/boardserve.py#L2036-L2041} {src:.harness/engine/core/toolpacks.py#L237-L261}.

A sync a person asks for (`company sync`, the board's Sync now and prefix buttons, the Save of Get ready) also moves into `.harness/runtime/company-backup/<time>/` the skills of the company's word that left `company/`, copies the ledger `company-copies.json` lists under an old word, and instruction copies whose source left; the sync at board start-up, after sharing connections and after a reinstall takes none of these back (the skills of a tool pack turned off are taken back by every sync). A skill folder `<prefix>-*` in `.github/skills/` that `company/` and the packs do not name counts as one that left, so a person's own skill with that prefix is moved too, into the backup; a file without the prefix that the ledger does not list is never touched {src:.harness/engine/core/company.py#L210-L307} {src:.harness/engine/modules/task/boardserve.py#L2282-L2290}. `company pack --out <folder>` zips what git holds and refuses on a dirty tree, a missing `skill_prefix`, a failing skill or `kb check` errors; `company update --apply` puts a package in place, for a person at a terminal {src:.harness/engine/core/company.py#L523-L619}.

## Knowledge base internals: where scripts do the structure and the model does the meaning

Scripts do what has one right answer: which objects exist and who uses what (`kb map`), the audit sample and score, the order and batches (`kb order`), the paths for Flows (`kb flows`), the index lines of new cards (`kb index` takes type, path, lines and sha from the map and only for ids the map has), the form, staleness, the card relations and cited lines, and the steps {src:.harness/engine/core/kblearn.py#L1-L11}. The stated reasons: the same result every time at no token cost, and a summary of a summary drifts, so flows come from the map {src:docs/08-knowledge-base.md#L13-L13}. The model writes what an object is for, its rules with their lines, its traps, the prose of `architecture.md`, the domain proposal and the blind readings.

The seam is where the model's text meets the map. The checks there test consistency, not truth: relations equal the map, a cited range lies inside the object's code, a flow arrow follows the map within three steps {src:.harness/engine/core/kblearn.py#L335-L403}. Nothing checks that a rule says what the cited lines do, that a `verified` level is earned (`kb index` writes the level it is given, default `verified`), or that a stamped card was read. A use the model sees and the map lacks is not added to the card but declared, fixed in the toolkit, or noted in `hidden-uses.jsonl`.

The line has three limits. The script side is partly model-authored: the extractors are Python the model wrote in `/generic-kb-toolkit-build`, checked by 5 to 10 known facts and by a sampled audit whose readings the model also makes, with a bar of 0.95, which accepts one use in twenty wrong per type {src:.harness/contracts/kb/map.md#L19-L19}. The blind reading, the rule never to stamp or index a card not written from the code, and one batch at a time are text only {src:.github/skills/generic-kb-learn-batch/SKILL.md#L54-L56}. And the environment is outside both sides: the harness never connects to one, so what only it can tell is asked of a person in `requests.md` {src:.harness/contracts/kb/README.md#L89-L91}.

## Knowledge base internals: limits

- **No timeout and no sandbox** for an extractor: an endless loop or a runaway regular expression hangs the map, and only `Exception` is caught, so `SystemExit` and `KeyboardInterrupt` from an extractor are not {src:.harness/engine/core/kbextract.py#L60-L67}.
- **`kb map` and `kb stale` see committed base-branch content only**; the working tree and other branches are not seen {src:.harness/engine/core/kbmap.py#L198-L301}.
- **`kb check` is the form, not the truth**: it does not check that a sha is right or a card accurate, and the size limits are warnings {src:.harness/engine/core/kbstd.py#L91-L186}.
- **The audit and `kb cardcheck` test agreement, not truth.** The blind reading is text; `kb audit` scores only objects the agent wrote lines for; `kb cardcheck` checks cites against the object's range, not against the rule {src:.harness/engine/core/kbaudit.py#L117-L179}.
- **Staleness is per source file, and a stamp is trusted**: a card is fresh when its listed sources are unchanged even if a file it depends on changed, and the code cannot tell whether a stamped card was checked {src:.harness/engine/core/kbstd.py#L233-L247}.
