This file holds the code-level detail behind the feature file 18 Knowledge base: why the harness ships no knowledge base and where one plugs in, the cost rule and what the code holds of it, the files of a domain in the standard form, what `kb check` and `kb stale` do, how `kb map` and the toolkit work, how `kbmap.py` caches per file by git blob and how `kbextract.py` isolates extractors. It is for "how does it work" and "where in the code" questions. Code locations are at harness version 1.8.3.

## Knowledge base internals: shipped empty, and how the code tells empty from content

The harness ships without a knowledge base: in 1.8.3 the folder `knowledge-base/` is not in the package and is made when a team imports its own. The rule, written for agents that change the harness itself, is that `knowledge-base/` must be empty when shipped, is only the place where a team's knowledge base goes, and that business knowledge must not be put, faked or wired in {src:AGENTS.md#L11-L15}. The stated reason is upgrade safety: unpacking a new harness over a copy never writes the team's knowledge base {src:docs/03-configure.md#L116}. Where code moves content, `harness reinstall --from <old copy>` (applied only by a person at a terminal) carries the old `knowledge-base/` into the new copy only when the old one has team content and the new one is a placeholder {src:.harness/engine/core/reinstall.py#L182-L189}. The target policy also ships empty: `repos_root` is an empty string and `repos` an empty object, with `base_ref` `main`; a team's own values go in `target.override.json`, including the entry with `knowledge_base: true` that registers its knowledge base {src:.harness/policies/target.json#L1-L9}.

`targets.knowledge_base_content(folder)` decides what counts as content: nothing when the folder is missing, otherwise every item except `README.md`, `.gitkeep`, `.gitignore`, `.DS_Store` and any name starting with a dot {src:.harness/engine/core/targets.py#L170-L179}. `doctor`, Get ready, the setup status, `target init-kb` and `reinstall` all ask this one function. `doctor` reports the empty folder as a pass ("no knowledge base is plugged in"), and with content it only warns (no README, broken README links, an unregistered git repository, form errors, no instruction file Copilot would load) {src:.harness/engine/doctor.py#L522-L556}.

## Knowledge base internals: where it plugs in

A knowledge base plugs in at four places. The folder `knowledge-base/`, or a repository registered with `knowledge_base: true` {src:.harness/engine/core/targets.py#L1-L10}. The instruction file `.github/instructions/knowledgebase.instructions.md`: its `applyTo: 'knowledge-base/**'` fires only when the agent touches a file there, so `copilot-instructions.md` links it to make it count for every read {src:.github/instructions/knowledgebase.instructions.md#L1-L4} {src:.github/copilot-instructions.md#L6}; `doctor` passes the file only when its `applyTo` is a broad pattern (`**`, `**/*`, `*`, `**/**`) or `AGENTS.md` or `copilot-instructions.md` names it {src:.harness/engine/doctor.py#L490-L499}. The `company/` folder inside the knowledge base: `harness company sync` copies its skills to `.github/skills/`, its instruction files to `.github/instructions/` (`knowledgebase.instructions.md` keeps its name and replaces the harness's), and its `connections.json` and `computer.json` to `.harness/policies/` {src:.harness/engine/core/company.py#L1-L19}. And the hook: at a stop of a task that is not a `kb` task, not in autorun, once per session, while no domain is learned and the code repositories and a knowledge base are set up, `kb_offer_stop` blocks the stop once with a line naming the next step; `kb_offer: false` in `task.json` turns it off {src:.harness/engine/modules/task/handler.py#L462-L483}.

Docs and code disagree on one point: `docs/03-configure.md` calls `knowledgebase.instructions.md` an empty placeholder when shipped {src:docs/03-configure.md#L116}, but at 1.8.3 it ships with its full text. It is a text instruction to the model; no code forces the agent to follow it {src:.github/instructions/knowledgebase.instructions.md#L1-L41}.

## Knowledge base internals: the cost rule and what follows

The standard states one test for every rule in it: reading the knowledge must cost less than reading the code it describes and give a better answer; a card longer than the code, a list kept in three places and a fact with no source each break it {src:.harness/contracts/kb/README.md#L5-L5}. It is a design test, not a measured guarantee: no code measures what a read costs, and no check compares a card with the code it describes except the long-object limit below. Where the knowledge base and the code disagree, the code wins; that is written in the docs, and the instruction file tells the agent to treat knowledge the code or a run shows otherwise as wrong, and the page as the problem {src:docs/08-knowledge-base.md#L11-L11} {src:.github/instructions/knowledgebase.instructions.md#L8-L8}.

What follows is form, and part of it is checked. Each object is listed once, in `objects/index.jsonl`; `domain.yaml` lists no objects; a card is reached by a pointer `objects/<type>.md#<id>`, so the agent reads one section {src:.harness/contracts/kb/README.md#L65-L65} {src:.harness/contracts/kb/README.md#L80-L80}. The size limits are constants `CARD_MAX_LINES` 120 and `ARCHITECTURE_MAX_LINES` 300 {src:.harness/engine/core/kbstd.py#L36-L37}; `kb check` reports an overlong card or `architecture.md` as a warning, never an error. A card's length is the lines under its `##` heading; a long object may have more: when its index line has `lines` (`[first, last]`, written by `kb index`) the limit is the larger of 120 and one line per 10 lines of its code {src:.harness/engine/core/kbstd.py#L83-L88}. "A list in three places" has these checks only: an id twice in one domain's index is an error, and object-list keys in `domain.yaml` (`included_objects`, `core_objects`, `objects`) are a warning; nothing compares across domains {src:.harness/engine/core/kbstd.py#L105-L108} {src:.harness/engine/core/kbstd.py#L142-L144}.

The write-back path is text and approvals: the agent notes wrong or stale knowledge in the task's `LOG.md`, asks the person at the next stop, and changes the knowledge base only through a `kb` task with plan and write-back approval {src:.github/instructions/knowledgebase.instructions.md#L27-L34}. The harness never connects to an environment: what only an environment can tell is asked of a person in `requests.md`, and goes into `environment.md` only from the result they hand over {src:.harness/contracts/kb/README.md#L89-L91}.

## Knowledge base internals: a domain in the standard form

One folder per domain, `<knowledge base>/domains/<domain>/` {src:.harness/contracts/kb/README.md#L7-L26}. `architecture.md` has fixed sections in this order, at most 300 lines: Purpose, Flows, Key data, Where to start, Traps, Limits; nothing checks the order {src:.harness/contracts/kb/README.md#L85-L87}. Empty templates of each file are in `.harness/contracts/kb/templates/` {src:.harness/contracts/kb/templates/architecture.md#L1-L13}.

`domain.yaml`: required by code are `schema_version` (must be 1), `domain` (the folder name, any case), `description`, `sources` (each item needs `repo` and `commit`; usually `branch` too) and `entry_points`; optional and known are `updated`, `generated_by`, `boundaries`, `shared`, `excluded`, `systems`, `files` (each path must exist), `open_questions`, `environment`; any other key is a warning {src:.harness/engine/core/kbstd.py#L24-L31} {src:.harness/contracts/kb/README.md#L33-L63}.

`objects/index.jsonl`: one JSON object per line, sorted by id, written by scripts (`kb index`, `kb stamp`). Required: `id` (`<type>:<name>`; the name may hold spaces but not at its ends), `type`, `card`, `level` (`verified`, `supported`, `inferred`, `unknown` or `conflict`); with them `repo` and `sources`, a list of `{path, sha}` whose `sha` is the git blob of the source when the card was written. Optional: `lines`, `source_missing` (`{seen_in, last_in_git}`, level `unknown` or `conflict`), `family` lines (`pattern`, `member_type`, `members`), `name`, `classification` {src:.harness/contracts/kb/README.md#L67-L83}. The sort order is not tested.

A card is a `## <id>` section in `objects/<type>.md`: a What line; a relations line Reads, Writes, Called by, Calls (the map's, not the model's); a Level line naming the repository and the commit it was read at; the logic, each rule citing its lines as `L120-L145`; and Traps {src:.harness/contracts/kb/README.md#L118-L134}. `kb cardcheck`, not `kb check`, tests the relations line against the map and the cited lines against the object's code {src:.harness/engine/core/kblearn.py#L406-L428}.

`environment.md` is one table, newest first: Environment, Seen, Object, Code then, Fact, From, Level. `Code then` is the object's `sources[].sha` in the index on the day the fact was seen; when the index sha has moved on, the fact was seen against older code {src:.harness/contracts/kb/README.md#L89-L100}. `requests.md` is one table: Id, Object, Kind (`code`, `runtime`, `history` or `decision`), Why, How to get it, Status (`open`, `answered <date> by <who>: <where it went>`, or `declined <date>: <why>`, never asked again); one row per object and kind {src:.harness/contracts/kb/README.md#L102-L116}. No code reads the inside of either table.

## Knowledge base internals: what `kb check` verifies

`kb check` runs `check_domain` on every domain under `domains/` of every knowledge base, or on those named with `--domain` (repeatable, any case); no model reads anything {src:.harness/engine/core/kbstd.py#L189-L204}. Errors: in `domain.yaml`, missing, unreadable or not a mapping, `schema_version` not 1, a required key missing, `domain` not the folder name, a source without `repo` or `commit`, a `files` path that is missing; in the index, missing, a line that is not one JSON object, a missing `id`, `type`, `card` or `level`, a bad id, an id twice, a level outside the five, a bad `source_missing`, sources without `repo`, a card file or heading anchor that does not exist; an entry point not in the index (when the index has lines); and the local-path scan, which reads every `.md`, `.yaml`, `.yml`, `.json` and `.jsonl` file in the domain folder, cards included, for a path of one computer (`C:\Users\`, `/Users/<name>/`, `/home/<name>/`, `%LOCALAPPDATA%`, `%USERPROFILE%`, `~/`) {src:.harness/engine/core/kbstd.py#L91-L186}. Warnings: object lists or unknown keys in `domain.yaml`, a gap line at the wrong level, a line without usable sources, a card without an anchor, an overlong card, no `architecture.md`, one over 300 lines.

The exit code is 1 when there is any error or when a `--domain` name is no domain; warnings never change it. `kb check --path <folder>` checks one folder anywhere (a migration in a task's `DEV/`) and exits 1 on an error only {src:.harness/engine/core/kbstd.py#L198-L204} {src:.harness/engine/core/kbstd.py#L308-L312}. Not checked: the order of the `architecture.md` sections, what a card says, the inside of `environment.md` and `requests.md`, the index's sort order, and whether any `sha` is right. `doctor` turns the errors into one warning; Pack for colleagues refuses on them {src:.harness/engine/doctor.py#L559-L571} {src:.harness/engine/core/company.py#L529-L542}.

## Knowledge base internals: how `kb stale` finds out-of-date cards

`kb stale --domain <d> [--diff]` compares, for each source of each index line, the git blob sha stored when the card was written with the blob sha of the same file on the repository's base branch now {src:.harness/engine/core/kbstd.py#L207-L252}. It does not use the card's "as of" commit: the commit in a card's Level line and in `domain.yaml` is a note for readers, and the code never reads it for staleness. It groups the pairs by the line's `repo`, asks git for the blob shas of those paths with `git ls-tree -r -l -z --full-tree <base_ref> -- <paths>` in chunks of 200 paths, and compares {src:.harness/engine/core/gitread.py#L19-L20} {src:.harness/engine/core/gitread.py#L52-L70}. The `base_ref` is the repository's own in the target policy, default `main`; only committed content on it is seen, never the working tree or another branch.

Each source falls in one class {src:.harness/engine/core/kbstd.py#L233-L247}: `gone` (path not on the base branch); `unstamped` (path there, no `sha` on the line); `changed` (the recorded sha, 12 characters, is not a prefix of the current blob sha); otherwise fresh. Also listed: `unknown_repos` (a `repo` the target policy does not know) and, only when git failed, `unreadable_repos`. Lines with `source_missing` and `family` lines have no sources and are not judged.

Blobs, not commits, because a blob sha changes only when that file's content changes: another file changing in the same commit does not make a card stale. A git failure is never read as "everything gone": `gitread.run` raises `GitError` when git is missing, times out (30 seconds) or fails; `kb stale` catches it per repository, lists the repository in `unreadable_repos`, and judges none of its cards {src:.harness/engine/core/gitread.py#L36-L49} {src:.harness/engine/core/kbstd.py#L228-L232}. With `--diff`, each `changed` entry gets the `git diff -U2` between the old and the current blob, at most 120 lines (`diff_cut: true` when cut); when git no longer has the old blob the diff is empty and the entry carries a note to read the source as it is {src:.harness/engine/core/kbstd.py#L240-L246} {src:.harness/engine/core/gitread.py#L92-L96}. Staleness never sets the exit code: `kb stale` exits 0 whether or not cards changed; an unknown domain, or a domain with no index file, is an error and exits 1 {src:.harness/engine/modules/observe/commands.py#L48-L52}.

The same computation is used elsewhere. `task fetch` marks a card `stale` for each fetched file when the card has a sha and the base branch blob does not start with it; on a git failure it gives no cards, never a wrong "stale" {src:.harness/engine/core/kbstd.py#L275-L302}. The board's book button counts `changed` plus `gone` over all domains, refreshed about every ten minutes {src:.harness/engine/core/kbdetail.py#L17-L47} {src:.harness/engine/modules/task/web/dock.js#L111-L124}. `kb stamp`, in a task's `DEV/` only, sets the named objects' source shas (all by default) to the first 12 characters of the current base branch blob, and refuses to stamp from a git answer it did not get {src:.harness/engine/core/kbstd.py#L315-L367}.

## Knowledge base internals: the repository map, `kb map` and `kb survey`

`kb map` builds the map of every object and every use in the target repositories, by script. It reads each repository's committed base branch (`rev-parse --verify <base_ref>`, then `ls-tree` of that commit), not the working tree; by default it maps every target repository except the knowledge base, and `--repo` names others {src:.harness/engine/core/kbmap.py#L194-L242} {src:.harness/engine/core/kbmap.py#L304-L311}. A repository with no such branch gets a note and is not mapped; one git cannot read gets the git error as its note and the others are still mapped {src:.harness/engine/core/kbmap.py#L320-L335}. Without a toolkit, `kb map` refuses and points to `/generic-kb-toolkit-design`; `kb survey` needs none: per repository it lists the kinds of file by suffix, the busiest folders and a few sample files of each kind (`--samples`, 1 to 10), and is the start of the design {src:.harness/engine/core/kbmap.py#L320-L327} {src:.harness/engine/core/kbmap.py#L354-L382}.

A run reports, per repository, `files`, `read`, `objects`, `empty`, `failed`, `skipped`; and over the graph the objects by type, the uses by kind, the entry points, `unused`, `dynamic`, `missing`, `external`, `unresolved`, `obsolete_used` and `failed_files` {src:.harness/engine/core/kbgraph.py#L319-L343}. It then checks `facts.jsonl` on every run and lists each fact not found as `missing`, and adds the `declared.jsonl` uses: a declared use counts only when its evidence text is found, ignoring case and spacing, within 5 lines of its stated line on the base branch; otherwise it is listed as `stale` and left out. Facts are checked before declared uses are added, so a declared use never makes a fact pass {src:.harness/engine/core/kbmap.py#L249-L301} {src:.harness/engine/core/kbmap.py#L336-L348}.

`kb map` is a plain `harness` command with no task and no approval of its own; the skills tell the agent when to run it. Its cache is under `.harness/runtime/`, which the gate lists as admin-locked, and is not knowledge {src:.harness/engine/modules/observe/commands.py#L94-L99} {src:.harness/policies/gate.json#L19-L22}. `kb audit` is a separate command. `--toolkit <folder>` tries a toolkit being built: the folder must be inside `.workspace/sandbox/tasks/`, else the command stops, and the trial's map replaces the cached map until `kb map` runs again without it {src:.harness/engine/core/kbmap.py#L151-L160} {src:.github/skills/generic-kb-toolkit-build/SKILL.md#L51-L51}.

## Knowledge base internals: the toolkit and the extractor contract

The toolkit lives in the knowledge base at `toolkit/`: `toolkit.json`, the `extract_*.py` extractors, `facts.jsonl`, `declared.jsonl`, `inventory/` (the read-only query a person runs on production, used by `kb gaps --inventory`) and `DESIGN.md` {src:.harness/contracts/kb/map.md#L5-L19}. `toolkit.json` requires `schema_version`, `name` and `extractors`; optional are `repos`, `ignore`, `obsolete`, `markers`, `names` (`sql` or `plain`), `entry_types`, `executable_types`, `stop_words`, `shared_min`. Each extractor rule has a `glob` and either `file` (inside the toolkit folder) with `function` (default `extract`), or `builtin: regex` with `node` and `edges` patterns; `ignore` is tested first and the first matching rule wins {src:.harness/engine/core/kbmap.py#L59-L62} {src:.harness/engine/core/kbmap.py#L114-L131}.

An extractor is `def f(text, context)`, standard library only, no import of the harness. `context` holds `path`, `stem`, `folder`, `repo`, `rule` and the markers. It returns objects with `id` (`<type>:<name>`), `type`, `name`, `line`, `dynamic` and `refs` (`kind`, `name`, optionally `as`) {src:.harness/contracts/kb/map.md#L37-L59}. The harness ships no toolkit, one builtin extractor (`regex`), and two samples in `.harness/examples/kb-toolkits/` {src:.harness/engine/core/kbextract.py#L81-L110}. An extractor is Python the harness runs. The claim is that a person read it in the approved write-back that put it in the knowledge base; there is no sandbox and no code review step, and a trial toolkit in a task folder runs before anyone reviewed it {src:.harness/contracts/kb/map.md#L19-L19}.

## Knowledge base internals: `kbmap.py` caches per file by git blob

`build_one` maps one repository and re-reads only files whose blob changed {src:.harness/engine/core/kbmap.py#L194-L242}. The cache is `.harness/runtime/kbmap/<repo>.json`, compact JSON with `schema_version` 4 (missing, unparsable or another version counts as empty), the commit, toolkit name and signature, and per file `sha`, `lines`, `objects` and any `error` {src:.harness/engine/core/kbgraph.py#L22-L22} {src:.harness/engine/core/kbgraph.py#L87-L101}. The steps: `git ls-tree` of the base commit gives sha, size and path of every file; the toolkit's rules choose which are mapped; a file is read when its cached sha differs from the current blob sha; files over 5,000,000 bytes among them are listed under `skipped`, not read; the blobs come from `git cat-file --batch`, 400 per call, and a sha git does not return is not cached, counts as failed and is tried again next run; a file that errored is cached with its sha and error and not retried until its blob or the signature changes; the record is written atomically (temporary file, then replace) {src:.harness/engine/core/gitread.py#L73-L89} {src:.harness/engine/core/state.py#L129-L144}.

The toolkit signature is the first 16 hex characters of a sha256 over `toolkit.json` and, sorted, each extractor file it names (a missing file counts as a dash); `facts.jsonl` and `declared.jsonl` are not in it. When the cached signature differs, nothing cached is kept and every file is read again; `--fresh` does the same {src:.harness/engine/core/kbmap.py#L134-L148} {src:.harness/engine/core/kbmap.py#L201-L203}. The report fields: `files` (mapped), `read`, `objects`, `empty` (no object, no error), `failed` (errors plus unread shas), `skipped` {src:.harness/engine/core/kbmap.py#L236-L242}.

## Knowledge base internals: `kbextract.py` isolates each extractor call

`kbextract.run` calls the extractor on one decoded file inside `try/except Exception`: an exception becomes the error string `<ExceptionName>: <message>` and the file gets no objects; a return that is not a list becomes the error `did not return a list`; items without an `id` and a `type` are dropped, and refs without a `kind` and a `name` are dropped {src:.harness/engine/core/kbextract.py#L60-L74}. So one failing or odd file is counted under `failed` and the map goes on.

`kbextract.load` imports the extractor file under the unique module name `kbtoolkit_<first 12 hex of the sha256 of its resolved path>` (two toolkits may both have `extract_sql.py`) with bytecode writing off, so no `__pycache__` appears in the knowledge base. A file that is missing, cannot be loaded, raises on import or lacks the named function raises `ToolkitError`, which `kbmap` turns into a `MapError` that stops the whole map, on purpose: the toolkit's owner must know {src:.harness/engine/core/kbextract.py#L36-L57} {src:.harness/engine/core/kbmap.py#L64-L73}. The extractor loads when the first file needing it is read, so a run that finds every file cached never loads it. `decode` never raises: UTF-16 with a byte order mark, then UTF-8, then cp1252 with replacement {src:.harness/engine/core/kbextract.py#L24-L33}.

## Knowledge base internals: limits

- **No timeout and no sandbox** for an extractor: an endless loop or a runaway regular expression hangs the map, and only `Exception` is caught, so `SystemExit` and `KeyboardInterrupt` from an extractor are not {src:.harness/engine/core/kbextract.py#L60-L67}.
- **`kb map` and `kb stale` see committed base-branch content only**; the working tree and other branches are not seen {src:.harness/engine/core/kbmap.py#L198-L201}.
- **`kb check` is the form, not the truth**: it does not check that a sha is right or a card accurate, and the size limits are warnings {src:.harness/engine/core/kbstd.py#L91-L186}.
- **Staleness is per source file, and a stamp is trusted**: a card is fresh when its listed sources are unchanged even if a file it depends on changed, and the code cannot tell whether a stamped card was checked {src:.harness/engine/core/kbstd.py#L233-L247}.
