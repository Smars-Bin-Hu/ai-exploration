This file holds the code-level detail behind the feature file 15 The gate and guardrails: which hook events exist and who handles them, the path of one call through `launch.py`, `hook.py`, the adapter and the modules, how decisions are merged, what happens when a module or the engine fails, and how the gate reads a command line. It is for "how does it work" and "where in the code" questions; for what the gate is for and what it stops, read the feature file first. Code locations are at harness version 1.8.3.

## Gate internals: the hook events and which module handles each

`.github/hooks/harness.json` configures nine hook events, and every one starts the same command, `python3 .harness/engine/launch.py` (`python` on Windows), in the repository folder with a 30-second timeout: `SessionStart`, `UserPromptSubmit`, `userPromptTransformed`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SubagentStart`, `SubagentStop` and `Stop` {src:.github/hooks/harness.json#L1-L113}. `userPromptTransformed` is the only camelCase key: it is the config name of the event the code calls `UserPromptTransformed`, which only the Copilot SDK engine sends {src:.harness/engine/core/events.py#L8-L22}.

The code knows ten event names. The tenth, `PreCompact`, is accepted by the adapter and by the registry schema, but `harness.json` does not configure it and no module subscribes to it, so a hook process never receives it {src:.harness/engine/core/events.py#L8-L22} {src:.harness/engine/core/registry.py#L37}. `harness doctor` compares what is configured with what is needed: the needed events are the ones core tracks (`SessionStart`, `UserPromptSubmit`, `UserPromptTransformed`, `PreToolUse`, `SubagentStart`, `SubagentStop`, `Stop`) plus the events of every enabled, non-retired module; a needed event with no entry in the hook config is an ERROR, a configured event nobody needs is a WARN, and a hook command that does not contain `.harness/engine/launch.py` is an ERROR {src:.harness/engine/doctor.py#L217-L252} {src:.harness/engine/core/state.py#L48-L49}. A module that listed `PreCompact` in the registry would therefore be flagged until the hook config gained the event.

The registry subscribes modules to events, in this registry order {src:.harness/registry.json#L92-L321}:

- **`task`** (enforcement S, C, H): `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `Stop`.
- **`gate`** (S, H): `PreToolUse`, `UserPromptSubmit`, `SessionStart`, `PostToolUse`, `PostToolUseFailure`.
- **`observe`** (V): `PostToolUseFailure` only.
- **`evalcheck`** (V): no event at all; it only offers `doctor` checks of the scenario files and a command line command {src:.harness/engine/modules/evalcheck/handler.py#L1-L22}.

What each module does per event {src:.harness/engine/modules/task/handler.py#L629-L652} {src:.harness/engine/modules/gate/handler.py#L758-L812}:

- **`SessionStart`:** the task module returns the task state text as context; the gate returns the connections line (`wrapped_context`) and starts the reachability probes (`watch_reach`).
- **`UserPromptSubmit`:** the task module reads the marks only the person may set (`[review]=n`, a reply-language mark, `/generic-mapreduce`) and returns the task state text; the gate sets or clears the read-only marks of the super agent chat and of a question turn, and adds the text about approved outside calls and named servers.
- **`PreToolUse`:** the gate decides every call (the order is in the section "Gate internals: the order of checks on a call"); the task module judges only the question tool while autorun is on, and subagent calls.
- **`PostToolUse`:** the task module notes a finished question call, a write inside the task and the end of the reviewer's call; the gate, for terminal tools only, reads what the terminal printed for the reachability check and may add text for the agent. **`PostToolUseFailure`:** only the gate's terminal branch; by its own header, `observe` subscribes to it only so that a failed call is an event the hook is needed for and gets its line in the log {src:.harness/engine/modules/observe/handler.py#L1-L6}.
- **`SubagentStart`:** the task module adds context for the `mapper`, for the `worker` while the task's autorun is on, and for the reviewer when a check is waiting; core records the new subagent as waiting for its session.
- **`SubagentStop`:** the task module acts only for the `worker` subagent of a task whose autorun is on: it writes the `end` line of the autorun ledger and returns no decision, so it never blocks {src:.harness/engine/modules/task/handler.py#L582-L596}.
- **`Stop`:** the task module can block the agent from stopping. It collects the blocks of `review_stop` (the result has not passed its checks), `task_file_stop` (task files were written in this prompt and `TASK.md` was not) and `write_back_stop` (the write-back is done but steps of `TODO.md` are not ticked or `COMMIT-MESSAGE.md` is missing); a knowledge base offer is added only when nothing else blocks; in autorun it pushes the agent to the next step instead; a second `Stop` with `stop_hook_active` always lets the agent stop {src:.harness/engine/modules/task/handler.py#L599-L626}.
- **`UserPromptTransformed`:** no module; core answers it (the section "Gate internals: restoring the injected text at userPromptTransformed").

Separately from the subscriptions, `hook.py` hands every call it decided to the `observe` module, whatever the event: `main` calls `observe()` after the answer is made, which imports `modules.observe` and calls `record_call` when the registry entry is enabled and not retired {src:.harness/engine/hook.py#L156-L164} {src:.harness/engine/hook.py#L374-L375}. So the call log has a line for every hook call, including events that no module subscribed `observe` to.

## Gate internals: one tool call from launch.py to the answer

One hook event is one Python process, and the steps of a call live in these places {src:.harness/engine/hook.py#L1-L16}:

1. **VS Code runs `launch.py`.** `launch.main` reads all of stdin as bytes, loads `hook.py` by path with `importlib`, puts the same bytes back as `sys.stdin`, and calls `hook.main()`; if loading or running raises anything, including `SystemExit`, it prints its own answer instead {src:.harness/engine/launch.py#L50-L60}.
2. **`hook.main`** (L342-378) reads stdin as text, runs the integrity check, raises `ENGINE_FAULT` if the engine imports failed, and either answers an integrity problem itself or calls `process` {src:.harness/engine/hook.py#L342-L378}.
3. **`process`** decodes the JSON (it must be an object), picks the adapter (`adapters.detect`), turns the payload into a `HookEvent` (`adapter.parse`), loads the registry (`load_registry`, schema-checked), lists the subscribed modules (`modules_for`), and finds which of them the registry marks `H` (the guards) {src:.harness/engine/hook.py#L90-L99}.
4. **The session.** For a `UserPromptSubmit` of a session with no state file yet, `state.claim_child` looks for a parent that just started a subagent and, on a match, lets the new session inherit the parent's task and sets `event.from_subagent` {src:.harness/engine/hook.py#L100-L102} {src:.harness/engine/core/state.py#L303-L354}. Then `state.session` takes the session lock, reads the state file and yields it {src:.harness/engine/hook.py#L110-L117}.
5. **Core before the modules:** `track_before` (subagent bookkeeping, breaker reset). **The modules:** `run_modules` imports `modules.<name>` and calls `handle(event, ctx)` for each name that `modules_for` returned, in registry order. **The merge:** `events.merge` combines the decisions. **The breaker:** `breaker.apply`. **Core after:** `track_after`. **Write-back:** `state.session` writes the state file when the block ends without an exception {src:.harness/engine/hook.py#L111-L129}.
6. **The record and the answer.** `callrecord.build` makes the record, `adapter.render` makes the output JSON, `main` stamps the record with the duration and process id, calls `observe`, and prints the JSON followed by a newline; the process exit code is always 0 {src:.harness/engine/hook.py#L135-L153} {src:.harness/engine/hook.py#L372-L378}.

`registry.modules_for` only returns the list of module names (enabled, status not `retired`, event in the module's `events`, in the order of the registry file). It calls no module; `hook.run_modules` does {src:.harness/engine/core/registry.py#L128-L134} {src:.harness/engine/hook.py#L58-L87}.

## Gate internals: launch.py, the small file in front of hook.py

`launch.py` is about 64 lines of standard library only, and its header says it is small on purpose, so that nobody has a reason to change it {src:.harness/engine/launch.py#L1-L5}. It exists because the hook config names it for every event, and a syntax error, a conflict marker or a missing `hook.py` would otherwise leave Copilot with no answer. It loads `hook.py` inside `try/except BaseException`, after reading stdin once and putting it back for `hook.py`, and on any failure prints one JSON line and exits 0 {src:.harness/engine/launch.py#L50-L60}.

The answer of `launch.py` depends on the event it reads from the payload (`hook_event_name`, or `PreToolUse` inferred when there is a tool name and no tool result) {src:.harness/engine/launch.py#L29-L47}:

- **`PreToolUse`:** `{}` (no objection) when the tool is in its `SAFE` list and the tool input has no string `command`; otherwise `{"permissionDecision": "deny", "permissionDecisionReason": ...}` with an English text naming the file and the fault.
- **`UserPromptSubmit` and `SessionStart`:** `{"additionalContext": ...}` with the same words, so the agent hears of the fault at the start.
- **Every other event:** `{}`.

The `SAFE` list has 22 names, a copy of `SAFE_TOOLS` in `hook.py`; a test keeps the two equal, so `launch.py` has no different list of its own {src:.harness/engine/launch.py#L14-L15} {src:.harness/engine/hook.py#L170-L173}. The 22 names are `read_file`, `list_dir`, `grep_search`, `file_search`, `semantic_search`, `Read`, `Grep`, `Glob`, `search_code_subagent`, `WebFetch`, `skill`, `tool_search_tool`, `task_complete`, `AskUserQuestion`, `ask_user`, `Agent`, `runSubagent`, `read_bash`, `read_powershell`, `list_bash`, `list_powershell` and `report_intent`. Reads and searches pass, and so do the web fetch, the skill loader, the meta tools, the question tool and subagent calls.

`launch.py` answers less than the emergency answer of `hook.py`: its words are English only (no language choice), it runs no integrity check, writes no log line and no board record, and knows nothing of tool packs, so a call to a governed program is not refused with program-specific words {src:.harness/engine/launch.py#L16-L47}. There are two layers: `launch.py` covers a `hook.py` that cannot be loaded, and `hook.py` covers an engine that cannot be imported. `harness doctor` compiles both files and names the file and line of a syntax error; a fault in `launch.py` itself cannot be covered, because Copilot could not start it {src:.harness/engine/doctor.py#L255-L267}.

## Gate internals: the adapter that turns a payload into an event

`adapters.detect` returns the first adapter whose `matches(payload)` is true; only the VS Code Copilot adapter (`copilot_vscode`, surface `vscode`) exists, and a payload no adapter matches raises `ValueError`, which `main` treats as a failure to decide {src:.harness/engine/adapters/__init__.py#L9-L17}. The adapter reads the event name from `hook_event_name`; a payload with no name and both `sessionId` and `agentName` is a `SubagentStart`, and one with `sessionId` and `transformedPrompt` is a `UserPromptTransformed`; a name outside the ten known ones does not match {src:.harness/engine/adapters/copilot_vscode.py#L33-L43}.

`copilot_vscode.parse` fills the `HookEvent`: the session id (`session_id` or `sessionId`), tool name and tool input, the prompt and `words` (what the person typed, with the text of a skill removed, so a mark such as `[review]=n` inside a skill's text is not the person's), the tool result text, the error of a failed call, agent id and type (`agent_type` or `agentName`), `stop_hook_active` and the transformed prompt {src:.harness/engine/adapters/copilot_vscode.py#L71-L106}. `common.build_event` rejects an event name outside `EVENT_NAMES` and a missing session id with `ValueError` {src:.harness/engine/adapters/common.py#L95-L130}.

`build_event` derives the rest from `tool_kinds.json`. The kind is `tools.get(name, "other")` for a tool name, and the empty string when the payload has no tool name. The command is the tool input's `command` key when it is a string. The tool input may be an object, a JSON string, or plain text; plain text is kept under the key `input`, which is how a patch from a GPT model arrives {src:.harness/engine/adapters/common.py#L44-L54}. The paths are every value under the configured `path_keys` (`filePath`, `path`) at the top level, then in nested objects and lists down to depth 4 (for example `replacements[].filePath`), and, for edit and create tools only, the paths in patch headers (`*** Add File:`, `Update File:`, `Delete File:`, `Move to:`) found in any string value {src:.harness/engine/adapters/common.py#L57-L84}. A terminal call counts as a search (`is_search`) when its command starts with one of `rg`, `grep`, `git grep` or `find` after the start of the line or a `;`, `&` or `|` {src:.harness/engine/adapters/common.py#L32-L41}. For a `skill` call the skill name is read from `skill_key`; for a subagent call the target from the first non-empty of `agentName`, `agent_type`, and the prompt from `prompt` {src:.harness/engine/adapters/common.py#L121-L129}.

## Gate internals: tool_kinds.json, the table of tool names

`.harness/engine/adapters/tool_kinds.json` has one surface, `vscode` (marked verified from recordings of the Copilot SDK engine and an earlier recording of the older tool names), with 30 tool names, and the lookup is case-sensitive: `Bash` and `bash` are both listed, `BASH` is not {src:.harness/engine/adapters/tool_kinds.json#L1-L39}. The kinds and their names:

- **read:** `read_file`, `list_dir`, `Read`.
- **search:** `grep_search`, `file_search`, `semantic_search`, `Grep`, `Glob`, `search_code_subagent`.
- **create:** `create_file`, `Write`.
- **edit:** `replace_string_in_file`, `Edit`, `multi_replace_string_in_file`, `insert_edit_into_file`, `apply_patch`, `edit_notebook_file`.
- **terminal:** `run_in_terminal`, `Bash`, `bash`, `PowerShell`, `powershell`.
- **subagent:** `runSubagent`, `Agent`.
- **web:** `WebFetch`. **skill:** `skill`. **meta:** `tool_search_tool`, `task_complete`. **ask:** `AskUserQuestion`, `ask_user`.

The file's description lists the kind `mcp` as well, but no tool name maps to it: an MCP tool, a browser tool or any name not in the table is `other` {src:.harness/engine/adapters/tool_kinds.json#L3} {src:.harness/engine/adapters/common.py#L111}. Seven names, `multi_replace_string_in_file`, `insert_edit_into_file`, `apply_patch`, `edit_notebook_file`, `bash`, `PowerShell` and `powershell`, are marked `unrecorded_tools`: the edit tools are named in VS Code but were never recorded under these names (`apply_patch` reaches the hook as `Edit` with plain text), and the three terminal names are guesses, listed so that the gate reads their `command` whatever the name {src:.harness/engine/adapters/tool_kinds.json#L51-L60}. The other keys of the `vscode` surface are `path_keys`, `command_key`, `skill_key`, `subagent_prompt_key`, `subagent_target_keys` and the `terminal_search_commands` list {src:.harness/engine/adapters/tool_kinds.json#L40-L68}.

What each kind triggers downstream, in the code {src:.harness/engine/modules/gate/handler.py#L758-L812}: **edit and create** go to the gate's write checks (and a write tool with no readable path is refused); **terminal** goes to the terminal checks; **subagent** and **ask** are judged by the task module on `PreToolUse` (subagent calls always; the question tool only while a task's autorun is on); **other** goes to the tool pack check for MCP tools; every kind except the terminal goes through the board-port check, and every kind goes through the secrets check. **read, search, web, skill and meta** reach no gate rule beyond those two, so they pass. In emergency mode only the names in `SAFE_TOOLS` pass, and a name that is not in the table, and not in that list, is refused: the opposite of normal mode, where an unknown tool is let through {src:.harness/engine/hook.py#L261-L266}. Five names of `SAFE_TOOLS` (`read_bash`, `read_powershell`, `list_bash`, `list_powershell`, `report_intent`) are not in `tool_kinds.json`, so in normal mode they are kind `other`.

## Gate internals: unseen tools, and what is recorded about them

`core/unseen.py` keeps a short list of tool calls the harness could not place, for `harness doctor` only {src:.harness/engine/core/unseen.py#L1-L4}. A call is unseen when its kind is `other`; or its kind is `edit` or `create` and no path could be read; or its kind is `terminal` and it has no command {src:.harness/engine/core/unseen.py#L36-L41}.

For an unseen call the file `unseen-tools.jsonl` in the logs folder gets one line with the surface, the tool name, the kind and the shape of the tool input (the sorted key names of an object, or the type name), plus `first_seen`; never a value, a path or a prompt {src:.harness/engine/core/unseen.py#L44-L56}. A record is written only if no line with the same four fields exists and the file holds fewer than 200 lines (`MAX_LINES`); `note_call` catches every exception, so it never gets in the way of a call {src:.harness/engine/core/unseen.py#L17-L19}. The gate calls it on `PreToolUse` after the super agent, question turn, board-port and tool pack checks, so a call that one of those already answered is not noted {src:.harness/engine/modules/gate/handler.py#L773-L786}. `doctor` reads the file and warns once per surface with the count and the last few tools; the list never changes a decision {src:.harness/engine/doctor.py#L327-L335}.

What the gate does with the three unseen shapes differs: an edit or create tool with no readable path is refused (`write-no-path`), because the gate cannot tell what it would change; an unknown tool name passes the gate unless the tool pack check, the board-port check or the secrets check refuses it; a terminal call with no command has no text for any rule to match and passes {src:.harness/engine/modules/gate/handler.py#L834-L836} {src:.harness/engine/modules/gate/terminal.py#L187-L205}.

## Gate internals: session state and the bookkeeping core does for every event

The session state file is `.harness/runtime/state/<surface>/<session>.json`, written by `state.session` through a temporary file and an atomic replace. Its schema requires `surface`, `session_id`, `subagents` (`active`, `pending_prompts`) and `modules` {src:.harness/engine/core/state.py#L53-L97} {src:.harness/engine/core/state.py#L129-L146}. The lock is an operating system lock on a file in the system temp folder named by a hash of the state path; a caller waits up to `LOCK_TIMEOUT_SECONDS` = 20 seconds and then raises `TimeoutError`, which `main` turns into the "harness was busy, run the same call again" answer {src:.harness/engine/core/state.py#L29-L34} {src:.harness/engine/core/state.py#L205-L226} {src:.harness/engine/hook.py#L308-L309}. `state.session` writes the state back only when the block ends without an exception {src:.harness/engine/core/state.py#L229-L237}.

Core, not a module, does this bookkeeping before the modules run (`track_before`) {src:.harness/engine/core/state.py#L262-L300}:

- It drops subagent entries older than 1800 seconds and pending prompts older than 300 seconds.
- `SessionStart` empties both lists and resets the breaker's counts. `SubagentStart` adds an `active` entry marked `awaiting_child`. `SubagentStop` removes the entry whose agent type matches. `Stop` empties `active`.
- `UserPromptSubmit` in a session that has a parent sets `from_subagent` and returns (a subagent session never receives a user prompt). In another session, a prompt that matches the stored reason of a `Stop` block within 120 seconds is marked `continuation` (the engine feeding the reason back); any other prompt is a real user prompt and resets the breaker.

After the decision, `track_after` remembers two things: the reason of a `Stop` block (as `continuation`, with a time), and for `UserPromptSubmit` the digest and the injected text of the prompt (`prompt_context`); for an allowed subagent call it keeps the call message in `pending_prompts` (at most 8) so a new session can be matched to its parent {src:.harness/engine/core/state.py#L357-L371}.

## Gate internals: how run_modules calls each module and what a raise does

`hook.run_modules` goes through the module names in order. Before each module it deep-copies the session state; it imports `modules.<name>` and calls `handle(event, ctx)`. A returned `Decision` goes into the list of sources together with the module's name, and the `facts` it carries are merged into one dictionary, a later module overwriting an earlier one with the same key {src:.harness/engine/hook.py#L58-L87}.

When a module raises an `Exception`, `run_modules` writes the error to `hook-errors.jsonl` (`log_error`), restores the state from the copy taken just before that module (the module's own changes are lost, the changes of earlier modules stay), and treats the module as having no opinion. What the module had already written outside the session state, such as an approval file or a task file, is not rolled back: the rollback covers the session state only {src:.harness/engine/hook.py#L66-L77}. Then the rules differ by whether the module is a guard, which means the registry marks it `H` {src:.harness/engine/hook.py#L77-L83}:

- **A module that is not a guard** (`observe`, `evalcheck`): no opinion, the call goes on.
- **A guard module on `PreToolUse` that is not in `GUARDS_FOR`** (the gate): `GuardFailed` is raised. It leaves `process` before the state is written back, so the state changes of the whole call, including those of modules that ran earlier, are not saved, and `main` answers with the fail-closed output {src:.harness/engine/hook.py#L51-L55} {src:.harness/engine/hook.py#L361-L371}.
- **The task module on `PreToolUse`:** `GUARDS_FOR` holds a test for it, true for a subagent call. For a subagent call it returns a deny with the text `hook.module_failed` ("no subagent can be started now"); for any other call it has no opinion. The task module's other work goes on {src:.harness/engine/hook.py#L55} {src:.harness/engine/core/messages.en.json#L3896}.
- **A guard module on any other event:** nothing is refused. The failure is kept as the fact `guard_failed`; for `UserPromptSubmit` and `SessionStart` `process` adds a message to the context of the answer (the task module's own text for it, the general engine text for the gate), so the agent is told at the start. On `PostToolUse`, `PostToolUseFailure`, `SubagentStart`, `SubagentStop` and `Stop` nobody is told: the fact is dropped and the error is only in `hook-errors.jsonl` {src:.harness/engine/hook.py#L119-L121}.

The gate also wraps itself: when its whole handler raises, `gate.handle` asks `failclosed.decision` first. For a `PreToolUse` terminal line that names a program a tool pack governs, or a tool of kind `other` that a tool pack names, it returns a deny with the call's own words and the error; for any other call it raises the error again, which leads to `GuardFailed` {src:.harness/engine/modules/gate/handler.py#L722-L733} {src:.harness/engine/modules/gate/failclosed.py#L37-L49}. The comment in `handle` still says the hook counts a failing gate as having no opinion; the code in `hook.py` does not.

## Gate internals: how the decisions of several modules are merged

`events.merge` takes the list of decisions the modules returned and drops the empty ones (an empty decision has no permission, no block, no context and no prompt; a decision with only facts is empty) {src:.harness/engine/core/events.py#L62-L93}. Then:

- **Permission:** the highest of `allow` (1), `ask` (2) and `deny` (3) among the decisions that carry one.
- **Block:** true when any decision blocks (only `Stop` and `SubagentStop` output uses it).
- **Reason:** the reasons of the decisions whose permission equals the winning permission, and of those that block, joined with a newline. A reason of a losing permission is dropped.
- **Context:** the contexts of all non-empty decisions, including those of a module whose permission lost, joined with a blank line in registry order (`task` first, then `gate`).
- **Prompt:** the first non-empty one.
- **Facts:** `merge` ignores them; `run_modules` has collected them separately, and a later module overwrites a key an earlier one set.

No module in the code returns `allow`: a search of the modules finds no `permission="allow"`. A call passes because no module put any permission on it, not because one allowed it {src:.harness/engine/modules/gate/handler.py#L117-L167}. The merged `Decision` goes to the breaker, and the call record keeps which modules decided it (those whose permission equals the final one, or that block) {src:.harness/engine/core/callrecord.py#L32-L40}.

## Gate internals: the output the adapter prints

`adapters.common.render` turns the merged decision into the JSON Copilot reads, in plain top-level keys: the code notes that a nested `hookSpecificOutput` is ignored by the SDK engine. An empty decision prints `{}`. A permission is printed only for `PreToolUse` (`permissionDecision`, and `permissionDecisionReason` when there is a reason). A block is printed only for `Stop` and `SubagentStop` (`decision: "block"` and `reason`). `additionalContext` is printed for every event except `Stop`, `SubagentStop` and `UserPromptTransformed`. For `UserPromptTransformed` the only output is `modifiedTransformedPrompt` {src:.harness/engine/adapters/common.py#L133-L149}. So an `ask` is passed to Copilot as `permissionDecision: ask`, and Copilot decides how to show it.

## Gate internals: the call record and the log line

After the decision, `callrecord.build` makes one record, and the `observe` module writes it as one JSON line to `.harness/runtime/logs/vscode/<session>.jsonl` through `logs.log_call`; a record with no session id is not written, and `_append` swallows every error {src:.harness/engine/core/callrecord.py#L43-L98} {src:.harness/engine/core/logs.py#L52-L58} {src:.harness/engine/modules/observe/handler.py#L89-L93}. The record has surface, engine (`cli` for a Copilot SDK session, `legacy` for an older Local one, `unknown`), event, session, tool name and kind, the modules that ran, the outcome (`deny`, `ask`, `block`, `context` or `none`), and for a refusal, ask or block the deciding modules (`by`), the reason, and the paths and command of a `PreToolUse` deny or ask; the breaker's entry and the `kind`, `judge`, `verdict`, `task`, `kb` and `external` facts are added when present {src:.harness/engine/core/callrecord.py#L43-L98}. A call that went through keeps a ten-character hash of its terminal command, the paths a finished call touched (at most five), and the names of knowledge base files it read, never a command text. The observe policy cuts texts to `max_text_chars` and replaces the values of passwords and tokens first {src:.harness/engine/modules/observe/handler.py#L41-L61}. A failure of the log or of building the record is written to `hook-errors.jsonl` and never changes the answer {src:.harness/engine/hook.py#L135-L153}.

The board reads this log for one more purpose. Whether a task's session "made a hook call lately" is the modification time of the session's log file compared with `board.active_seconds` (default 300): no hook call, no change of the time, so a task nobody works on is not shown as working {src:.harness/engine/modules/task/tasklife.py#L777-L786}.

## Gate internals: restoring the injected text at userPromptTransformed

VS Code's own prompt handler (the reminder to rename the chat) takes the one `additionalContext` slot of `UserPromptSubmit`, so the text the harness injects there (rules, session id, language, task state) was lost on a part of the prompts: the code comment records about a third of them in a recording of 2026-10-22 {src:.harness/engine/core/state.py#L378-L383}. The SDK engine sends a second event, `userPromptTransformed`, with the whole text the model is about to receive, and the hook can answer with a replacement.

No module handles it. `process` answers it in core: at `UserPromptSubmit`, `track_after` stores the prompt's digest (first 16 hex characters of a SHA-256) and the injected text as `prompt_context`; at `UserPromptTransformed`, `restored_prompt` returns an empty decision unless the stored text is non-empty, the stored note is at most 120 seconds old, the digest matches this prompt, and the first line of the stored text is missing from the transformed prompt. When it is missing, the stored text is appended in a `<system_reminder>` block and returned as `modifiedTransformedPrompt`, with the fact `context_restored` {src:.harness/engine/hook.py#L122-L124} {src:.harness/engine/core/state.py#L374-L394} {src:.harness/engine/adapters/common.py#L147-L148}. The event can add text and cannot refuse anything. Because `doctor` counts it among the events core needs, the hook config must include it even though no module subscribes {src:.harness/engine/core/state.py#L48-L49}. If the answer fails, the failure is an engine failure like any other: a non-`PreToolUse` event gets `{}`.

## Gate internals: the breaker that ends a repeated refusal

`core/breaker.py` is called from `hook.process` after the merge, through `call_safely`, so any error in it is logged and the original refusal stands {src:.harness/engine/hook.py#L125} {src:.harness/engine/core/failopen.py#L11-L17}. A hook can answer only allow, ask or deny with a reason; it cannot stop an agent that keeps trying, so the reason text is the one lever, and the breaker changes it after repeated identical refusals {src:.harness/engine/core/breaker.py#L1-L6}.

What counts: only a `PreToolUse` decision whose permission is `deny` and whose reason is not empty. An `ask`, an allow, a `Stop` block and a `PostToolUse` result are not counted, and neither is a deny whose fact `kind` is `autorun-ask` (autorun tells the agent to write the question down and go on) {src:.harness/engine/core/breaker.py#L46-L51}. "Identical" means an identical reason text: the key is the first 12 hex characters of the SHA-256 of the reason, kept in the session state under `denials`, so the text decides, not the command: two refusals with the same text count together even when the commands differ, and the same command refused with two different texts counts apart {src:.harness/engine/core/breaker.py#L52-L56}.

The limit is `circuit_breaker.repeat_limit` in `gate.json` (default 3); 0 turns the breaker off, and a value that is not a non-negative whole number, or a policy that cannot be read, falls back to 3 {src:.harness/engine/core/breaker.py#L19-L31} {src:.harness/policies/gate.json#L187-L189}. From the limit on, `decision.reason` is replaced by the text `breaker.stop`: "Refused: <original reason>", then that the same refusal has come up N times, and an instruction to stop retrying, not to look for a way around it, to tell the user and to wait for the user to decide; a leading "Refused:" of the original is removed so the word is not doubled {src:.harness/engine/core/breaker.py#L38-L43} {src:.harness/engine/core/messages.en.json#L524}. The decision stays a deny: the breaker can only change the text of a refusal, never turn it into an allow.

The window: counts reset at `SessionStart` and at a real user prompt (not at a subagent's prompt, and not at a continuation of a `Stop` block). The count is per session, so a subagent, which runs in a session of its own, has its own count {src:.harness/engine/core/state.py#L268-L300}. The breaker does not end the session or block later calls, and no code checks whether the agent obeys the text.

## Gate internals: the order of checks on a call

The gate's `_handle` runs these steps in order for every event it subscribes to {src:.harness/engine/modules/gate/handler.py#L758-L812}:

1. **The read-only marks.** `superagent.mark` and `askturn.mark` update the marks on a real user prompt; then, on `PreToolUse`, `superagent.check` and `askturn.check` refuse any call that is not read, search or meta (and not one of seven read-only harness commands) in a marked session or turn; a mark that cannot be read refuses {src:.harness/engine/modules/gate/superagent.py#L18-L89} {src:.harness/engine/modules/gate/askturn.py#L21-L53}.
2. **Events other than `PreToolUse`:** `SessionStart` and a finished terminal call do reachability work and give context; `UserPromptSubmit` gives context; nothing is refused here.
3. **`PreToolUse` of a tool that is not the terminal:** if its whole input text names the board server's port at `127.0.0.1`, `localhost`, `[::1]` or `0.0.0.0`, refuse (the question tools `ask_user` and `askuserquestion` are skipped, because their input only shows text). If the kind is `other`, the tool pack MCP check may answer.
4. **Every `PreToolUse`:** the unseen note, then `check_secrets`: a path that resolves to `.harness/.env`, a terminal line naming it, a dump of the whole environment (`env`, `printenv`, `set`, `export -p`, `Get-ChildItem env:` and similar, run with nothing after them), or a secret variable name that is not owned by the outside call the line makes, is refused; the line is also read with a PowerShell escape removed {src:.harness/engine/modules/gate/handler.py#L620-L650}.
5. **Only `edit`, `create` and `terminal` calls go further.** All others return no decision.
6. **The policy is loaded:** `gate.json` with the company and the person's layers, validated without the core-path floor, compiled once (`Compiled`) together with the target repositories. If that raises, the built-in copy is used and `fallback.refine` is applied afterwards; if the target policy could not be read, `targetfault.check` runs on any call that did not already get a deny {src:.harness/engine/modules/gate/handler.py#L789-L812}.
7. **A terminal call:** `judge_external` and `check_wrapped` for tool pack and `harness as` calls, then `check_terminal` (below). **A write call:** no readable path is `write-no-path`; otherwise `check_write` {src:.harness/engine/modules/gate/handler.py#L815-L836}.

`check_write` goes over each path the call names, resolved against the repository root and the call's working folder (a path that starts with `~`, `$` or `%` is also tried expanded). For each path it refuses, in this order: a path inside any `.git` folder; the guarded folder outside the workspace (`~/.copilot-harness` or the folder of `HARNESS_INTEGRITY_DIR`), also in admin mode; a path a target repository lists in `refused_paths`; a path inside a target repository's working tree. For the repository-relative readings it then refuses a guardrail path (in admin mode only `admin_locked_paths`) and a path only the command line writes. Only after all paths pass does `check_task_write` apply the task folder rules {src:.harness/engine/modules/gate/handler.py#L38-L61}.

`check_terminal` runs these in order, the first deny winning: terminal write to a guardrail path; to a command-line-owned path; to a `.git` or target `refused_paths` path; to a target repository's working tree by its full path; a never-approved git command (only when target repositories are set up); a person-only harness command (`harnesscmd.check`); a script the line runs that writes to a guardrail path (`scriptcheck.refusal`); then the deny list and the ask list of `gate.json` over the line and over every shell string nested in it, the strictest answer standing; the board's port; the tool pack check; then a git write that needs approval, which is passed once if an approval for that exact command exists (valid for `git.approval_minutes`, default 10) and otherwise refused with a code; last, the `ask` answer, if the lists gave one {src:.harness/engine/modules/gate/handler.py#L117-L167}. A command that matches none of these passes.

Two other lists exist beside it. `admin_locked_paths` is what stays closed in an admin session {src:.harness/engine/core/guardrails.py#L36-L38}. ## Gate internals: how a terminal command line is read

The gate reads a command line as text, with these steps, and not as a shell would run it {src:.harness/engine/modules/gate/terminal.py#L1-L5}:

- **Normalisation.** `terminal.normalize` turns `\` into `/` and blanks the separator characters (`;`, `&`, `|`, `(`, a new line) that sit inside a quoted string, so `rg "rm -rf|x" src` does not look like two commands; a quote that never closes is left alone {src:.harness/engine/modules/gate/terminal.py#L23-L43}.
- **A `cd` before a write.** `after_cd` writes out the relative paths that follow a `cd` (also `pushd`, `chdir`, `set-location`) so a write by a short name is judged by its full relative path; a `cd` to a variable ends the rewriting. The write rules run on the line and on the rewritten line {src:.harness/engine/modules/gate/terminal.py#L67-L124}.
- **A PowerShell escape.** A line with a backtick is also read with the escape removed (`r` + backtick + `m` is `rm`), and a deny of either reading stands {src:.harness/engine/modules/gate/terminal.py#L176-L184}.
- **Rules.** The deny rules of `gate.json` run first, then the ask rules; the patterns use the placeholders `{cmd}` (a command start: the line start or after `;`, `&`, `|`, `(`, a new line, with an optional `sudo`) and `{guard}` (the guardrail paths). A web call to an address a known outside system judges is not asked about a second time, except when it writes a file (`curl -o`, `wget` that does not print to the output, `-OutFile`) {src:.harness/engine/modules/gate/terminal.py#L187-L205} {src:.harness/engine/modules/gate/policy.py#L14-L20}.
- **Shell strings inside the line.** `external.nested` returns the command strings a shell is given inside the line (`bash -c`, `pwsh -Command`, `cmd /c`, `eval`, `harness as ... --`, `harness wait --run`), and the ones inside those, down to three wrappers deep (`MAX_DEPTH` = 3); each is judged as a bare line, and the strictest answer stands {src:.harness/engine/modules/gate/external.py#L1342-L1356} {src:.harness/engine/modules/gate/handler.py#L141-L147}.

What the gate cannot see is what the text does not show: a path built at run time, a program that chooses where it writes, a file written earlier and run later. A script is read as it is on disk at the moment of the call, so a script written by an earlier call or changed in the same line is not what is read {src:.harness/engine/modules/gate/scriptcheck.py#L355-L384}. This is why the gate is a guardrail for an agent that means well and makes mistakes, and not a sandbox against one that tries to break out; the accepted-list integrity check is the after-the-fact backstop for the guardrail files {src:docs/12-guardrails-and-gate.md#L7} {src:.harness/engine/integrity.py#L1-L12}.

Programs a tool pack governs are recognised in several spellings: a path in front of the name, `.exe`, `.cmd` or `.bat` after it, a PowerShell escape, a wrapper before it, or the name inside a here-document or a shell string. The rule added in 1.7.25 is that every word of the line that is the name of a governed program must be accounted for: it is the program of a command the gate judged, or an argument of a program on its read-only list; otherwise the line is held, because the gate cannot tell what the program that has the name among its words will do with it {src:.harness/engine/modules/gate/external.py#L282-L289} {src:.harness/engine/modules/gate/external.py#L1210-L1250}. Text the line does not show is refused as unreadable: `Invoke-Expression` and `iex`, text piped into a shell or an interpreter, `source <(...)`, `-EncodedCommand` and `Start-Process` of a governed program; a fourth wrapper that names a governed program is refused, and one that names git asks {src:.harness/engine/modules/gate/external.py#L1334-L1339} {src:.harness/engine/modules/gate/external.py#L1382-L1411} {src:.harness/engine/modules/gate/gitcmd.py#L312-L324}.

## Gate internals: wrappers and shellwords.py

`modules/gate/shellwords.py` is the one place that knows the names of shells and interpreters (`SHELL_NAMES`: `bash`, `sh`, `zsh`, `dash`, `fish`, `ksh`, `csh`, `tcsh`, `nu`, `xonsh`; `POWER_NAMES`: `pwsh`, `powershell`; `INTERPRETERS`: those, `python`, `python3`, `py`, `node`, `ruby`, `perl` and `cmd`), how to find what code a wrapper hands on (`interp`: a script file, a module, code after `-c`, `-e`, `-Command` or `/c`, or nothing because the code comes on stdin), how to build the texts to judge (`readings`), and how to remove a PowerShell backtick or `cmd` caret escape (`dialect`) {src:.harness/engine/modules/gate/shellwords.py#L1-L9} {src:.harness/engine/modules/gate/shellwords.py#L17-L19} {src:.harness/engine/modules/gate/shellwords.py#L49-L113}.

`readings(words, kind)` makes the texts for the words that follow the flag. One word is a whole command line and is read as it is. Several words give several texts: for a POSIX shell, the first word alone (the rest are `$0`, `$1`), the first word followed by the others each quoted again (`shellwords.quote`), and all words joined with spaces; for PowerShell and `cmd`, only the last two, because they join the words with spaces and read the result as code. Each text is added once more with its PowerShell or `cmd` escape removed, empty texts and duplicates are dropped {src:.harness/engine/modules/gate/shellwords.py#L140-L156}. The reason for more than one reading is that POSIX shells and PowerShell or `cmd` join the words differently, and the gate cannot know which will run: every reading is judged and the strictest answer stands, so a wrapper is never freer than the bare line {src:.harness/engine/modules/gate/gitcmd.py#L178-L191}.

The rule behind `readings` is that a word that was split and unquoted once is never joined with spaces and read a second time. The case it fixes: a word such as `'SELECT 1; DROP TABLE t'` given to a program was cut at the `;` when the words were joined and read again, so the statement counted as two commands {src:.harness/engine/modules/gate/shellwords.py#L1-L9}.

`harness as <alias> -- <command>` is not handled by `shellwords.py`. `external.as_run` reads it, in the shapes the command line's own parser (`argparse`) accepts: harness options before `as` (every word starting with `-` is skipped), a `--` before or after the alias or none, `python3 .harness/engine/cli.py`, or `python3 -m cli`, and `--json` anywhere removed. It returns one reading: the words after the alias, each quoted again with `shellwords.quote` and joined, with any `NAME=value` settings that stood in front put before the command, so a `;` inside one word stays inside it {src:.harness/engine/modules/gate/external.py#L1441-L1469}.

Limits of the reading: wrappers are followed three deep; a stdin-fed shell (`bash -s`, `-`, `<<<`), `iex` and PowerShell's `-EncodedCommand` (any start of the word) cannot be read, and the gate does not let them through: `iex` and `Invoke-Expression` are refused, text piped into a shell or an interpreter is refused, and an encoded command is held as an unreadable call {src:.harness/engine/modules/gate/shellwords.py#L49-L118} {src:.harness/engine/modules/gate/external.py#L1382-L1411}.

## Gate internals: person-only harness commands read the way a shell reads them

The deny rules of `gate.json` for the person-only commands (for example `task close`, `task approve-plan`, `approve-action`, `admin on`) are patterns over text, and a shell does not read text: it removes quotes and fills in variables. `harnesscmd.py` reads each harness call the way a shell does, writes it as `harness <words>` and gives that to the same deny rules {src:.harness/engine/modules/gate/harnesscmd.py#L1-L8} {src:.harness/policies/gate.json#L131-L144}. So `harness task 'cl''ose'`, `harness task "close"` and `C=close; harness task $C` all become `harness task close`, while a raw-text pattern would miss `cl''ose` because the quotes stay in the text {src:.harness/engine/modules/gate/harnesscmd.py#L79-L106}.

The steps in `calls(command)`: take the line, the line with a PowerShell backtick removed, every shell string nested in either, and the bodies of here-documents; for each text, split into command segments the way a shell does; a segment that only sets variables (`NAME=value`, `export`, `declare`, `typeset`, `local`, `readonly`, `$env:NAME=...`) records them; later segments have those variables put in (`external._expand`; a variable that stands for a whole word may split into several words); redirections are removed; if the segment starts the harness command line (`harness`, `harness.cmd`, `.harness/bin/harness`, `cli.py`, `python3 cli.py`, `python3 -m cli`) it is written as `harness <words>` with `--json` removed {src:.harness/engine/modules/gate/harnesscmd.py#L25-L49} {src:.harness/engine/modules/gate/harnesscmd.py#L79-L106} {src:.harness/engine/modules/gate/external.py#L504-L533}. `check` first skips a line that names none of `harness`, `cli`, `python`, `node`, `perl`, `ruby`, `xargs`; then refuses an unreadable call; then matches each rewritten call against the deny list {src:.harness/engine/modules/gate/harnesscmd.py#L109-L120}.

Calls that cannot be read are refused with "write the harness command out in full": `xargs` together with `harness` or `cli.py`; a `find -exec` or `-execdir` of it; a one-line interpreter whose code names the harness and starts a process (`subprocess`, `os.system`, `popen`, `exec`, `spawn`, `check_output`, `runpy`, `import cli`, `child_process`, a backtick); and a harness word that still holds `$` or a backtick after the variables were put in {src:.harness/engine/modules/gate/harnesscmd.py#L20-L21} {src:.harness/engine/modules/gate/harnesscmd.py#L52-L64} {src:.harness/engine/modules/gate/harnesscmd.py#L97-L104}. For `harness as <alias> -- <command>` only the words up to the alias count as harness words; the command after it is read as a line of its own {src:.harness/engine/modules/gate/harnesscmd.py#L67-L76}.

What is not covered: a script file the agent runs that starts the harness, aliases (they are not followed), and a leading harness option. `calls` keeps every word after `harness`, so `harness --short task close` becomes the text `harness --short task close`, which the deny pattern (it expects `task` right after `harness`) does not match; the harness command line itself accepts `--short` as a global flag, and no test in the suite covers this shape. The same holds for every person-only pattern in `gate.json`: each expects the command right after `harness`, so a leading `--short` gets the line past the text rule (checked on `calls` at 1.8.3); the commands that also check for a person at a terminal (the approvals, `confirm-req`, `admin on`) still refuse there {src:.harness/policies/gate.json#L136}. `task close` has no second layer: unlike the approval commands, it does not check for a person at a terminal, so it rests on this reading {src:.harness/engine/modules/gate/harnesscmd.py#L105} {src:.harness/engine/cli.py#L131-L132} {src:.harness/engine/modules/task/commands.py#L123-L133}.

## Gate internals: scriptcheck.py, a script judged by what it writes

`scriptcheck.refusal(command, root, cwd, folder, policy, admin)` reads the script a line runs and refuses when the target of a write is a guardrail path. It never raises: any internal error returns None, so the check fails open and the other checks of the gate stand {src:.harness/engine/modules/gate/scriptcheck.py#L398-L446}.

What it reads: script files that interpreters, `source` and `. file` run (also `./x.sh`, `pwsh -File`, `Import-Module`), the inline code of `python3 -c`, `node -e`, `perl -e` and `ruby -e`, here-document bodies handed to an interpreter, and the shell strings nested in `bash -c` and the like, to the same three levels; the line is also read with a PowerShell escape removed. A one-liner that opens a file by name counts that file as a script only when the code runs what it loads (`exec(open(...).read())`, `runpy`, `eval`, `require`) {src:.harness/engine/modules/gate/scriptcheck.py#L398-L446} {src:.harness/engine/modules/gate/external.py#L1245-L1292}.

How writes are found (`writes_of`, `_shell_writes`): `open()` and its relatives in a write mode (an unreadable mode counts as a write), path methods (`write_text`, `unlink`, `mkdir`, `rename`, `save`, `to_csv` and others), `os`, `shutil`, `fs`, `File` and `FileUtils` functions, bare Node and PHP functions, process calls whose command line is read as a shell line, and in shell text redirections, `rm`, `mv`, `cp`, `tee`, `sed -i`, `curl -o`, `wget -O` and similar. The "target" argument is chosen by call: the first argument of `write_text`-like calls, the last of `copy`-like calls, the destination of `cp`-like shell commands {src:.harness/engine/modules/gate/scriptcheck.py#L173-L197} {src:.harness/engine/modules/gate/scriptcheck.py#L223-L326}.

How the target is judged: the target text is matched against a pattern made from the guardrail paths (each without `/**`) and always-named names (`.harness`, `.github/hooks`, `.copilot-harness`, `HARNESS_INTEGRITY_DIR`, and the file names `AGENTS.md` and the two start files), also after the script's own simple assignments and `for` heads are put in (`BASE = ".harness"`, `P += "/engine"`) and after its string pieces are joined with nothing or a slash (`".har" + "ness"`, `os.path.join(".harness", "engine")`) {src:.harness/engine/modules/gate/scriptcheck.py#L28-L49} {src:.harness/engine/modules/gate/scriptcheck.py#L60-L117}. A script that changes directory into a guardrail folder (`cd .harness/engine`, `os.chdir`) and writes by a short name is refused: after such a `cd` in the line every write counts, and inside a script a `chdir` to a guardrail path makes the first write count {src:.harness/engine/modules/gate/scriptcheck.py#L329-L349} {src:.harness/engine/modules/gate/scriptcheck.py#L438-L446}. A path built in pieces is not always missed: a test refuses `(Path('.harness') / 'engine' / 'x.py').write_text('')` and a variable set to `Path('.harness')` that is used on a later line {src:.harness/tests/test_c13_fr2.py#L466-L468}; the header of `scriptcheck.py` says that a path made at run time from pieces in several statements still passes {src:.harness/engine/modules/gate/scriptcheck.py#L8-L11}.

What passes: a script that only reads a guardrail file or names one in a comment or a string; a script that imports another that writes; `python3 -m module` (a module is not read); a path passed as `sys.argv`; a file that is missing, a binary (a zero byte in its first 8000), or over 200 KB (`MAX_BYTES`); the harness's own `.harness/engine/` and `.harness/tests/` files; any internal error. In an admin session only what stays closed there counts (`.harness/runtime/**`, the integrity folder, `.copilot-harness`) {src:.harness/engine/modules/gate/scriptcheck.py#L27-L49} {src:.harness/engine/modules/gate/scriptcheck.py#L355-L384}.

## Gate internals: why the gate does not stop a read

The gate decides further only for the tool kinds edit, create and terminal; a call of any other kind is returned with no decision after the board-port, tool pack and secrets checks {src:.harness/engine/modules/gate/handler.py#L787-L788} {src:.harness/engine/modules/gate/handler.py#L1-L14}. The shipped policy states the rule in its own words: "The gate only guards writes. It never blocks a read." {src:.harness/policies/gate.json#L3}

The harness gives two reasons. The first is from experience: reads used to be limited to the sandbox too, and the agent could not read the skills, took detours everywhere and used up its budget with nothing to show; this is stated in the skill that answers newcomers' questions {src:.github/skills/harness-rookie-wondering/references/05-tools.md#L64-L64}. The second is how the gate sorts work, by what a mistake costs. The design document's table puts read-only work (Q&A, looking things up in the knowledge base) and changes to the task folder in the row "Not stopped", and it puts changes to a target repository, git and production behind approvals {src:docs/05-design.md#L69-L74}. A read changes nothing, so a stop on a read would get in the way of normal work and prevent nothing. The shipped policy says the rule in one line: the gate only guards writes and never blocks a read {src:.harness/policies/gate.json#L3-L3}.

The reads the gate does refuse {src:.harness/engine/modules/gate/handler.py#L633-L650} {src:.harness/engine/modules/gate/handler.py#L773-L777}: a read of `.harness/.env` (the secrets file), printing a variable that carries a sign-in or dumping the whole environment, and a tool call whose input names the board's port. The super agent chat (a session whose first prompt starts with `/harness-super`) and a question turn (a prompt starting with `/harness-ask`) are kept to reading and to seven read-only harness commands, the reverse case; the release notes list both under 1.8.3 while the code comments date them 1.8.1 and 1.8.2 {src:.harness/engine/modules/gate/superagent.py#L18-L31} {src:.harness/engine/modules/gate/askturn.py#L1-L5} {src:docs/07-release-notes.md#L34-L36}. In emergency mode, reads stay open on purpose: the agent can still look and tell the person what is wrong {src:.harness/engine/hook.py#L11-L15}. The pattern in everything the gate guards is that it is a change that outlives the call (a file, a git history, an outside system); a read changes none of them. That is an inference, not a stated reason.

## Gate internals: fail open for local work, fail closed for governed calls

Since 1.7.38 the hook splits failures into two kinds. Local work (reads, tests, writes inside the task folder) and anything that is only shown or written down (the log, the call record, reminders, what the board shows) is not stopped by a failure; a call that may run a command or change a file, and a call to a program or MCP tool a tool pack governs, does not pass when the guardrail cannot decide {src:.harness/engine/hook.py#L11-L15} {src:.harness/engine/modules/gate/failclosed.py#L1-L8}.

The fail-open side, in the code {src:.harness/engine/hook.py#L58-L87}: a module that raises and is not marked `H` has no opinion and its session state changes are rolled back; `observe` and `evalcheck` are of this kind. The record of a call and the log never change the answer; `call_safely` runs the breaker so its failure keeps the original refusal {src:.harness/engine/hook.py#L125} {src:.harness/engine/hook.py#L151-L153}. On events other than `PreToolUse`, a failing guard module refuses nothing: on `UserPromptSubmit` and `SessionStart` the agent is told in the context; and when the whole hook fails on those two events the emergency answer is `additionalContext`, while on every other event it prints `{}` {src:.harness/engine/hook.py#L269-L283}.

The fail-closed side {src:.harness/engine/hook.py#L297-L309}: when `process` raises (a payload that cannot be decoded, a registry or a session state that cannot be read, a lock timeout, the gate raising on a `PreToolUse` call, a changed guardrail file), `fail_closed` tries `failclosed.on_hook_error` first, which answers without the engine: for a `PreToolUse` terminal line that names a program a tool pack or the tools policy governs, or a non-command tool a pack names, it returns a deny with the program's name and the fault; the program names are read as plain text from the pack files and the tools policy (`core/govern.py`, every `cli` and `programs` list, valid JSON or not). Otherwise `emergency` answers. This layer exists because a call to a governed program reaches a system outside, and a gate that could not judge it must not pass it; the old behaviour, "no opinion", passed it {src:.harness/engine/modules/gate/failclosed.py#L1-L8} {src:.harness/engine/modules/gate/failclosed.py#L52-L71} {src:.harness/engine/core/govern.py#L1-L4}.

When `gate.json` or a layer cannot be read (not the same as the gate raising), the gate does not raise: it runs on the built-in copy, then `fallback.refine` adds a strict part. Reads and local work inside the open task folder stay free; the section "Gate internals: when gate.json or target.json cannot be read" says what is refused.

## Gate internals: the emergency answer of hook.py, with the standard library only

`hook.py` imports the engine inside `try/except BaseException`; on failure it stores the exception as `ENGINE_FAULT`, and the rest of the file, whose top-level imports are the standard library (`json`, `os`, `sys`, `time`, `traceback`, `pathlib`, `typing`), still works. `main` raises `ENGINE_FAULT` inside its own try, so the answer comes from `fail_closed`, which tries `failclosed.on_hook_error` and falls back to `emergency`. The header says everything the emergency answer needs must stay in this file and must not move into a module the engine imports {src:.harness/engine/hook.py#L11-L16} {src:.harness/engine/hook.py#L31-L48} {src:.harness/engine/hook.py#L352-L353}.

The shapes {src:.harness/engine/hook.py#L269-L283}: `PreToolUse` gives `{}` (the call may go) or `{"permissionDecision": "deny", "permissionDecisionReason": <text>}`; `UserPromptSubmit` and `SessionStart` give `{"additionalContext": <text>}`; every other event gives `{}`. The function never raises: anything unreadable gives `{}`, which is why a payload that cannot be read as a tool call is not refused.

Which tools stay allowed {src:.harness/engine/hook.py#L169-L174} {src:.harness/engine/hook.py#L261-L266}: `may_pass` returns false for an empty tool name, for the terminal tool names (`run_in_terminal`, `Bash`, `bash`, `PowerShell`, `powershell`), and for any tool whose input has a string `command`; otherwise it is true only for a name in `SAFE_TOOLS`, the 22 names listed in the section "Gate internals: launch.py, the small file in front of hook.py". So reads, searches, `WebFetch`, `skill`, the meta tools, the question tools and subagent calls pass; an edit or create tool, the terminal, and any name not in the list are refused.

Which guard modules can cause it: the gate on `PreToolUse`, and, because the rule is by the registry's `H` mark and not by name, any guard module not named in `GUARDS_FOR`; the task module is limited to subagent calls {src:.harness/engine/hook.py#L51-L55} {src:.harness/engine/hook.py#L99}.

The refusal text is `hook.emergency` ("The harness engine cannot decide, so nothing that runs a command or changes a file is allowed until it is repaired: <file:line: error>"), or `hook.busy` for a `TimeoutError` (the lock), or `hook.integrity` and `hook.integrity.upgrade` for a guardrail file that is not as accepted. `_say` reads the text from `core/messages.<lang>.json` as a plain file and falls back to the English text in `hook.py` when the file cannot be read or the text lacks `{why}`. The language is `HARNESS_LANGUAGE` when it is `en` or `zh`, else `language` in `user.json` and then `user.override.json`, else `en` {src:.harness/engine/hook.py#L175-L180} {src:.harness/engine/hook.py#L208-L230}. `where(error)` names the file and line of the engine fault, cut to 300 characters. ## Gate internals: when gate.json or target.json cannot be read

**`gate.json` or a layer unreadable.** `_handle` catches the error, runs `Compiled` on `builtin.policy()` (the 14 guardrail paths, the terminal rules and the git setting, without the company and person layers) and then `fallback.refine` {src:.harness/engine/modules/gate/handler.py#L792-L803} {src:.harness/engine/modules/gate/builtin.py#L1-L12}. `refine` keeps a deny, adding a note naming the file and the fault (a deny about an outside system, a connection wrapper or a secret says only its own reason). In an admin session it adds nothing more, so the file can be mended. Otherwise it refuses, with a reason that names the file and what is wrong: an edit or create tool unless every path is inside the open task's folder (with no open task, no write passes); a git command that writes; and a shell command that writes a file outside that folder (`>`, `tee`, `rm`, `mv`, `cp`, `mkdir`, `touch`, `sed -i`, `dd of=`, and the PowerShell writers); a path it cannot read (a variable, a command inside the word) counts as outside. **`target.json` or a layer unreadable.** When the target policy cannot be read, the gate does not know where target repositories are, so `targetfault.check` takes every git repository other than the harness's own for a possible target, for a call that has not already been refused. An edit or create tool whose path is inside such a repository is refused; a git writing command is refused unless it certainly runs in this repository (the terminal is in this folder or in no repository and the line names no other place with `-C`, `--git-dir`, `--work-tree`, `cd`); and a shell command that writes inside such a repository (by the rules of `gate.json`, also after the line's paths are written out in full) is refused. ## Gate internals: the two cases the hook cannot handle itself, and what doctor checks

The platform decides two cases: the hook cannot start (Python missing or broken) and the hook times out. When it cannot start, the platform counts that as a refusal: every tool call fails and the screen says only "hook errored". On a timeout the platform lets the call through with no notice. Both were measured once, in a Copilot (SDK) session on 2026-10-10; the repository records no other measurement, so another session type, a slow machine or a later platform version may behave otherwise. Both happen outside the harness's process, so only `doctor` warns beforehand {src:docs/05-design.md#L167-L170} {src:.harness/engine/doctor.py#L38-L41} {src:.harness/engine/doctor.py#L74-L79}.

`check_interpreter` finds `python` (Windows) or `python3` with `shutil.which` and runs `-c "print(1)"` with a 15-second limit; a missing or broken one is an ERROR that says every tool call is refused when the hook cannot start. `check_hook_activity` (only with the observe module enabled and log rows present) reads the `ms` of recent `PreToolUse` rows, takes the timeout from the first `.github/hooks/*.json` (`timeoutSec`, else `timeout`, else 30) and warns when the slowest call reached half of it ("a call whose hook times out is let through, so the gate guards nothing") {src:.harness/engine/doctor.py#L37} {src:.harness/engine/doctor.py#L74-L104} {src:.harness/engine/doctor.py#L120-L157}.

`docs/05-design.md` (line 165) still says that when the hook fails itself, local work passes. The code of 1.8.3 does not: a failed engine or gate refuses a command or a write and lets reads and the safe list pass (see the section "Gate internals: fail open for local work, fail closed for governed calls") {src:docs/05-design.md#L165} {src:.harness/engine/hook.py#L297-L309}.

## Gate internals: the integrity check inside hook.py

Before it imports any of the engine, `main` runs `integrity_problem` for the three events that decide something (`PreToolUse`, `UserPromptSubmit`, `SessionStart`). It returns nothing when the session is in admin mode (read from the state file as plain JSON; a subagent session is never admin) and otherwise asks `integrity.status` {src:.harness/engine/hook.py#L312-L326} {src:.harness/engine/integrity.py#L220-L229}. A check that cannot run because `integrity.py` cannot load counts as a problem.

`integrity.walk` lists the watched files with size and modification time: every file under `.harness/engine`, `.harness/bin`, `.github/hooks` and `.harness/toolpacks` (not `__pycache__`, `.pytest_cache`, `.git`, and not `.pyc`, `.pyo`, `.lock`, `.tmp` files), `.harness/registry.json`, and the `.json` files directly in `.harness/policies` except `*.override.json` and `*.company.json` {src:.harness/engine/integrity.py#L27-L97}. `changes` compares with the list the person accepted: a file whose size and time match is trusted; one whose size or time differs is hashed (SHA-256) and is `changed` only if the hash differs; files not in the list are `new` and missing ones `gone`. If there is no accepted list yet, nothing is reported {src:.harness/engine/integrity.py#L135-L161}. The list is one file per copy of the harness in `~/.copilot-harness/integrity/` (or `HARNESS_INTEGRITY_DIR`), named by a hash of the repository path {src:.harness/engine/integrity.py#L36-L53}.

`status` says `upgrade` when the list was made for another version of the harness than `registry.json` now says, and `changed` for the same version. A problem on a `PreToolUse` call gives the `emergency` answer with the files named (at most five); on a prompt or a session start the answer is produced as usual and the words are appended to its `additionalContext`; the refusal is written to the session log with the kind `integrity` {src:.harness/engine/hook.py#L350-L360} {src:.harness/engine/integrity.py#L180-L193}. The list is made when the person accepts, in four ways: at the board's start when none exists or the version changed (`accept_on_start`), `harness doctor --accept`, `admin off`, and the Accept button on the board's Enter screen (the section "Gate internals: the integrity list: record, coverage and the four ways it is accepted" says how each works). A list for this version that the files do not match is not replaced at start {src:.harness/engine/integrity.py#L196-L208}.

## Gate internals: the integrity list: record, coverage and the four ways it is accepted

The accepted list is one JSON file named by the first 16 hex characters of the SHA-256 of the resolved repository path, in `~/.copilot-harness/integrity/` (or `HARNESS_INTEGRITY_DIR`). Fields: `version` (1), `root`, `harness` (the version in `registry.json` then), `at` (UTC time) and `files`, a map from relative path to `[size, modification time in ns, SHA-256]`. `accept` hashes every watched file and writes through a temporary file and `os.replace`; a file it cannot read is left out and shows as `new` later. `read` gives no list when the file is missing, unreadable, not an object or without `files`; the check then reports nothing and `doctor` warns {src:.harness/engine/integrity.py#L33-L53} {src:.harness/engine/integrity.py#L100-L128}.

The list differs from the gate's `guardrail_paths`. What it covers is fixed in `integrity.py` (`DIRS`, `FILES`, `POLICIES`) and read from no policy. So a path added in `extra_guardrail_paths` is guarded against writes but not hashed, and `.harness/.env`, the start files, `.vscode/settings.json`, `.vscode/mcp.json`, `LICENSE`, `NOTICE`, `.harness/runtime/**` and the override and company policy layers are guarded against writes and are not in the list {src:.harness/engine/integrity.py#L23-L28} {src:.harness/engine/integrity.py#L55-L82}.

Four ways make the list; the header names the first three, the fourth came in 1.7.39 {src:.harness/engine/integrity.py#L1-L10}.
- **The board's start** (`accept_on_start`): writes the list when none can be read or `registry.json` names another version; for the same version it writes nothing and returns `changed` or `kept`; `none` when it could not write. It never stops the board starting {src:.harness/engine/integrity.py#L200-L210} {src:.harness/engine/modules/task/boardserve.py#L2282-L2296}.
- **`harness doctor --accept`**: needs a person (`require_person(..., typed=False)`: stdin and stdout a TTY, or the one-time code of a command typed in the board's Terminal window), asks no typed code, prints the files it takes in, writes the list, and exits 1 with the reason if it cannot write. The gate refuses the text on an agent's command line {src:.harness/engine/doctor.py#L1017-L1032} {src:.harness/engine/core/approval.py#L28-L47} {src:.harness/policies/gate.json#L136}.
- **`admin off`** on a session that was in admin mode, run by anyone: it has no person check, and the gate's person-only pattern lists `admin on` but not `admin off`. A failed write is swallowed and `doctor` says the list is behind {src:.harness/engine/modules/gate/commands.py#L122-L136}.
- **The Accept button** on the Enter screen. When doctor finds changed files, the doctor line shows the button "Accept these files" instead of "Check again". The page asks `POST /api/integrity` without a `step` and gets `changed`, `was` and `now`, shows the files in the window "Accept N guardrail files as they are now?", and only on Accept sends `step: accept`, which calls `integrity.accept` and makes doctor run again. An unpaired browser gets 403, so the agent, which has no pairing cookie, cannot use it {src:.harness/engine/modules/task/boardserve.py#L2007-L2020} {src:.harness/engine/modules/task/ready.py#L395-L405} {src:.harness/engine/modules/task/ready.py#L633} {src:.harness/engine/core/messages.en.json#L2868-L2873}.

A person decides in the first, second and fourth way. In the third, whoever runs `admin off` decides, and the gate does not stop the agent of an admin session from ending its own mode, which makes the files as they are then the accepted ones.

## Gate internals: integrity.py, how every call is checked cheaply and where the check is blind

`integrity.py` uses the standard library only, because `hook.main` runs it before any engine module is imported. For each `PreToolUse`, `UserPromptSubmit` and `SessionStart` call it stats the watched files, 307 in the shipped 1.8.3 tree (267 under `engine`, 4 in `bin`, 1 hook file, 24 in `toolpacks`, `registry.json`, 10 policy files), and opens none of them when nothing differs. A file is hashed (64 KiB blocks) only when its size or modification time in nanoseconds differs; a message names five files at most (`SHOWN`) {src:.harness/engine/integrity.py#L55-L90} {src:.harness/engine/integrity.py#L131-L168}.

It runs first and fails closed. In `main`, `integrity_problem` comes before the engine fault is raised and before `process`; if `integrity.py` cannot load or raises, that counts as a problem. A problem on `PreToolUse` gets the `emergency` answer with `hook.integrity` (or `.upgrade`): no command or write, reads free, and the agent is told to report the files and not to repair or go round them; the person runs `harness doctor --accept` if the change was meant, or restores the files from the zip. `refusal_record` logs it with the kind `integrity`, so the task page, Live and the report show "guardrail files changed", and `doctor` gives an ERROR. The agent cannot accept: `doctor --accept` is person-only, the button needs the pairing cookie, and the list's folder is closed to its writes {src:.harness/engine/hook.py#L312-L360} {src:.harness/engine/doctor.py#L973-L998} {src:.harness/engine/core/messages.en.json#L3897-L3898}.

Where the check is blind, from the code. A file with the listed size and modification time is not hashed, so a rewrite that keeps both is not seen. A file that was touched but has the same hash is never reported, yet it is hashed again on every call until the next accept, because `changes` writes nothing back. `status` and `problem` swallow their own exceptions and say "no problem"; a watched file that cannot be stat'd is left out of the walk. Admin mode skips the check for that one session, so while an admin session has changed watched files the other sessions of the copy are refused until `admin off` or another accept. A process of the same user can rewrite the list too: the module header says it stops a slip and plain tampering, not a process that means to break out. It is kept because it costs a few stat calls, runs before the engine is trusted, and turns a silent change of the gate's own files into a refusal that names them {src:.harness/engine/integrity.py#L1-L10} {src:.harness/engine/integrity.py#L160-L183}.

## Gate internals: why the folder ~/.copilot-harness stays guarded in admin mode

The folder of the accepted list is a guardrail in both modes. It is held in code (`guardrails.home_folders()`: `~/.copilot-harness`, the whole folder, and the folder `HARNESS_INTEGRITY_DIR` names), not in `gate.json` or `admin_locked_paths`. The reason, from the comment: the list is what the person accepted, so an agent that could rewrite it could make any change count as accepted. Admin mode opens the guardrail files, not the person's record of accepting them; `admin off` writes the list itself, as a process of the CLI and not an edit through the gate {src:.harness/engine/core/guardrails.py#L46-L61} {src:docs/12-guardrails-and-gate.md#L119}.

In `check_write`, `compiled.home_match` comes right after the `.git` check and before the guardrail patterns, so it holds whichever paths `Compiled` carries; in admin the refusal says the file "cannot be changed in admin mode either". For terminal writes, `Compiled` builds the guarded-path pattern from the policy's paths (in admin only `admin_locked`), then `.copilot-harness/**`, then the home folders, so `~/.copilot-harness/...`, `$HOME/...` and the full path are refused in both modes. `scriptcheck.names_of` names `.copilot-harness`, `HARNESS_INTEGRITY_DIR` and the home folders in admin too, but `.harness`, `.github/hooks`, `AGENTS.md` and the start files only outside it. Reads of the folder are not refused {src:.harness/engine/modules/gate/handler.py#L36-L61} {src:.harness/engine/modules/gate/policy.py#L111-L120} {src:.harness/engine/modules/gate/scriptcheck.py#L28-L46}.

The same folder holds the board Terminal window's one-time proof of a person, in `person/`. For each line typed there that runs a harness command, `boardperson.issue` puts a random token (`secrets.token_urlsafe(32)`) in the command's environment (`HARNESS_BOARD_PERSON`) and keeps only its SHA-256 as a file name, with `until` 600 seconds ahead. `boardperson.use` removes the variable, finds and deletes the file and accepts if not expired, once per process; `drop` removes it when the command ends. A writable folder would let an agent write a fingerprint for a token of its own and pass the person-only checks. A process of the same user that builds the path at run time can still reach the folder: this raises the bar and is not a sandbox {src:.harness/engine/core/boardperson.py#L1-L90} {src:.harness/engine/modules/task/boardterm.py#L139-L145}.

## Gate internals: admin mode, who switches it on, the code, how it ends

Admin mode is `state["admin"] = {"on": true, "at": <time>}` in the session's state file; `admin_on(state)` is true only for that flag in a session with no `parent_session_id`, so a subagent session is never admin {src:.harness/engine/core/state.py#L246-L248}. Only `harness admin on --session-id <id>` sets it, in this order: `require_person` (stdin and stdout a TTY, or the board's one-time code); the session must have a state file; a subagent session is refused; a session that holds an open task is refused; a session already in admin mode gets a note and no code is asked; then four lines say what opens and what stays closed, and the person types the code (capitals compared, anything else cancels). Nothing reads `at` as an end time (`admin status` shows it as `since`), so the mode has no expiry and lasts until `admin off` {src:.harness/engine/modules/gate/commands.py#L84-L119} {src:.harness/engine/core/approval.py#L16-L56}.

The code is not a secret: it is the first 6 hex characters, in capitals, of the SHA-256 of `admin`, the surface and the session id joined by line breaks; the prompt prints it, and the session id is in the rules text the agent gets with every prompt. What stops an agent is the TTY test and the gate's refusal of the text `admin on` on its command line (the same pattern as the other person-only commands, with the same `harness --short` gap). The TTY test checks the process's stdin and stdout; it does not tell an agent's terminal from a person's {src:.harness/engine/modules/gate/commands.py#L115} {src:.harness/engine/core/approval.py#L24-L34} {src:.harness/engine/core/messages.en.json#L109} {src:.harness/policies/gate.json#L136}.

The board's Terminal window cannot switch admin mode on, and the board has no admin button (no request of the board server mentions admin). ## Gate internals: admin mode, what opens, what stays in force, and why it is a session switch

In the gate, admin mode changes one thing: which guardrail paths count. `Compiled(..., admin=True)` takes `admin_locked(policy)` (`.harness/runtime/**` and the policy's `admin_locked_paths`) in place of `guardrail_paths(policy)`, for edit tools, terminal writes and `scriptcheck`. `ctx.admin` is read only for that, for the wording of those refusals, in `fallback.refine` (an admin session on the built-in copy is told nothing more, so the policy file can be mended) and in `targetfault`. Every other rule stays in force in admin mode: the terminal `deny` and `ask` rules (the dangerous commands), the git write approvals and the commands git never gets approved for, the person-only harness commands, secret reads, outside-system and wrapper rules, command-line-owned files, `.git` and target repositories {src:.harness/engine/modules/gate/handler.py#L1-L8} {src:.harness/engine/modules/gate/handler.py#L113-L140} {src:.harness/engine/modules/gate/policy.py#L111-L120} {src:.harness/engine/modules/gate/fallback.py#L161-L181}.

Elsewhere in the engine: the prompt text becomes `admin_rules` plus the language text instead of the session rules (it lists what stays closed, forbids subagents and tasks, says only the user runs the approval commands, and points to the skill `harness-admin`); a subagent call is denied (`rules.subagent.admin`) before the `mapper` check, so even `mapper` is denied; `attach` in `task.py` and `check_session` in `tasklife.py` refuse an admin session; the integrity check is skipped; and `callrecord.build` puts `admin: true` on every call record of the session, so every log line carries it {src:.harness/engine/modules/task/handler.py#L69-L74} {src:.harness/engine/modules/task/handler.py#L164-L165} {src:.harness/engine/modules/task/handler.py#L283-L290} {src:.harness/engine/modules/task/task.py#L157-L158} {src:.harness/engine/modules/task/tasklife.py#L133-L134} {src:.harness/engine/core/callrecord.py#L77-L79}.

Why a switch on the session and not a custom agent called admin: the hook payload gives the gate no name of the main agent. The only agent name the engine takes from a payload for a decision is the target of a subagent tool call (`subagent_target`); `admin_on` reads only the session state. A subagent named `admin` gets nothing: it is denied in an admin session, and outside a task only the reviewer, the worker and a `mapper` the person asked for pass the task module. Until 1.5.32 an admin agent file held the guidance; it gave no right the switch did not, the text moved to the skill `harness-admin`, and `test_admin.py` asserts that `.github/agents/admin.agent.md` does not exist and the skill does {src:.harness/engine/adapters/common.py#L124-L128} {src:.harness/engine/modules/task/handler.py#L283-L296} {src:.harness/tests/test_admin.py#L228-L233} {src:docs/05-design.md#L195-L198}.

The switch is bounded: one session, revocable, no task, no subagent, a typed code, every call logged with `admin: true`. The accepted cost: while it is on, the whole default-agent session is trusted with the guardrail files, and only `admin off` ends it.

## Gate internals: why one entry file serves every event

Every event runs `launch.py`, which runs `hook.py`, and modules subscribe through `registry.json`; the alternative would be one script per event. What the single path gives {src:.harness/engine/hook.py#L1-L16}:

- **One decision algorithm.** `merge` is where deny wins over ask over allow, for every event; a new module needs a registry entry and a `handle(event, ctx)` function and takes part in the merge without further code.
- **A check that the wiring is right.** `doctor` compares the registry's events with those in `.github/hooks/*.json` and checks that each hook command is `launch.py` {src:.harness/engine/doctor.py#L217-L252}.
- **The failure answers are written once.** The fail-closed answer, the integrity check, the breaker and the `launch.py` wrapper are shared by all events; nine separate scripts would each need their own.

The costs, as the code shows them: every event starts a fresh Python process (the header says one process per hook event); the registry and the hook config must be kept in step, which `doctor` reports and the code does not enforce at run time; and a registry that cannot be read affects every event, because `process` raises for all of them: a `PreToolUse` call then gets the fail-closed answer, and a prompt or session start gets the words as context {src:.harness/engine/hook.py#L97-L99} {src:.harness/engine/hook.py#L361-L371}.

## Gate internals: limits and differences between text and code

- **The comment in `gate.handle` is out of date.** It says that when the whole handler raises the hook counts the gate as having no opinion and the call goes through; `run_modules` raises `GuardFailed` for the gate on `PreToolUse`, and the call is refused unless it is a read from the safe list {src:.harness/engine/modules/gate/handler.py#L722-L724} {src:.harness/engine/hook.py#L77-L83}.
- **Rollback is for the session state only.** A module that raises loses its changes to the session state; files it already wrote, such as an approval file or a task file, stay {src:.harness/engine/hook.py#L66-L77}.
- **A guard failure on a call is not reported on every event.** Only `UserPromptSubmit` and `SessionStart` tell the agent; after a tool call or at a stop the failure is only in `hook-errors.jsonl` {src:.harness/engine/hook.py#L119-L121}.
- **Seven of the 14 guardrail paths are fixed in code;** the others can be dropped by a layer that replaces `guardrail_paths`, and `docs/04-reference.md` describes the list only as "the paths that cannot be changed" {src:.harness/engine/core/guardrails.py#L9-L19} {src:docs/04-reference.md#L199}.
- **`harness --short task close` is not matched** by the deny pattern as the code reads it, and no test covers it (see the section on person-only commands) {src:.harness/engine/modules/gate/harnesscmd.py#L105}.
- **`launch.py` is less than `hook.py`'s emergency answer** (English only, no integrity check, no log, no program-specific words), and a fault in `launch.py` itself is covered by nothing {src:.harness/engine/launch.py#L16-L47} {src:.harness/engine/doctor.py#L255-L267}.
- **Reads are open to the gate** apart from the secrets file, secret variables, the environment dump, the board's port and the two read-only turns; a read of a knowledge base or code file is never refused {src:.harness/engine/modules/gate/handler.py#L633-L650}.
