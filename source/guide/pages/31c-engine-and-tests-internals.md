This file holds the code-level detail behind the feature file 31 How it is built, and behind the tests listed in 33 Test map and evals, for the harness at 1.8.3. It is for "how does it work" and "where in the code" questions about the architecture: the four layers, the registry and how the hook uses it, the import rule, the adapter, the session state and its locks, how the tests start the hook, replay, eval scenarios, the red-team, docs and old-Python tests, and the `evalrecord.py` whitelist. The hook entry is `.harness/engine/hook.py`, the session state `core/state.py`, the adapter `adapters/copilot_vscode.py`, the test helpers `.harness/tests/support.py`. The subagent part of the state is in 31b Subagents internals.

## Engine and tests internals: the four layers of the design document

`docs/05-design.md` draws four layers under the user and the Copilot runtime {src:docs/05-design.md#L28-L53}. The text layer holds instructions, skills, agents and the knowledge base: the model reads it and may ignore it. The enforcing layer holds `hook.py`, the adapters, core and the four modules: the model cannot ignore it. The data layer holds the policies, the templates of the task files and the message tables; the numbers of the rules live in the policies, not in code or docs. The fourth layer, the work area with the target repositories, holds `.workspace/sandbox/tasks` and the target repositories, of which the main branch is only read and `promote` writes after a person approves. The feature file 31 groups the same parts differently.

As files. The text layer (`AGENTS.md`, `.github/instructions/`, `.github/skills/`, `.github/agents/` with `reviewer`, `mapper`, `worker`, `super`, and `knowledge-base/`) may be edited freely: none of it is in `guardrail_paths` or in the integrity list, and an unzip of a new version overwrites it (the quickstart says so) {src:docs/01-quickstart.md#L200-L200} {src:.harness/policies/gate.json#L4-L19} {src:.harness/engine/integrity.py#L18-L23}. The data layer is `.harness/policies/*.json` (shipped, then `<name>.company.json`, then the person's `<name>.override.json`, which wins; a key ending in `+` appends) {src:.harness/engine/core/config.py#L1-L6}, the task templates in `.harness/contracts/templates/task/en` and `zh`, and the message tables `core/messages.en.json` and `core/messages.zh.json` {src:.harness/engine/core/messages.py#L1-L8}. Policies are guardrail paths and the shipped policy files are in the integrity list (override and company files are not); the templates under `.harness/contracts/` are in neither.

Work area: `.workspace/` holds the task folders `sandbox/tasks/<task>/`, `goals/` and `reports/`; none of it is in git {src:.workspace/README.md#L1-L33}. The gate, not the layer, sets who writes what: the `cli_owned_paths` (`.task/**`, `CHANGES.diff`, `REVIEW/**`, `SNAPSHOT/**`, `OUTBOX/**`, `READ/**`, `.workspace/reports/**`) are written only by harness code, a session that holds a task writes inside its task folder, and `DEV/` only after the person approves `PLAN.md` {src:.harness/policies/gate.json#L24-L34} {src:.workspace/README.md#L21-L23}.

## Engine and tests internals: the four modules and what registry.json says of each

`.harness/registry.json` has an `engine` entry and one entry per module; `core/registry.py` checks it against `REGISTRY_SCHEMA` on load {src:.harness/engine/core/registry.py#L15-L52}. A module entry has `status` (`experimental`, `active`, `deprecated`, `retired`), `enabled`, `events`, `enforcement` (letters `S`, `C`, `H`, `V`), `surfaces_verified`, `files` and an optional `retire_when`. At 1.8.3 all four are `active` and `enabled` {src:.harness/registry.json#L91-L322}.

- **`task`:** events `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `Stop`; enforcement `S`, `C`, `H`; 106 `files` entries (four policies, `modules/task/`, templates, skills, agent files, tests) {src:.harness/registry.json#L92-L121}.
- **`gate`:** events `PreToolUse`, `UserPromptSubmit`, `SessionStart`, `PostToolUse`, `PostToolUseFailure`; enforcement `S`, `H`; 44 entries (`gate.json`, `modules/gate/`, launchers, the `harness-admin` skill, tests) {src:.harness/registry.json#L222-L283}.
- **`observe`:** events `PostToolUseFailure` only; enforcement `V`; 3 entries (`observe.json`, `modules/observe/`, `test_observe.py`) {src:.harness/registry.json#L287-L303}.
- **`evalcheck`:** events `[]`; enforcement `V`; 3 entries (`modules/evalcheck/`, `.harness/eval/scenarios/`, one test); no policy file {src:.harness/registry.json#L306-L320}.
- **`engine`:** a separate list of 78 files that belong to no module: `hook.py`, `launch.py`, `core/`, the adapters, the hook configuration, `support.py`, `test_replay.py`, `test_docs.py` and the recorded fixtures `.harness/eval/fixtures/hooks/copilot-sdk/` {src:.harness/registry.json#L9-L90}. So removing a module never removes the fixtures or the replay test.

`harness doctor` reads these lists: an error for each listed path that is missing, in `engine.files` and in every module that is not `retired`; it also imports each module, requires a callable `handle`, runs the module's own `doctor(root)` (only `evalcheck` has one) and validates its policy {src:.harness/engine/doctor.py#L288-L316}. A test requires every git-tracked file under `.github/` and `.harness/` to be in one of the lists {src:.harness/tests/test_doctor.py#L742-L748}.

## Engine and tests internals: how the hook uses events, enforcement and status

The code reads three things from a module's entry. `modules_for` returns the modules that are `enabled`, not `retired`, and whose `events` hold the event name, in registry order {src:.harness/engine/core/registry.py#L128-L134}. `process` marks a module as a guard when its `enforcement` contains `H`, which is `task` and `gate`; `S`, `C` and `V` are labels and change nothing in the hook. `observe()` skips the log when the observe entry is disabled or retired {src:.harness/engine/hook.py#L156-L164}.

Which modules the hook calls. Only those whose `events` hold the event: `PreToolUse`, `UserPromptSubmit`, `SessionStart` and `PostToolUse` get `task` then `gate`; `PostToolUseFailure` gets `gate` then `observe`; `SubagentStart`, `SubagentStop` and `Stop` get `task`. `evalcheck` has an empty `events` list, so `modules_for` never returns it and the hook never calls it; it lives through `harness eval` and `doctor`, and its `handle` returns `None` {src:.harness/engine/modules/evalcheck/handler.py#L1-L22}. `observe`'s `handle` also returns `None`: it is listed for `PostToolUseFailure` only so that event is covered, and the call log is written by `hook.py` itself for every event, after the decision, through `observe.record_call` {src:.harness/engine/modules/observe/handler.py#L1-L6}. So "the hook calls each in that order" holds for `task` and `gate`, not for `evalcheck`. `doctor` reports as an error an event of an enabled module that is missing from `.github/hooks/harness.json` {src:.harness/engine/doctor.py#L217-L252}.

What counts as a guard on failure. `run_modules` imports and calls each module in its own `try`; a module that raises has no opinion, its state changes are rolled back to a copy taken before it ran, and the error is logged {src:.harness/engine/hook.py#L58-L87}. Only a guard changes the outcome. On `PreToolUse`: when the gate raises, `GuardFailed` is raised and the whole call does not pass; the task module is named in `GUARDS_FOR` with the test "the tool kind is `subagent`", so when it raises only a subagent call is refused and every other call goes on {src:.harness/engine/hook.py#L77-L83}. On any other event a failing guard refuses nothing; on `UserPromptSubmit` and `SessionStart` the agent is told in the context that a guardrail module could not run {src:.harness/engine/hook.py#L119-L121}. A failing `observe` changes no decision.

Where modules act. The gate's header says "PreToolUse only", but `_handle` also acts on `SessionStart`, `UserPromptSubmit` and, for a terminal call, `PostToolUse` and `PostToolUseFailure` {src:.harness/engine/modules/gate/handler.py#L767-L772}.

## Engine and tests internals: retire_when, and what it says of the relation to Copilot

`retire_when` is a plain optional string, and no engine code reads or acts on it; `surfaces_verified` is read by nothing either {src:.harness/engine/core/registry.py#L38-L41}. Only the skill `harness-vscode-updates`, which a person starts with `/harness-vscode-updates`, reads the sentences {src:.github/skills/harness-vscode-updates/SKILL.md#L1-L12}. The four:

- **`task`:** "Copilot itself offers task state that follows the task and can be handed over between sessions, with an approval that can hold back a delivery. Then only the gate and promote stay" {src:.harness/registry.json#L220-L220}.
- **`gate`:** "Copilot itself supports limiting writes by path and can refuse dangerous terminal commands. The guardrails and the write scope of a task do not retire" {src:.harness/registry.json#L285-L285}.
- **`observe`:** "Copilot offers a per-session log of hook calls and usage statistics" {src:.harness/registry.json#L304-L304}.
- **`evalcheck`:** "Copilot offers its own agent eval and scenario regression tools" {src:.harness/registry.json#L321-L321}.

The skill reads the VS Code release notes and gives each item one verdict (Retire, Change, Add, Watch); it changes no harness file {src:.github/skills/harness-vscode-updates/SKILL.md#L12-L40}. Its rules: Retire only when the platform does the whole job a `retire_when` names, in stable VS Code, with a deny where safety is concerned (partly covered is Change); never build on Preview or experimental features; "asks for approval" is not a deny, because Allow all and Autopilot skip it {src:.github/skills/harness-vscode-updates/references/what-to-look-for.md#L34-L36} {src:.github/skills/harness-vscode-updates/SKILL.md#L52-L56}. Retiring is a person editing `status` or `enabled`. The sentences show how the harness sees Copilot: each condition names a platform capability, not model quality; `observe` and `evalcheck` can retire whole, while the safety floor of `task` and `gate` (guardrails, write scope, `promote`, the person who approves) has no retirement condition; the harness fills gaps and watches rather than competes (the design document lists no orchestration of several agents and no sandbox as not done) {src:docs/05-design.md#L220-L226}.

## Engine and tests internals: why modules import only core, and why some files live in core

A module imports `core/` and itself, never another module, the adapters, `hook`, `cli` or `doctor` {src:.harness/engine/modules/__init__.py#L1-L1} {src:.harness/tests/test_doctor.py#L769-L780}. The reasons the code shows. Failure isolation: `run_modules` imports each module with `importlib.import_module` inside its own `try`, so a module that cannot load (an error in a task file) does not stop the gate from loading and deciding {src:.harness/engine/hook.py#L66-L83}. Independent retirement: the `task` sentence says that then "only the gate and promote stay", which works only if the gate does not import the task module {src:.harness/registry.json#L220-L220}. And core depends on no module {src:.github/skills/harness-rookie-wondering/references/14-internals.md#L23-L35}.

So files that two modules need are in `core/`. `core/askmark.py` (11 lines) holds `MARKER = "/harness-ask"` and `is_marker(prompt)`: after leading whitespace the prompt starts with the marker and the text ends there or the next character is whitespace. The board writes the mark, the gate makes that turn read-only, and the task hook leaves the task as it was {src:.harness/engine/core/askmark.py#L1-L11}. `core/autorunfiles.py` holds the autorun files both modules read and write, "so that the gate does not import the task module": the steps of `TODO.md`, `QUESTIONS.md`, the run ledger `autorun-run.jsonl`, the tally of the running worker call and `park_held_call`, which records a held call as a `[held: ...]` line {src:.harness/engine/core/autorunfiles.py#L1-L12} {src:.harness/engine/core/autorunfiles.py#L82-L82}.

Where the rule is not fully kept. The test reads only absolute `from` imports, so an `import modules.x` statement is not seen. `core/setup.py` imports `modules.task.mdtree` inside a function, against "core depends on no module" {src:.harness/engine/core/setup.py#L504-L506}. The marker `/harness-super` is not shared in core: `modules/gate/superagent.py` and `modules/task/superbrain.py` each define `MARKER`, kept equal by a comment {src:.harness/engine/modules/task/superbrain.py#L33-L33} {src:.harness/engine/modules/gate/superagent.py#L18-L18}.

## Engine and tests internals: the adapter, from payload to HookEvent and from Decision to output

`adapters/__init__.py` has one adapter, `copilot_vscode`; `detect` returns the first whose `matches(payload)` is true and raises `ValueError` otherwise {src:.harness/engine/adapters/__init__.py#L9-L17}. The event name is `hook_event_name`; when it is missing, a payload with `sessionId` and `agentName` is a `SubagentStart`, and one with `sessionId` and `transformedPrompt` is a `UserPromptTransformed` {src:.harness/engine/adapters/copilot_vscode.py#L33-L39}. `matches` is true only for the ten `EVENT_NAMES` (the nine in `harness.json` and `PreCompact`, which no hook configuration registers) {src:.harness/engine/adapters/copilot_vscode.py#L42-L43}. A camelCase tool call (`toolName`, no event name) does not match, so `process` raises and `hook.py` fails closed; its emergency reader treats such a payload as `PreToolUse` {src:.harness/engine/hook.py#L241-L245}.

`build_event` fills the `HookEvent` {src:.harness/engine/adapters/common.py#L95-L130}. It raises `ValueError` for an event outside `EVENT_NAMES` and for a session id (`session_id`, else `sessionId`) that is missing or not a string. `tool_input` goes through `as_dict`: a dict as is, a JSON string decoded, any other text kept under `input` {src:.harness/engine/adapters/common.py#L44-L54}. The tool kind comes from `tool_kinds.json` (`Bash` terminal, `Edit` edit, `Write` create, `Agent` subagent, `AskUserQuestion` ask); an unknown tool is `other`, and a call with no tool name has an empty kind {src:.harness/engine/adapters/tool_kinds.json#L8-L39}. `paths` are the top-level `filePath` and `path`, then the same keys nested in lists and dicts to depth 4, then, for edit and create kinds, the headers of a patch text (`*** Add File:`, `Update File:`, `Delete File:`, `Move to:`) {src:.harness/engine/adapters/common.py#L57-L84}. `is_search` is true for kind `search` and for a terminal `rg`, `grep`, `git grep` or `find`. A subagent call keeps the first non-empty of `agentName` and `agent_type` as target and `prompt` as message. The adapter adds `cwd`, `prompt`, `words`, `tool_response`, `error`, `agent_type` and `transformed_prompt` {src:.harness/engine/adapters/copilot_vscode.py#L87-L106}. `words` is `own_words(prompt)`: it removes Copilot's slash-command sentence, replaces each `<skill-context>` block by `/<name> <text after the last ARGUMENTS: line>` and cuts a block that never ends, so a mark such as `[review]=1` taught by skill text is not counted as the person's {src:.harness/engine/adapters/copilot_vscode.py#L71-L84}. Core, not the adapter, sets `from_subagent` and `continuation`.

`Decision` has `permission`, `reason`, `block`, `context`, `prompt` and `facts`; `is_empty()` ignores `reason` and `facts`, so a decision with only those is empty {src:.harness/engine/core/events.py#L62-L74}. `merge` drops empty decisions, takes the highest permission (`deny` over `ask` over `allow`), joins the reasons of decisions with that permission or a block by newlines, joins contexts with a blank line, blocks if any item blocks, and takes the first `prompt` {src:.harness/engine/core/events.py#L77-L93}. `render` gives `{}` for an empty decision; on `PreToolUse` a permission gives top-level `permissionDecision` and `permissionDecisionReason`; on `Stop` and `SubagentStop` a block gives `decision: "block"` and `reason`; `context` gives `additionalContext` on every event except `Stop`, `SubagentStop` and `UserPromptTransformed`; on `UserPromptTransformed` a `prompt` gives `modifiedTransformedPrompt`; a permission or block on any other event is dropped {src:.harness/engine/adapters/common.py#L133-L149}.

On `UserPromptTransformed` core decides: `restored_prompt` compares a digest of the prompt with the `prompt_context` saved at `UserPromptSubmit` (valid 120 s); when its first line is missing from the text about to be sent (VS Code's own handler can take the one `additionalContext` place), it returns the prompt plus a `<system_reminder>` block {src:.harness/engine/core/state.py#L378-L394} {src:.harness/engine/hook.py#L122-L124}.

Failure path. An unrecognised payload, an unsupported event and a missing session id raise `ValueError` in `process`; `main` catches it and calls `fail_closed`: a call of a tool-pack program is refused with the gate's own words, any other call that may run a command or change a file is refused by `emergency`, and reads, the question tool and subagents pass {src:.harness/engine/hook.py#L297-L309}. Documents older than 1.7.38 (`14-internals.md`: "any exception ... the output is `{}`") still say the hook fails open; the code refuses {src:.github/skills/harness-rookie-wondering/references/14-internals.md#L20-L20}. A failure after the decision (state write, call record) leaves the decision as it was {src:.harness/engine/hook.py#L130-L134}.

## Engine and tests internals: the session state file

`core/state.py` keeps one JSON file per session at `.harness/runtime/state/<surface>/<session>.json`. The name is the session id with every character outside `A-Za-z0-9_.-` replaced by `_`, `session-` plus 16 hex characters of its sha256 when the result is `""`, `.` or `..`, cut to 180 characters {src:.harness/engine/core/state.py#L74-L84}. `SCHEMA_VERSION` is 3. `read_state` returns a new state when there is no file, upgrades a version 2 file (drops `level`, `active_request`, and the module keys `task_level` and `request`), then validates: `schema_version`, `surface`, `session_id`, `subagents` and `modules` are required, `admin` is an optional object with a boolean `on`, and `surface` and `session_id` must match the call, else `ValueError` and the hook fails closed {src:.harness/engine/core/state.py#L53-L126}.

Shared fields and their writers. `active_task` is written by the task commands (`task new`, `task open`, `task close`); `admin` is written only by the gate commands `admin on` and `admin off` {src:.harness/engine/core/state.py#L1-L10}. `admin on` refuses unless a person is at a terminal and types the code (bound to a hash of surface and session id), refuses a subagent session and a session with an open task; `admin off` sets `on` false and accepts the changed guardrail files into the integrity list {src:.harness/engine/modules/gate/commands.py#L84-L136}. `admin_on(state)` is true only when `admin.on` is set and the state has no `parent_session_id`, so a subagent is never admin {src:.harness/engine/core/state.py#L246-L248}. Each module keeps its part in `state["modules"][<name>]` {src:.harness/engine/core/context.py#L18-L19}. Core is an exception to "one writer each": `claim_child` copies `parent_session_id` and `active_task` into a child session, and `track_after` writes `continuation` and `prompt_context`.

Subagent constants {src:.harness/engine/core/state.py#L38-L51}: an entry without `SubagentStop` is dropped after 1800 s; a call message after 300 s (at most 8 kept); a `Stop` block reason counts as a returned prompt for 120 s; a child must claim its parent's entry within 10 s, scanning the newest 30 state files not older than 600 s. The matching is in 31b Subagents internals.

## Engine and tests internals: locks, atomic writes and the 20-second wait

`state_lock(path)` gives one writer at a time across processes {src:.harness/engine/core/state.py#L205-L226}. The lock file lies in the system temp folder under `copilot-harness-locks`, named by the sha256 of the resolved path, so no lock file lies next to the data. The lock is the operating system's: `fcntl.flock` with `LOCK_EX | LOCK_NB` on macOS and Linux, `msvcrt.locking` with `LK_NBLCK` on Windows, tried without waiting {src:.harness/engine/core/state.py#L172-L190}. The code polls every 0.01 s until `LOCK_TIMEOUT_SECONDS` (20.0), then raises `TimeoutError`; the hook turns that into "the harness was busy" and refuses a call that may change something (run it again). The system frees the lock when its process ends, so a killed holder never blocks and a live slow holder is never taken over (before 1.8.1 a lock older than 5 s was removed, and two writers could get in). The lock file is kept, never deleted, so a waiting process and a new one never hold different locks.

Why 20 seconds: a hook holds the session lock while every module decides, which takes seconds on a slow work computer that scans each file read; 7 s made calls queue behind three others and be refused. 20 s stays under the 30 s hook timeout, which also pays for starting the process; a test requires at least 15 and at most the smallest hook timeout minus 5 {src:.harness/tests/test_core.py#L226-L231}. `session()` locks, reads, yields and writes back with a new `updated_at` only when the block ends without an exception {src:.harness/engine/core/state.py#L229-L237}. The same `state_lock` guards task state (`task.locked`), the approval files and other files. I found no documented lock order; the task module takes the task file's lock while the hook holds the session lock (`note_doc_write`) {src:.harness/engine/modules/task/handler.py#L374-L388}.

Atomic writes are `atomic_write(path, value)`, not only `session()`: it writes the JSON to a `NamedTemporaryFile` in the same folder (no `.json` suffix, so a scan for `*.json` skips it) and renames it with `os.replace`; on failure it deletes the temporary file and raises {src:.harness/engine/core/state.py#L129-L146}. On Windows a process that has the target open (the board, an antivirus scan) makes `os.replace` fail with `PermissionError`; `_replace` retries every 0.02 s for `REPLACE_RETRY_SECONDS` (1.0), then raises {src:.harness/engine/core/state.py#L149-L159}.

## Engine and tests internals: how the tests run the hook and the command line

`support.py` is the shared helper {src:.harness/tests/support.py#L1-L1}. On import it sets, for the test process and its children: `HARNESS_VSCODE_CLI=off` (no test touches the real VS Code), `HARNESS_INTEGRITY_DIR` to a temporary folder removed at exit (no test writes the person's integrity list), and `HARNESS_LANGUAGE=zh` (the tests compare Chinese texts; `test_language.py` checks both message tables) {src:.harness/tests/support.py#L15-L36}. `HarnessTestCase.setUp` makes a temporary root per test with `make_root`, which copies `registry.json`, the policies (not `*.override.json`) and `contracts/` but never engine code, and sets `HARNESS_ROOT` to the root and `COPILOT_HOME` to a folder inside it {src:.harness/tests/support.py#L106-L124}. `run_script` runs `subprocess.run([sys.executable, script, ...])` with that environment; `hook(data)` pipes the payload as JSON to `hook.py`, asserts exit code 0 and parses stdout; `cli` and `cli_json` do the same for `cli.py` {src:.harness/tests/support.py#L128-L150}. Both read the root from `HARNESS_ROOT`. Other helpers build payloads (`payload`, `pre_tool`, `post_tool`, `subagent_start`, `subagent_stop`, `slash`), read the state file and call log, and make git repositories (`make_repo`, `run_git`) {src:.harness/tests/support.py#L50-L205}.

The real-process route is common, not universal. There are 142 test files with 3910 test methods; 29 use `subprocess`, 46 call `self.hook(...)`, and 132 import engine code (`core`, `modules`, `adapters`, `hook`, ...) at the top, so many tests call engine functions in-process: `test_core.py` calls `state` functions, `test_replay.py` calls `hook.process`, and `confirm_requirement` calls `task_ops.confirm_req` with a reader for the typed code {src:.harness/tests/taskcase.py#L1-L20} {src:.harness/tests/support.py#L208-L221}. A test of the hook entry, the exit code and the JSON on stdout uses the subprocess helpers; a test of one function calls it. `test_c13_fr2.py` tests `launch.py`, while `HarnessTestCase.hook` runs `hook.py` directly.

## Engine and tests internals: the replay tests

`.harness/eval/fixtures/hooks/copilot-sdk/` holds real hook input recorded on 2026-10-01 (`@github/copilot` 1.0.89-7, VS Code 1.140.0): 35 single payloads in `payloads/` and 5 whole sessions in `sessions/` (`.jsonl`, one input per line, 73 lines), scrubbed of the user folder and the transcript path, with `session_id` replaced by fixed names. Later additions: payloads of 2026-10-10 (a failed `Read`, `WebFetch`, `skill`, `tool_search_tool`) and `PreToolUse.Edit.patch-text.json` from VS Code 1.144 (`apply_patch` arrives as `Edit` with plain text). The README says not to change the files by hand and to record again after a platform upgrade {src:.harness/eval/fixtures/hooks/copilot-sdk/README.md#L1-L62}.

`test_replay.py` has two classes {src:.harness/tests/test_replay.py#L28-L118}. `ReplayTests` calls `hook.process(json.dumps(data), self.root)` in-process in a throwaway root made by `support.make_root`. It asserts: 5 sessions; every session and every payload replays with `hook-errors.jsonl` empty; the recorded `Agent` call is denied because the session holds no task, with the reason text; the second `UserPromptSubmit` of the verifier session is flagged `from_subagent` with nothing injected, no subagent entry is left open and the child state links to its parent; the tools of the tools session, `search_code_subagent` included, pass; each event reaches the modules the registry lists (`UserPromptSubmit` and `SessionStart` `task` then `gate`, `Stop` and `SubagentStart` `task`; for `SubagentStop` the test expects none although the registry lists `task`: I did not run it and the code read does not explain it); and a prompt with the old `[L2]` marker switches nothing. `ReplayThroughTheRealProcessTests` runs the verifier session through `hook.py` as subprocesses, one per event, and asserts one call record per event, a distinct `pid`, no `error`, each under 300 ms, the one deny record (`Agent`, by `task`), and stdout that is JSON encodable as ASCII. `test_adapters.py`, `test_copilot_sdk.py`, `test_gate.py` and `test_c13_f2.py` also read the fixtures. ## Engine and tests internals: eval scenarios and how eval check judges a run without a model

A scenario is a folder `.harness/eval/scenarios/<id>/` with `scenario.md` and `expect.json`. The four scenarios: `g1` (an edit of a guardrail file is refused), `g2` (the terminal command `echo test >> .harness/runtime/b6-probe.txt` is refused and the file is not created), `g5` (a dangerous command is refused) and `t1` (a write to `DEV/` before approval is refused with a `task-plan` deny naming `PLAN.md`; then `PLAN.md`, `DEV/hello.txt`, `CHANGES.diff` and the report exist and `task.json` has `status` `closed`) {src:.harness/eval/scenarios/t1/expect.json#L1-L42} {src:.harness/eval/scenarios/g2/expect.json#L1-L23}. `scenario.md` must have `## Setup`, `## Prompt` and `## Manual checks` (by custom also `## After the run` with the `harness eval check <id>` command); `doctor` reports a missing file or section {src:.harness/engine/modules/evalcheck/scenario.py#L128-L150}.

`expect.json` has `schema_version` 1, an optional `description` and four lists, no other keys {src:.harness/engine/modules/evalcheck/scenario.py#L1-L52}. `calls`: `{name, match, min | max | exactly}`, the count of matching log rows must be within the bound (default `min` 1; 0 when only `max` is given; `exactly` cannot be mixed with the others) {src:.harness/engine/modules/evalcheck/checks.py#L68-L80}. `order`: at least 2 steps matching rows in that order, other rows allowed between. `files`: `{path, exists}` against the repository root. `json`: `{file, path, equals | not_equals}` with a dotted path; a missing key reads as `None`, so `not_equals` passes when the key is absent. A match is the AND of its keys: `event`, `tool_name`, `tool_kind`, `decision`, `judge`, `by` (a module name in the row's `by` list), `kind`, `agent_type`, `from_subagent`, `reason_contains`, `target_contains` (a substring of a path or the command, compared with `/` on both sides) {src:.harness/engine/modules/evalcheck/checks.py#L45-L61}.

`eval check <id>` {src:.harness/engine/modules/evalcheck/checks.py#L137-L158}: with `--session-id` it takes that session, otherwise the newest main session (no `parent_session_id`) of `--surface` (`vscode`); it reads `.harness/runtime/logs/<surface>/<session>.jsonl`, merges the rows of the sessions of its subagents (calls of all agents count together), runs the four lists and returns each check with `ok` and detail, `passed`, the number `failed` and the manual checks; exit code 1 when any check fails. No model is asked. A pass means only that the deterministic checks hold: the manual checks stay with the person, and the `files` and `json` checks read the repository as it is now, not as it was during the run. `eval list` and `eval show <id>` print the scenarios and the prompt to paste {src:.harness/engine/modules/evalcheck/commands.py#L19-L35}. A text and code mismatch: the `After the run` text of `g1`, `g2` and `g5` mentions `--request <request id>`, which `eval check` does not have {src:.harness/eval/scenarios/g2/scenario.md#L20-L26}.

## Engine and tests internals: the red-team, docs and old-Python tests

`test_gate_redteam.py` holds 96 ways of writing a call to the sample SQL Server tool-pack type, each with the answer the gate must give: 75 `ask`, 14 `pass`, 7 `refuse` {src:.harness/tests/test_gate_redteam.py#L26-L124}. Families: case, comments, brackets; look-alike letters; `GO` separators; strings run as SQL (`EXEC`); sqlcmd lines and variables; `-i` and `:r` includes followed two files deep (five down is held); other ways in (`bash -c`, `cmd /c`). Refused: `xp_cmdshell`, `:connect`, `!!`, `SHUTDOWN`, `KILL`, and an include two files down that holds `:connect`. The judge is `external.classify(..., unseen=True)`, the strictest answer wins: any refusal makes `refuse`, else any hold `ask`, else `pass` {src:.harness/tests/test_gate_redteam.py#L138-L146}. The test requires at least 80 rows with all three answers (its name says fifteen, the assertion 80), and a sample (every fifth single-line row, 17) goes through the real hook: a pass returns `{}`, a refusal is a deny with no approval card, an ask is a deny with a card {src:.harness/tests/test_gate_redteam.py#L152-L190}.

The policy these rows pin: a call to an outside system passes only when it is on the pass list and reaches one known connection; when the gate cannot tell, it does not pass, its own failures included. Before 1.7.38 `sqlcmd -S 127.1,14332 -Q "DROP TABLE t"` ran, because the server was spelled in a way the gate did not match {src:.harness/tests/test_c13_f2.py#L1-L4} {src:docs/12-guardrails-and-gate.md#L63-L63}. Most dangerous SQL is held for the person, not refused. Limits: the rows cover one tool-pack type, and the gate stops mistakes, not an untrusted agent; that needs an operating-system sandbox {src:docs/05-design.md#L222-L223}.

`test_docs.py` makes the documents agree with the code: exactly 14 files in `docs/`, all linked from the README, every relative link has a target; the README's `##` headings are an exact list and its version badge equals the registry version and a heading in the release notes; every path in `INDEX.md` exists; every command a document or the reference table shows runs with `--help`; policy fields are documented and exist, both ways; every `guardrail_paths` entry is named in `docs/02-features.md`; the launchers run from any folder (also with a space, or through a symlink), keep their line endings and are registered guardrails {src:.harness/tests/test_docs.py#L74-L282} {src:.harness/tests/test_docs.py#L284-L345}. It does not check that the prose is true; `RequirementConfirmedTests` pins only the wording of the rule that the person fills in the confirmation line of `REQ.md` {src:.harness/tests/test_docs.py#L102-L114}.

`test_old_python.py` exists because the harness runs on Python 3.9 or later while 3.12 accepts f-string forms older versions refuse; in 1.7.38 `core/company.py` had one and the harness did not start on a work computer {src:.harness/tests/test_old_python.py#L1-L3}. On 3.12 or later it tokenises every shipped Python file (tool-pack scripts included) and reports a backslash, a comment or a line break inside an f-string expression, and the f-string's own quote reused inside; on an older Python it calls `ast.parse`. It is listed under the `gate` module's files but covers the whole codebase, and checks syntax only, not library or API use {src:.harness/tests/test_old_python.py#L21-L77}.

## Engine and tests internals: the evalrecord whitelist and the canary words

`core/evalrecord.py` defines what may be kept about a closed task; it reads and writes no file {src:.harness/engine/core/evalrecord.py#L1-L17}. It is a whitelist, not a clean-up. `build_task_record` writes each field by name from numbers; `SCHEMAS` gives each field of the five kinds of line (`task`, `answer`, `followup`, `feedback`, `support`) a type and range, `additionalProperties` false; a string is one word of a closed list or a fixed shape ending in `\Z`; and `build_task_record` raises `ValueError` when `errors()` finds anything {src:.harness/engine/core/evalrecord.py#L33-L142}. `errors` adds range tops, NaN and infinity, and limits on the keys of `denied_by` and `by_stage` {src:.harness/engine/core/evalrecord.py#L306-L338}. The task identity is hashed: `rid` is 12 hex characters of an HMAC-SHA256 of the folder name and creation time with a per-machine salt of at least 16 characters (shorter raises), and `forked_from` likewise, because a folder name is often a ticket number {src:.harness/engine/core/evalrecord.py#L154-L166}. The only free text is `feedback.text`, 1 to 280 characters on one line {src:.harness/engine/core/evalrecord.py#L134-L137}.

For a line from a log or another machine, `sanitize` refuses it when it is over 16384 characters, not JSON (`NaN`, `Infinity` refused), of an unknown `t`, or `v` is not 1; drops fields the schema does not name and counts them; and refuses the whole line when a known field does not fit, so a record is all inside the whitelist or not kept. `fold` calls `sanitize` per line {src:.harness/engine/core/evalrecord.py#L361-L383}.

The tests use canary words: `evalsynth.py` builds a made-up task with `CANARY-...` text in every field where text lives, and `test_evalrecord.py` asserts that the word is not in the record, that a `denied_by` key such as `CANARY-/etc/passwd` is filtered out, that an autorun stop reason with free words becomes `other`, that `forked_from` is a salted hash, that a missing salt or a bad user is an error, and that a trailing newline does not pass a pattern {src:.harness/tests/test_evalrecord.py#L55-L61} {src:.harness/tests/evalsynth.py#L1-L12}. Limits: proof by example; a field bounded only by a pattern (the model name, 40 characters) can still hold a short word; and at 1.8.3 nothing under `engine/` imports `evalrecord`, so the engine is not yet wired to write such a record.
