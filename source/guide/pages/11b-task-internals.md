This file holds the code-level detail behind the feature file 11 Task: the functions, the fields of the state file, the defaults and the order of checks that make a task work in harness 1.8.3. It is for "how does it work" and "where in the code" questions; what a task is, how a person uses it and what it guarantees are in 11 Task. Paths are in the harness repository; most of the task code is in `.harness/engine/modules/task/` (`tasklife.py`, `task.py`, `accept.py`, `handler.py`, `taskstages.py`, `taskfork.py`, `rewind.py`) and in `.harness/engine/core/tasks.py`, with the write scope in `.harness/engine/modules/gate/handler.py`.

## Task internals: the folder, its files and who may write them

The task folder is `.workspace/sandbox/tasks/<name>/` (`TASKS_DIR` in `core/tasks.py`). `tasks.folders` lists every sub-folder of that directory whose name does not start with a dot, whether or not it has a state file. The state file is `<task>/.task/task.json`; `tasks.read` returns it as a dict, and returns None when the file is missing, is not valid JSON or is not a JSON object {src:.harness/engine/core/tasks.py#L19-L50} {src:.harness/engine/core/tasks.py#L82-L89}. The constants of the folder are in the same file: `TASK.md`, `TODO.md`, `LOG.md`, `REQ.md`, `PLAN.md`, the folders `DEV` and `READ` (code fetched only to be read, never written back), `DEV/_manual` (made under the plan, run by hand, never written back), `.task/base`, and the two diff files `CHANGES.diff` and `PROMOTE-PLAN.diff` {src:.harness/engine/core/tasks.py#L19-L37}.

Tier files: `TIER_FILES` in `tasklife.py` lists what each tier adds: `light` has `TASK.md`; `medium` adds `REQ.md`, `REQ/`, `REF/` and `LOG.md`; `full` adds `TODO.md`, `DEV/` and `TEST/`. `files_of(tier)` returns the files of the tier and of every lower tier. No tier makes `INBOX/`: the board server creates it when the person gives something on the task page {src:.harness/engine/modules/task/tasklife.py#L39-L45} {src:.harness/engine/modules/task/tasklife.py#L78-L83} {src:.harness/engine/modules/task/taskinbox.py#L1-L11}.

`INBOX/` is filled by the board server (`taskinbox.py`), not by the agent. Text and pictures the person pastes into a form on the task page are written under `INBOX/<ENV>/<time>/` as `given.txt` (the output), `ran.txt` (the commands, when given) and `image-N.<type>`; a command the person runs with the Run button leaves the same two files under `INBOX/BOARD/<time>/`. The server picks every name; the environment name must match a short pattern (a letter, then up to 11 letters, digits, `_` or `-`); a text is cut at 400,000 bytes, the commands at 100,000, a task page takes at most 10 pictures of at most 8 MB, and a picture's type is read from its first bytes (PNG, JPEG, GIF), not from its name {src:.harness/engine/modules/task/taskinbox.py#L1-L36}. The agent reads the newest folder of the environment and records it with `task test record` or `task run record` {src:.harness/engine/modules/task/taskinbox.py#L1-L11}.

Task folder, who may not write which part: three groups of paths are closed to the agent's edit tools. The person's folders `REQ/`, `REF/` and `INBOX/` (`PERSON_DIRS`, lower case, because the gate compares without case); the paths only the command line writes (`cli_owned_paths` in `gate.json`: `.task/**`, `PROMOTE-PLAN.diff`, `CHANGES.diff`, `CHANGES_r*.diff`, `REVIEW/**`, `SNAPSHOT/**`, `OUTBOX/**`, `READ/**` and `.workspace/reports/**`); and `DEV/` until the plan is approved {src:.harness/engine/core/tasks.py#L37} {src:.harness/policies/gate.json#L23-L33}. The first two groups are refused whether or not a plan is approved; the third is refused by a check that reads the plan's approval each time (next section).

## Task internals: the gate's write scope for a session that holds a task

Task write scope, order of checks: the gate's `check_write` runs for every edit or create tool call, in this order, for each path the tool names. A path inside a `.git` folder is denied. A path in the integrity-list folder is denied, in admin mode too. A path a target repository lists as refused is denied, and so is a path inside a target repository's working tree. Then the path is read as repository-relative: a guardrail match is denied (admin mode gives a different message and keeps only the admin-locked paths closed), and a match with the command-line-owned paths is denied. Only when none of these refuses does `check_task_write` run {src:.harness/engine/modules/gate/handler.py#L38-L61}.

`check_task_write` is the task folder rule. It returns "no objection" when the session's state has no `active_task`, and also when that task's `task.json` cannot be read or its status is not `open`, so a session bound to a closed or missing task is not confined to any folder. Otherwise, for each path: a path that is not inside the repository, or not inside the task folder, or is the task folder itself or its `DEV` folder itself, is denied (fact kind `task-scope`). Inside the folder the checks go in this order: the autorun narrowing (only while the task's autorun state is `on`); `DEV/` (denied until `tasks.plan_approved` holds; the message differs when the plan was approved before and the requirement's three sections changed since, `task_plan_req`, from when no plan was ever approved, `task_plan_first`); the first path component below the task folder, which is denied when it is `req`, `ref` or `inbox` in any case. Every other path in the folder passes with no approval: `TASK.md`, `REQ.md`, `PLAN.md`, `TODO.md`, `LOG.md`, `TEST/`, and results at the root of the folder (`RCA.md`, `DESIGN.md`) {src:.harness/engine/modules/gate/handler.py#L64-L94}. `REQ.md` is a file in the folder, so it is open to the agent; only the folder `REQ/` is closed. Comparisons are case-insensitive {src:.harness/engine/modules/gate/handler.py#L112-L114}.

Task write scope under autorun: when the task's `autorun.state` is `on`, `_autorun_write` applies first. The task's own chat (a session with no `parent_session_id`) may write only four files directly in the task folder, `TODO.md`, `TASK.md`, `LOG.md` and `QUESTIONS.md`, and every other path is denied with an autorun message. A session with a `parent_session_id` (the worker) may write anything the other rules allow, except those four, which are denied to it. A path in a sub-folder never counts as one of the four {src:.harness/engine/modules/gate/handler.py#L75-L109}.

Task write scope, what it does not cover: it applies to the tools the harness lists as edit or create tools, and to a session whose `active_task` names an open task. It does not apply to a session with no task, to a task that is closed, or to a tool that no tool pack names. A write tool with no path the gate can read is denied; any other call the gate cannot read is allowed. The terminal is checked by separate rules (`check_terminal`), which look for guardrail, command-line-owned, `.git` and target-repository paths in the command text and do not confine the agent to the task folder {src:.harness/engine/modules/gate/handler.py#L1-L15} {src:.harness/engine/modules/gate/handler.py#L117-L139} {src:.harness/engine/modules/gate/handler.py#L836}.

Task write scope, "open a task first": nothing in code refuses an edit because the session has no task. The agent is told by text (`AGENTS.md`, the skill `harness-my-task`, the hook's per-prompt rules) to open a task before it produces or changes files; the gate's `check_task_write` returns "no objection" for a session without `active_task` {src:AGENTS.md#L46-L47} {src:.harness/engine/modules/gate/handler.py#L64-L72}.

## Task internals: how `task new` makes a task

`harness task new <name>` needs `--kind` (one of `qa`, `rca`, `design`, `dev`, `test`, `kb`, `other`) and `--session-id`; `--tier` is optional (`light`, `medium`, `full`; default by kind); `--surface` takes only `vscode`; `--domain` may repeat and names business domains. The command-line parser refuses a call without `--kind` or `--session-id` {src:.harness/engine/modules/task/commands.py#L166-L173}. When `--domain` is given, `cmd_new` checks the domain names first, so a wrong name stops the call before a task is made {src:.harness/engine/modules/task/commands.py#L76-L83}.

Task creation, `tasklife.new`, in order: (1) `clean_name` checks the name; (2) the tier is taken from `--tier`, or from the kind's default; (3) if the folder already exists, the call is refused (`task.exists`: use `task open` or another name); (4) `check_session` requires that the session's state file exists, that it is not a subagent session and that it is not in admin mode, and it runs before the folder is made, so a refused call leaves nothing behind; (5) the folder is made; (6) `add_files` writes the files of the tier; (7) `attach` records the kind and tier, creates `task.json` and binds the session; (8) the result carries `made` (the files written) {src:.harness/engine/modules/task/tasklife.py#L126-L134} {src:.harness/engine/modules/task/tasklife.py#L163-L174}.

`clean_name` refuses: an empty name; a name with `/` or `\`, one that starts with a dot, one of `.` or `..`, or one longer than 80 characters (`NAME_LIMIT`); on Windows the characters `<>:"|?*`, a trailing dot or a control character; on every system a name with a character the shells read as a command, quote, variable or wildcard (`SHELL_BAD`: `& ^ % ! ( ) ; , = ' " ` $ | < > ? * : { } [ ] ~ #`, space and tab) and a name starting with `-`. The refusal names the offending characters and suggests the same name with each risky character turned into a hyphen. The reason is stated in the code: a name with such a character breaks `harness task open <name>` unless it is quoted right in the shell of the day {src:.harness/engine/modules/task/tasklife.py#L33-L38} {src:.harness/engine/modules/task/tasklife.py#L57-L75}.

`add_files` makes only what is missing: for each file or folder of the tier it skips a path that exists, makes a folder (names ending in `/`) with `mkdir`, and writes a file from the template with the placeholders `{name}`, `{kind}`, `{tier}` and `{created}` filled in; other braces in a template are left alone. Nothing that exists is changed, moved or deleted. The template is looked up in the folder for the language of the run, then directly in `templates/task/` (a team's own, one language), then the default language folder; when none is found the file is one line, `# <name>`, so a task never fails to start over a template {src:.harness/engine/modules/task/tasklife.py#L86-L123}.

The `task new` answer, built by `tasklife.attach` and `next_text`, carries `read_first` (`<task>/TASK.md`), `next` (text for the agent: the tier's first step, for a `qa` task of the `light` tier the line that says to deliver, for the full tier or a task with a plan the next step, otherwise how this kind ends, the task the session left open if any, and the domains to name when the knowledge base has some), `made`, `round`, `plan_approved`, `kind`, `tier`, `left_open` and, with target repositories configured, `branch` and `target_repos` {src:.harness/engine/modules/task/tasklife.py#L137-L160} {src:.harness/engine/modules/task/task.py#L210-L218}.

## Task internals: how `task open` picks a task up, and a hand-made folder

`tasklife.open_task` picks up a task that exists, in order: the text is read as a task name (looked up in the tasks folder) or, when it contains a slash, as a path (`task_ops.resolve`); an unknown task is refused; `check_session` applies the same three refusals as `task new` (unknown session, subagent, admin); the task's state before is read; `attach` runs with no kind or tier; `reopened` is true when the state before said `closed`. For a reopened task whose kind is not `dev` or `kb` (`WRITES_BACK`), the answer adds the text "this kind of task has no new round; start a new task from this one with `task fork`" {src:.harness/engine/modules/task/tasklife.py#L177-L193} {src:.harness/engine/core/messages.en.json#L17}.

A hand-made folder with no `task.json` can be opened. `open_task` needs only that the folder exists under the tasks directory. `attach` finds no state, and builds a new one with `kind` and `tier` empty (`""`), round 1, `promote` state `none`, status `open` and a `start` event; no template file is written, so a hand-made folder keeps exactly the files it had. Because the tier is empty, the per-prompt hook text uses the short head (`task.inject.head.plain`, name and round only) instead of the head with kind and tier. The kind can be set later with `task upgrade --kind`, since an empty kind is one of the two kinds that may change {src:.harness/engine/modules/task/task.py#L164-L173} {src:.harness/engine/modules/task/handler.py#L93-L106} {src:.harness/engine/modules/task/tasklife.py#L196-L221}.

`task_ops.attach` is the one function that binds a session to a task; `task new` and `task open` both end in it. Under the session's lock it refuses a session with no state file, a subagent session and an admin session. Under the task's lock, on a task that already has a state: a `promote` state of `partial` is refused (a write-back stopped halfway: the person runs `task recover` first); a state of `done` starts a new round (`archive_round`); otherwise the task is resumed. It then sets `task`, `name`, `status` = `open`, `session_id` and `surface`; records a `new-round` or `resume` event; appends the pick-up to `sessions[]` (the last 100 are kept); sets `waiting` to None; clears `paused` with an `unpause` event; copies `[review]=n` from the prompt that went on to open the task into `review.n` (capped by `review.max_n`, default 5); sets the branch name when target repositories are configured (`feature/<name>` from the ASCII letters and digits of the name, with a fallback when a name has few of them); for the `full` tier makes `DEV/`; and last writes `active_task` into the session's state {src:.harness/engine/modules/task/task.py#L140-L218} {src:.harness/engine/modules/task/task.py#L62-L72}.

`archive_round` starts a new round after a write-back, and it tests only `promote.state == "done"`, not the kind. It writes `CHANGES_r<n>.diff` when the round changed something, renames a non-empty `DEV/` to `DEV_r<n>`, deletes `.task/base`, renames `PLAN.md` to `PLAN_r<n>.md`, appends the round to `rounds[]` (round number, start, plan record, promote record, branch, files, deletes), then sets the round to n+1 and resets `plan` to empty, `promote` to `none` and the branch to empty. The new round therefore has no plan, and the old one cannot be approved again by mistake {src:.harness/engine/modules/task/task.py#L221-L251}.

## Task internals: the tiers and how `task upgrade` raises one

`harness task upgrade` takes exactly one of `--tier {light,medium,full}` or `--kind` (a kind other than `qa`); the parser makes them mutually exclusive and one is required. `--task` is optional: left out, the one open task is used, and several open tasks make the call fail {src:.harness/engine/modules/task/commands.py#L193-L196} {src:.harness/engine/modules/task/task.py#L115-L130}.

`tasklife.upgrade` runs under the task's lock in this order. A task whose status is not `open` is refused. With `--kind`: a task whose current kind is not empty and not `qa` is refused (any other kind change must be a fork); the target tier is the kind's default tier, or the task's current tier when that is the same or higher. With `--tier`: a tier equal to the current one is refused ("already"), a lower one is refused ("a tier only goes up, never down"). Then `add_files` runs for the new tier and kind, the state records the new `tier` and `kind`, a `kind` event notes `<was> -> <kind>` for a kind change, and an `upgrade` event notes `<from> -> <to>` when the tier changed {src:.harness/engine/modules/task/tasklife.py#L196-L221}.

`add_files` in an upgrade skips every path that exists and creates only what is missing, so nothing is deleted, moved or overwritten. The code writes the new `tier` and `kind` into `task.json` and nowhere else: no code in `upgrade` or `add_files` edits the Kind and Tier lines of `TASK.md`, so they keep their old values until the agent edits them. For a `qa` task upgraded by tier only, the answer adds a hint that more files do not make it another kind of work and that the page goes on saying Q&A {src:.harness/engine/modules/task/tasklife.py#L108-L123} {src:.harness/engine/modules/task/tasklife.py#L212-L221}.

`task upgrade` binds no session and is not person-only. It does not call `attach`, so `active_task` is unchanged, and the gate's list of person-only commands does not include it, so the agent may run it itself {src:.harness/engine/modules/task/tasklife.py#L196-L221} {src:.harness/policies/gate.json#L131-L137}.

The tier changes a few things beyond the files. `attach` creates `DEV/` for a task whose tier is `full`; `waiting` adds the reason `req` only for tier `full`; and `next_text` names the next step for tier `full` at once. The gate does not read the tier: the write scope depends on `active_task`, the task's status and the plan's approval only {src:.harness/engine/modules/task/task.py#L205-L206} {src:.harness/engine/modules/task/tasklife.py#L310-L315} {src:.harness/engine/modules/task/tasklife.py#L137-L152} {src:.harness/engine/modules/gate/handler.py#L64-L94}.

## Task internals: kinds, and what "done" means for each

The kind list and default tiers are in `core/tasks.py`: `qa`, `rca`, `design`, `dev`, `test`, `kb`, `other`; default tier `light` for `qa`, `medium` for `rca`, `design` and `other`, `full` for `dev`, `test` and `kb` {src:.harness/engine/core/tasks.py#L20-L23}. What a result must contain for each kind is written in the skill `harness-my-task`, as text for the agent: `qa`, the answer has a source (a look on a server names each command and what it returned); `rca`, a chain of evidence (what was seen, logs, root cause, verification); `design`, options and trade-offs; `dev`, the changes match the approved plan, with a record of self-testing; `test`, cases and results are on disk; `kb`, the source is clear and the change goes through the promote; `other`, no fixed standard, a "Done when" agreed with the person and written in `REQ.md` {src:.github/skills/harness-my-task/SKILL.md#L40-L52}. No code checks any of these contents. `deliver` and the board's buttons check no such thing; the one content check at delivery is a non-empty summary {src:.harness/engine/modules/task/accept.py#L45-L50}.

Kind and the ribbon: the board's stage ribbon (`taskstages.of`) is worked out from files and state at each look, and nothing is kept. `qa` has no ribbon. `rca`, `design` and `other` have two steps, `doing` and `done`; `done` means the task is closed. `dev` and `kb` have `requirement`, `plan`, `developing`, `writeback`, `done` (or, when `DEV/` holds only `DEV/_manual/` and nothing for a repository, `requirement`, `plan`, `developing`, an apply step and `done`). `test` has `guide`, one step per environment, and `done`. The ribbon is a picture: it is wrapped in a try block that returns None on any error, and no check or gate reads it {src:.harness/engine/modules/task/taskstages.py#L1-L15} {src:.harness/engine/modules/task/taskstages.py#L26-L32} {src:.harness/engine/modules/task/taskstages.py#L56-L67} {src:.harness/engine/modules/task/taskstages.py#L261-L280}.

Test kind, the ribbon in detail: the environments are the `## <ENV>` headings of `TEST-GUIDE.md` (a heading of a letter followed by up to 11 letters, digits, `_` or `-`; the template's `## <DEV>` is not one); when the guide names none, `DEFAULT_ENVS` are `DEV`, `IST`, `UAT`. An environment's step is done when the results file for it, `TEST/results-<ENV>*.md`, holds a line `Verdict for <env>: PASS`. `env_of` takes `results-IST.md` as IST's, and `results-IST-run2.md` as IST's too unless the guide has an environment named `IST-RUN2`. The verdict of a file is the last `Verdict for ...: PASS|FAIL|NEEDS MORE` line outside code blocks (what the person pasted sits in a code block and cannot say it); of several files for one environment, the one written last counts. A FAIL flags the step `failed`; the `guide` step is done when `TEST-GUIDE.md` is non-empty, and `done` when every environment is PASS {src:.harness/engine/modules/task/taskstages.py#L28-L32} {src:.harness/engine/modules/task/taskstages.py#L94-L139} {src:.harness/engine/modules/task/taskstages.py#L177-L185}.

Kind and how a task ends: with a target repository configured (`target_mode`), `dev` and `kb` end by the promote and the board's close (see the section on how a task ends). Without target mode `finish_text` gives `dev` and `kb` the same ending as every other kind: the agent writes a summary, runs `task deliver` and stops, and the person accepts. So a development task with no repository to write back to is delivered and accepted, like an RCA {src:.harness/engine/modules/task/task.py#L267-L275}.

Kind and the reviewer: the reviewer subagent's instructions judge the work against `REQ.md`, `PLAN.md` and the files, and name no kind; the Done-when items of `REQ.md` are what is checked, not the kind. The kind decides only what counts as something to check (`has_something`): files under `DEV/` for `dev` and `kb`, a results file under `TEST/results-` for `test`, and any file besides `REQ.md` for every other kind {src:.github/agents/reviewer.agent.md#L44} {src:.harness/engine/modules/task/taskreview.py#L170-L177}.

Kind and the plan: the waiting reason `plan` is skipped for a task of kind `test` (a test task writes nothing back, so a plan it has is not asked for). The hook's next-step text still names a plan when none is written. The plan's approval is read by the gate for `DEV/` writes, and by `task fetch`, `task promote` and `approve-promote`, each of which calls `require_plan` {src:.harness/engine/modules/task/tasklife.py#L289-L294} {src:.harness/engine/modules/task/task.py#L260-L305} {src:.harness/engine/modules/task/task.py#L404-L406} {src:.harness/engine/modules/task/task.py#L636-L637}.

Delivery and unticked steps: `task deliver` and `task close` (from a terminal) are refused while `TODO.md` has steps that are not ticked, unless `--todo-open "<why>"` is given. `todo_left` returns the unticked steps; the refusal lists up to five. The board's Accept and close and Close pass `check_todo=False` and note how many steps were left in `TODO.md` {src:.harness/engine/modules/task/task.py#L338-L361} {src:.harness/engine/modules/task/accept.py#L51-L54} {src:.harness/engine/modules/task/accept.py#L167-L181}.

## Task internals: why 1.1 dropped the Levels, and what guards a task now

Version 1.0 had three Levels, L1, L2 and L3, and the person picked one first each time. The harness design document gives three reasons for dropping them in 1.1: L2 was the only one in use; L3's three-role setup was no better than one agent on a task with a clear requirement, at about 4.5 times the usage and about 6 times the time; and picking a level first was a needless step, and with two sets of rules side by side the agent was unsure and gave wrong explanations {src:docs/05-design.md#L57-L63}. Session state from before 1.1.0 is upgraded by dropping the `level` and `active_request` keys and the modules `task_level` and `request`; the task the session holds stays {src:.harness/engine/core/state.py#L116-L126}.

The two things that decide how a task is guarded now are the cost of a mistake, which code judges from paths and commands, and the task's kind, which decides what "done" means and which files exist {src:docs/05-design.md#L65-L69}. In code the first is the gate: paths (guardrail, command-line-owned, `.git`, target repository, the task folder and `DEV/` before the plan's approval), terminal commands, git commands and calls to outside systems are each classified by the gate's rules, with no per-task choice by the person {src:.harness/engine/modules/gate/handler.py#L1-L15}. The second is the kind: default tier, the wait for a plan (a `test` task is exempt), the ribbon, what counts as a result to check, whether a reopened task is told it has a new round (the text for kinds other than `dev` and `kb` says it has none; the code starts a new round whenever the promote is done) and whether the kind may change (only from empty or `qa`, with `task upgrade --kind`; any other change is a fork) {src:.harness/engine/core/tasks.py#L20-L23} {src:.harness/engine/modules/task/tasklife.py#L196-L221} {src:.harness/engine/modules/task/tasklife.py#L191-L192}.

What survived of L3's extra safety is the person's `[review]=n`. The hook reads `[review]=<digits>` in the words the person typed (the marker regex takes one or two digits; the cap is `review.max_n`, default 5), or the number is set on the task page (`task review set`). With `n` above 0, `task promote --dry-run` calls `taskreview.require` and is refused unless the passes in a row, counted on the files as they are now, reach `n`, or the person waived the checks for that version; with `n` = 0 the check is satisfied at once. Only the person can extend or waive {src:.harness/engine/modules/task/taskreview.py#L44-L67} {src:.harness/engine/modules/task/taskreview.py#L240-L262} {src:.harness/engine/modules/task/taskreview.py#L563-L568} {src:.harness/engine/modules/task/task.py#L911-L928}.

Git commands in the gate: some git commands are never approved, whatever the person says to the gate: `push`, `clean` (a dry run with `-n` or `--dry-run` as its first argument passes), `filter-branch`, `filter-repo`, `update-ref`, `prune`, `reset --hard`, `gc --prune`, `reflog expire` or `delete`, `branch -D`, any force option, and any `gh pr` command. A git command that is a clear read passes; any other git command is refused until the person approves that exact command with `approve-command`. This classification runs only when target repositories are configured (`guard_git` is `found.configured`); the rule that a path inside a `.git` folder is always denied does not depend on it {src:.harness/engine/modules/gate/gitcmd.py#L30-L37} {src:.harness/engine/modules/gate/gitcmd.py#L262-L296} {src:.harness/engine/modules/gate/handler.py#L130} {src:.harness/engine/modules/gate/handler.py#L824}.

The task folder write scope applies only while a session holds an open task (see the section on the gate's write scope). "Open a task first" is text for the agent, not a refusal in code {src:.harness/engine/modules/gate/handler.py#L64-L72}.

## Task internals: how a session is bound to a task (`active_task`)

The binding is one field of the session's state file `.harness/runtime/state/<surface>/<session id>.json`: `active_task`, the repository-relative folder of the task the session holds, or empty. The file's header says it is written by the task command line (`task new`, `task open`, `task close`) {src:.harness/engine/core/state.py#L1-L10}. In code three places write it: `task_ops.attach` sets it to the task (both `task new` and `task open`); `task_ops.close` sets it to None for the session named in the task's `session_id` and `surface`, only when that session's `active_task` still names the task; and a subagent's new session inherits its parent's `active_task` through `claim_child` when its first prompt arrives {src:.harness/engine/modules/task/task.py#L209} {src:.harness/engine/modules/task/task.py#L362-L368} {src:.harness/engine/core/state.py#L303-L354} {src:.harness/engine/hook.py#L100-L103} {src:.harness/engine/hook.py#L113-L115}.

A binding is believed only while its task is open. `tasks.open_of` returns the task only when `task.json` is readable and its status is `open`; the gate does the same before it confines writes; so a session whose `active_task` names a closed task counts as holding no task. The board asks the other way round: `tasklife.held` reads the session state named by the task's `session_id` and `surface` and is true when that `active_task` equals the task; a session that opened another task, a session that closed this one, or a state file that is gone (a reinstall without `runtime/`) is not holding it {src:.harness/engine/core/tasks.py#L100-L106} {src:.harness/engine/modules/task/tasklife.py#L817-L829}.

The binding cannot be faked by the agent's edit tools. `.harness/runtime/**` is both a guardrail path and an admin-locked path, so the edit tools are refused on it in every chat, admin mode included; a terminal command that writes it is refused by the terminal rules, and the person's admin mode does not open it {src:.harness/policies/gate.json#L5-L22}. The session state is written only inside `core/state.py` under a lock (`session()`), by the hook and the task command line {src:.harness/engine/core/state.py#L230-L238}.

How another session picks a task up after the first one breaks: the new chat's session id is new, so it holds no task. The per-prompt hook lists the open tasks (the newest five, `OPEN_TASKS_SHOWN`) and tells the agent to run `harness task open <name>`; the agent, following the skill, runs it. `attach` appends the new session to `sessions[]`, sets `session_id` to the new session and sets the new session's `active_task`. The old session's state file is not touched, so an earlier session whose `active_task` still names the task keeps its binding and its scope; `held` looks only at the newest holder {src:.harness/engine/modules/task/handler.py#L44} {src:.harness/engine/modules/task/handler.py#L129-L142} {src:.harness/engine/modules/task/task.py#L174-L209}. A task whose write-back stopped halfway (`promote.state` `partial`) is refused by `task open` and by `task close` until the person runs `task recover`, which only a person at a terminal or on the board may do {src:.harness/engine/modules/task/task.py#L174-L177} {src:.harness/engine/modules/task/task.py#L354-L356}. `task open` answers with `read_first` (`<task>/TASK.md`) and `next`, the next step {src:.harness/engine/modules/task/tasklife.py#L155-L160}.

Compaction: the harness has no compaction-specific handling. `PreCompact` is a known event name in `core/events.py`, but `.github/hooks/harness.json` registers no hook for it and no module subscribes to it. The state file is looked up by the session id in each hook call, and no step of the harness changes or copies it at a compaction, so the binding and the gate's scope stay as they were as long as the chat reports the same session id. That the id survives a compaction is a property of Copilot; this code does not show it {src:.harness/engine/core/events.py#L5-L18} {src:.github/hooks/harness.json#L1-L112}.

After a compaction the per-prompt injection restores the task's context: at every prompt, `prompt_text` gives the session id rule, the language rule and, for a session that holds an open task, `task_text`: the head (task, round, kind, tier), the next step, the `REQ.md` line, the review count (`n`, passes, checks used and limit) or a note that checks are off, the write scope, the task page address when the board runs, the domain skills, and under autorun the step count {src:.harness/engine/modules/task/handler.py#L93-L126} {src:.harness/engine/modules/task/handler.py#L162-L177}. On VS Code's side the engine drops this context on about a third of prompts (recorded 2026-10-22, in the code's own comment); the `UserPromptTransformed` event comes within moments of `UserPromptSubmit`, and `restored_prompt` appends the saved text to the prompt when its first line is not already in it, only for the same prompt (by a 16-character digest) within 120 seconds {src:.harness/engine/core/state.py#L378-L394} {src:.harness/engine/core/state.py#L50-L51}.

The board shows the size of the chat's context as a bar from the board's link to VS Code. The bar turns amber from `health.context_notice` (50, percent of the window) and a warning tag fires above `health.context_percent` (70); there is a Compact button that sends `/compact` to an idle chat (`/api/compact`, paired browser only), and under autorun the board ends the turn and compacts at `autorun.compact_percent` (70; 0 never) {src:.harness/policies/task.json#L32-L39} {src:.harness/policies/task.json#L72-L79} {src:.harness/engine/modules/task/health.py#L160-L177} {src:.harness/engine/modules/task/boardserve.py#L1444-L1453}.

## Task internals: the state file `task.json`, and why `task list` reads it and not Markdown

Why JSON: the harness design document states the reason: `.task/task.json` is the state for machines to read, `task list` reads it, not Markdown, because progress an agent writes by hand misses ticks and gets things wrong. The conversation is not the handover either, because a conversation is compressed and sessions change; the handover is `TASK.md` (written by the agent for a person or a new session) and the state is the JSON (written by harness code) {src:docs/05-design.md#L100-L108}.

How `task list` reads: `list_tasks` goes through `tasks.folders`, calls `tasks.read` for each, and builds each row from `task.json` fields only (`status`, `kind`, `tier`, `updated_at`, the waiting reason from `waiting()`, `session_id`, `paused`, `autorun`, the checks, the state). `TASK.md` is never parsed for state anywhere in the task module. Without `--all` it drops tasks whose status is not `open`; `--text` prints a table, `--watch` redraws it {src:.harness/engine/modules/task/tasklife.py#L858-L898} {src:.harness/engine/modules/task/commands.py#L66-L71}.

`TASK.md` and the JSON can disagree, and the list believes the JSON. The only code that writes `TASK.md` is `accept.mark_done`, which replaces the Status and Updated lines (found by their labels, in either language, when the file has them as the template makes them) after `task deliver`, an accept or a promote close; it never reads the Status line back, and it returns False and changes nothing when the lines are not there. A `TASK.md` whose Status says "done" while `task.json` says `open` is listed as open {src:.harness/engine/modules/task/accept.py#L80-L101}.

A `task.json` that cannot be parsed gives the state `broken` with no Markdown fallback: `list_tasks` finds `tasks.read` returning None, `tasks.damaged` is true (the file is there, the read failed), the row has status `new`, empty kind and tier and the state `broken`, shown as "task file damaged"; the board's action text says only a person can restore it from a copy {src:.harness/engine/modules/task/tasklife.py#L862-L870} {src:.harness/engine/core/tasks.py#L92-L97} {src:.harness/engine/core/messages.en.json#L393}.

Writing: `task_ops.locked` locks the file, reads the data, lets the caller change it, sets `updated_at` and writes the whole file with `atomic_write` (a temporary file, then a replace; on Windows the replace is tried again for a second). `note` appends one line to `events[]` (time, round, what, detail, optional facts) and keeps the last 200; `sessions[]` keeps the last 100. `set_waiting` and `note_doc_write` write under the lock without touching `updated_at`. The fields: path, name, kind, tier, status, round, `round_started_at`, `session_id`, `surface`, `sessions[]`, `target_mode`, `branch`, `targets`, `target_files`, `deletes`, `req`, `plan`, `promote`, `waiting`, `paused`, `deliver`, `handoff`, `review`, `allow_conn`, `links`, `autorun`, `events[]`, `rounds[]`, `doc_writes[]` (the last 100 moments `REQ.md` or `PLAN.md` was written, for the report), `forked_from` and `chat` {src:.harness/engine/modules/task/task.py#L38-L40} {src:.harness/engine/modules/task/task.py#L82-L98} {src:.harness/engine/core/state.py#L129-L146} {src:.harness/engine/modules/task/handler.py#L375-L388}.

Marks stored in `task.json`: several of the facts a task's state is told from are stored, and all are written by harness code. `waiting` is `{since, why}` (the Stop hook's mark, `asking`, `cancelled`, `go-*`); `deliver` is `{at, summary, skipped, todo_open}`; `handoff` is `{what, env, since, detail}`; `paused` is `{since, by}`; `promote.state` is `none`, `dry_run`, `done` or `partial`, with `approved_plan_sha256` once the write-back is approved; `review` holds `n`, `rounds[]`, `extra` and `waived`. The agent can cause some of them (`task deliver` writes `deliver`; `task handoff` writes `handoff`), the person causes others (`task pause`, the approvals), and no edit tool of the agent can write the file {src:.harness/engine/modules/task/tasklife.py#L460-L472} {src:.harness/engine/modules/task/tasklife.py#L499-L517} {src:.harness/engine/modules/task/accept.py#L60-L64}.

The requirement and the prompt: `REQ.md` holds the requirement as the agent understands it; the agent writes it from the conversation and the person confirms it. The person's exact words are not kept as the requirement, because a prompt may leave things out and the requirement changes over several turns (the design document says so); the harness keeps the digest of what the person confirmed (`req.confirmed_sha256`) in `task.json` {src:docs/05-design.md#L109} {src:.harness/engine/modules/task/task.py#L601-L612}.

The `TASK.md` reminder at Stop: `task_file_stop` blocks a Stop once per prompt when edit or create tools wrote a file inside the task folder in this prompt (`relay.wrote`) and `TASK.md` was not among the files written (`relay.task_file`); `relay` is reset at each prompt of the person. It returns nothing, and no block, when the policy `task_file_reminder` is false (default true), when `TASK.md` does not exist, when `task.json` has a `deliver` (because `task deliver` already wrote the Status line), or when the reminder was already given in this prompt. It sees only writes made by edit and create tools, not terminal writes, and checks that `TASK.md` was written, not that it is right {src:.harness/engine/modules/task/handler.py#L350-L372} {src:.harness/engine/modules/task/handler.py#L423-L435} {src:.harness/policies/task.json#L7}.

## Task internals: how the board state of a task is worked out

The state of a task is not stored: it is worked out each time from facts by code (`list_tasks`, `waiting`, `at_work`, `held`, `state_of`), not kept by a skill or set by the agent. `list_tasks` builds each row in this order: a folder with no readable `task.json` becomes a row with state `broken` (file present, unreadable) or `new` (no file), set before `state_of` is called; a task that is not open is dropped unless `--all` is given; for an open task that is not paused, `waiting()` gives the waiting reason; `held()` says whether a session still holds it; `at_work()` says whether the agent is in the middle of a turn; and `state_of` makes the one state from five facts: status, whether paused, the waiting reason, held and at work {src:.harness/engine/modules/task/tasklife.py#L842-L898}.

`state_of(status, paused, why, is_held, is_active)` tests in this order, first that holds: status `new` gives `new`; a status other than `open` gives `closed`; a paused mark gives `paused`; at work gives `working`; a waiting reason gives `waiting`; otherwise `quiet` when a session holds the task and `unheld` when none does. So `working` comes before `waiting`: a plan that waits for approval does not show as waiting while the agent is still in a turn {src:.harness/engine/modules/task/tasklife.py#L842-L855}.

The eight states and their labels: `broken` ("task file damaged"), `waiting` (the board shows the reason's text, for example "the plan waits for your approval", not the word), `working`, `quiet`, `unheld` (the label is "no session"), `paused`, `closed` and `new` (the label is "not started"). `quiet` is a held task with nothing it waits for and no recent activity: the session holds it, its log is older than the activity limit, and no mark says it stopped {src:.harness/engine/modules/task/tasklife.py#L814} {src:.harness/engine/core/messages.en.json#L389-L393} {src:.harness/engine/core/messages.en.json#L1862-L1863}.

The display order differs from the test order. The rows are sorted twice, so the result is by state in the order of `STATES` (`broken`, `waiting`, `working`, `quiet`, `unheld`, `paused`, `closed`, `new`), within a state by the longest wait first (`waited_s`, descending), and ties by the newest `updated_at` {src:.harness/engine/modules/task/tasklife.py#L892-L893}.

A paused task gets no waiting reason: `list_tasks` skips `waiting()` for a task with a paused mark, so a paused task shows no reason, and `waiting_now` returns None for one {src:.harness/engine/modules/task/tasklife.py#L673-L681} {src:.harness/engine/modules/task/tasklife.py#L873-L875}. The time a person had a task paused is taken out of every wait: `waited_since` subtracts the time between a `pause` event and the next `unpause` or `close` from the length of a wait that began before or during the pause {src:.harness/engine/modules/task/tasklife.py#L411-L450}.

The board has one override the command line does not see: `apply_ask`. For an open task that is not paused, when the board's link to VS Code reports that the task's chat waits for the person to allow a command or answer a question, the board puts the row in state `waiting`, with a waiting reason of `confirm` or `question` and `active` false; it comes before everything else the task waits for. `apply_ask` is called only from the board's row builder (`taskboard`), so `task list` in a terminal does not show it {src:.harness/engine/modules/task/tasklife.py#L348-L374} {src:.harness/engine/modules/task/taskboard.py#L148-L152}.

One more thing happens on the board server and not in `state_of`: the board server closes a promoted `dev` or `kb` task by itself when the agent has stopped and nothing else waits. The feature file 11 Task says a task closes only when a person accepts it or closes it, with this one exception; the conditions are in the section on how a task ends {src:.harness/engine/modules/task/accept.py#L186-L218}.

## Task internals: how "working" is decided (`at_work`)

`tasklife.at_work(root, data, why)` is true (state `working`) only when all of these hold; the first that fails makes it false. (1) The task's status is `open`, it is not paused, it has no stored `waiting` mark of any kind and no `handoff` mark. (2) A session still holds the task (`held`) and either made a hook call lately or has a subagent running for it. (3) The agent is not sitting in `harness wait --approval` on a held outside call of this task (`outbox.agent_waiting`: it makes no call and no model run then, so the task waits for the person). (4) The reason, when the caller has it, is not `cancelled`; when the caller has none, `cancelled_at` is read from Copilot's own record {src:.harness/engine/modules/task/tasklife.py#L793-L805}.

"Made a hook call lately": `active_now` reads the modification time of the session's hook log, `.harness/runtime/logs/<surface>/<session id>.jsonl`, and is true when it is no older than `board.active_seconds` (default 300 seconds, from `.harness/policies/task.json`); a log file that cannot be read gives false. The log's content is not read, only its time, so no hook call means no change, and a long tool call that makes no hook call looks idle after 300 seconds {src:.harness/engine/modules/task/tasklife.py#L776-L787} {src:.harness/engine/core/logs.py#L35-L36} {src:.harness/policies/task.json#L40-L46}.

"A subagent running": `subagent_running` reads the session's state, `subagents.active`, and is true when an entry's start time is within `SUBAGENT_ACTIVE_TTL_SECONDS` (1800 seconds); an older entry is not believed, so a missing SubagentStop does not leave a task "working" for ever. The Stop event also clears the list {src:.harness/engine/modules/task/tasklife.py#L832-L839} {src:.harness/engine/core/state.py#L39} {src:.harness/engine/core/state.py#L283-L285}.

Stop mark and quiet: a held session whose log has been quiet for more than 5 minutes and that left no stop mark is `quiet`, not `working`, because `active_now` is false and the waiting reason is empty. A session that stopped leaves the mark (`waiting`), and any mark makes `at_work` false at once, however fresh the log is. A cancelled turn leaves no Stop hook, so the person's cancel is read from Copilot's record: `copilot_events.cancelled_at` returns the time of an `abort` row in the tail of the session's events file with no newer `user.message` or `assistant.turn_start`, ignoring rows of subagents {src:.harness/engine/core/copilot_events.py#L447-L472} {src:.harness/engine/modules/task/tasklife.py#L398-L408}.

Why it matters to the person's buttons: `require_idle` refuses `task pause`, `task close` and `task autorun on` from a terminal while the task is at work (the message says the agent is in the middle of a turn; `--force` goes on), and the board's `idle` check refuses its actions the same way, with the host's own word that the bound chat runs no turn winning over the log. The approvals do not wait, since each is bound to the digest of what the person saw {src:.harness/engine/modules/task/tasklife.py#L808-L811} {src:.harness/engine/modules/task/boardserve.py#L685-L696}.

## Task internals: the waiting reasons, in the order `waiting` checks them

`tasklife.waiting(root, task, data)` returns `{why, since}`; `why` is empty when the task waits for nothing. The first condition that holds wins; the rest are not looked at. The order is by how much a reason blocks: a question the agent asked, a broken write-back, the plan, the write-back, used-up checks, a delivery to accept, the requirement, an outside call, a hand-over, files to commit, then the stored marks, then a cancel {src:.harness/engine/modules/task/tasklife.py#L276-L338}.

In code order the reasons and their conditions are as follows. (1) `asking`: the stored mark `waiting` has `why` = `asking` and a `since`, and the person has not cancelled since (no cancel newer than `since`); it comes first, and held calls can still be approved meanwhile. (2) `recover`: `promote.state` is `partial`; since the last `promote-partial` event. (3) `plan`: the kind is not `test`, `PLAN.md` exists and `plan_approved` is false; since `PLAN.md`'s modification time. (4) `promote`: `promote.state` is `dry_run` and the promote record has no `approved_plan_sha256`. (5) `review`: checks are on (`n` above 0), there is a result to check, the checks are not waived, passes are fewer than `n`, no check is pending, and the checks used have reached the limit (`n` plus `extra_checks`, default 2, plus the person's `extra`). (6) `accept`, first form: the stored mark has `why` = `accept` and a `since`, `deliver` is a dict, the status is `open` and no outside call waits. (7) `req`: the tier is `full`, the plan is not approved and `req_state` is `open` or `changed`; since `REQ.md`'s modification time, so it waits since the agent wrote it, not since the task opened. (8) `outbox`: a held outside call exists that the agent waits for. (9) `tests` or `run`: the `handoff` mark has `what` in those two words. (10) `commit`: `promote.state` is `done`, the status is `open` and the write-back left a repository with no commit (`commitmsg.to_commit`). Then, if a stored mark with a `since` exists: (11) a `go-*` mark; (12) `cancelled` kept as a mark; (13) `accept`, second form; (14) `autorun`: the autorun state is `off`, its `stopped` record is not later than the mark and its reason is not `person`; (15) `stopped`. Last, (16) `cancelled`, read from Copilot's record. The task's `since` is turned into a wait length by `waited_since`, less paused time {src:.harness/engine/modules/task/tasklife.py#L282-L338} {src:.harness/engine/modules/task/taskreview.py#L161-L177}.

Condition details. `plan` is skipped for `test` (B65 in the code's comment: a test task writes nothing back). `promote` waits for the person's approval of the write-back plan after `task promote --dry-run`. `review` is the only reason that reads the reviewer's records, in a try block so that one task's broken checks never make the list fail. `req` covers only the full tier. `handoff` reasons are the two words in `HANDOFFS`: `tests` (the agent handed the tests of an environment to the person) and `run` (a run before the write-back). `commit` means the files were written back and still need the person's commit; a knowledge base's write-back commits itself and is not counted. The agent clears a hand-over with `task handoff clear`, which for `run` first requires the result to be saved in `RUNS/<ENV>/` {src:.harness/engine/modules/task/tasklife.py#L270-L273} {src:.harness/engine/modules/task/tasklife.py#L650-L665} {src:.harness/engine/modules/task/commitmsg.py#L115-L118}.

The `go-*` marks: `GO_MARKS` are `go-req`, `go-plan`, `go-promote`, `go-recover` and `go-review`; each is written when the person approves something (`confirm-req` with no plan yet and no delivery; `approve-plan`; `approve-promote`; `recover`; `review extend`, `waive` or `dismiss`) and means "an approval was given and the agent has not been told". The next prompt of the person takes the mark away {src:.harness/engine/modules/task/tasklife.py#L273} {src:.harness/engine/modules/task/task.py#L471} {src:.harness/engine/modules/task/task.py#L596-L597} {src:.harness/engine/modules/task/task.py#L1023} {src:.harness/engine/modules/task/task.py#L1059} {src:.harness/engine/modules/task/taskreview.py#L507} {src:.harness/engine/modules/task/taskreview.py#L527} {src:.harness/engine/modules/task/taskreview.py#L555}.

The second form of `accept` is narrower than it looks. It is reached only when no outside call waits (an outside call returns `outbox` earlier) and the first form did not hold, that is, the mark says `accept` but `deliver` is not a dict or the status is not `open`. In normal use the first form is the one that fires. A held outside call that the agent waits for outranks `accept`: the task shows `outbox` until the call is decided {src:.harness/engine/modules/task/tasklife.py#L306-L317} {src:.harness/engine/modules/task/tasklife.py#L328-L329}.

Held calls count only when the agent waits for them: `waited_calls` takes the calls of the task that wait in the outbox and drops those the agent moved on from (`outbox.moved_on`: the agent neither runs `harness wait --approval` on the code nor was told to end its turn on it, within a short grace). Such a call stays in the outbox and the person may still approve or dismiss it, but the task is not "waiting for you" because of it {src:.harness/engine/modules/task/tasklife.py#L341-L345} {src:.harness/engine/core/outbox.py#L184-L218}.

## Task internals: the Stop hook's mark, the delivery and the "to accept" mark

The Stop hook's mark and "to accept" are one stored mark, `waiting`, with different `why` values. `task deliver` (`accept.deliver`) writes only the `deliver` field of `task.json`: `{at, summary, skipped, todo_open}`. It does not set the mark. When the agent really stops, the task module's Stop handler calls `mark_waiting`, which calls `tasklife.set_waiting` with `why` = `accept` when `deliver` is present and `why` = `stopped` when it is not. `tasklife.waiting` reports `accept` when that mark, an open status and `deliver` are all present and no held call waits {src:.harness/engine/modules/task/accept.py#L9-L10} {src:.harness/engine/modules/task/accept.py#L60-L66} {src:.harness/engine/modules/task/handler.py#L486-L499} {src:.harness/engine/modules/task/tasklife.py#L306-L309}.

`task deliver` checks, in order: the task resolves; the summary is not empty (it keeps line breaks, cut at 1500 characters, `SUMMARY_CHARS`); no steps of `TODO.md` are unticked, unless `--todo-open "<why>"` is given; then, under the lock, the task is open; and a `dev` or `kb` task whose `promote.state` is `done` is refused (the promote is the acceptance). It then stores `deliver` (`--skipped` lines, at most 6 of 300 characters, for an environment the person skipped; `todo_open` cut at 300 characters, when steps were left), adds a `deliver` event, writes the Status and Updated lines of `TASK.md` itself (so the Stop hook has no `TASK.md` reminder to give; that reminder was one extra turn for every delivery), and marks held calls the agent never waited on as left behind (`outbox.agent_left`), so the task shows "to accept" and not "waits for your approval". The summary can also be given as a file inside the task folder (`--summary-file`) {src:.harness/engine/modules/task/accept.py#L25-L28} {src:.harness/engine/modules/task/accept.py#L45-L68} {src:.harness/engine/modules/task/commands.py#L136-L146} {src:.harness/engine/modules/task/commands.py#L386-L390}.

When the Stop mark is set, case by case in `on_stop`: for a subagent session or an admin session the handler does nothing; for a session with no open task it does nothing; at the end of a `/harness-ask` question turn (`in_ask_turn`) `end_ask_turn` leaves what the task waited for as it was, and puts the plain mark only when the task waits for nothing and is not paused; in autorun, `autorun_stop` may block the Stop to push the agent to the next step (no mark); when the run stays on after the stop cap or a pit stop, the mark is set with no block; when `stop_hook_active` is true (the second Stop after a block) the mark is set; otherwise the three reminders (`review_stop`, `task_file_stop`, `write_back_stop`) and then the knowledge-base offer are tried, and a Stop that one of them blocks sets no mark; a Stop that none blocks sets the mark. So the mark is set only on a real stop {src:.harness/engine/modules/task/handler.py#L599-L626} {src:.harness/engine/modules/task/handler.py#L221-L230}.

What takes the mark away: `set_waiting(root, task, None)` stores no mark, and it also pops `deliver` from the state: it is the only place a delivery is withdrawn. Three things call it. First, the person's next normal message: `on_user_prompt` runs `mark_waiting(ctx, data, False)` when the task has a `waiting` mark or a `deliver`, which is `set_waiting(None)`; this includes a message sent as Not yet and a reply typed in the board's reply box. Second, the board's own `wake` (an answer sent for the person's decision), `send` and `say` call `set_waiting(None)` after the message was handed to the chat, so the card goes at once, not when the hook of the new turn runs. Third, closing the task, whether by Accept and close, by Close or by `task close`, ends it {src:.harness/engine/modules/task/tasklife.py#L460-L472} {src:.harness/engine/modules/task/handler.py#L262-L263} {src:.harness/engine/modules/task/boardserve.py#L929-L944} {src:.harness/engine/modules/task/boardserve.py#L1270-L1285} {src:.harness/engine/modules/task/boardserve.py#L1303-L1325}.

What does not take the mark away. A message from a subagent session, a reason the harness fed back after a blocked Stop (`event.continuation`) and a `/harness-ask` question turn do not clear it: `on_user_prompt` returns early for them. A question the agent asks with its ask tool (`ask_user`, `askuserquestion`) and its answer leave the task still to accept: `note_asking` sets the mark `asking` before the tool call, and after it returns, when a `deliver` exists, puts the mark back to `accept` with the delivery's time, else removes it. `task open` sets `waiting` to None directly in `attach`, and does not pop `deliver` {src:.harness/engine/modules/task/handler.py#L233-L244} {src:.harness/engine/modules/task/handler.py#L505-L527} {src:.harness/engine/modules/task/task.py#L187}.

Ranking: `accept` is outranked by `asking`, `recover`, an unapproved plan, a write-back dry run waiting for approval, used-up checks and a held outside call the agent waits for; it is shown before the unconfirmed-requirement wait (`req`) and the rest. The card for "to accept" (`accept.view`) is built only when the status is `open`, the mark's `why` is `accept` and `deliver` is a dict {src:.harness/engine/modules/task/tasklife.py#L276-L338} {src:.harness/engine/modules/task/accept.py#L71-L77}.

For `dev` and `kb` tasks the promote is the acceptance and no delivery is used: `deliver` is refused once the promote is done, and the board closes the task (`accept.sweep`), described in the next section {src:.harness/engine/modules/task/accept.py#L1-L11} {src:.harness/engine/modules/task/accept.py#L58-L59}.

## Task internals: how a task ends, and why the agent cannot close one

The agent cannot close a task because the harness takes closing as the person's acceptance. The reasons the code states: closing voids the task's held outside calls (they can never be approved or run) and releases the session, so it is a person's call; and the "close the task?" question would cost the agent a turn, while Accept and close on the board closes the task with no chat and no tokens. The gate has a deny rule for `harness task close` in the agent's terminal commands, with a message that tells the agent to run `task deliver` and stop {src:.harness/engine/modules/task/accept.py#L1-L8} {src:.harness/policies/gate.json#L138-L144}.

The gate does not read the command line as plain text. `harnesscmd.py` (since 1.7.38) reads each harness call as the shell would: it takes the quotes away and puts variables the line set in, so `harness task 'close'`, `harness task cl''ose`, `C=close; harness task $C` and `echo close | xargs harness task` are all the same command and are refused. A call whose words cannot be read (a variable the line did not set, a command inside a word, arguments on a pipe, `xargs` or `find -exec` with the harness, a one-line interpreter that starts it) is refused, with the way to write the command out in full. It reads the same through `bash -c`, `pwsh -Command`, `eval` and a here-document {src:.harness/engine/modules/gate/harnesscmd.py#L1-L8} {src:.harness/engine/modules/gate/harnesscmd.py#L38-L66}. The command itself has no check that a person runs it: a script the agent writes and runs is checked only for guardrail paths. `close_task` refuses a person at a terminal while the agent is at work (unless `--force`), and `task.close` refuses unticked steps of `TODO.md` unless `--todo-open` is given {src:.harness/engine/modules/task/commands.py#L125-L133}.

What `task_ops.close` does: resolve the task; refuse when `TODO.md` has unticked steps and no `--todo-open` was given (the board passes `check_todo=False`); refuse when `promote.state` is `partial`; set status `closed` and note a `close` event with the reason and the count of unticked steps; release the session (set its `active_task` to None) when it still names the task; void the task's held outside calls (`outbox.void_for_task`), noting a `void` event; save the chat's rounds to `.task/transcript.jsonl`; and write the report. A failure of the transcript or the report does not undo the close {src:.harness/engine/modules/task/task.py#L345-L398}.

How each kind ends in code. `dev` and `kb` with a target repository: the promote is the acceptance; after it the board closes the task (below). Every other kind, and `dev` and `kb` without a target repository: the agent runs `task deliver`, and the person accepts with **Accept and close** or closes with **Close**. `qa` is included: `DELIVER_KINDS` lists every kind, and the skill says a look is delivered and accepted. The command-line help for `task deliver` still says "not for a Q&A task (it closes itself)", which the code does not do {src:.harness/engine/modules/task/accept.py#L25} {src:.github/skills/harness-my-task/SKILL.md#L88-L99} {src:.harness/engine/modules/task/commands.py#L386}.

Accept and close (`accept.accept`, board action `accept`): refused unless `tasklife.waiting` is `accept` ("not waiting for acceptance"). It lists the task's held outside calls; when any wait and the person has not said yes to void them (`void`), or a call came after the list the page showed (`seen`), it is refused with the count. Then it closes the task with `check_todo=False` (the unticked steps are noted in `TODO.md`, using the delivery's `todo_open` words when there are some) and writes the Status line "accepted". The board's `idle` check applies first, so it is refused while the agent is at work. There is no `task accept` command; accepting is a board action only {src:.harness/engine/modules/task/accept.py#L167-L181} {src:.harness/engine/modules/task/boardserve.py#L685-L696} {src:.harness/engine/modules/task/boardserve.py#L759-L765}.

Close on the board (`Board.close`): any open task, the paired browser, no typed code; `idle` first; the same held-call confirmation; `check_todo=False`; the person's words from the dialog become the reason and the note in `TODO.md` {src:.harness/engine/modules/task/boardserve.py#L696-L711}.

Not yet: the card's second button opens the board's reply box; what the person writes there reaches the chat as a message, so the next-message rule above takes the mark and the delivery away, and the agent goes on from the person's words and delivers again {src:.harness/engine/modules/task/accept.py#L1-L8} {src:.harness/engine/modules/task/handler.py#L262-L263} {src:.github/skills/harness-my-task/SKILL.md#L95}.

The board's own close of a promoted task: `accept.sweep` returns the names of the tasks it closed. A candidate is an open task with kind `dev` or `kb` and `promote.state` `done`. `promoted_and_quiet` requires all of: status `open`, kind `dev` or `kb`, promote `done`; autorun not `on`; not paused; no `handoff`; the stored mark has `why` = `stopped` (the agent ended its turn); the task is not at work; and `waiting()` is empty, `stopped` or `commit` (`QUIET_WAITS`), so files still to commit do not hold the close. Any other reason, for example `asking`, `review`, `outbox` or `recover`, keeps it open. There is no check of `TODO.md` here. The task is closed with a reason that says it was closed because of the promote, and its Status line is written as promoted {src:.harness/engine/modules/task/accept.py#L186-L218}.

When the sweep runs: only inside a running board server. `serve` starts a thread (`start_sweeper`) that calls `close_promoted` every `SWEEP_EVERY` (5 seconds), which also runs when a page asks for the rows; a person at a terminal gets the server with `task board`, and `task board --serve` also starts it. With no served board nothing calls `sweep`, so a promoted task stays open. The server needs the person's start (`person("task board --serve")`) {src:.harness/engine/modules/task/boardserve.py#L434-L458} {src:.harness/engine/modules/task/boardserve.py#L2307-L2331} {src:.harness/engine/modules/task/commands.py#L92-L100}.

## Task internals: how `task fork` copies a finished task into a new one

`harness task fork <new name> --from <old> --kind <kind> --session-id <id> [--tier <tier>]` needs the new name, `--from`, `--kind` and `--session-id`; `--tier` defaults by kind. The old task is found with `task_ops.resolve` and must have a readable `task.json`: otherwise the call stops with "there is no task to fork from". The old task may be open or closed; its status is not checked {src:.harness/engine/modules/task/commands.py#L174-L181} {src:.harness/engine/modules/task/taskfork.py#L102-L106}.

The new task is made like `task new`: `fork` first plans the copy (`plan`), then calls `tasklife.new`, which refuses an existing name before anything is copied and binds the calling session to the new task. Then the files are copied into `REF/from-<old>/` of the new task; `FORK.md` is written there; the new task gets `forked_from` = the old task's folder and a `fork-from` event; and the old task gets one `fork` line in its history and nothing else {src:.harness/engine/modules/task/taskfork.py#L102-L143}.

What is copied (`why_left` returns an empty reason): the old task's `REQ/`, `REF/`, `RUNS/` and `TEST/` folders (from `TEST/` only the `.md` files), every top-level `.md` file except `TASK.md` and `TODO.md` (so `REQ.md`, `PLAN.md`, `LOG.md`, `RCA.md`, `DESIGN.md` and the others), and `CHANGES.diff`. A file over 2 MB (`MAX_FILE_BYTES`) is not copied, and neither is any file once the total would pass 20 MB (`MAX_TOTAL_BYTES`); these are listed in `FORK.md` as too large {src:.harness/engine/modules/task/taskfork.py#L24-L33} {src:.harness/engine/modules/task/taskfork.py#L40-L77} {src:.harness/engine/modules/task/taskfork.py#L113-L124}.

What is deliberately not copied, with the reason `FORK.md` gives: `TASK.md` and `TODO.md` (the old task's state), `.task/` (state), `PROMOTE-PLAN.diff` (the old write-back plan), `DEV/` and `READ/` (code: what changed is in `CHANGES.diff` and the promote put it on a branch), `SNAPSHOT/` and `REVIEW/` (the old checks and snapshots), `DEV_r<n>/`, `PLAN_r<n>.md` and `CHANGES_r<n>.diff` (earlier rounds), any other folder and any top-level file that is not `.md` (not a document of the task), non-`.md` files of `TEST/`, and symlinks (a link, not a file), including a symlink inside a copied folder. Files are copied with `copyfile`, not moved: the old task's report, checks and history still point at its own files, and a closed task may be moved out of the repository later {src:.harness/engine/modules/task/taskfork.py#L1-L10} {src:.harness/engine/modules/task/taskfork.py#L29-L33} {src:.harness/engine/modules/task/taskfork.py#L58-L77}.

`FORK.md` says where the copy came from (old and new task and the time), the kinds (`old -> new`), how the old task stood (kind, tier, status, round; the repository, branch, base commit and commit of its write-back, or that it was not written back; its checks: passes, `n`, used and last verdict), the files copied and the files not copied with a reason for each {src:.harness/engine/modules/task/taskfork.py#L80-L99} {src:.harness/engine/modules/task/taskfork.py#L125-L134}.

What the skill `harness-task-fork` asks of the agent (text, not code): find the old task and the new kind (ask once with numbered options when the kind is unclear); run the command; read `REF/from-<old>/FORK.md` first, then the files that matter for the pair of kinds; write the new `REQ.md` from those files and from what the person asked now, and leave the confirmation line to the person; go on as for any task of that kind; do not ask whether to close the old task. When `CHANGES.diff` and the old `REQ.md` disagree, the skill says to write the new requirement from the diff and `LOG.md` and tell the person. Only a `qa` task can change its kind with `task upgrade --kind`; every other change of kind is a fork {src:.github/skills/harness-task-fork/SKILL.md#L21-L40}.

## Task internals: how rewind takes and uses a restore point

When a restore point is taken: `on_user_prompt` calls `rewind.take(root, task, session)` for each message of the person in a session that holds an open task, after it has cleared the waiting mark. No point is taken for an admin session (`data` is None there), for a subagent's message, for a reason the harness fed back after a blocked Stop (`event.continuation`; for that, `note_harness` adds a point of kind `harness` with no files, so the page knows the message is not the person's), or for a `/harness-ask` question turn, which returns before any of this. A point that cannot be taken never holds up the message {src:.harness/engine/modules/task/handler.py#L233-L272} {src:.harness/engine/modules/task/rewind.py#L153-L164}.

How a point is stored: `.task/rewind/points.json` is the index (`seq`, `at`, `session`, `kind`, `round`; kinds `prompt`, `before` and `harness`); `.task/rewind/points/<seq>.json` is one point's manifest: the head, `files` (relative path to `{sha, size, mtime}`, with `big: true` instead of `sha` for a file too large to keep) and `dirs` (every folder walked, empty ones too); `.task/rewind/objects/<first two characters of sha>/<sha>` holds each content once. A file whose size and modification time equal the newest earlier point's, and whose object still exists, is not read again. Links are not followed. A file that cannot be read (locked on Windows) is left out of that point. Everything under the task folder is kept except the top-level folders `.task`, `req`, `ref`, `inbox`, `snapshot`, `review` and `_deleted` (compared without case); `REQ.md` itself is a file and is kept, only the `REQ/` folder is skipped {src:.harness/engine/modules/task/rewind.py#L30-L38} {src:.harness/engine/modules/task/rewind.py#L55-L79} {src:.harness/engine/modules/task/rewind.py#L112-L150}.

Limits and pruning: the policy `board.rewind` in `.harness/policies/task.json` has `points` (default 30; 0 switches rewind off, and `take` returns None) and `max_file_mb` (default 20; a larger file is listed but its content is not kept). After each point `prune` keeps the newest `points` points of the person's messages and the `before` points newer than the oldest of them, deletes the other manifests, and deletes every object no kept manifest names {src:.harness/engine/modules/task/rewind.py#L41-L48} {src:.harness/engine/modules/task/rewind.py#L167-L194} {src:.harness/policies/task.json#L49}.

What is never rewound: everything outside the task folder (a terminal write elsewhere, the files a promote wrote into a target repository); the task's own state in `.task/`; the person's `REQ/`, `REF/` and `INBOX/`; `REVIEW/` and `SNAPSHOT/`; and `_deleted/`. The restore moves files that came later into `_deleted/rewind-<time>/` and deletes nothing {src:.harness/engine/modules/task/rewind.py#L1-L12} {src:.harness/engine/modules/task/rewind.py#L306-L338}.

Matching a chat message to a point: the board gives the time of the message; `point_for` takes the nearest point of the wanted kinds whose time lies from 10 seconds before to 30 seconds after it (`MATCH_BEFORE`, `MATCH_AFTER`). `why_not` says why a task cannot go back to that point: `none` (no point), `closed` (the task is not open), `chat` (the point belongs to another session), `round` (an earlier round), `promote` (a `promote` or `promote-partial` event at or after the point's time); empty means it can. The board's rewind action accepts only points of kind `prompt`; its preview asks the link to VS Code how many turns would go; the act step puts the files back and then cuts the chat before that turn, and refuses when the chat has an active turn or the turn is not found. A `rewind` event is noted in `task.json` {src:.harness/engine/modules/task/rewind.py#L203-L225} {src:.harness/engine/modules/task/boardserve.py#L1608-L1646} {src:.harness/engine/modules/task/vslink.py#L1109-L1140}.

The preview and restore: `preview` compares the point with the folder now. `back` lists files to write as they were; `removed` lists files that came later (moved aside); `lost` lists files that cannot come back, because they were too large when the point was taken (and changed since) or their stored content is gone (pruned): these are reported and left as they are. It also says `plan: lost` when the plan is approved now and `PLAN.md` goes back to another text, and `req: lost` when the requirement is confirmed now and `REQ.md` goes back to a text that is not confirmed, so each waits for the person again. `restore` first takes a point of kind `before`, then moves, writes and re-creates folders (a folder the later files leave empty goes only when it was not there then) {src:.harness/engine/modules/task/rewind.py#L249-L338}.

Why a rewound plan is no longer approved: the plan's approval is a record in `task.json` (`plan.approved_sha256` and `plan.req_sha256`), and `plan_approved` is true only when the digest of the `PLAN.md` on disk equals `approved_sha256` and the requirement digest is unchanged. A rewind puts `PLAN.md` back to the text it had at the point; when that text is not the one that was approved, the digests differ, `plan_approved` is false, the gate closes `DEV/` again to the edit tools, and `waiting` reports `plan` {src:.harness/engine/core/tasks.py#L109-L164} {src:.harness/engine/modules/task/rewind.py#L277-L284}.

## Task internals: why rewind keeps the task's state out of the restore point

The task's approvals and checks are bound to file contents, not copied into a restore point. `rewind.py` reads `task.json` and never writes it (only the board's act step adds a `rewind` event afterwards), so a rewind leaves approvals, events, check records and the promote record as they are. Each of those is a digest compared with the files each time: the plan (`approved_sha256`, `req_sha256`), the requirement (`confirmed_sha256`), the write-back (`plan_sha256`, `approved_plan_sha256`), the independent checks (the digest of the result files at each check, `waived.digest`) {src:.harness/engine/modules/task/rewind.py#L9-L11} {src:.harness/engine/core/tasks.py#L122-L164} {src:.harness/engine/modules/task/taskreview.py#L240-L262}.

Because of that, rewind needs no special logic. An agent's edit, a terminal write, a person's manual edit and a rewind all change files, and all go through the same digest comparison; `plan_approved`, `req_digest` and the check digest do not know which of them changed the file. If the state were part of the restore point, every one of these records would need its own restore rule, and a restored record could say "approved" about a file that is no longer what was approved {src:.harness/engine/core/tasks.py#L159-L164} {src:.harness/engine/modules/task/rewind.py#L1-L12}.

A rewind also cannot reset what must not be resettable. The check budget (`review.rounds[]` counted by `used`, the limit of `n` plus `extra_checks` plus `extra`), the person's waiver, the promote state and the held calls live in `task.json` or the outbox, outside the restore point; if they were restored, going back would hand out fresh checks. Because `approved_sha256` is never erased, a plan the person approved stays approved for the exact text they approved: if a later point holds that text, the approval holds again with no new action {src:.harness/engine/modules/task/taskreview.py#L161-L169} {src:.harness/engine/modules/task/taskreview.py#L240-L262}.

Some effects cannot be undone, so rewind refuses instead of pretending: `why_not` returns `promote` for a point at or before any `promote` or `promote-partial` event, because the files a promote wrote into a target repository are outside the task folder. The same holds for outside calls: they are made outside, and a rewind only puts the task folder back {src:.harness/engine/modules/task/rewind.py#L211-L225}.

## Task internals: limits and points the code does not settle

- **The same-session-id after compaction is Copilot's, not the harness's.** The harness has no code that handles a compaction; whether Copilot keeps the session id when it compacts is not shown in this repository {src:.harness/engine/core/events.py#L5-L18} {src:.github/hooks/harness.json#L1-L112}.
- **A rewind's `before` point is kept, but the board does not restore it.** `restore` takes a point of kind `before` so that a rewind can be undone, as `rewind.py` says; the board's rewind action finds only points of kind `prompt`, so in 1.8.3 no board action restores a `before` point. The files are in `.task/rewind/` {src:.harness/engine/modules/task/rewind.py#L306-L313} {src:.harness/engine/modules/task/boardserve.py#L1617}.
- **A new round is decided by the promote state, not the kind.** `attach` starts a new round when `promote.state` is `done`; only the text for kinds other than `dev` and `kb` says there is none {src:.harness/engine/modules/task/task.py#L178-L180} {src:.harness/engine/modules/task/tasklife.py#L191-L192}.
- **`task open` clears the waiting mark and not the delivery.** `attach` sets `waiting` to None and leaves `deliver`; the next Stop of that session then sets the mark `accept` again because `deliver` is still there; only a message of the person removes `deliver` {src:.harness/engine/modules/task/task.py#L187} {src:.harness/engine/modules/task/handler.py#L486-L499}.
- **The sweep needs the served board.** No other process closes a promoted task {src:.harness/engine/modules/task/boardserve.py#L2330}.
- **Working is read from the age of the hook log** (300 seconds by default); a tool call longer than that looks idle {src:.harness/engine/modules/task/tasklife.py#L776-L787}.
- **The ribbon and the kind check no content.** Delivery needs a summary, and the reviewer judges the Done-when items of `REQ.md`; nothing else in code decides that a result is complete {src:.harness/engine/modules/task/accept.py#L45-L50}.
