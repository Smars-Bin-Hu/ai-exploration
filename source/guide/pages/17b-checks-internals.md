This file holds the code-level detail behind the feature file 17 Independent checks: the review state in `task.json`, who sets the number of checks and how the mark is read, what `task review start` refuses and writes, what the review package holds, the exact order of checks of the task module's subagent rule, how the reviewer is told where its package is, which hook saves the verdict and why the agent cannot change it, how passes are counted, and what happens after a failed check. It is for "how does it work" and "where in the code" questions; for what an independent check is and why the harness has it, read the feature file first. Code locations are at harness version 1.8.3.

## Independent checks internals: the state, `review` in `task.json`

The state of the checks of one task is the key `review` in the task's state file `.task/task.json`, with four fields: `n` (the passes wanted in a row, 0 when checks are off), `rounds` (the list of checks), `extra` (the checks the person added with `task review extend`) and `waived` (the person's waiver, or none); the page setting adds `set` {src:.harness/engine/modules/task/taskreview.py#L122-L128}. Only the `harness` command line and the task module's hook write it; `.task/**` is a path the gate keeps for the command line, so the agent's edit tools and terminal writes that name it are refused {src:.harness/policies/gate.json#L24-L34}.

Each entry of `rounds` is one check: `number` (its folder number, counted over every check the task ever had, refunded and dismissed ones included), `task_round` (the round of the task it belongs to; a task opened again after a write-back is a new task round), `digest` (the sha256 of the result when the check started), `snapshot`, `ordinal` (how many counted checks of this task round came before it, plus one) and `verdict` (empty while the reviewer works). The answer adds `finished_at`, `answer`, `dropped`, `invalid` and `refunded`; the person's dismissal adds `dismissed` {src:.harness/engine/modules/task/taskreview.py#L359-L436}.

Four small functions define what the rest of the code asks. `counted` is true for an entry that has a verdict and is neither `refunded` nor `dismissed`. `done_now` is the counted entries of the task's current round, in order. `pending` is the last entry of the current round that has no verdict, or none. `used` is the length of `done_now`, and the limit is held against it {src:.harness/engine/modules/task/taskreview.py#L131-L169}. The numbers come from `review` in `.harness/policies/task.json`: `extra_checks` 2, `max_n` 5, `free_invalid` 2; a broken policy falls back to these defaults, so it never opens or closes a gate by accident. The limit on checks is `n + extra_checks + extra` {src:.harness/engine/modules/task/taskreview.py#L40-L60}.

## Independent checks internals: who sets n, and how the mark is read

Only a person sets n, in three ways. The first is the mark `[review]=n` in a prompt the person types: the regex takes one or two digits, ignores case and accepts the full-width equals sign. `user_review` reads it from `event.words`, the prompt with the text a slash command's skill brings in cut away, so an example mark in a skill never counts (since 1.6.109) {src:.harness/engine/modules/task/taskreview.py#L44-L66} {src:.harness/engine/modules/task/handler.py#L77-L81}. In a session that holds an open task, `keep_review` calls `set_n`, which cuts n to `review.max_n` (5) and writes it only when it differs from the stored n. In a session with no task the mark is kept in the module state as `review_n`, the prompt text says a task is needed first, and `task new` or `task open` in that prompt cut it to `max_n` and store it in the task.

The second way is the number under Independent review on the task page of the served board, and the third is `harness task review set` in the person's terminal; both call `set_by_person`: a whole number from 0 to `max_n`, otherwise refused with the range. It asks no typed code. The person check is `approval.require_person`: a terminal whose stdin and stdout are a TTY, or the board's Terminal window. The gate also refuses `task review set`, `extend`, `waive` and `dismiss` on the agent's command line {src:.harness/engine/modules/task/taskreview.py#L476-L493} {src:.harness/engine/core/approval.py#L37-L58}.

Marks that are not the person's words are not read. `on_user_prompt` returns before it reads any mark when the prompt is a subagent's call message (`from_subagent`) or the reason of a Stop block the engine fed back (`continuation`), so a `[review]=n` an agent writes in a call message or finds in Stop feedback changes nothing; it also returns first for a board question turn (`/harness-ask`) {src:.harness/engine/modules/task/handler.py#L233-L244} {src:.harness/engine/core/state.py#L262-L298}. The board's own messages never carry the mark: `chatsend.py` says `[review]` is never in a message, because the number is set on the task page.

Each prompt of a task with n above 0 carries the line `review.inject` (n, passes, checks used, limit) {src:.harness/engine/modules/task/handler.py#L93-L113}. Autorun needs checks: `autorun.requirements` lists a problem when `n < 1`, so `task autorun on` is refused until n is at least 1 {src:.harness/engine/modules/task/autorun.py#L125-L139}.

## Independent checks internals: what a check costs

Each counted check is one call of the `reviewer` subagent, a model run of its own; the harness docs say `[review]=1` is at least one more reviewer and, when it does not pass, one fix and one check more, `[review]=2` at least two {src:docs/06-cost-optimization.md#L73-L76}. Text and a limit hold the cost down: the package tells the reviewer to read the diff first, the call message is one sentence, and from the second counted check only what affects correctness is reported {src:.harness/engine/core/messages.en.json#L49-L59}. For a task with n above 0, the sha256 of every result file is computed at each prompt (`task_text`) and each Stop (`review_stop`); the docs put it at a few dozen milliseconds for a file of several MB, and with n = 0 nothing is hashed for this. The real Credits of a check are not counted by the checks code: the task report and the board show the independent check as a stage of its own, with time and Credits read from Copilot's session record.

The one measurement behind the design was made at version 1.0 on a simulated repository, with four tasks each done once by a three-role setup and once by a single agent: both passed all four, the setup used about 4.5 times the usage and 6 times the time, and the docs say the extra money bought mainly the independent check. Each task ran once, and the effect of n of 0, 1 and 2 on real tasks was not measured {src:docs/06-cost-optimization.md#L82-L101}.

## Independent checks internals: `task review start`, the order of refusals and what it writes

`taskreview.start` is called by the agent (it is not person-only) and goes over the task state twice, each time under the task's lock {src:.harness/engine/modules/task/taskreview.py#L359-L436}. The first pass refuses in this order, and no refusal uses a check: the task is not open (`require_open`, the refusal every task command gives for a closed task); n is 0 (`review.off`); there is nothing to check yet (`has_something`: a file under `DEV/` for kinds `dev` and `kb`, a `test/results-*` file for kind `test`, any file besides `REQ.md` for other kinds); the person's run is not back (`not_ready`: an open handoff, or an `[R…]` item of `REQ.md` with no file yet under `RUNS/<environment>/`). When a run is missing and no handoff is open, `mark_run` hands the run to the person itself, so the board shows the task waiting for it {src:.harness/engine/modules/task/taskreview.py#L170-L178}.

The second pass repeats the open and run checks, then refuses when the passes already reach n on the current digest (`review.enough`), and when no round is waiting and `used` has reached the limit (`review.limit`, which tells the agent to stop and show the person where the last findings are). If those pass, it writes `CHANGES.diff` when `DEV/` holds files and the task has `target_files` or `manual_files`; takes a snapshot of the result files under `SNAPSHOT/`; creates or updates the round entry; writes `REVIEW/round-NNN/package.md`; adds the history line `review-start`; and returns the package path with the text that tells the agent to call the reviewer with a one-sentence message.

Running `start` again while a round is waiting (a round with no verdict) makes no new round: the number is the waiting entry's, the entry gets the new digest, snapshot and ordinal, the folder `round-NNN` is reused, `package.md` is written again, and the limit is not held against it {src:.harness/engine/modules/task/taskreview.py#L392-L409}.

The Stop hook does not start a check. `review_stop` blocks the agent's Stop once per prompt with `review.stop` and `next_text`, which says what to run; it is silent when n is 0, a handoff is open, a waiver holds, the passes suffice, there is nothing to check, or the limit is used up {src:.harness/engine/modules/task/handler.py#L404-L420}.

## Independent checks internals: what the review package holds, in order

`package_text` builds `package.md` from message keys and task files. It holds paths and metadata, never the contents of files; the reviewer reads the files itself {src:.harness/engine/modules/task/taskreview.py#L283-L317}. In order: a title with the task name and the round's folder number; `This is check 1. Do a full check.` or, from the second counted check, `This is check <ordinal> (the 2nd or later)` with the instruction to report only what affects correctness; the paths of `REQ.md`, `PLAN.md` and `REQ/` that exist; a note when the confirmation line of `REQ.md` is empty (not a finding); the judging rules for numbered "Done when" items; the path of `CHANGES.diff` when one was written; the files table; the saved runs, when there are any; the previous check, when there is one to show; and how to answer {src:.harness/engine/core/messages.en.json#L54-L79}.

The package carries two numbers that differ. The title says `check <number>`, the folder number counted over every check the task ever had. The text says `check <ordinal>`, the number of counted checks of this task round plus one, so a refunded or dismissed check does not raise it and a check after a write-back starts at 1 {src:.harness/engine/modules/task/taskreview.py#L283-L292} {src:.harness/engine/modules/task/taskreview.py#L396}. "The 2nd or later" depends on this count and not on a previous FAIL: after a first PASS with n = 2, the second check already gets the instruction.

The files table has the header `File | sha256 | Bytes` and one row per result file: the path inside the task folder, the first 16 hexadecimal characters of its sha256, and its size in bytes {src:.harness/engine/core/messages.en.json#L625} {src:.harness/engine/modules/task/taskreview.py#L300-L302}. The full sha256 is in the snapshot's manifest and in the digest; the reviewer's agent file still says "the sha256 of each". The result files are the task folder minus the status files, the person's folders and the harness's own folders.

The runs block lists every numbered saved run of the task (from `RUNS/*/results.md` and `TEST/results-*.md`), one line each: the id `[E<n>]`, the environment, who ran it (`the agent` or `you`, meaning the person) and the first line of the command, cut at 160 characters {src:.harness/engine/modules/task/evidence.py#L82-L108} {src:.harness/engine/modules/task/taskreview.py#L303-L306}. The block's text says the reviewer may run a read of an outside system again and compare, and that a write or a procedure is refused to it by the gate.

## Independent checks internals: what the package quotes of the last check

`previous` is the last counted check when its verdict is not PASS; when a refunded check is newer than the last counted one, that refunded check is `previous` {src:.harness/engine/modules/task/taskreview.py#L399-L402}. After a counted check that did not pass (a FAIL, or an answer with no verdict, recorded as `unknown`), the package says so, gives the path of its `verdict.md`, quotes the first 40 lines of its stored answer, each prefixed with `> `, and lists the findings the script dropped, each cut at 200 characters, with the reason. After a refunded check it says the last check was not counted, gives the path and lists the dropped findings, without quoting the answer. After a PASS no earlier answer is quoted {src:.harness/engine/modules/task/taskreview.py#L308-L316}.

The quote comes from the `answer` stored in the task state (the first 6000 characters), not from `verdict.md` {src:.harness/engine/modules/task/taskreview.py#L412-L437}. The package tells the reviewer to confirm one by one whether each problem of the last check is fixed and then do the full check; the agent file adds that every check is a full check {src:.harness/engine/core/messages.en.json#L62}.

## Independent checks internals: the order of checks of the subagent rule

The hook runs the task module on `PreToolUse`, and `handle` sends a call whose tool kind is `subagent` to `on_subagent_call` {src:.harness/engine/modules/task/handler.py#L629-L652}. The kind comes from the tool name (`runSubagent` and `Agent` map to `subagent`), and the called agent's name is the first string among the input keys `agentName` and `agent_type` {src:.harness/engine/adapters/tool_kinds.json#L47-L50}. `on_subagent_call` works through these checks in this fixed order, and the first that applies decides {src:.harness/engine/modules/task/handler.py#L278-L300}:

1. The call is made from inside a subagent session (the session state has a `parent_session_id`): no opinion, because the platform does not nest subagents.
2. The name is read: the target with spaces stripped, or "the general subagent" when the call names none. Names are compared in lower case.
3. The session is in admin mode: the call is refused with `rules.subagent.admin` ("Admin mode allows no subagent ... Do the work yourself."). Admin mode refuses every subagent call, the reviewer's too {src:.harness/engine/core/messages.en.json#L112}.
4. The name is `mapper`: the decision goes to `mapreduce.on_call`, which allows it only after the person typed `/generic-mapreduce`, within its limits.
5. The session holds no open task: refused with `rules.subagent.no_task`, which says the reviewer can be called only after the user writes `[review]=n` {src:.harness/engine/core/messages.en.json#L111}.
6. The name is `worker`: the decision goes to `worker_call`, which asks `autorun.on_subagent_call` and refuses when the task's autorun is off or a condition of the run fails.
7. The name is anything other than `reviewer`: refused with `review.call.other` {src:.harness/engine/core/messages.en.json#L102}.
8. The task's n is 0 (checks are off): refused with `review.off`, which tells the agent not to switch checks on itself {src:.harness/engine/core/messages.en.json#L45}.
9. `taskreview.pending(data)` is none, that is, the current round holds no check without a verdict: refused with `review.call.no_round`, which tells the agent to run `task review start` first {src:.harness/engine/core/messages.en.json#L103}.
10. Otherwise the module returns no opinion, which is how the reviewer call is allowed: the call goes on unless another module refuses it.

The module never reads the call message of a reviewer call, so the rule that the message holds only the package path is text, not code.

## Independent checks internals: why the agent cannot fake an open round, and what a crash does

"Open" means one thing: `pending` finds an entry of the current task round with no verdict. Only `task review start` creates or reopens such an entry, and only `record` fills the verdict; both write `.task/task.json`, a path in `cli_owned_paths`. The gate refuses the agent's edit tools on it, and a terminal command that writes it with a redirect, `tee`, `rm`, `mv`, `cp`, `sed -i`, git, or an inline `python -c` that opens it for writing is refused with `gate.cli_owned.terminal` {src:.harness/policies/gate.json#L24-L34} {src:.harness/engine/modules/gate/handler.py#L38-L61}. The round closes when the verdict is recorded, so one `start` buys one reviewer call. The gate reads a terminal line as text and its script check reads a script's writes only for guardrail paths, so a script file the agent writes and runs that opens `.task/task.json` is not read by it.

A crash of the task module on a subagent call fails closed. The registry marks the task module as a guardrail (`H`). On `PreToolUse` a guardrail module that raises normally stops the whole call (`GuardFailed`, as the gate does), but a module named in `GUARDS_FOR` is refused only for the calls it judges, and the task module is named there with the test "tool kind is subagent". So when the task module raises on a subagent call, that call gets a deny with `hook.module_failed`; on any other call it has no opinion and the session goes on {src:.harness/engine/hook.py#L55-L87}. On other events, such as the `PostToolUse` that saves the verdict, a crash is logged, the module's state changes are rolled back and nothing is refused.

## Independent checks internals: how the reviewer is told where its package is

At `SubagentStart` the hook runs `on_subagent_start` in the main agent's session; the agent name is `agent_type` or, when empty, `agentName` {src:.harness/engine/adapters/copilot_vscode.py#L100-L103}. For the reviewer it takes the session's open task and `taskreview.pending(data)`. With no open task, another agent type, or no waiting round, it returns nothing and adds no context. Otherwise it builds `<task>/REVIEW/round-NNN/package.md` from `round_dir` and `PACKAGE` and returns a decision whose context is `review.start.context` plus `rules.language`. The hook does not check that the package file exists {src:.harness/engine/modules/task/handler.py#L328-L344}.

The text of `review.start.context` is: "The review package of this check: {package}. Read it first and check as it says. Your answer is saved as written, as verdict.md in the same folder." {src:.harness/engine/core/messages.en.json#L106}. The Copilot adapter prints a decision's context as the output key `additionalContext` for every event except `Stop`, `SubagentStop` and `UserPromptTransformed`, so the reviewer gets it as added context when it starts {src:.harness/engine/adapters/common.py#L133-L149}. `SubagentStart` cannot refuse a start; keeping an uncalled reviewer out is the `PreToolUse` rule above. The reviewer's own session is linked to its parent when it sends its first prompt (`claim_child`), so it inherits the parent's task, and that first message is flagged `from_subagent`.

## Independent checks internals: which hook saves the verdict, and what it writes

The verdict is saved by the task module's `PostToolUse` handler, not by `SubagentStop`. `handle` runs `on_task_write` and then `on_review_done` for every `PostToolUse`; `on_review_done` does nothing unless the session holds an open task, the tool kind is `subagent` and the called agent is `reviewer`, and then calls `taskreview.record(root, task, event.tool_response)`, where `tool_response` is the text the subagent call returned to the main agent {src:.harness/engine/modules/task/handler.py#L391-L401} {src:.harness/engine/adapters/copilot_vscode.py#L64-L68}. `SubagentStop` in the task module acts only for the autorun `worker`.

`record` runs under the task's lock and takes `pending(data)`; with no open round it returns nothing and the answer is stored nowhere. Otherwise it reads the verdict with `parse_verdict`, sets `verdict`, `finished_at` and `answer` (the first 6000 characters), and for a FAIL runs the script check. It then writes the whole answer, trailing whitespace trimmed and one newline added, to `<task>/REVIEW/round-NNN/verdict.md`, adds the history line `review round-NNN <verdict>`, and returns the verdict and counts to the hook, which puts them in the call log; the decision adds no text for the agent. If the script check raises, `record` catches it and keeps the answer with no dropped findings, so a bug in the form check never loses the reviewer's answer {src:.harness/engine/modules/task/taskreview.py#L412-L437}.

The authoritative record is the state in `.task/task.json`; `verdict.md` is a readable copy, and the next package quotes the state's answer. The agent cannot change either: `.task/**` and `REVIEW/**` are in `cli_owned_paths` of `gate.json`, `check_write` refuses an edit tool on them and `check_terminal` refuses the write patterns of the guardrail list, in every session, admin mode included {src:.harness/policies/gate.json#L24-L34} {src:.harness/engine/modules/gate/handler.py#L38-L61}. The outcome of a recorded check can be changed only by the person, with `task review dismiss`, `waive` or `extend`, each a person-only command with a typed code that the gate refuses to the agent.

Hooks after a call are fail-open. If `record` raised before it wrote anything, the module's state is rolled back, the error goes to `hook-errors.jsonl`, nothing is refused and the round stays open; the next `task review start` reuses it and the `PreToolUse` rule lets a second reviewer call through {src:.harness/engine/hook.py#L58-L87}.

## Independent checks internals: how the verdict is read and a FAIL is checked

`parse_verdict` looks at the first three non-empty lines (`VERDICT_LINES`), strips markdown marks from each end, and matches `VERDICT: PASS` or `VERDICT: FAIL` in any case with an ASCII or full-width colon; the first match decides, and with no match the verdict is `unknown` {src:.harness/engine/modules/task/taskreview.py#L43-L85}. An answer with no verdict is a used check: it has a verdict, is not refunded, counts in `used` and as a non-pass, and its text is quoted in the next package. The script check runs only for `FAIL`.

For a FAIL, `reviewcheck.check` takes each bullet with a `| basis:` part as a finding and drops it for the first of these reasons: its basis cites only `[A…]` items; it names no `file:line`; its file is found nowhere (looked for from the repository root, the task folder, each target repository and as the end of a path inside the task folder, at most 5000 files searched); or its line is outside the file. When no finding is left, including when the FAIL had no bullet with a basis, the check is invalid {src:.harness/engine/modules/task/reviewcheck.py#L106-L186}. An invalid FAIL is refunded while fewer than `free_invalid` (2) checks of the current task round were refunded; the next counts as a FAIL. A refunded check has a verdict but `counted` is false, so it is not in `used`, the ordinal or the passes {src:.harness/engine/modules/task/taskreview.py#L131-L135}. The script judges the form only, never whether a finding is right.

## Independent checks internals: how passes are counted, and why they are not stored

`passes(data, digest)` walks `done_now` from the newest counted check backwards and counts while each check has the verdict PASS and a digest equal to the digest passed in, and that digest is not empty; the first check that fails any of the three ends the count {src:.harness/engine/modules/task/taskreview.py#L151-L158}. An empty digest, which `digest_of` returns for a task with no result files, never counts as a pass. The digest is one sha256 over the lines `<path><tab><file sha256>` of every result file, so adding, removing or changing a result file, `REQ.md` or `PLAN.md` changes it, and the files outside the result set (`TASK.md`, `TODO.md`, `LOG.md`, `QUESTIONS.md`, `COMMIT-MESSAGE.md`, and what a write-back puts into `DEV/`) do not {src:.harness/engine/modules/task/tasksnap.py#L28-L90}.

The module docstring gives the reason passes are not stored: they are counted from the rounds and the digest of the result as it is now, "so nobody has to remember to reset them" {src:.harness/engine/modules/task/taskreview.py#L20-L22}. What follows from the code is that every route by which a result file changes (the agent's edit tools, a terminal command, the person's own editor) changes the digest whether or not a hook saw it, while a stored number would stay right only on the routes where code remembered to reset it. Every gate and display (the Stop reminder, the prompt rules, `task review status`, autorun, the dry-run check) asks `summary`, which hashes the files at that moment {src:.harness/engine/modules/task/taskreview.py#L240-L263}.

A waiver is bound to the work and the round: `waive` stores `{digest, at, task_round}`, and `summary` counts it only when the stored digest equals the digest now and `task_round` equals the task's round; the command refuses when the work changed while the person was confirming {src:.harness/engine/modules/task/taskreview.py#L240-L257} {src:.harness/engine/modules/task/taskreview.py#L512-L529}. The board's dots (`dots`) show a waiver by round only, and are for display. For a settled task (write-back done, or closed), `summary(settled=True)`, used by the status command and the board, does not compare with today's files: it shows `streak`, the PASSes in a row at the end of the counted checks that share the digest of the last one. The gate for the dry run always uses the files as they are: `require` refuses `task promote --dry-run` unless n is 0, passes reach n, or the waiver holds.

## Independent checks internals: after a failed check, how the agent reworks

`task review status` calls `next_text`, which gives the agent its next step by this order of cases: n is 0 (`review.off`); the person waived; the passes reach n (go on); a round is waiting (call the reviewer with the package path); there is nothing to check; a handoff is open (the person's result comes first, whatever the last verdict said); the checks used reach the limit (`review.limit`: stop, show the person the last `verdict.md`, ask for `extend` or `waive`); the last counted verdict is not PASS (`review.next.fix`: read the verdict file, fix the work, run `task review start` again); otherwise `review.next.more` (run `task review start`) {src:.harness/engine/modules/task/taskreview.py#L449-L470} {src:.harness/engine/core/messages.en.json#L47-L53}. The agent reworks by following that text; the code never changes the work.

After the agent changes the work, the digest changes and the next `start` opens a new round whose package quotes the first 40 lines of the failed answer. If the agent starts again without changing the work, a new check opens too; the failed one stays counted, so the passes do not rise and the limit falls by one. After the person dismisses a check, the stated next step is that the agent runs `task review start` again without changing the work for that check's findings {src:.harness/engine/core/messages.en.json#L89}. `dismiss` takes only the newest counted check of the current task round when it did not pass (a FAIL followed by a PASS cannot be dismissed), asks for a typed code bound to that check's digest, marks the entry `dismissed`, sets the task waiting with the reason `go-review`, and adds a line to `LOG.md`; a dismissed check leaves `used`, the ordinal and the FAIL count {src:.harness/engine/modules/task/taskreview.py#L531-L560}. `extend` (the board's button gives 2) and `waive` also need a typed code bound to the digest of the work now.

## Independent checks internals: what code does not stop in the reviewer's separation

The principle is stated in text: the reviewer's agent file says its value is that it has not seen the author's reasoning {src:.github/agents/reviewer.agent.md#L12-L13} {src:docs/05-design.md#L111-L129}. Code enforces part of it: the reviewer is a separate subagent session and the author's reasoning is not in the package. It does not read the call message, and the reviewer is not blocked by code from reading `LOG.md` or `TODO.md`: the gate never blocks a read, and only the agent file forbids it. The gate holds the reviewer's terminal by its general rules and by the guardrail and command-line-owned path rules, not by a rule for the reviewer, so a terminal write that names none of those paths is not stopped by code; "read-only commands only" is a text rule.

No separate model family is forced: `agents.json` has an empty `different_series` and lists the reviewer in `any_series`, so no rule makes its model differ from the main agent's {src:.harness/policies/agents.json#L1-L20}. The docs say two reviewers have been seen to give different verdicts on the same work; the repository holds no figures for it {src:docs/02-features.md#L105}. Who decides: the person sets n and extends, waives or dismisses; code decides whether the reviewer may be called, what the package holds, what the verdict is, what counts as a pass and the limit; the agent following text decides when to start a check, what its call message says and how to fix; the reviewer, a model, judges the work.

## Independent checks internals: limits and points the code does not settle
