This file holds the code-level detail behind the feature file "19 Tool packs, connections and MCP". Use it for "how does it work" and "where in the code" questions: the pack folder, how SQL text is cut and judged, how a call is tied to a connection, what is refused and what is held, what Approve and Open do, how the agent waits, how files are pinned, how the agent is told about connections, where sign-ins live, and how evidence is numbered. The feature file says what a tool pack is for and what each sample pack lets through.

## Tool packs internals: tool pack, connection type, connection and Local in code

The harness knows no outside tool; four kinds of file give it one. A **tool pack** is a folder read where it lies: the factory packs in `.harness/toolpacks/`, the company's in `company/tools/packs/`, and folders a person added with `toolpack add` {src:.harness/engine/core/toolpacks.py#L45-L91} {src:.harness/engine/core/toolpacks.py#L210-L358}. A **connection type** is one file `types/<type>.json` of a pack: fields, ways to sign in, a test, and the gate's verbs, lists and rules. A **connection** is one place with a name: an entry in the company's `connections.json`, or a connection of the person's own kept in `.harness/.env` under `HARNESS_CONNECTION_<NAME>_ALIAS`; the name must match `^[a-z][a-z0-9-]{0,40}$`, and a company connection of the same name wins over an own one {src:.harness/engine/core/connections.py#L37-L45} {src:.harness/engine/core/connections.py#L272-L323}. The fourth file is the **computer recipe** `company/tools/computer.json` (a CA bundle address, a proxy, hints where a program is installed), copied to `.harness/policies/computer.company.json`; it prefills the Local window, holds no secret, and is never given to the agent {src:.harness/engine/core/launchenv.py#L1-L86} {src:.harness/contracts/toolpack/README.md#L9-L30}.

Each connection becomes one gate system. `connections.derived` makes a system for every connection whose type has `cli` and `match`, has no type problem and has an environment in `dev, ist, qat, prod, none`: its program is the type's `cli`, its `reach.when` is the type's `match` filled with the connection's fields, its rules are the connection's own `rules` else the type's, and its `open` word is the type's lowered by the connection's own. A probe `needs` is added only when the pack is on; a hand-written system with the same name wins {src:.harness/engine/core/connections.py#L606-L662}. So the gate's action `{system, env, verb, target}` has the connection's name as its system. The connection list holds fields only: the code that reads a person's own connection from `.env` leaves out every `_ACCOUNT`, `_PASSWORD`, `_KEYFILE` and `_TOKEN` key. Sign-ins are written to `.harness/.env` by `write_env`, mode 0600 on macOS and Linux, only when the type's test passed (or kept as "not tested yet" when the test never reached the server, see the section on identities) {src:.harness/engine/core/connections.py#L272-L323} {src:.harness/engine/core/connections.py#L1073-L1090}.

**Local** is the third card of Get ready, and it has three blocks. Why it exists: the agent's terminal commands run in the editor's agent host, which has the environment VS Code was started with, so an editor terminal's setting does not reach them; the board therefore puts these into VS Code's environment each time it opens VS Code, and an already open VS Code keeps its own {src:.harness/engine/core/launchenv.py#L1-L86}. (1) **Programs**: every program in an active pack's `needs.programs`, and in the `needs` of the sign-in ways its connections use, is looked for on the PATH VS Code will get: the system PATH, the folders in `HARNESS_TOOL_PATH` (`.harness/.env`) and each active pack's `bin/`. A program not found makes the pack "not usable yet: X not found"; saving is never blocked; a file that is there without the run bit is told as "cannot run" {src:.harness/engine/core/toolpacks.py#L374-L434} {src:.harness/engine/core/launchenv.py#L231-L253}. (2) **Network**: a CA bundle at `.harness/certs/ca-bundle.pem` for a proxy that inspects TLS, named by `REQUESTS_CA_BUNDLE` and by the variables a pack asks for in `needs.trust`; `make` keeps the bundle only when a check with it passes {src:.harness/engine/core/launchenv.py#L729-L765}. (3) **MCP**: `HARNESS_MCP` in `.env`; MCP is blocked unless the value is `allowed` .

"Local" has other meanings. "Local work" is what the gate leaves free: reading the repository, writing in the task folder, running tests, and any line that names no governed program. "Harness & Local" is the required block of the Enter screen, as against the optional block "From the company". A Copilot "Local session" is an old session type that is not supported {src:docs/12-guardrails-and-gate.md#L107-L107} {src:docs/01-quickstart.md#L24} {src:docs/05-design.md#L159}.

## Tool packs internals: why packs and not only MCP servers

The harness docs give three reasons. (1) Whether the company can use it: many companies switch MCP off by policy, so a pack reaches its tool through a plain program in `bin/` run in the terminal the editor already allows; MCP is an extra. (2) Who holds "a write waits for the person": an MCP server does not say which tool is a read, which item a write changes, or whether the task is linked to it, while a pack's connection type does (`verbs`, `item`, `say`, `body`, `show`). (3) Skills are needed either way: a server says what can be called, not when, in what order or how the company does it, so the pack's SOP skills are the half MCP never had {src:docs/13-tool-packs-and-mcp.md#L1-L31}. The rule that follows: every pack must work where MCP is blocked and give a command-line way for everything; `mcp.json` and a `via: mcp` type are extras {src:.harness/contracts/toolpack/README.md#L62-L95}.

The cost the docs name: a pack's own program follows the tool's public interface and its author keeps it current, where an official MCP server is kept by its vendor; so the factory packs cover systems with stable public interfaces. In code an MCP call is weaker than a program call: `check_mcp` judges a tool only when a pack names it in `mcp.tools`, its log facts say `env: none`, and it never reaches the outbox, because a card and its code are bound to a command line the agent runs again, which an MCP call has not got; a named write only makes Copilot ask {src:.harness/engine/modules/gate/handler.py#L213-L333}. A pack that is off still guards (see the section on off packs). The gate on the terminal path is a net, not a sandbox: it is for an agent that follows the rules and makes mistakes {src:.harness/contracts/toolpack/README.md#L115-L158}.

## Tool packs internals: what the pack folder holds and what the engine requires

Only `toolpack.json` is required. `manifest()` raises "not a pack" when it is missing, and a folder that has `types/`, `bin/` or `rules.json` but no readable `toolpack.json` is reported by `unreadable()` as a faulty pack, while a folder with none of them is not a pack at all {src:.harness/engine/core/toolpacks.py#L45-L91} {src:.harness/engine/core/toolpacks.py#L210-L358}. `types/` is optional in code: `problems()` loops over `types/*.json` only when the folder exists, so a pack may hold only skills, a `bin/` program and rules {src:.harness/engine/core/toolpacks.py#L109-L172} {src:.harness/contracts/toolpack/README.md#L9-L30}.

`problems()`, run by `harness toolpack check`, `add` and doctor, rejects a pack for: a `name` that does not match `^[a-z][a-z0-9]{1,30}$`, is reserved (`harness`, `generic`, `domain`) or equals the company's skill prefix; no `version`; a `harness` minimum above the running version; a malformed `needs`, `commands`, `mcp.tools` (a verb outside `read, write, exec, destroy`, or a pattern that does not compile), `mcp.json` or `links` (a `url` not starting with `https://` or `{url}`, a bad `id` or `example`); a type file that is not JSON or fails `type_problems`; a `rules.json` that fails `systems.validate`; and a skill folder not named `<name>-...` (or `<prefix>-<name>-...`) or failing `skillcheck` {src:.harness/engine/core/toolpacks.py#L109-L172}. Which MCP tool is a read, write, exec or destroy lives in `mcp.tools` of `toolpack.json`, matched case-insensitively on the tool name, first match wins; `mcp.json` only lists the servers {src:.harness/engine/core/toolpacks.py#L563-L713}.

The `commands` field is read by the gate since 1.7.38: for a system whose program is the pack's own, a call whose subcommand (the first word after the program, or the first group of the type's `command` pattern) is not listed is refused with one line saying the program has no such command, and no card is made; a pack that lists none is not checked {src:.harness/engine/modules/gate/external.py#L94-L114} {src:.harness/engine/modules/gate/external.py#L898-L940}. `needs.programs` and `needs.trust` only feed Local: a missing program is a yellow state, never a block on Save. The skills of a pack that is on are copied into `.github/skills/` as `<prefix>-<pack>-<skill>` (the company prefix is added unless already there), and taken back, to `.harness/runtime/toolpack-backup/`, when the pack goes off {src:.harness/engine/core/toolpacks.py#L812-L953}. No account, password or token sits in a pack; a type's `test` may use `{field}` and `{auth}` but never `{password}` {src:.harness/contracts/toolpack/README.md#L62-L95}.

`rules.json` holds `{"systems": {...}}` in the form of `tools.json`, for commands no connection type covers (the `ado` pack's `curl` rules, the SQL pack's `bcp` and `isql`). Its keys: `reach.also` (hosts a connection type holds in a field join `reach.when`), `blocked` (the text every call of the system's programs is refused with) with `reach.code` (words that refuse a one-line `python3 -c` or `node -e`), and `reach.by_address` (`curl` is a call of the system only when every address in the line matches `reach.when`) {src:.harness/contracts/toolpack/README.md#L97-L123}. The tools policy merges the company's `tools.json`, then the packs' rules, then the person's `tools.override.json` (the person's file wins), then derives connection systems and adds the broken-pack systems {src:.harness/engine/core/config.py#L96-L134}.

A pack's `mcp.json` is applied by `apply_mcp`: where MCP is allowed it adds each active pack's servers to `.vscode/mcp.json`; where it is blocked, or the pack is off, it removes the servers it had added (a ledger remembers which are the pack's); a server of the same name that is not the pack's is left alone {src:.harness/engine/core/toolpacks.py#L1089-L1128} {src:.harness/engine/core/toolpacks.py#L812-L953}. A company pack with the name of a factory pack makes `company sync`, `toolpack add`, `remove` and the on/off switch stop before anything changes, and doctor reports an error; the company's pack is not read until renamed. The same stop applies when the company's `packs.json` cannot be read, and then the gate guards every factory pack as if it were on {src:.harness/engine/core/toolpacks.py#L210-L358}.

**A faulty file fails closed.** A type file that cannot be read or is not valid (unknown key, a pattern that does not compile, a list of the wrong shape), a `rules.json` that is not valid, or an unreadable `toolpack.json` of a pack the gate reads, makes `faults()` list the pack and `broken_systems()` build a system `broken-<pack>` that owns every program the pack declares: the `cli` of its types, `needs.programs`, the files of its `bin/`, and the programs of its `rules.json`. Every call of those programs is held for the person (zone `broken`, no Open button), and the card and the agent's text name the file and the fault. When the type file can still be read as JSON, its refuse list is read first, so a `KILL` is refused with the type's reason even then {src:.harness/engine/core/toolpacks.py#L563-L713} {src:.harness/engine/modules/gate/external.py#L718-L835}. The rest of the gate is not touched. A connection list that cannot be read has the same effect for the programs of every pack that brings a connection type, on or off {src:.harness/engine/core/connections.py#L326-L395}.

## Tool packs internals: the three answers and what each promises

A call of a program whose type carries a `reads` list gets one of three answers, and each answer carries a different promise. **Pass** (the type's `reads` list) is a guarantee: nothing outside the list passes unasked, so a spelling nobody thought of asks. **Refuse** (the type's `refuse` list) is best effort: it names what is forbidden, such a list is never complete, and a spelling it misses is not passed, it lands in ask. **Ask** (held for the person) is the safety net and promises nothing about being right. Behind all three stand the account's rights, the final guarantee for a database; no code checks them {src:.harness/contracts/toolpack/README.md#L97-L123} {src:docs/12-guardrails-and-gate.md#L22-L63}.

The order of the decision is fixed. The refuse list is read first over every statement and sqlcmd line of the text and of the script files it reads, whatever else is wrong with the call. Then a call that gave the gate nothing to read, a text with a shell variable, or a script file the gate could not read asks. Then the pass list, then the write list for an opened connection, then ask {src:.harness/engine/modules/gate/external.py#L718-L835}. **Pass** needs three things together: every statement of the call and of its script files matches a `reads` pattern whole, no sqlcmd line is left that is not in the type's `directives` list, and the call reaches exactly one connection the gate can name (next sections). On prod this is all that runs, because prod's default rules refuse a write, run and destroy.

**Refuse** is final. Nothing a company's rules or an opened connection says changes it, the call makes no card and no code (classify gives the decision `deny` for zone `refuse`), and the agent is told the type's `reason`, which must name the right way, then to stop and tell the user {src:.harness/engine/modules/gate/external.py#L1472-L1525} {src:.harness/engine/modules/gate/handler.py#L405-L469}. No refusal loops back to a card. Refusals also arise elsewhere: a call that names no connection the gate can read (unpinned), a program of a pack that has no connection, a program or code a system lists in `blocked` and `reach.code`, a `harness as <alias>` that wraps a call of another connection, and a script file that another command of the same line may change before it runs {src:.harness/engine/modules/gate/external.py#L718-L835} {src:.harness/engine/modules/gate/handler.py#L601-L693}.

**Ask** is the rest. A call in the read zone still becomes ask when the line also carries a write setting the type's `verbs` name (`-o` outside the task folder, `-q`, `SQLCMDINI=`), or when the type's `verbs` call the text a destroy although the read list says read (a read list too wide: the person decides). Calls with nothing to read (no `-Q` and no `-i`: the program reads its input), shell variables in the `-Q` text (`$name`, `${`, `$(`, a backtick), a script file that is missing, over 200 KB, not text, or named again in the same line, and more than 12 files or three levels of `:r` includes, all ask {src:.harness/engine/core/inputfiles.py#L21-L24} {src:.harness/engine/core/inputfiles.py#L130-L190}. An asked call is held for that exact command and for the files as they were; opening a connection does not pass an asked call, only calls in the write zone; and when autorun is on or the caller is a subagent, a hold becomes a refusal ({src:.harness/engine/modules/gate/handler.py#L405-L469}). The type's `rules` then decide what that kind of call gets in each environment: an asked call on prod is a write, so prod's defaults refuse it, and on QAT the sample sends a destroy to `deny` {src:.harness/engine/modules/gate/external.py#L1472-L1525} {src:.harness/engine/core/systems.py#L33-L38}.

## Tool packs internals: why three answers and why a refusal needs a right way

Listing every harmful call never ends, because there is always one more spelling. So the harness says what may pass (the pass list), refuses what the agent has no good reason to do and has a right way around (the refuse list), and sends only the rest to the person {src:docs/12-guardrails-and-gate.md#L22-L63}. With two answers (pass and ask) every call off the list goes to a person, who after approving many cards stops reading them, and then the gate guards nothing. With three, a gap in the refuse list costs attention, not safety, because a missed call falls into ask. A call refused by mistake costs a stalled task.

A refusal stops the agent, so it is right only when the agent can change its own call: name the server, run a shell command in the terminal, write the output into the task folder. Where only a person's judgment helps, the call must be ask, not refuse. A refusal with no way out stalls the task and teaches the agent to hunt a workaround. The code enforces only that each refuse entry has a non-empty pattern and a reason; whether the reason names a workable way cannot be checked and is the pack author's duty {src:.harness/engine/core/systems.py#L109-L112} {src:.harness/contracts/toolpack/README.md#L97-L123}. History: the first 1.7.38 lists refused `DROP`, `TRUNCATE`, a string run as SQL (`EXEC('...')`), `$(name)`, and each of these in the body of a procedure; ETL tests on DEV need all of them, the agent stopped and tasks stalled, so they were taken off the refuse list and are now held (on an opened connection the write list passes the ones it names). Release 1.7.44 widened the read list so that a read does not wait: `SET @n = (SELECT ...)`, an `IF` that only reads, and statements that need no `;` (`SET NOCOUNT ON`, `USE db`) are judged on their own {src:docs/12-guardrails-and-gate.md#L22-L63} {src:docs/07-release-notes.md#L216-L273}.

## Tool packs internals: what the sample SQL Server lists hold, and what the account's rights do

The refuse list of the sample SQL Server type is short on purpose: only what has a right way around. It holds `KILL`, `SHUTDOWN` and `RESTORE` (anywhere in a statement), a line that starts with `!!` (a shell command: run it in the terminal), `:connect` (the next statements go to another server: call it with `-S <that server>`), `:out`, `:error` and `:perftrace` (they write to a file the gate does not see), and `xp_` extended procedures outside the body of a procedure being deployed. Each entry carries an `en` and `zh` reason {src:.harness/toolpacks/sqlserver/types/sqlserver.json#L142-L178}. A `DROP TABLE` or `TRUNCATE TABLE` is not on it: its verb is destroy, and the type's `rules` hold it on DEV and IST, refuse it on QAT, and the prod default refuses it; it is on the write list, so on an opened DEV or IST connection it passes {src:.harness/toolpacks/sqlserver/types/sqlserver.json#L254-L279} {src:.harness/engine/modules/gate/handler.py#L213-L333}.

The pass list errs toward asking: its patterns carry look-aheads that reject any hidden second statement, because the server needs no `;` between statements. `statements.py` cuts a piece without `;` only at a bounded form at its front (`SET <option> ON|OFF`, `USE <db>`, `DECLARE @a ...`, `SET @a = <constant>` or `SET @a = ( <query> )`) when the next word starts a statement {src:.harness/engine/core/statements.py#L82-L93}; `SELECT 1 UPDATE t SET a = 1` therefore stays one statement, and only the look-aheads of the pass patterns keep the hidden `UPDATE` from passing as a read. The `WHERE` guard on `UPDATE` and `DELETE` is a slip guard, not a boundary: a statement with no `WHERE`, or one that is always true, matches neither list and asks even on an opened connection, while `WHERE id > 0` passes there {src:.harness/contracts/toolpack/README.md#L97-L123} {src:.harness/toolpacks/sqlserver/README.md#L20-L20} {src:.harness/engine/core/statements.py#L266-L325}. Ask is limited by the person's attention (a person who approves forty cards a day stops reading), so the refuse and pass lists take away what needs no judgment.

Environment rules sit in the type: DEV and IST read allow, write, run and destroy outbox; QAT write outbox, run human, destroy deny; prod is not written, so it takes the default (read allow, the rest deny); `open` is `all` for DEV and IST, `no` for QAT and prod {src:.harness/engine/core/systems.py#L33-L38} {src:.harness/engine/modules/gate/external.py#L94-L114}. A pattern that does not compile matches nothing, so the call asks {src:.harness/engine/core/statements.py#L266-L325}. Nothing in code checks what the account can actually do: the advice to use a DEV account that cannot drop tables, or a read-only account, is text in the protocol and the docs. Whatever the lists miss, the account's rights are the last guarantee {src:.harness/contracts/toolpack/README.md#L97-L123}.

## Tool packs internals: statements.py cuts the text into statements

`core/statements.py` prepares the text of a call (the `-Q` text and each script file) and cuts it into statements; `judge` then answers by the lists. `split(text, variables)` goes through the lines. A `:setvar name value` line ends the batch, records the variable under its lower-cased name, and from then on each `$(name)` in a later line is filled in before the line is read, as sqlcmd does; a variable set again to a different value is stored as `None`, because a file the text includes is read after the whole text and the gate cannot tell which value it gets, so uses of it ask. The call's own `-v name=value` seeds the same dictionary {src:.harness/engine/core/statements.py#L202-L250}.

A line that is only `GO` (an optional count, an optional `--` comment) ends a batch, and so does a sqlcmd directive line (`:` and a letter, or `!!`), which becomes an item of its own marked as a directive. These lines are found first, on the raw lines, so a `GO` inside a string still ends the batch for the gate, as it does for sqlcmd {src:.harness/engine/core/statements.py#L1-L50} {src:.harness/engine/core/statements.py#L202-L250}. Inside a batch, `_cut` makes one pass: `--` and nested `/* */` comments become one space; a string literal becomes `''`; `[name]` and `"name"` become the plain name; and a `;` outside strings and comments ends a statement. White space becomes one space {src:.harness/engine/core/statements.py#L136-L199}.

An unfilled `$(name)` is kept visible, also inside a string or a comment (marked ` $( `), because sqlcmd fills it in there too, and it marks the statement `odd`; so does a look-alike character that a program might fold into the end of a hidden span (a curly quote inside a string, a fullwidth `]` in a name, a fullwidth `*` or `/` in a block comment). An odd statement is on no list: it asks {src:.harness/engine/core/statements.py#L1-L50}. A batch that is a single `CREATE [OR ALTER]` or `ALTER` of a `PROCEDURE`, `FUNCTION` or `VIEW` stays one statement (its inner `;` cut nothing) and its body is not read by the refuse list, because deploying it runs nothing of it; a `GO`-like line inside it makes it odd; a `TRIGGER` is cut normally and asks {src:.harness/engine/core/statements.py#L67-L133}.

Where SQL has no `;`, the cut happens only at `;`, `GO`, directive lines and, since 1.7.44, at fixed leading forms: `SET <option>[, ...] ON|OFF`, `USE <database>`, `DECLARE @a <type>[(n)] [= constant]`, `SET @a = <constant>` and `SET @a = ( <query> )`, each cut off only when the next word starts a statement. Nothing else is cut, so the pass list's look-aheads must reject a hidden second statement {src:.harness/engine/core/statements.py#L67-L133}.

`judge(system, items)` answers in this order. First, over every item that is not a definition, `refuse_entry` runs the refuse patterns with `re.search`, anywhere in the text, any case, and the first hit is a refusal with the entry's reason and the statement as written. Then each item: a directive on the type's `directives` list that is not odd is skipped; any other directive or odd statement is on no list; `reads` and `writes` patterns are matched with `fullmatch`, any case. All items on the read list is `read`; every item on the read or write list with at least one write is `write`; else `ask`, naming the first statement on no list. A pattern that does not compile matches nothing {src:.harness/engine/core/statements.py#L266-L325}.

## Tool packs internals: pin.py decides which connection a call reaches

For a program whose type declares a `pin`, the gate does not guess the target. `pin.read` looks at the words after the program and returns a state, tested in this order: `none` when the pin names no option; `other` when a word is one of the type's `other` options (`-D`, a data source name); `free` when the type declares no `free` and every word is one of `--help`, `-h`, `-?`, `--version` (the default help words, and only those), or when the type's own `free` words occur and no server value is given; `word` when the type says `subcommand` and the first word is not an option; `unread` when an option stands last with no value; `none` when no option names a server; `many` when more than one does; `unread` when the one value is empty, not plain ASCII, or holds `$`, a backtick, `*`, `?`, `~`, `{`, `}` or `%name%`; else `ok` with the value and its folded form {src:.harness/engine/modules/gate/pin.py#L25-L98}. Options are read as `-S x`, `-Sx`, `--server x` and `--server=x`.

Only the string `<first option> <folded value>` (for the sample, `-S host,port`) is matched against each connection's `match` pattern, so a `-S` inside a statement is no server. The connection whose pattern matches the most of that string wins (two servers on one host differ by port), and a call whose server matches no connection has the state `unknown` {src:.harness/engine/modules/gate/external.py#L718-L835} {src:.harness/engine/modules/gate/external.py#L158-L190}. What the winning connection gives is its environment, and that environment, with the call's verb, decides what the call gets.

Folding is only what the type's `fold` list says, applied in order with the case ignored. The sample folds a leading `tcp:`, spaces around the comma, `host:port` into `host,port`, a dot ending the host and zeros in front of the port, and adds `,1433` when no port is given {src:.harness/engine/modules/gate/pin.py#L60-L68}. The engine folds nothing of its own and looks nothing up in a name server: `127.0.0.1`, `localhost`, an IP number in hex or decimal, `(local)` and a pipe name match nothing. The reasons: the gate folds only spellings that are certainly the same place; a call passes only when the gate can show it reaches one known connection; and a text rule is offline and stateless. Before 1.7.38 the gate read "cannot tell" as "not mine": `sqlcmd -S 127.1,14332 -Q "DROP TABLE t"` ran, because the server was spelled a way the gate did not match {src:docs/12-guardrails-and-gate.md#L22-L63} {src:docs/07-release-notes.md#L216-L273}.

## Tool packs internals: calls whose target the gate cannot tell are refused, not held

A call of a pinned program whose server the gate cannot tell is refused, not held. The states are `none` (no server option; the default server, `SQLCMDSERVER` and a data source are not a connection), `many` (the option twice), `unread` (a variable, a command inside the word, a pattern, an empty value, a character that is not plain text), `word`, `other` and `unknown` (one server that matches no connection after the type's fold). For all of them `_unpinned` builds an action with zone `unpinned`, `classify` gives the decision `deny` without asking the rules, `_judge_one` returns it with `refused: unpinned` before any plan, subagent check, opened connection or approval is looked at, and `check_external` answers with the kind `external-unpinned` {src:.harness/engine/modules/gate/external.py#L718-L835} {src:.harness/engine/modules/gate/external.py#L1472-L1525} {src:.harness/engine/modules/gate/handler.py#L213-L333} {src:.harness/engine/modules/gate/handler.py#L405-L469}. So there is no card, no code, nothing for the person to approve, and the same holds for a subagent, an approved plan and an opened connection. This applies only to a program whose connection type declares a `pin` (`sqlcmd`); a type with no `pin` whose call matches no connection is judged by nothing and is not refused {src:.harness/engine/modules/gate/external.py#L898-L940}.

One exception and one ordering rule. A call made only of help words (`free`: `--help`, `-h`, `-?`, `--version`, or the type's own) reaches nothing and passes, once the refuse list has nothing; a help word beside an argument that could name a target makes it an ordinary call. The refuse list is read first, so a `DROP` or `KILL` in the same call gets the type's own reason and the unpinned reason together {src:.harness/engine/modules/gate/external.py#L718-L835}. What the agent is told: run `harness connections find <words>`, write the call with `-S <server>` as that line prints it, and if no connection has the server, stop and ask the user to add one; when the call was wrapped in `harness as <alias> --`, the text adds that the prefix gives the sign-in, not the server {src:.harness/engine/modules/gate/rules.py#L136-L190}.

## Tool packs internals: a pack that is off, and a program that has no connection

A program of a pack that has no connection of its type is refused with zone `blocked` (kind `external-blocked`), no card. `connections.unconnected` makes, for every pack this computer knows (on or off, factory, company, added), a system `no-connection-<type>` for each program no system lists, with the type's lists and its `noconn` data; the refuse list is read first and its reason comes with the refusal; a call made only of help words passes unless the refuse list catches something {src:.harness/engine/core/connections.py#L397-L480} {src:.harness/engine/modules/gate/external.py#L718-L835} {src:.harness/engine/modules/gate/handler.py#L405-L469}.

Whether a pack is on or off does not decide whether the gate judges it. `toolpacks.guarded` is the set the gate reads: the packs that are on, plus any pack that is off but whose connection type a connection uses (a type an active pack already brings is not looked up again in an off pack); with `use_fault` it is every factory pack {src:.harness/engine/core/toolpacks.py#L210-L358}. A pack that is off keeps its guard while a connection uses its type; turning it off takes back only its skills, its `bin/` on the PATH and its MCP servers. A system made for a connection of an off pack has no `needs`, so nothing probes it. A pack that is off and used by no connection gets the `noconn` system with `direct_only`: a direct call of its program is refused, but the program's name inside a script, or as a plain word of a line, is not read. The documented price: `echo 'ado items' | sh` is not seen {src:.harness/engine/core/connections.py#L397-L480} {src:.harness/engine/modules/gate/handler.py#L213-L333}.

Failures stay closed: an unreadable pack file holds the pack's programs, an unreadable `packs.json` guards every factory pack as if on, an unreadable connection list holds the programs of every connection type, and a failure of the judging itself refuses a line that names a pack's program {src:.harness/engine/modules/gate/handler.py#L213-L333} {src:.harness/engine/modules/gate/failclosed.py#L1-L7}.

## Tool packs internals: the held card, Approve, and Open a connection for this task

A card exists only for the decision `outbox`. A call of kind exec (decision `human`: the person runs it) and a destroy (decision `deny`) get a text for the agent, not a card, and a call in autorun or from a subagent is denied outright {src:.harness/engine/modules/gate/handler.py#L405-L469}. The card shows the exact command, and two buttons decide it: **Approve** and **Do not approve** (with a reason: command is wrong, wrong connection or environment, not now, do it another way).

**Approve** runs `outbox.approve_action` on the server side. It needs an interactive caller, that is the paired board browser or the person's own terminal; it re-pins the files the command names (see the pinfiles section); it marks the entry `approved`, and the approval is used up when the agent runs the command: it matches the same session and the exact command with white space collapsed, within `git.approval_minutes` of `gate.json` (default 10) {src:.harness/engine/core/outbox.py#L155-L302} {src:.harness/engine/core/approvals.py#L150-L244}. The board refuses Approve while the agent is in the middle of a turn (a page may be ten seconds old and the agent may be answering), except when it sits in `harness wait --approval`, because it then makes no call (`at_work` is false), or when VS Code says the bound chat runs no turn. **Open** works while the agent is at work, because `task allow` is among the settings the agent reads at its next step {src:.harness/engine/modules/task/boardserve.py#L685-L695} {src:.harness/engine/modules/task/boardserve.py#L96-L99} {src:.harness/engine/modules/task/tasklife.py#L793-L805}.

**Open `<connection>` for this task** changes the connection, not the call. The button is offered only when `_judge_one` finds an offer: for `all`, only a call with decision `outbox`, in a connection whose scope is `all`, that is not a destroy unless the type's write list names it, and is not in zone `ask` or `broken`; for `items`, only a write to an item the task is linked to that is not yet open; for `no`, never; and with no open task the card offers none. A line with writes to two connections has one offer each, and when another part of the line would still wait, no offer is made {src:.harness/engine/modules/gate/handler.py#L213-L333}.

The mechanics: the board's request needs the code of a held call of this task whose entry offers that connection (`offer_for`), and then `tasklife.set_allow` writes `allow_conn[name] = {at, env}` into `task.json` for scope `all`; for scope `items` it records `allow_links` with the task's linked items at that moment (an item linked later is not open); scope `no` is an error. Then `mark_opened_everywhere` removes that offer from every held call of the task that offered it, and a call with no offer left becomes `opened`: it is not an approval, the agent runs the same command again and the gate judges it anew {src:.harness/engine/modules/task/boardserve.py#L774-L792} {src:.harness/engine/modules/task/tasklife.py#L520-L595} {src:.harness/engine/core/outbox.py#L155-L302}. An item the task is not linked to is refused even when the connection is open. The scope is ordered `no < items < all`: the type's `open` word (per environment, or one word; `openable: true` is `all` in dev, ist and qat; a type with `item` and `link` that says nothing is `items`) can only be lowered by the connection's own `open`, and prod is `no` {src:.harness/engine/core/connections.py#L606-L662} {src:.harness/engine/core/systems.py#L217-L240}.

The gate reads an opening only while the task is open (`_open_task` requires status `open`); the entry is not cleared when the task closes, so it is in force again if the same task is opened again; the person can close it on the task page with one click, which runs the same function with `on` false {src:.harness/engine/modules/gate/handler.py#L370-L390}. The lock is not the code alone: the agent is told the code of its held call, but `task allow` and `approve-action` are on the gate's deny list for the agent's command line (read as the shell reads them), a request of the agent to the board's port is refused, and the board's approvals need the paired browser {src:.harness/policies/gate.json#L131-L137} {src:.harness/engine/modules/gate/handler.py#L501-L598} {src:.harness/engine/modules/task/boardserve.py#L1-L20}.

## Tool packs internals: `harness wait --approval` waits for the person without a model call

The agent is told in the hold text to run `harness wait --approval <code>`. `run_approval_wait` is one terminal process that reads the entry in `action-approvals.json` every second (`approvals.find`) and calls no model. Its timeout is clamped to 5 to 570 seconds, default 540, under the 10 minutes after which VS Code returns a terminal call to the agent {src:.harness/engine/modules/gate/wait.py#L122-L160} {src:.harness/engine/modules/gate/commands.py#L162-L297}.

It returns at once on any state but `pending`: `approved` (run the same command again, once, within the minutes), `opened` (a connection was opened: run it again), `dismissed` (exit code 1, with the reason and the person's line), and `used` (the call was approved and has already run, so a late wait must not make the agent run it again). On timeout it marks `timeout`, and returns `waiting` with text telling the agent to end its turn and say what waits; the board wakes it when the person decides later {src:.harness/engine/core/outbox.py#L498-L508}. While it runs it writes a beat into the entry's `wait` field every 5 seconds; the board treats a beat younger than 20 seconds as "the agent waits" (`running_wait`), and a wait that dies (terminal closed, an error) writes `gone` {src:.harness/engine/core/outbox.py#L155-L302} {src:.harness/engine/core/approvals.py#L150-L244}.

The gate lets it through with no special case. `harness` is in `READ_ONLY_PROGRAMS`; `_wait_run` only unwraps `--run`, so `--approval` has nothing to judge; the command is not on the harness-command deny list, which holds `approve-action` and `task allow`; the beat is written by the harness's own Python process, not by an agent write; and the wait cannot approve anything, since it only reads the entry. The test `test_outbox.py` pins that `harness wait --approval C` and its spellings get no gate decision while `approve-action` is still denied {src:.harness/engine/modules/gate/external.py#L158-L190} {src:.harness/engine/modules/gate/external.py#L1472-L1525} {src:.harness/tests/test_outbox.py#L99-L109}. That the agent uses the wait, and then ends its turn, is a rule it follows from the hold text, not a lock {src:.harness/engine/core/messages.en.json#L444-L444}.

## Tool packs internals: pinfiles.py pins the files a held call reads

An approval is for one command line, but `sqlcmd -i load.sql` runs whatever the file holds when it runs. `core/pinfiles.py` therefore keeps a sha256 of each file the command names, taken when the person approves, and compares again when the agent runs the command {src:.harness/engine/core/pinfiles.py#L1-L171}.

Which words count: `words()` splits the line with quotes removed, and `--opt=value` or `@value` gives its value too. Each word is looked up as a path in the terminal's own folder, a folder a `cd` of the line goes to, the repository root, then the task folder; the first place the file exists is the one, and the path is resolved, so a symlink that points outside is not pinned. Only a file inside the task folder or a target repository counts (`find`); a file elsewhere is not pinned and not shown. The key is the path relative to the task folder, or `repo:<name>/<path>` for a target repository; with no task the pin is empty. At most 12 files are pinned (`MAX_FILES`), and a file over 8 MB is pinned by its first 8 MB and its size {src:.harness/engine/core/pinfiles.py#L1-L171}. What is not pinned: the 13th and later files, files a script reads or imports, here-document or pipe input, and text inside `-Q`.

Two checks use it. (1) The card sends its pin as `seen`; the page returns what View showed; when the request carries `seen` and the files now are not those, `approve_action` raises `FileChanged` and approves nothing, so the person presses View again. A terminal approval has no `seen`, so only the second pin applies {src:.harness/engine/core/outbox.py#L155-L302}. (2) At run time `_changed_files` compares the kept pins with the files now over the union of both sets, and a changed, deleted or newly appeared file all count. `consume` marks the approval `used` even when files changed, so the call is held anew with a new code and a note naming the files. A read error says changed (fail closed); an approval made before 1.7.38, with no files kept, is not held to files {src:.harness/engine/modules/gate/handler.py#L405-L469} {src:.harness/engine/core/pinfiles.py#L1-L171}. There is no lock between the comparison and the program's own read of the file, so a change in that small window is not seen.

## Tool packs internals: how the agent is told about connections, a little at a time

The agent is told in layers, so a prompt does not carry every host and port. The layers are text and context only; code enforces that a call it cannot place is refused and a write is held. **Layer 0**, at chat start: the SessionStart hook gives the line `connections.kinds.context` with kinds and counts (`3 SQL Server, 1 Azure DevOps`), never a name; nothing is added when there are no connections; extra lines say how many connections are not in this VS Code window (`away`), whether it is unknown what the window carries (VS Code was not started from the board), and which go through `harness as` {src:.harness/engine/modules/gate/handler.py#L695-L720} {src:.harness/engine/core/connections.py#L767-L851}.

**Layer 1**, `harness connections find <words>`: it first reports a fault in the connection list or in `packs.json` and tells the agent not to wait for connections to be set up. A word fits a connection when it is, or starts (three or more letters), a word of the name, type, `about`, label, `repos` or `domains`; the weight is name 3, type 2, the rest 1; an environment word must be the word itself and filters out connections of other environments (a ticket board with no environment is kept); the connection that fits the most words comes first. At most five are shown, with "N more fit and are not shown". Each line is `alias  (Type, ENV)  about`, then `call:` with the call line (prefixed `harness as <alias> --` when the window does not carry the identity). The text then tells the agent to ask the user when unsure, never guess, and not to preselect PROD or put a connection the user just turned down first {src:.harness/engine/core/connections.py#L767-L851} {src:.harness/engine/modules/gate/commands.py#L162-L297}.

**Layer 2**, details on demand: at UserPromptSubmit when the prompt names an alias as a whole word (`named_servers`), and at PostToolUse the first time a terminal command reaches a connection, whether it worked or not (`first_reach`; a held call did not run, so the card speaks then). Each happens once per session per connection (the `told` list). The text has the call line first, then facts (the connection's fields, never an account), `about`, the pack's skills and program, a line when a `tool` sign-in (such as `az login`) is missing or a needed program is not on the computer, and whether the person opened the connection for this task {src:.harness/engine/modules/gate/handler.py#L501-L598}. **Layer 3**, the held card: the deny text gives the agent the `wait --approval` command and the button names (`Open <name> for this task`; a connection that opens only linked items has its own words) {src:.harness/engine/modules/gate/rules.py#L136-L190}.

## Tool packs internals: identities, `harness as`, and reach.py

A connection's identity is kept per type: `env` (variables), `netonly` (a Windows account the window holds), `keyfile`, `token` (one secret), or `tool` (the program keeps its own sign-in, such as `az login`: the harness keeps no secret, only the account name the test answered, as `HARNESS_TOOL_<PROGRAM>_USER`, one per program shared by every connection of the type). An MCP type has no test: the test returns state `mcp` {src:.harness/engine/core/connections.py#L37-L45} {src:.harness/engine/core/connections.py#L499-L538} {src:.harness/engine/core/connections.py#L907-L1017}.

VS Code gets the identities through the process. `plan` decides which chosen identities the window holds itself (`direct`: one Windows account per window, one value per variable) and which go through `harness as <alias> -- <command>` (`wrap`); `launch` starts VS Code with the variables in its environment, and for a netonly account on Windows through `CreateProcessWithLogonW` with `LOGON_NETCREDENTIALS_ONLY` (what `runas /netonly` does: the account is used for the network only and the password is never on a command line); a pack's `launch/*.cmd` script does the same for a team that does not save identities {src:.harness/engine/core/connections.py#L1239-L1334} {src:.harness/engine/core/netonly.py#L1-L10}. `run_as` refuses (exit 2) any command that is not a call of that connection, so the identity never goes to `echo` or `env`. A VS Code started by hand has no record, so each connection whose identity must be in the window is marked `unknown` and told with the prefix, which works either way {src:.harness/engine/core/connections.py#L717-L738}.

Why the hooks test some connections: a hook is started by VS Code and inherits its environment, which the board cannot see; so the identity a window-only connection needs is probed from the hook. At SessionStart `watch_reach` calls `reach.start`, which starts `tools reach --probe` detached and returns at once, unless every probe answered well in the last 30 minutes (`FRESH_MINUTES`). After a call of a listed system, PostToolUse calls `note_call`: the type's `denied` pattern in the output means the identity was refused, a `down` pattern or an answer is recorded. States (`ok`, `denied`, `failed`, `unknown`) are kept in `.harness/runtime/state/reach.json` under `<system>:<env>`, with `who` (the first group of `expect`, never a password). A probe is cut at 5 seconds, and one that got no answer is run once more after one second {src:.harness/engine/core/reach.py#L1-L196} {src:.harness/engine/modules/gate/handler.py#L601-L693} {src:.harness/engine/core/systems.py#L33-L38}.

In 1.8.3 the hook does not probe everything in VS Code's identity. `tools reach --probe` first takes the connections the board can check itself (`probe_keys`: a `tool` identity, or an identity kept in `.env`) and checks them as the board does, with the saved identity, the tool folders and the CA bundle; only the rest, the window-only identities, are probed in the hook's environment. The reason is that the first-step run in VS Code's environment had none of the three for a connection signed in on the board, so it wrote "failed" or "denied" over the board's own "ok" {src:.harness/engine/modules/gate/commands.py#L162-L297} {src:.harness/engine/core/connections.py#L907-L1017}. `harness doctor` reports and writes nothing to the reach state: the board runs it in a child with the PATH of a new terminal, and what it finds there must not replace what the board found {src:.harness/engine/core/reach.py#L1-L196}. The board's own Test and sign-in write their result through `reach.record`, to the same file. A doc and code disagreement: `.harness/.env.example` still shows the old keys `HARNESS_SERVER_<ALIAS>_<FIELD>` and `.harness/kinds/`, while the code reads `HARNESS_CONNECTION_` {src:.harness/.env.example#L1-L8} {src:.harness/engine/core/connections.py#L37-L45}.

## Tool packs internals: evidence `E<n>`, and why the reviewer may run the reads again

Every run saved in a task has a number `E<n>`, whichever way it came: a run the person did (`task run record`), a run the agent did itself, or a test run (`task test record`). The number is the task's `evidence_n` in `task.json`, allocated under the task's lock when the run is recorded; it is written in the run's heading (`## Run 2 (E7)`) and in a marker line `<!-- evidence E7 by agent at <time> env <ENV> leave=... -->` that the board reads. Documents at the task's root cite it as `[E7]`; a figure with no `[E...]` is a claim {src:.harness/engine/modules/task/evidence.py#L1-L126}.

The skill `generic-evidence-run` gives the agent this flow: run the exact command in the terminal (the gate decides whether it runs); save `RUNS/<ENV>/steps.md` whole, one step per command, command and output as printed; run `harness task run record --env <ENV> --steps-file ... --run-by agent`; cite `[E<n>]` where the fact is used. `--run-by agent` means the agent ran the environment itself: no screenshot is needed (the missing-screenshot warning is skipped), the "who" is the agent, and the marker carries `leave=` {src:.harness/engine/modules/task/runrecord.py#L33-L80}. The code looks each recorded command up in the gate's call notes (`.task/calls.jsonl`, written by the gate for a call that went through) and writes how it was let through: `allow` (a read), `plan`, `runner`, `opened`, `approved` with its code, or `unknown` when nothing was noted {src:.harness/engine/core/calls.py#L1-L90}. `task test record --run-by agent` also requires the person's grant of that environment (`task test runner`); `task run record --run-by agent` checks none, and the help text that says it needs the grant is text only {src:.harness/engine/modules/task/testrecord.py#L255-L257}. The Evidence tab lists each number, who ran it, what let it through, and where it is cited; a number nobody cites is grey {src:.harness/engine/modules/task/evidence.py#L1-L126} {src:.github/skills/generic-evidence-run/SKILL.md#L64-L64}.

Honest limit: the output text is what the agent wrote into `steps.md`; the code does not compare it with the terminal, and `RUNS/` is not a path only the CLI writes (`cli_owned_paths` lists `.task`, `OUTBOX`, `REVIEW`, `SNAPSHOT`, `READ` and the diffs, not `RUNS`) {src:.harness/policies/gate.json#L24-L34}. So the saved output is the agent's own transcription of what came back, which is why the reviewer runs the reads again. The reviewer's text says: when the review package lists the runs the task cites, run the reads again on the same environment and compare with the saved output; a write or a procedure is refused to you, judge it by what was saved; a differing result is a finding {src:.github/agents/reviewer.agent.md#L33-L34}. In the gate, a subagent's call passes only on policy `allow` (a read), because the person's leave (a plan, an opened connection, an approval) is the main agent's; the reviewer runs in the same VS Code identity and writes no evidence {src:.harness/engine/modules/gate/handler.py#L213-L333}.

## Tool packs internals: limits, and what code does not check

- **The type's refuse list and the secret check are different things.** The refuse list (statements) is judged by `statements.judge`; the refusals about `.harness/.env` and sign-in variables are `check_secrets`, which refuses a read of the file, a dump of the environment, and a command that names a sign-in variable unless every call in it goes to that variable's own connection {src:.harness/engine/modules/gate/handler.py#L601-L693}.
- **MCP tools no pack names are not judged**, and a named MCP write only asks, with no code and no linked-item check {src:.harness/engine/modules/gate/handler.py#L213-L333}.
