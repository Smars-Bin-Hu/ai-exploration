## Task: what it is

A task is one piece of work kept as a folder on disk, so that it outlives the chats that do it. The folder `.workspace/sandbox/tasks/<task name>/` holds a handover note (`TASK.md`), the requirement (`REQ.md`), the plan (`PLAN.md`), the results, and a state file `.task/task.json` that harness code writes; the agent's edit tools, and a terminal command that names the file, are refused on it {src:.harness/engine/core/tasks.py#L1-L37} {src:.harness/policies/gate.json#L24-L34}. The agent is told to open a task before it produces or changes files; the code does not force it to {src:AGENTS.md#L46-L47}. Any later chat can open the task and go on from the files. A task stays open until the person accepts or closes it, or, for a written-back development or knowledge base task, until the board closes it once nothing waits; `task close` itself has no check that a person runs it, only the gate's refusal on the agent's command line {src:.harness/engine/modules/task/tasklife.py#L177-L193} {src:.harness/engine/modules/task/accept.py#L1-L11} {src:.harness/engine/modules/task/accept.py#L184-L218} {src:.harness/engine/modules/task/commands.py#L123-L133}.

Every task has a kind and a tier. The kind says what "done" means: `qa` (a question or a look at a server or files), `rca` (root cause analysis), `design`, `dev` (development), `test`, `kb` (knowledge base update) or `other`. The tier says which files the folder has: `light` has `TASK.md`; `medium` adds `REQ.md`, `REQ/`, `REF/` and `LOG.md`; `full` adds `TODO.md`, `DEV/` and `TEST/`. Each kind has a default tier: `qa` light; `rca`, `design` and `other` medium; `dev`, `test` and `kb` full {src:.harness/engine/core/tasks.py#L19-L23} {src:.harness/engine/modules/task/tasklife.py#L39-L45}.

## Task: how it works

Five parts and the person do the work of a task, and the figure shows who calls whom and the life of a task.

![The parts of a task and who calls whom, above, and the life of a task from opened to closed, below](fig/pattern.svg)

The parts, as the figure draws them:

- The **agent** is a chat in VS Code and holds one task at a time {src:.harness/engine/core/state.py#L1-L10}.
- The **task hook** tells the agent at session start and at every prompt where its task stands: kind, tier, round, the next step, the write scope and the checks {src:.harness/engine/modules/task/handler.py#L93-L126} {src:.harness/engine/modules/task/handler.py#L162-L177}.
- The **gate** keeps the edit tools of a chat that holds an open task inside its folder; a chat with no task is not bound {src:.harness/engine/modules/gate/handler.py#L64-L94}.
- The **task** is the folder: handover note, requirement, plan, code, state. Its state file is written by harness code; the agent's edit tools are refused on it {src:.harness/policies/gate.json#L24-L34}.
- The **task commands** (`harness task ...`) open, approve, write back and close, and each checks the facts it depends on before it acts {src:.harness/engine/modules/task/task.py#L1-L10}.
- The **person** asks, approves and accepts. The agent opens tasks, delivers results and writes back.

The life of a task has two paths. A task that changes a repository (`dev`, `kb`) is opened; its requirement is confirmed; its plan is approved; the agent writes code in `DEV/`; the write-back is approved; the files are written back; then the board closes the task once the agent has stopped and nothing else waits, without waiting for the commit {src:.harness/engine/modules/task/task.py#L570-L612} {src:.harness/engine/modules/task/task.py#L428-L475} {src:.harness/engine/modules/task/task.py#L984-L1024} {src:.harness/engine/modules/task/accept.py#L184-L218}. A task whose result stays in the folder (analysis, design, test, question) is opened; the result is written in the folder (an analysis or a design at its root, test results in `TEST/` and run records in `RUNS/`, a Q&A answer in `TASK.md`); the agent delivers it with a summary (`task deliver`), and the person accepts it with **Accept and close** {src:.harness/engine/modules/task/taskstages.py#L122-L139} {src:.github/instructions/workspace.instructions.md#L15-L16} {src:.github/instructions/workspace.instructions.md#L20} {src:.github/skills/harness-my-task/SKILL.md#L84} {src:.harness/engine/modules/task/accept.py#L45-L68} {src:.harness/engine/modules/task/accept.py#L167-L181}. Confirming the requirement, approving the plan and the write-back, and accepting are the person's moves; closing a written-back task is the board's. The requirement's confirmation line in `REQ.md` is also plain text the agent can write (see the section "Task: limits"). Any later chat may open a task again, closed or not {src:.harness/engine/modules/task/tasklife.py#L177-L193}. Between the plan approval and the write-back, the person may switch the task to autorun (since 1.8.0): the task's agent then only schedules, and a `worker` subagent does each open step of `TODO.md` in a fresh context; the file 20 Autorun explains it {src:.harness/engine/modules/task/autorun.py#L1-L5}.

## Task: how it moves from one stage to the next

A task's stage is not a value the agent sets: it is worked out each time from the files and the state, so a task whose requirement changed falls back to the right stage by itself {src:.harness/engine/modules/task/taskstages.py#L1-L15}. For `dev` and `kb` the stages are requirement, plan, developing, write-back, done; for `rca`, `design` and `other`, doing and done; for `test`, the guide and one stage per environment; `qa` has none {src:.harness/engine/modules/task/taskstages.py#L56-L67}.

What moves the work forward is the agent, told by text; what stops it at each gate is code. The text: the hook's next-step line, the skill `harness-my-task` and the workspace instructions tell the agent to write `REQ.md`, ask the person to look at it, write `PLAN.md`, stop and give the link {src:.harness/engine/core/messages.en.json#L14-L15} {src:.github/skills/harness-my-task/SKILL.md#L75-L99}. The code at each gate:

- **Requirement to plan.** `task approve-plan` refuses a plan while `REQ.md` is still the bare template (the template's opening placeholder is still there), or its "User confirmed" line is not filled in, or what it asks changed since it was confirmed; `--with-req` confirms the requirement and approves the plan with one code {src:.harness/engine/modules/task/task.py#L428-L469} {src:.harness/engine/modules/task/task.py#L481} {src:.harness/engine/modules/task/task.py#L551-L567}. The confirmation is read from that text line, which the agent can write, and a missing `REQ.md` or line is not checked at all {src:.harness/engine/modules/task/taskreview.py#L88-L110}.
- **Plan to developing.** For the chat that holds the task, the gate refuses the edit tools any write under `DEV/` until the plan is approved as it is now, for the requirement as it is now; a chat with no task is not bound, but nothing in `DEV/` is written back without an approved plan and an approved write-back {src:.harness/engine/modules/gate/handler.py#L86-L90} {src:.harness/engine/core/tasks.py#L152-L164}.
- **Developing to write-back.** `task promote --dry-run` needs an approved plan and, when the person switched checks on, enough passes of the independent check {src:.harness/engine/modules/task/task.py#L911-L928} {src:.harness/engine/modules/task/taskreview.py#L563-L568}. `task promote` needs the person's approval of the same plan digest {src:.harness/engine/modules/task/task.py#L941-L944}. In autorun nothing is written back on the way: the run ends with the promote plan, and the write-back still waits for the person {src:.harness/engine/modules/task/autorun.py#L9} {src:.harness/engine/modules/task/autorun.py#L21}.
- **Done.** Closing is the person's: the gate refuses `task close` on the agent's command line, and the agent is told never to close a task; the command itself has no person check, so a script the agent runs is not stopped {src:.harness/policies/gate.json#L138-L144} {src:.harness/engine/modules/task/commands.py#L123-L133}.

So the answer to "is the workflow a skill or code" is both: the skill says the order, the code holds the gates, and a person holds the keys of the gates.

## Task: how it differs from a chat session

A session is one Copilot chat and lives as long as that chat; a task outlives its sessions. The two point at each other, so either can end or change without the other: the session's state names the one task it holds (`active_task`), and the task's state names its latest session (`session_id`) {src:.harness/engine/modules/task/task.py#L140-L218}.

![What lives with the session and what lives with the task, and the pointer each keeps to the other](fig/task-vs-session.svg)

What lives with the session: the Copilot chat with its context and transcript, kept by Copilot under `~/.copilot/session-state/<id>/` {src:.harness/engine/core/copilot_events.py#L1}; the harness's session state `.harness/runtime/state/<surface>/<session>.json`, with `session_id`, `active_task` (the one task it holds), `parent_session_id` (set for a subagent's session), `admin` (admin mode, which holds no task), the running subagents (reviewer, mapper, worker) `modules.task` (per-prompt counters) and, since 1.8.3, `modules.gate` (the marks of a super agent chat and of a question turn), written by `core/state.py` under a lock {src:.harness/engine/core/state.py#L1-L10} {src:.harness/engine/core/paths.py#L86-L87}; and the hook log `.harness/runtime/logs/<surface>/<session>.jsonl` {src:.harness/engine/core/logs.py#L35-L36}.

What lives with the task: the task files (`TASK.md`, `REQ.md`, `PLAN.md`, `TODO.md`, `LOG.md`, `DEV/`, `REQ/`, `REF/`), which any session reads by path, and `.task/task.json`, written by harness code (the command line, the hook and the board), under a lock, and replaced whole at each write {src:.harness/engine/modules/task/task.py#L82-L98} {src:.harness/engine/core/state.py#L129-L146}. Since 1.8.1 the lock is one the operating system holds for the process, in a file in the system's temp folder: it is freed when that process ends, a slow holder is never taken over, and a call waits up to 20 seconds for it {src:.harness/engine/core/state.py#L29-L34} {src:.harness/engine/core/state.py#L162-L226}. Its fields are listed in the section "Task: where its record is kept, and what is in it".

The rules between them: one session holds at most one task, and opening another leaves the first open {src:.harness/engine/modules/task/task.py#L140-L160}. Any later session may open the task again: a new holder, the same state. A subagent's session inherits its parent's task; a subagent or an admin session cannot open one {src:.harness/engine/core/state.py#L303-L354} {src:.harness/engine/modules/task/tasklife.py#L126-L135}. Copilot compacts a chat as its context fills, at about 80%; the task's files do not depend on the chat {src:.harness/policies/task.json#L3}.

## Task: where its record is kept, and what is in it

A task's record is its folder, `.workspace/sandbox/tasks/<task name>/`, on the person's computer; the folder is ignored by git {src:.harness/engine/core/tasks.py#L19-L37} {src:.gitignore#L27-L30}. The files, by tier {src:.harness/engine/modules/task/tasklife.py#L39-L45}:

- `TASK.md`: the handover note a new session reads first: kind, tier, status, what is being done, the next step, the decisions, the open questions {src:.harness/contracts/templates/task/en/TASK.md#L1-L23}.
- `REQ.md`: the requirement as the agent understands it, with the "User confirmed" line and the sections What to do, What not to do, Done when, Source, Not clear yet, Changes {src:.harness/contracts/templates/task/en/REQ.md#L1-L42}.
- `REQ/`, `REF/`, `INBOX/`: what the person gave (documents, reference files, results given on the task page); for the chat that holds the task, the gate refuses the agent's edit tools there {src:.harness/engine/core/tasks.py#L37} {src:.harness/engine/modules/gate/handler.py#L91-L93}.
- `PLAN.md`, `TODO.md`, `LOG.md`; in autorun, `QUESTIONS.md` (the questions of parked steps, asked at the end) {src:.harness/engine/core/autorunfiles.py#L15-L22}; `DEV/` for code that goes back to a repository; `TEST/` for test results; results that stay in the task (`RCA.md`, `DESIGN.md`) at the root.
- Files only the command line writes: `.task/` (state and the base versions of fetched files), `REVIEW/` (each independent check and its verdict), `SNAPSHOT/`, `OUTBOX/`, `READ/`, `CHANGES.diff`, `PROMOTE-PLAN.diff` {src:.harness/policies/gate.json#L24-L34}.
- `READ/`: code of a target repository copied only to be read, with `task fetch --read` (since 1.7.42), as the base branch has it; it needs no plan and is never written back {src:.harness/engine/core/tasks.py#L30} {src:.harness/engine/modules/task/task.py#L676-L703}.

The state file `.task/task.json` holds: the task's path, name, kind and tier; `status` (open or closed); `round` (one more each time a written-back task is opened again); `session_id` (the latest holder) and `sessions[]` (every pick-up, the last 100); `req` (the digest of the confirmed requirement); `plan` (the approved plan's digest and the requirement digest it was approved for); `promote` (none, dry_run, done or partial, with the approved digest); `waiting` and `paused`; `deliver` and `handoff`; `review`, `allow_conn` and `links`; `autorun` (the run's state and counts; its models and spend limit are in `.task/autorun.json`, and each worker call is a start and an end line of `.task/autorun-run.jsonl`) {src:.harness/engine/modules/task/autorun.py#L246-L254} {src:.harness/engine/core/autorunfiles.py#L20-L22}; `events[]` (the history, the last 200); `rounds[]` (earlier write-backs); and `chat` (the bound VS Code chat) {src:.harness/engine/modules/task/task.py#L37-L40} {src:.harness/engine/modules/task/task.py#L165-L190} {src:.harness/engine/modules/task/task.py#L234-L251} {src:.harness/engine/modules/task/task.py#L469}.

When a task closes, the chat's rounds (prompts, the agent's text, tool names, times, credits; no thinking and no tool results) are copied into `.task/transcript.jsonl`, and a report is written to `.workspace/reports/tasks/<task name>/report.md` {src:.harness/engine/modules/task/task.py#L386-L398} {src:.harness/engine/modules/task/chatrounds.py#L1-L10}. Closing changes only the state: the folder stays where it is {src:.harness/engine/modules/task/tasklife.py#L10-L11}.

## Task: how a new chat continues the same task

A new chat continues a task from its files, by name. A session that holds no task is told at every prompt which tasks are open (the newest five) and to run `harness task open <task name>` when the person means one of them {src:.harness/engine/modules/task/handler.py#L129-L142} {src:.harness/engine/core/messages.en.json#L107}. So the person says "go on with" and the task's name, and the agent, following the skill `harness-my-task`, runs `task open` {src:.github/skills/harness-my-task/SKILL.md#L58-L65}. On the board, **Go on in a new chat** on the task page starts a new chat in VS Code that picks the task up; what was said only in the old chat, and is in no task file, does not come along {src:.harness/engine/core/messages.en.json#L2383-L2384}.

`task open` makes the new session the task's holder: it records the pick-up in `sessions[]`, sets `session_id`, clears the waiting mark and a pause, and sets the session's `active_task` {src:.harness/engine/modules/task/task.py#L174-L209}. It refuses an unknown session, a subagent, an admin session and a write-back stopped halfway {src:.harness/engine/modules/task/task.py#L140-L177}. Its answer tells the agent to read `TASK.md` first, then `REQ.md`, `REQ/` and `REF/` {src:.harness/engine/modules/task/tasklife.py#L155-L160} {src:.harness/engine/core/messages.en.json#L14-L15}. A closed task is opened again as it was; a written-back task opened again starts a new round, with the old `DEV/` and plan moved aside and a new plan to approve {src:.harness/engine/modules/task/task.py#L174-L183} {src:.harness/engine/modules/task/task.py#L234-L251}.

## Task: going back to an earlier state (rewind, and the snapshots at the gates)

A task can go back to how its folder was before a message of the person, with rewind on the task page (since 1.6.109). At each message of the person in the chat that holds the task, the hook keeps a restore point of the task folder in `.task/rewind/`: a list of the files with their sha256, each content stored once; the newest 30 points stay, and a file over 20 MB is listed but not kept (`board.rewind` in `.harness/policies/task.json`) {src:.harness/engine/modules/task/rewind.py#L1-L7} {src:.harness/engine/modules/task/handler.py#L265-L270} {src:.harness/policies/task.json#L49}. A point does not keep `.task/`, the person's `REQ/`, `REF/` and `INBOX/`, the copies of the gates and checks, or `_deleted/` {src:.harness/engine/modules/task/rewind.py#L36}. Rewind runs only from the paired browser, only in the chat linked to an open task, in the same round, with no write-back since that message; it puts the kept files back, moves the files that came later into `_deleted/rewind-<time>/` (nothing is deleted), first takes a point so the rewind can be undone, and cuts the chat back to before the message {src:.harness/engine/modules/task/boardserve.py#L1608-L1612} {src:.harness/engine/modules/task/boardserve.py#L1899-L1901} {src:.harness/engine/modules/task/rewind.py#L211-L225} {src:.harness/engine/modules/task/rewind.py#L306-L338}. The task's state is not rewound: approvals, events and checks stay, and since they are bound to the contents, a plan put back to before its approval waits for an approval again {src:.harness/engine/modules/task/rewind.py#L9-L11}.

Separately, the command line copies the task's result files, with a sha256 manifest, to `SNAPSHOT/<gate>-<time>/` at each gate: when the plan is approved, before each independent check (the copy the reviewer is given) and before a write-back dry run {src:.harness/engine/modules/task/tasksnap.py#L1-L6} {src:.harness/engine/modules/task/task.py#L474} {src:.harness/engine/modules/task/taskreview.py#L394} {src:.harness/engine/modules/task/task.py#L927}. A snapshot older than 14 days is removed when a new one is made, the newest always stays, and a file over 5 MB is listed, not copied (`snapshots` in `task.json`) {src:.harness/policies/task.json#L17-L20} {src:.harness/engine/modules/task/tasksnap.py#L137-L149}. Snapshots are records to read (`harness task snapshot list`); no command puts one back {src:.harness/engine/modules/task/commands.py#L247-L255}.

## Task: who approves, and why the agent cannot approve its own plan

The agent cannot approve its own plan by the ways the harness gives it. Three things stand in the way. First, the gate refuses, on the agent's command line, `task confirm-req`, `task approve-plan`, `task approve-promote`, `task recover`, `task review set`, `extend`, `waive` and `dismiss`, `task test runner`, `task pause`, `resume`, `offwork` and `onwork`, `task autorun on`, `task allow` (every spelling, since 1.8.0), `task board` (except `--once`), `approve-command`, `approve-action`, `admin on` and `doctor --accept`, and reads them the way the shell does, so a quote, a variable or `xargs` does not hide them {src:.harness/policies/gate.json#L131-L137} {src:.harness/engine/modules/gate/harnesscmd.py#L1-L8}. Second, each approval command needs a person at their own terminal, with a keyboard and a screen, and a typed code {src:.harness/engine/core/approval.py#L28-L58}. Since 1.7.39 the board's Terminal window also counts as the person: the board gives each `harness` command typed there a one-time code that stands for the keyboard, so the person-only commands that ask for no code, such as `task pause`, `task review set` or `task allow`, run there; it gives no keyboard input, so a command that asks the person to type a code, such as `task approve-plan`, `approve-action` or `admin on`, is refused there. The agent gets no such code, since it has no paired browser {src:.harness/engine/core/boardperson.py#L1-L10} {src:.harness/engine/modules/task/boardterm.py#L139-L143} {src:.harness/engine/core/approval.py#L50-L56} {src:docs/04-reference.md#L9}. Third, on the board an approval goes through the buttons of the browser paired with the board server, which runs the same function with the code the person types {src:.harness/engine/modules/task/boardserve.py#L11-L16} {src:.harness/engine/modules/task/boardserve.py#L819-L830}; the agent cannot start the server (the gate refuses it), and its requests to the board's port are refused {src:.harness/engine/modules/task/boardserve.py#L1-L17} {src:.harness/engine/modules/gate/handler.py#L580-L585}. The board's super agent (1.8.3) approves nothing either: its chat may only read, and its proposals are cards of the board's own buttons, which act only when the person presses them {src:.harness/engine/modules/gate/superagent.py#L78-L89} {src:.harness/engine/modules/task/superact.py#L1-L7}.

The code the person types is the first six characters, in capitals, of a sha256 of what is approved: `PLAN.md` for the plan, `REQ.md` for the requirement, the write-back plan for a write-back {src:.harness/engine/core/approval.py#L17-L25}. `task approve-plan` checks `PLAN.md` again under the task's lock before it records the approval, so a plan changed while the person read it is refused {src:.harness/engine/modules/task/task.py#L460-L471}. `task approve-promote` looks at the write-back plan again under the lock only when the code came more than three seconds after the plan was shown (since 1.7.43, so a code typed on the board at once is not checked twice); `task promote` compares the plan with the approved digest again before it writes {src:.harness/engine/modules/task/task.py#L42} {src:.harness/engine/modules/task/task.py#L1014-L1020} {src:.harness/engine/modules/task/task.py#L941-L944}.

![The board's approval window for a plan: the file to read, what the approval opens, and the six-capital code to type](img/approve-dialog.png) The record (`plan.approved_sha256` and the requirement digest) is compared with the files before each edit-tool write to `DEV/`; a plan changed after the approval is not approved {src:.harness/engine/core/tasks.py#L159-L164}.

Two exceptions narrow this. The requirement's confirmation is the "User confirmed" line of `REQ.md`, a text line the agent can write {src:.harness/engine/modules/task/taskreview.py#L88-L110}. The approval records live in `.task/task.json`; a terminal command that names it is refused, but a script the agent runs is checked only for guardrail paths {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}.

## Task: what happens when the requirement changes after the plan was approved

When what `REQ.md` asks for changes after the plan was approved, the approval lapses and, for the chat that holds the task, `DEV/` closes again to the edit tools. The plan's approval keeps the digest of the three sections of `REQ.md` that say what is wanted (What to do, What not to do, Done when); a change there makes the plan count as not approved {src:.harness/engine/core/tasks.py#L117-L164}. A change to the confirmation line, the sources, the open questions or the change record does not undo the approval {src:.harness/engine/core/tasks.py#L122-L126}.

What follows, in code: for the chat that holds the task, the gate refuses the agent's edit-tool writes to `DEV/` and tells it to check the plan, stop, and ask the person to confirm the requirement and approve the plan again {src:.harness/engine/modules/gate/handler.py#L86-L90} {src:.harness/engine/core/messages.en.json#L427}. `task approve-plan` alone is refused; the person confirms the changed requirement and approves the plan with one code (`--with-req`, or **Approve plan** on the task page) {src:.harness/engine/modules/task/task.py#L444-L469}. The dry run, the write-back approval and the write-back all need the plan approved as it is now {src:.harness/engine/modules/task/task.py#L915} {src:.harness/engine/modules/task/task.py#L993}. The work already in `DEV/` stays.

What is asked by text: the hook tells the agent at every prompt to change `REQ.md` first, with a line in its change record, whenever the person asks for something different {src:.harness/engine/core/messages.en.json#L108}. The code sees only the file: a change said in the chat and never written into `REQ.md` does not undo the approval.

In an open task of any kind, a changed requirement is written into `REQ.md` and the work goes on in the same task {src:.harness/engine/core/messages.en.json#L108}. After a write-back is done, the same goal goes on as a new round of the same task: `task open` moves the old `DEV/` and plan aside and asks for a new plan {src:.harness/engine/modules/task/task.py#L174-L183} {src:.harness/engine/modules/task/task.py#L234-L251}. When a closed task of a kind with no write-back (`rca`, `design`, `test`, `other`, `qa`) is opened again, the agent is told that it has no new round and that a changed requirement is a new task forked from it {src:.harness/engine/modules/task/tasklife.py#L189-L192} {src:.harness/engine/core/messages.en.json#L17}.

## Task: what the agent may write

For a chat that holds an open task, the edit tools write only inside that task's folder. The edit tools are the VS Code tools the harness lists as edit or create tools (`create_file`, `replace_string_in_file` and the like); a tool it does not list, such as a file-writing MCP server a team adds that no tool pack names, gets no path check {src:.harness/engine/adapters/tool_kinds.json#L1-L10} {src:.harness/engine/modules/gate/handler.py#L778-L788}. Inside the folder, `REQ/`, `REF/` and `INBOX/` are refused always and `DEV/` until the plan is approved {src:.harness/engine/modules/gate/handler.py#L64-L94}. For every chat, task or not, the edit tools are refused on files only the command line writes (`.task/`, `REVIEW/` and the others), inside any `.git` folder, and inside a target repository's working tree; they are refused on guardrail files too, except in a chat the person switched to admin mode, where only `.harness/runtime/**`, the policy's `admin_locked_paths` and the integrity-list folder (`~/.copilot-harness`, or `HARNESS_INTEGRITY_DIR`) stay closed {src:.harness/engine/modules/gate/handler.py#L38-L61} {src:.harness/engine/core/guardrails.py#L21-L61}. While the task's autorun is on (since 1.8.0), the gate narrows the folder again: the edit tools of the task's own chat may write only `TODO.md`, `TASK.md`, `LOG.md` and `QUESTIONS.md`, and the worker's edit tools anything else the rules above allow, but not those four {src:.harness/engine/modules/gate/handler.py#L75-L109}. A question the person asks a task through the board (a message that starts with `/harness-ask`, since 1.8.3) makes that one turn read only: the gate refuses every write and every harness command but a few read-only ones, until the next normal prompt {src:.harness/engine/modules/gate/askturn.py#L1-L5} {src:.harness/engine/modules/gate/askturn.py#L42-L53}.

The terminal is not confined to the task folder. A terminal command is refused when it names a guardrail file, a command-line-owned file, or a `.git` path as a write target, in full or by a relative path after a `cd` in the same command line (the terminal's real working folder is not used), or a target repository folder by its full path only (also after a `cd` to that full path), or when a script it runs is found, as best effort, to write a guardrail file; other writes pass {src:.harness/engine/modules/gate/handler.py#L117-L139} {src:.harness/engine/modules/gate/terminal.py#L65-L117} {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}. A session that holds no task, or whose task is closed, is not kept to any folder by the edit-tool check {src:.harness/engine/modules/gate/handler.py#L67-L72}. The agent is told by text to work in a task and write only in its folder {src:.harness/engine/core/messages.en.json#L41} {src:.harness/engine/core/messages.en.json#L43}. The harness writes the approved files into a target repository only through `task promote`, after the person's approval; apart from that, a first `task fetch` of a repository in a round and every dry run fast-forward its local base branch to the remote, and stop on local changes (the file 16 Write-back) {src:.harness/engine/modules/task/basesync.py#L1-L14}; a git command the person approves with `approve-command` can also write there, and a write the text checks cannot see (a script, a path made at run time) is not stopped {src:.harness/engine/modules/task/task.py#L941-L957} {src:.harness/engine/modules/gate/handler.py#L153-L162} {src:.harness/engine/modules/gate/terminal.py#L1-L5}.

## Task: what "waiting for you" means

"Waiting for you" on the board means the task's next move is the person's and its agent is not in the middle of a turn. The board picks one state per task from facts, first that holds: closed, paused, working, waiting, quiet (held by a session, nothing to do), no session {src:.harness/engine/modules/task/tasklife.py#L842-L855}. Working is read from the age of the session's hook log (five minutes by default) and running subagents {src:.harness/engine/modules/task/tasklife.py#L776-L805}.

The reason a task waits is worked out by code from facts, in order of how much it blocks; several of the facts are marks that harness code stored in `.task/task.json` (`waiting`, `deliver`, `handoff`, `paused`, `promote.state`), and the Stop hook's mark is one of them, not the only one {src:.harness/engine/modules/task/tasklife.py#L276-L338}:

- the agent asks a question and waits for the answer;
- a write-back stopped halfway and waits for **Recover the repository**;
- the plan waits for your approval;
- the write-back waits for your approval;
- the independent checks are used up and wait for your decision;
- the task was delivered and waits **to accept**: `task deliver` saves the summary in `task.json`, and when the agent really stops the Stop hook turns it into the waiting mark `accept` (a stop with nothing delivered gives `stopped`, so the Stop hook's mark and "to accept" are one mark with two values); the person's next message clears the mark and the delivery together (this is how **Not yet** works), a question the agent asks with its ask tool and the answer leave the task still to accept, and otherwise **Accept and close**, or **Close**, ends it {src:.harness/engine/modules/task/accept.py#L9-L10} {src:.harness/engine/modules/task/handler.py#L486-L499} {src:.harness/engine/modules/task/tasklife.py#L460-L472};
- the requirement waits for your confirmation (`full` tier only);
- a call to an outside system waits for your approval;
- the agent handed you a run or a test to do;
- the files were written back and wait for your commit;
- you approved something and the agent has not been told yet;
- autorun stopped;
- the agent stopped: the Stop hook marks the task "waits for you" when the agent ends its turn (the same stored mark as "to accept", with `why` = `stopped` when nothing was delivered), and your next message takes the mark away {src:.harness/engine/modules/task/handler.py#L486-L499} {src:.harness/engine/modules/task/handler.py#L262-L263}.
- you cancelled the agent's turn in VS Code: "cancelled, waits for you" {src:.harness/engine/core/messages.en.json#L131}.

A question the person asks a task through the board (`/harness-ask`, 1.8.3) leaves this as it was: the turn clears no mark, and at its end the task waits for what it waited for before {src:.harness/engine/modules/task/handler.py#L221-L244} {src:.harness/engine/modules/task/handler.py#L605-L607}.

The task page shows the reason at the top with a button for the answer, and the board's Super agent view (1.8.3) lists what waits across all tasks (see the file 21 Super agent); the harness tutorials "1 A day with the harness" and "3 When the agent is stopped", in the OneDrive folder `3 Courses/Harness tutorials/`, show it on screen.

## Task: what is enforced by code, and what is not

Enforced by code:

- The state file is written by harness code; the edit tools are refused on it, and a terminal command that names it as a write target is refused (a script the agent runs is not checked for it) {src:.harness/policies/gate.json#L24-L34} {src:.harness/engine/modules/gate/handler.py#L121-L123}.
- For the chat that holds an open task, the edit tools stay inside its folder (a chat with no task is not bound); `REQ/`, `REF/`, `INBOX/` are refused, `DEV/` until the plan is approved {src:.harness/engine/modules/gate/handler.py#L64-L94}.
- The approvals of the plan and the write-back need a person and a typed code bound to a digest; the gate refuses the approval commands and `task close` on the agent's command line {src:.harness/engine/core/approval.py#L17-L58} {src:.harness/policies/gate.json#L131-L144}; `task close` itself has no person check {src:.harness/engine/modules/task/commands.py#L123-L133}.
- A plan cannot be approved while the "User confirmed" line of `REQ.md` is not filled in, when `REQ.md` has that line; the line is text the agent can write; a changed requirement or plan undoes the approval {src:.harness/engine/modules/task/task.py#L443-L451} {src:.harness/engine/core/tasks.py#L152-L164}.
- A write-back writes exactly the approved files to a new branch, uncommitted; a registered knowledge base gets one commit on its base branch instead {src:.harness/engine/modules/task/task.py#L941-L944} {src:.harness/engine/modules/task/promote_target.py#L1-L14}.
- The reviewer is called only in a task whose checks are on, and its passes are counted by code; the worker only in a task whose autorun is on {src:.harness/engine/modules/task/handler.py#L278-L300} {src:.harness/engine/modules/task/autorun.py#L415-L419}.
- In autorun, the task's own chat writes only `TODO.md`, `TASK.md`, `LOG.md` and `QUESTIONS.md`, and the worker the rest of the folder; the run stops on facts, the spend limit the person picked among them {src:.harness/engine/modules/gate/handler.py#L97-L109} {src:.harness/engine/modules/task/autorun.py#L7-L19}.
- A session holds one task at a time; a subagent or admin session cannot open one {src:.harness/engine/modules/task/tasklife.py#L126-L135}.

Asked of the model by text: open a task before producing files; read `TASK.md` first; write the requirement into `REQ.md` and change it first when the person changes their mind; leave the confirmation line alone; write the plan and stop; update `TASK.md` before stopping (the Stop hook reminds it once); deliver and never ask "close the task?" {src:.github/skills/harness-my-task/SKILL.md#L75-L113} {src:AGENTS.md#L46-L51}.

Left to a person: confirming the requirement, approving the plan and the write-back, switching autorun on with its spend limit, giving more checks or waiving them, recovering a failed write-back, accepting or closing the task, committing the branch {src:.harness/policies/gate.json#L131-L137}.

## Task: common questions

**Q: What is a task, and how is it different from a chat session?** A task is a folder that holds one piece of work and its state; a session is one Copilot chat. A session holds one task at a time, and any later session can pick the task up from its files {src:.harness/engine/modules/task/task.py#L140-L218}.

**Q: Can the agent approve its own plan?** Not by the ways the harness gives it: the gate refuses the approval commands on the agent's command line, the commands need a person at their own terminal or the paired board's buttons, and the code is bound to the plan's sha256 {src:.harness/policies/gate.json#L131-L137} {src:.harness/engine/core/approval.py#L17-L58}. The requirement's confirmation line is the exception: it is text the agent can write.

**Q: I closed VS Code yesterday. Can a new chat continue the same task?** Yes. Say "go on with" and the task's name in a new chat; the agent runs `harness task open <task name>` and reads `TASK.md` first. Or press **Go on in a new chat** on the task page {src:.harness/engine/modules/task/tasklife.py#L155-L160} {src:.harness/engine/core/messages.en.json#L2383-L2384}.

**Q: Where is a task's record kept?** In `.workspace/sandbox/tasks/<task name>/` on your computer: the Markdown files, and the state in `.task/task.json` with its history; at close also the chat's rounds and a report in `.workspace/reports/tasks/<task name>/` {src:.harness/engine/core/tasks.py#L19-L37} {src:.harness/engine/modules/task/task.py#L386-L398}.

**Q: What happens if the requirement changes after I approved the plan?** When what `REQ.md` asks changes, the approval lapses, `DEV/` closes to the edit tools of the chat that holds the task, and you confirm the requirement and approve the plan again with one code {src:.harness/engine/core/tasks.py#L152-L164} {src:.harness/engine/modules/task/task.py#L444-L469}.

**Q: Can the agent write files outside its task folder?** Its VS Code edit tools cannot, while its chat holds an open task; a chat with no task is not bound, and a tool the harness does not list as an edit tool is not path-checked. Its terminal commands are not confined to the folder: only writes that name a guardrail file, a harness-owned file or `.git`, in full or after a `cd` in the same line, or a target repository by its full path, are refused {src:.harness/engine/modules/gate/handler.py#L64-L139} {src:.harness/engine/modules/gate/terminal.py#L65-L117}. Guardrail files are open in a chat the person switched to admin mode.

**Q: Is the workflow controlled by a skill or by code?** The skill and the hook's text tell the agent the order; code holds the gates between stages {src:.harness/engine/modules/gate/handler.py#L86-L90} {src:.harness/engine/modules/task/task.py#L941-L944}.

**Q: Who closes a task?** The person, with **Accept and close** or **Close** on the board, or `task close` in their own terminal; the board closes a written-back development or knowledge base task once the agent stopped and nothing waits, without waiting for the commit. The gate refuses `task close` on the agent's command line, though the command itself has no person check {src:.harness/engine/modules/task/accept.py#L167-L218} {src:.harness/policies/gate.json#L138-L144}.

## Task: limits

- **The confirmation of the requirement is a text line.** The code reads the "User confirmed" line of `REQ.md`, which the agent's edit tools may write; a missing `REQ.md`, or one with no such line, counts as nothing to confirm, and the plan is then approved alone {src:.harness/engine/modules/task/taskreview.py#L88-L110} {src:.harness/engine/modules/task/task.py#L551-L567} {src:.harness/engine/modules/task/task.py#L445-L449}.
- **Admin mode opens the guardrails.** In a chat the person switched to admin mode, only `.harness/runtime/**`, the policy's `admin_locked_paths` and the integrity-list folder stay closed; the integrity check is skipped, and ending admin mode accepts the guardrail files as they are then. An admin chat cannot open a task {src:.harness/engine/core/guardrails.py#L21-L61} {src:.harness/engine/hook.py#L312-L323} {src:.harness/engine/integrity.py#L1-L5} {src:.harness/engine/modules/task/tasklife.py#L126-L135}.
- **The folder binds only a chat that holds an open task,** and only its recorded edit tools. Terminal writes are refused only when they name a protected path in full or after a `cd` in the same line (a target repository only by its full path, so a relative path into it passes), or when a script they run is found, as best effort, to write a guardrail file {src:.harness/engine/modules/gate/handler.py#L64-L139} {src:.harness/engine/modules/gate/terminal.py#L65-L117}.
- **The approval records are files.** They live in `.task/task.json`; a terminal command that names the file is refused, but a script the agent writes and runs is checked only for guardrail paths {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}.
- **After the plan is approved, some outside calls need no further approval.** Calls the company's policy marks `task`, and writes on a connection opened with `task allow`, pass without an approval of the code; on an opened SQL Server DEV or IST connection this includes `DROP TABLE` and `TRUNCATE TABLE` {src:.harness/engine/modules/gate/handler.py#L287-L308} {src:.harness/toolpacks/sqlserver/types/sqlserver.json#L254-L272} {src:.harness/engine/modules/gate/handler.py#L302-L303}.
- **`task allow --conn X --off` leaves a ticket board's linked items open.** For a connection whose type opens only the linked items, `--on` opens the task's linked items, but `--off` only takes X off the list of opened connections, where `--on` never put it, and says "X is closed for this task" while the linked items stay open; `task allow --links --off`, or **Close** on the board's linked-items row, closes them {src:.harness/engine/modules/task/tasklife.py#L543-L595} {src:.harness/engine/core/messages.en.json#L3853}.
- **A ticket the person links on the board while the linked items are open is opened at once,** though the board's pop-up says a ticket linked later still waits; a ticket the agent links with `task link add` is not opened {src:.harness/engine/modules/task/tasklife.py#L612-L635} {src:.harness/engine/modules/task/boardserve.py#L789-L792} {src:.harness/engine/core/messages.en.json#L3867}.
- **▶ Run on a task page is not checked by the gate.** The Run button of a shell code block starts the command from the board server, in the task folder, as the person; only the paired browser may ask, and the dialog warns that the gate does not check it, so the person's reading is the only check, also of a command the agent wrote {src:.harness/engine/modules/task/taskrun.py#L1-L8} {src:.harness/engine/core/messages.en.json#L2005-L2009}.
- **Start autorun sets Allow all on the task's chat,** so Copilot's own confirmation of the commands on the ask list does not show during the run, and, while the board runs, it wakes the agent by itself when its chat stops; the gate's refusals still hold {src:.harness/engine/modules/task/autorun_start.py#L1-L6} {src:.harness/engine/modules/task/autorun_relay.py#L1-L14}.
- **Opening a task does not release an earlier session that still holds it.** `task open` changes only the opening session's state; an earlier session whose `active_task` still names the task keeps it {src:.harness/engine/modules/task/task.py#L154-L209}.
- **The Stop reminder checks that `TASK.md` was written, not that it is right** {src:.harness/engine/modules/task/handler.py#L423-L435}.
- **Working is read from the age of the hook log** (300 seconds): a tool call longer than that looks idle {src:.harness/engine/modules/task/tasklife.py#L776-L805}.
