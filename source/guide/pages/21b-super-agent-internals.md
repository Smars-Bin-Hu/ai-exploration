This file holds the code-level detail behind the feature file 21 Super agent: how the view is built from the board's rows, why the super chat is a main chat and not a subagent, how the gate knows it by `/harness-super`, what the digest holds, when a new chat is made, how the daily Credits limit is checked, how a proposals block becomes a card and what is re-checked, how a question to one task becomes a read-only turn, and how the plan and changes previews are made. It is for "how does it work" and "where in the code" questions; for what the view is for and how a person uses it, read the feature file.

## Super agent internals: what the view shows, and where it comes from

The Super agent view is drawn from `GET /api/super`, which calls `BoardServer.rows()` (the rows the board already computes), runs `superview.build` on them and returns `status`, `mates` and `items`; it is a read and needs no pairing {src:.harness/engine/modules/task/boardserve.py#L2120-L2132}. `superview.build` is a pure function with no file, no model and no text of its own {src:.harness/engine/modules/task/superview.py#L1-L9}.

Which tasks give an item: only open rows with a `waiting_why` that does not start with `go-` and that are not paused. A `go-*` wait (requirement, plan, promote, recover or checks approved, the agent not yet told to go on) is left out because the person already approved and the board tells the agent; a paused task waits for nothing; a closed task is left out. A row has one `waiting_why`, so a task has at most one item {src:.harness/engine/modules/task/superview.py#L46-L59}.

Order of the items: three groups, then the longest wait first (`waited_s`, then `since`; a wait with no time last; then board order). Group 1 blocks running work (`confirm`, `question`, `asking`, `outbox`, `autorun`); group 2 holds decisions (`req`, `plan`, `promote`, `review`, `recover`, `accept`); group 3 is the rest (hand-offs, `commit`, `stopped`, `cancelled`) {src:.harness/engine/modules/task/superview.py#L17-L43}. An item keeps only the actions that answer a wait, so pause, close, steer and the like stay off the message {src:.harness/engine/modules/task/superview.py#L19-L37}.

Per task, `mates` has one entry per open row in board order: `state` is `you` when the task has an item, else `work` when the row's state is `working`, else `idle`; `count` is its items. `status` adds the totals (`watching`, `working`, `waiting`, `idle`, `as_of`). The page draws the avatar strip from `mates` and the robot's orbiting dots from the same states, one dot per task, at most twelve {src:.harness/engine/modules/task/superview.py#L55-L59} {src:.harness/engine/modules/task/web/pet.js#L174-L181}.

For an item whose wait is `stopped`, `accept` or `cancelled`, `/api/super` adds `said`: the agent's last words in that task's chat, taken from the link's cache with no call to the host, from the text parts of the last ended turn, cut to 1,200 characters; empty when the link does not know the chat {src:.harness/engine/modules/task/superroute.py#L210-L221} {src:.harness/engine/modules/task/boardserve.py#L2125-L2130}.

The summary on the first open of the day is asked by the page, not by the server. `morning()` in `super.js` asks for the summary only when the view is shown, the chat state is `idle`, today's conversation is empty and at least one item waits, and only once a day per browser: it keeps the key `super.morning` in `localStorage` with the UTC date (`toISOString`), and with no storage it makes no automatic call {src:.harness/engine/modules/task/web/super.js#L902-L908}. The code that decides is the page's JavaScript; the server's `/api/super/ask` sees only an ordinary summary request.

## Super agent internals: why the super chat is not a subagent, and why it only proposes

A subagent is started by a main agent's tool call, and its hook calls come from a child session: `state.claim_child` finds the parent that just started a subagent and records `parent_session_id` and the parent's task in the new session {src:.harness/engine/core/state.py#L303-L354}. The super chat is not made that way. The board's link makes it itself: `VsLink._super` calls the host's `createSession` with `provider`, the working directory, `agent: {uri: <.github/agents/super.agent.md>}` and `config` `{isolation: folder, mode: interactive, autoApprove}`, then sends the turn with the same `agent` in the message. The session has no parent and holds no task {src:.harness/engine/modules/task/vslink.py#L937-L985} {src:.harness/engine/modules/task/superbrain.py#L33-L36}. So it is a custom main agent in its own chat, not one of the harness's three subagents (reviewer, worker, mapper). The doc `docs/02-features.md` says "There are two only" and then lists three; the code and `AGENTS.md` say three {src:docs/02-features.md#L112-L117} {src:AGENTS.md#L53}.

The agent file `.github/agents/super.agent.md` sets `user-invocable: false`, `agents: []` (it may call no subagent), `tools: ['read', 'search']` and the model list Claude Haiku 5.5 {src:.github/agents/super.agent.md#L1-L8}. The board adds the model on each message: `send` looks up `claude-haiku-5.5` in the host's model list and falls back to `{id: claude-haiku-5.5}` {src:.harness/engine/modules/task/superbrain.py#L462-L474}. The tools are a first layer, held by Copilot; the gate's marker check is the second.

The reason for a separate mark: the hook cannot tell this chat from any other main chat, because `agent_type` is empty for a custom main agent {src:.harness/engine/modules/gate/superagent.py#L1-L5}. It cannot act, in code, because of three things taken together: the gate refuses every call that is not a read (next section), the agent file gives it no write tool, and its proposals are checked and then pressed by a person, never run by the board on its own (the section on proposals).

## Super agent internals: how the gate knows the super chat, and what that session may do

`gate/superagent.py` holds the mark. `is_marker(prompt)` strips leading whitespace and is true when the prompt starts with `/harness-super` and the next character is whitespace or the string ends, so `/harness-superb` does not mark {src:.harness/engine/modules/gate/superagent.py#L34-L36}. `mark` runs on every `UserPromptSubmit` and sets `modules.gate.super = true` in the session's own state only for a real person's prompt: it returns without marking when the prompt comes from a subagent, is a continuation (a Stop hook's feedback), or the session has a `parent_session_id`. Once set it is never cleared, so a session stays a super session for good, and any later person's prompt that starts with the marker is enough to set it {src:.harness/engine/modules/gate/superagent.py#L39-L44}.

`check` runs on `PreToolUse` only, and in `_handle` it comes first: before the ask-turn mark, the reachability steps and the normal rules {src:.harness/engine/modules/gate/handler.py#L758-L766}. For a session without the mark it returns nothing and the call goes on through the normal rules. For a marked session a call passes this check only when its `tool_kind` is `read`, `search` or `meta`, or when it is a terminal call that is exactly one read-only harness command. The kinds come from `adapters/tool_kinds.json` by tool name: for example `read_file` and `Read` are `read`, `grep_search`, `Grep` and `search_code_subagent` are `search`, `tool_search_tool` and `task_complete` are `meta`; `Agent`/`runSubagent` is `subagent`, `WebFetch` is `web`, `skill` is `skill`, `AskUserQuestion` and `ask_user` are `ask`, an unlisted tool is `other` {src:.harness/engine/modules/gate/superagent.py#L20-L20} {src:.harness/engine/adapters/tool_kinds.json#L8-L37}. Everything else is refused: edits, creates, other terminal commands, web, skills, subagent calls, the question tool and MCP tools {src:.harness/engine/modules/gate/superagent.py#L78-L89}.

A terminal line is read-only only when `_read_only` accepts it: no shell syntax (`; & | < > backtick $ ( ) { }`, line breaks, backslash), exactly one harness call found by `harnesscmd.calls` and none it cannot read, and the words are one of seven commands with only their listed options: `task list` (`--all`, `--text`), `task status`, `task autorun status` and `task review status` (`--task <name>`), `task queue`, `target list` and `target show`. A plain `ls` or `grep` in the terminal is therefore refused, as is a harness command with an option not on its list; `search_code_subagent` passes because it is a search tool, not a terminal call {src:.harness/engine/modules/gate/superagent.py#L22-L31} {src:.harness/engine/modules/gate/superagent.py#L55-L75}.

When the mark cannot be read (the session state has no `modules` object, or any error), `check` refuses the call, even in a session that never was a super session: not freer, refused {src:.harness/engine/modules/gate/superagent.py#L47-L52} {src:.harness/engine/modules/gate/superagent.py#L82-L88}. The refusal is a `deny` with the text "Refused: the super agent only reads and talks. It does not change anything. Use the buttons on the board to act." and `facts.kind` `super-agent` {src:.harness/engine/core/messages.en.json#L433}. A call that passes this check is not approved by it: it still goes through the gate's other rules. A chat started without the marker is not restricted by this check.

## Super agent internals: the digest the board sends

`superbrain.digest(view, at, closed)` builds the only text about the tasks the agent gets. The head is `Open tasks: N (a wait for the person, b working, c idle). As of HH:MM.` with the board's local time. Then one line per open task, tasks with a wait first in the view's order, then the others: `- <name> (<kind>): <state>`, where the state words are `needs the person`, `working` or `idle`, plus, for a task with an item, ` | waits for: <why>`, ` - <title>` and ` | <how long>` (`<1m`, `12m`, `2h05m`, `1d3h`). Names are cut to 60 characters, kinds to 20, titles to 100; spaces are folded to one {src:.harness/engine/modules/task/superbrain.py#L84-L98} {src:.harness/engine/modules/task/superbrain.py#L124-L145}.

The bound is 2,000 characters (`DIGEST_CHARS`). A line that would pass it is replaced by `(+N more tasks not shown)` and the list stops. A last line `Closed (not archived): a, b (+N more)` lists the closed tasks the board still shows, in board order, in at most 300 characters. With no open task the body is `No task is open.` {src:.harness/engine/modules/task/superbrain.py#L101-L145}.

The digest uses each item's `why` word and its `title` (the board's wait text), never the item's `detail`. The title is generic for most waits ("the plan waits for your approval"), but not for all: for a tool confirmation the board's title holds the first 70 characters of the command ("the agent asks to run: ..."), a hand-off adds its environment label and a stopped autorun adds its reason {src:.harness/engine/modules/task/tasklife.py#L348-L358} {src:.harness/engine/modules/task/tasklife.py#L475-L485}. A question's own text stays in `detail` for a question tool the board can take, so it does not reach the chat. Task names are user text and are in the digest, cut to 60 characters.

The message sent is `/harness-super`, a line break, the digest, a blank line, then the request: `Person asks: <words>` for a typed question (at most 1,000 characters, else `long`; empty is `empty`) or the fixed sentence `Give a short summary of what waits for me now, most urgent first.` for a summary {src:.harness/engine/modules/task/superbrain.py#L398-L413} {src:.harness/engine/modules/task/superbrain.py#L433-L433}. A new digest goes with every turn; the chat keeps the day's history, so the 2,000 characters are a limit per message, not per day. The conversation record keeps the person's words, or the label "Summary of what waits" for a summary, not the digest {src:.harness/engine/modules/task/superbrain.py#L43-L45} {src:.harness/engine/modules/task/superbrain.py#L457-L457}.

If the rows cannot be read or the digest cannot be built, `turn` returns `why: error` and no turn is sent {src:.harness/engine/modules/task/superbrain.py#L426-L431}.

## Super agent internals: one chat a day, and the record in super.json

The board keeps the chat's record in `.harness/runtime/super.json`: `day` (local date), `session`, `chat`, `sdk` (the Copilot session id), `exchanges` (each turn: id, kind `ask` or `summary`, the person's words, the answer and how it ended), `asks` (questions to tasks), `turn_nano` (what each ended turn cost), `cost` (`session`, read position `pos`, `nano`) and `prior_nano` {src:.harness/engine/modules/task/superbrain.py#L178-L179}. `load` returns this record only when `day` equals today's local date. A record of another day, or one that cannot be read, gives an empty one with no chat, so the next turn makes a new chat {src:.harness/engine/modules/task/superbrain.py#L181-L198}.

A new chat is therefore made by the first turn of a local day, never at midnight by itself: nothing runs a turn then. When a record of an ended day is loaded (any `talk`, `history` or turn call does it), `keep` writes it to the history first, as one file named for the day, `<day>.json`, in the folder `.harness/runtime/super-history/`. The file holds `day`, `spent` (Credits, 3 decimals), the exchanges' fields and the asks; an empty day is not written, a day already in `archived/` is not written again, and when the write fails `super.json` stays so the next load tries again {src:.harness/engine/modules/task/superbrain.py#L200-L215}. `history_act` archives (moves to `archived/`), restores or deletes a day and refuses today, because today's record holds the spend; archive and delete go through `/api/super/history/act`, which needs the paired browser {src:.harness/engine/modules/task/superbrain.py#L374-L396} {src:.harness/engine/modules/task/boardserve.py#L2110-L2119}.

Exceptions to one chat a day. First, the host can lose the chat (VS Code restarted and no longer knows it): in `send`, an `AhpError` while the record names a session or chat makes the board retry once with an empty session and chat, which makes a new chat; the first chat's spend is kept by adding its `cost.nano` to `prior_nano` and resetting `sdk` and `cost` {src:.harness/engine/modules/task/superbrain.py#L462-L474} {src:.harness/engine/modules/task/superbrain.py#L453-L456}. A failure with no session or chat on record is not retried. Second, when the send times out, the board still keeps the chat the link made, so the next ask does not make a second one {src:.harness/engine/modules/task/superbrain.py#L443-L450}. The turn is refused as `busy` while one runs, and a turn the chat never shows and that does not run is given up as `lost` after 180 seconds {src:.harness/engine/modules/task/superbrain.py#L249-L251} {src:.harness/engine/modules/task/superbrain.py#L286-L291}.

## Super agent internals: the daily Credits limit

The limit is `super.daily_credits` in `.harness/policies/task.json`, default 50; `limit_of` accepts a number of at least 0 that is not a boolean and falls back to 50 for anything else, and `0` leaves no room at all, so every turn is refused with `limit` {src:.harness/engine/modules/task/superbrain.py#L77-L79} {src:.harness/policies/task.json#L25-L27}.

`spent` is the larger of two numbers, divided by 1e9 to give Credits: the sum of `usage._meta.copilotUsage.totalNanoAiu` of the turns that have ended, and `prior_nano` plus the nanos read from the chat's events file, the `session.usage_record` lines read from the last position and only whole lines. A turn still running appears only in the events file, so the spend can lag until lines are written {src:.harness/engine/modules/task/superbrain.py#L155-L159} {src:.harness/engine/modules/task/superbrain.py#L260-L284}.

In `turn`, the checks run in this order after the record is loaded and synced: the link must be ready (else `asleep`), then spent must be under the limit (else `limit`), then no turn may run (else `busy`), then the digest is built (else `error`) {src:.harness/engine/modules/task/superbrain.py#L415-L431}. The limit is checked before the send, so the turn that crosses it is still spent. For the page, `talk` gives the state in this order: `asleep` when VS Code is not linked, `thinking` when a turn runs, `tired` when spent is at the limit, else `idle`; `tired` shows the banner with the spend and limit, and the messages and buttons go on working {src:.harness/engine/modules/task/superbrain.py#L295-L306} {src:.harness/engine/modules/task/web/super.js#L709-L726}. Questions to tasks are not counted here (see the section on asking a task).

## Super agent internals: how a proposals block becomes a card

`superbrain.shown` runs `superact.split` on every agent message and, for a message that had a block, `superact.check` against the rows of that moment, from `rows()` called fresh and the actions the board serves {src:.harness/engine/modules/task/superbrain.py#L308-L327}. `talk` does this on every poll, so a card is judged again at each refresh from the live rows; a day read from the history is not judged again {src:.harness/engine/modules/task/superbrain.py#L295-L306} {src:.harness/engine/modules/task/superbrain.py#L363-L372}.

`split` cuts the block with plain `str.find` on `<harness-proposals>` and `</harness-proposals>`, no regex. Text of each block is removed from what the person sees; an unclosed block cuts out the rest and gives no items; a stray closing tag is removed; only the last block counts. That block becomes one bad item, never an error of the whole talk, when it is over 40,000 characters, is not JSON (a `RecursionError` too), is not a list, or has more than 8 items {src:.harness/engine/modules/task/superact.py#L18-L57}. No block gives no proposals.

`check` judges each item by its `kind`. An item that is not an object, has another kind, or raises while judged becomes `{kind: bad, ok: false, why: bad}` with no button; what cannot be judged does not pass. If the rows cannot be read at all, the whole answer's proposals become one bad item {src:.harness/engine/modules/task/superact.py#L140-L160}. The text of an item (`text` of send, steer and new) is limited to 2,000 characters, not the whole item {src:.harness/engine/modules/task/superact.py#L60-L62}.

- **action**, in this order: the task must be a board row by its exact short name (`unknown`; in code any row qualifies, since the digest is only a text); the action must be in the fixed set `BOARD_ACTIONS` of 25 names (`kind`), which is wider than the 12 the agent file lists. Then `review set` needs an integer `n` from 0 to 9 (`n`), an open row and, when the served actions are known, `review set` among them (`state`). `steer` and `stop` need an open row whose state is `working` (`state`), and `steer` needs non-empty `text` of at most 2,000 characters (`text`). Any other action must appear among the row's own `actions` now (`state`) {src:.harness/engine/modules/task/superact.py#L23-L24} {src:.harness/engine/modules/task/superact.py#L71-L98}.
- **send**: the task exists (`unknown`), is open (`closed`), is not paused (`paused`), and the text is non-empty (`empty`) and at most 2,000 characters (`long`). At press time the page posts `/api/queue` when the task's chat is working and `/api/send` otherwise, as a normal message {src:.harness/engine/modules/task/superact.py#L101-L116} {src:.harness/engine/modules/task/web/super.js#L266-L275}.
- **new**: `name` passes `tasklife.clean_name` unchanged (`name`; at most 80 characters, no path marks, no shell-risky characters), is not taken by a row (`taken`), and the text is non-empty and at most 2,000 characters; a `task_kind` outside `qa, rca, design, dev, test, kb, other` silently becomes `dev` {src:.harness/engine/modules/task/superact.py#L119-L137} {src:.harness/engine/modules/task/tasklife.py#L57-L69}.

On the page, **Do all** appears only for `archive`, `pause`, `resume`, `close` and `review set` (grouped by `n`), and only when more than one proposal of the same group is ok and not yet pressed {src:.harness/engine/modules/task/web/super.js#L239-L310}. The calls behind a card's button are the board's own POST endpoints; they need the paired browser (an approval also needs the typed code), and that pairing, not the check above, is the real gate on acting {src:.harness/engine/modules/task/boardserve.py#L2082-L2088}. The check only keeps a button from appearing that the board would not offer.

## Super agent internals: asking one task, and the read-only turn

In the view, typed words go to a task when its avatar filter is on, or when they start with `@name` (the name ends at a space, the end or `, : ;`); the page posts `{task, text, lang: ""}` to `/api/super/route`, for the paired browser only {src:.harness/engine/modules/task/web/super.js#L767-L810} {src:.harness/engine/modules/task/boardserve.py#L2089-L2095}. `superroute.ask` checks in this order: text empty (`empty`), over 1,000 characters (`long`), `open_task` (the name must resolve to a task whose status is `open`, else `unknown`, so a closed task is refused), paused (`paused`) {src:.harness/engine/modules/task/superroute.py#L75-L88}.

Then it builds the message `/harness-ask`, a line break and the text. `chatsend.steer_text` puts `[ZH]` first when `lang` is `zh`, and `with_english` adds `[EN]` only when `en` is chosen for a chat that replies in Chinese; this page always sends an empty `lang`, so it adds neither {src:.harness/engine/modules/task/superroute.py#L89-L93} {src:.harness/engine/modules/task/chatsend.py#L168-L170} {src:.harness/engine/modules/task/chatsend.py#L201-L208}. The link then checks the task's chat: `send` when idle; when it is busy (`not-idle`), `queue`, so the question waits for the end of the turn and is never steered into it. Reasons are mapped: `off` and `not-ready` to `asleep`, `unbound` and `unsure` to `nochat`, a chat that waits in its own question tool (`not-busy`) to `asking`; any other host failure is `error`. The message goes with the task's own model (`chat.model`) {src:.harness/engine/modules/task/superroute.py#L94-L128}. The ask is recorded under `asks` in the day's record with the state `sent` or `queued`.

The answer is read back from the link's cache, with no call to the host. `read` finds the turn by its id, or, for a queued one, the first turn whose message equals what was sent; an ended turn gives `answer` (its text parts, cut at 20,000 characters) and state `answered` when it completed, else `failed` with the turn's end state. If the link does not know the chat, nothing is judged; if the turn is found nowhere and the ask is not in the chat's queue, it is `failed` as `lost` after 180 seconds {src:.harness/engine/modules/task/superroute.py#L23-L27} {src:.harness/engine/modules/task/superroute.py#L171-L207}.

The turn is read-only by `gate/askturn.py`, on the task's own chat session. `mark` runs on a real person's prompt (not a subagent, not a continuation, no `parent_session_id`): a prompt starting with `/harness-ask`, with the same whitespace rule as the super marker, sets `modules.gate.ask`; any other person's prompt clears it if it was ever set, so the turn after the question is normal. `check` then allows only what the super chat may do, reusing `ALLOWED_KINDS` and `_read_only`, and refuses the rest, including subagent, MCP, web, skill and question-tool calls, with "Refused: this turn is a question from the person through the board" {src:.harness/engine/modules/gate/askturn.py#L21-L53} {src:.harness/engine/core/askmark.py#L6-L11} {src:.harness/engine/core/messages.en.json#L434}. An unreadable mark refuses too. In `_handle` the ask check runs after the super check {src:.harness/engine/modules/gate/handler.py#L758-L766}.

The task module leaves the task as it was in that turn: on the prompt it clears no wait and no delivery and adds no restore point, and at the turn's `Stop` the task waits for what it waited for before, with nothing asked of the agent {src:.harness/engine/modules/task/handler.py#L221-L244} {src:.harness/engine/modules/task/handler.py#L605-L607}. Questions to tasks run in the task's chat with its model, so they spend that chat's Credits and are not counted by the super chat's daily limit.

## Super agent internals: previews of a plan or a promote

The page draws a preview only under an item whose wait is `plan` (kind `plan`) or `promote` (kind `changes`); no other wait gets one. It asks `/api/super/preview` once per item id (`<task>|<why>|<since>`), with an 8-second wait, and draws the answer folded in a `details` element above the buttons, with a link "Open full plan" or "Open changes" to the task page; a refusal, an error or nothing to show draws nothing {src:.harness/engine/modules/task/web/super.js#L421-L474}. The endpoint needs the paired browser and reads task files {src:.harness/engine/modules/task/boardserve.py#L2096-L2099}.

`superpreview.preview` first finds an open task by name (`unknown` when there is none), then by `kind` (`kind` when it is not `plan` or `changes`); any exception gives `error`, never a trace {src:.harness/engine/modules/task/superpreview.py#L95-L108}. For `plan`, it reads `PLAN.md` up to 256 KB, skips fenced code, and takes the top-level numbered items; only when there are none does it take the headings and top-level bullets. Indented items are left out, links, emphasis and checkboxes are stripped, each line is cut to 160 characters, and at most 12 lines are returned with `total` (all lines) and `more`, which the header shows as a count with an "and more" tail; a missing or empty `PLAN.md` gives `missing` {src:.harness/engine/modules/task/superpreview.py#L18-L56} {src:.harness/engine/modules/task/superpreview.py#L72-L80}. For `changes`, it uses the list the task page's Changes tab shows, without the diff text, drops files that are `unchanged` and files under `DEV/_manual/`, and returns at most 12 files with path, added, removed and action, and `more` {src:.harness/engine/modules/task/superpreview.py#L83-L92}.

## Super agent internals: what the code-made digest buys, and what is only asked

What code does: the board builds the digest from its own rows, so the model is never given the task files, the chat history of the tasks or any detail text (`detail`, a question's words, the command in the longer tip); the message is capped at 2,000 characters; and the chat uses Claude Haiku 5.5 with no subagents, in one chat a day. That is the cost side: no task file is read into the model by the board, and the size of what the board adds to each turn is bounded {src:.harness/engine/modules/task/superbrain.py#L124-L145}.

The safety side is made of layers that are each code. The agent file gives it only read and search tools {src:.github/agents/super.agent.md#L7-L7}. The gate (`superagent.py`) refuses everything but read, search and meta tools and seven read-only harness commands, and a failed read of the mark refuses {src:.harness/engine/modules/gate/superagent.py#L78-L89}. A proposal is checked against the live rows and needs a person to press it, with the board's pairing and, for an approval, a typed code {src:.harness/engine/modules/task/superact.py#L1-L8}. So a chat that is fooled by task text in a name or a title can at worst write a proposal that code checks and a person presses, or a misleading answer.

What code does not prove: that the agent keeps to the digest. The text of the agent file asks it to use the digest as its only view of the tasks, to answer in at most 100 words, to name only tasks the digest shows and never to say it did something; nothing checks these {src:.github/agents/super.agent.md#L12-L42}. The agent still has read and search tools, and the gate lets read and search calls pass anywhere they reach; it is not restricted to the digest in code, so "the agent never sees file content" is not a guarantee, only the digest's own content and what the agent file asks. The task names in the digest are user text, cut to 60 characters, and the first 70 characters of a command that waits for approval can be in a title. A proposal naming a task the digest does not show is only refused if no board row has that name {src:.harness/engine/modules/task/superact.py#L65-L68}.
