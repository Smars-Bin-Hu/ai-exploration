This file holds the code-level detail behind the feature file 12 The board: the checks `boardserve.py` makes on every request, pairing, the gate's refusal of the board's port, the Enter screen, the link to VS Code (`core/ahp.py`, `vslink.py`, `chatlink.py`), the ten chat actions and the state each needs, the fixed message text, the stage ribbon (`taskstages.py`), safe drawing of task files (`mdtree.py`), the health warnings (`health.py`) and the read-mostly rules. It is for "how does it work" and "where in the code" questions; what the board shows and what a person does with it are in 12 The board. Paths are in the harness repository at version 1.8.3, mostly under `.harness/engine/modules/task/`.

## Board internals: the server, its address and the checks on every request

The board is Python's `ThreadingHTTPServer` (one thread per request) bound to `("127.0.0.1", port)` only; the port is `--port`, else `board.port` of the task policy, else 8765. If the bind fails and no board of this copy answers, `serve` stops with `serve.port.busy` {src:.harness/engine/modules/task/boardserve.py#L119-L122}.

`handler_for` builds two sets from the port: the hosts `127.0.0.1:<port>` and `localhost:<port>`, and the origins `http://127.0.0.1:<port>` and `http://localhost:<port>`. `host_ok` compares the `Host` header with the hosts exactly. A GET with another Host gets an empty 403, a POST gets 403 `serve.refused.request`. That stops DNS rebinding: a page of another site that resolves to 127.0.0.1 still sends its own name as Host {src:.harness/engine/modules/task/boardserve.py#L1672-L1707}.

`do_POST` refuses before it reads the body when any of three tests fails: the Host is not in the hosts; there is an `Origin` header and it is not in the origins; the header `X-Harness-Board` is not exactly `1`. A request with no `Origin` header passes the Origin test, so a command-line client or script is not stopped by Origin, only by pairing (next section) {src:.harness/engine/modules/task/boardserve.py#L1814-L1818}. GET requests are checked for Host only; `/wall/<name>` also refuses a foreign `Origin` and any `Sec-Fetch-Site` other than same-origin or none {src:.harness/engine/modules/task/boardserve.py#L1780-L1795}.

Why the header works: a browser sends a cross-origin request with a custom header only after an OPTIONS preflight that the server approves. `Handler` defines `do_GET` and `do_POST` and no `do_OPTIONS`, and no response of the module sets an `Access-Control-Allow-*` header, so a page of another site cannot make a browser send the POST. A program that is not a browser sets the header freely, so the header is the first ring and not the only one {src:.harness/engine/modules/task/boardserve.py#L8-L10} {src:.harness/engine/modules/task/boardserve.py#L1683-L1699}.

Response hardening. `send` sets `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, and every `text/html` response the `Content-Security-Policy` in `CSP` (inline script and style only, `connect-src 'self'`, `form-action 'none'`, `frame-ancestors 'none'`). A POST body is read only up to a limit chosen by route: 4,096 bytes for most, 64 KiB for `/api/answer`, about 28 MB for `/api/send`, `steer`, `queue` and `create` (20 MiB of files as base64), 40 MiB for `/api/inbox` and `/api/intake`, 3 MiB for `/api/fileop`; over the limit, or not a JSON object, is 400 {src:.harness/engine/modules/task/boardserve.py#L84-L89}.

## Board internals: pairing, the cookie and the session set

`Board` takes its code from the environment variable `HARNESS_BOARD_RESTART` (popped, not kept), else `secrets.token_urlsafe(12)`; it lives in memory only. `serve` opens the browser at `http://127.0.0.1:<port>/#pair=<code>` (a fragment is not sent to the server). The page script (`serve.js`, `trade`) removes `#pair=` from the address bar and history with `history.replaceState` before anything is sent, asks `/api/status`, and only when the answer is "not paired" posts the code to `/api/pair`; a tab with the cookie of an earlier pairing spends no code {src:.harness/engine/modules/task/boardserve.py#L293-L294} {src:.harness/engine/modules/task/web/serve.js#L436-L446}.

`Board.pair(code)`, under the lock: `secrets.compare_digest`; a wrong code, or an empty `self.code`, gives None (403 `serve.pair.wrong`) and keeps the code. On success `self.code` becomes `""` (the code works once), a token `secrets.token_urlsafe(24)` joins the set `self.sessions`, and `first_pair` is set. `paired(token)` is true when the token is not empty and in that set; the set is memory only, with no expiry and no removal. The cookie is `harness_board_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` (the port is in the name because cookies do not tell ports apart); no `Secure` flag, no `Max-Age` or `Expires` {src:.harness/engine/modules/task/boardserve.py#L386-L399} {src:.harness/engine/modules/task/boardserve.py#L380-L384}.

Never paired, by design: `embedded()` tests the user agent with `\bElectron/\d`. `token()` returns an empty string for such a browser, so every cookie check fails, and `/api/pair` refuses it with `serve.pair.embedded` before the code is touched, so the code is not used up. The reason, in the code: the agent can drive VS Code's browser with its browser tools {src:.harness/engine/modules/task/boardserve.py#L1709-L1721}.

New codes. `new_code()` replaces `self.code` and leaves `self.sessions` alone, so a paired browser stays paired. It runs when the person presses Enter in the board's terminal, and when `open_page` opens the browser for a second start (at most once in 3 seconds). `/api/reopen` answers only `{"opened": true|false}`, never the code, so it needs no cookie. An Enter within 2 seconds after the browser paired (`EARLY_ENTER`) is ignored, because a launcher on Windows can leave a line in the input; when no browser paired within 60 seconds the wheel in the terminal stops and the next Enter counts at once {src:.harness/engine/modules/task/boardserve.py#L365-L378}.

Restart board. `Board.restart()` makes `next_code`, stops the server after 0.3 s and `relaunch` runs the same command with `HARNESS_BOARD_RESTART=<code>`; the new process holds no session and does not open a browser. Its route is the second `/api/restart` branch of `do_POST`, but the VS Code button of the Enter screen posts to the same path and its branch comes first and answers every request, so by reading the code the Restart board button runs the VS Code restart in 1.8.3 (found by reading, not by running) {src:.harness/engine/modules/task/boardserve.py#L1218-L1222} {src:.harness/engine/modules/task/boardserve.py#L1857-L1872} {src:.harness/engine/modules/task/boardserve.py#L2022-L2025}.

## Board internals: which calls need no cookie, and what the rest need

Every POST that acts calls `board.paired(self.token())` and answers 403 `serve.pair.needed` (`unpaired: true`) when it is false. These POST routes do not check the cookie: `/api/pair`, `/api/reopen`, `/api/status`, `/api/ready`, `/api/live`, `/api/board`, `/api/desk`, `/api/file`, `/api/wall`, `/api/super` (the view), `/api/super/talk`, `/api/super/history`, `/api/intake` with `action` `read`, and `/api/act` when `action` is in `FREE`: `pause`, `resume`, `offwork`, `onwork`. Every other route checks it, among them all chat routes, `/api/run`, `/api/term`, `/api/create`, `/api/skill`, `/api/open`, `/api/close`, `/api/archive`, `/api/batch`, `/api/inbox`, `/api/fileop`, `/api/connections` and the autorun routes {src:.harness/engine/modules/task/boardserve.py#L96-L96} {src:.harness/engine/modules/task/boardserve.py#L1899-L1912}.

All GET routes check the Host only: the board and task pages, `/setup`, the saved pages and report pages, `/file/<task>/<path>` (pictures), `/download/<task>/<path>` (originals of the Files tab) and `/wall/<name>`; the one exception is `GET /api/autorun`, which needs the cookie {src:.harness/engine/modules/task/boardserve.py#L1723-L1812}.

A cookie alone does not approve anything. `Board.act` checks that the action is in `board.actions` of the task policy (else `serve.action.off`), then runs the terminal command's own function in two steps: `preview` hands the screen text and the code to the page; `act` runs it with the code the person typed. A plan or requirement that changed between the steps has another code, and the function refuses {src:.harness/engine/modules/task/boardserve.py#L746-L760}.

## Board internals: one board for a copy, and the person-only start

`serve` begins with `task_ops.person("task board --serve", interactive, typed=False)`, which calls `approval.require_person`: it passes when stdin and stdout are both a terminal, or when the board's Terminal window has vouched for the command with a one-time code (`boardperson`, environment `HARNESS_BOARD_PERSON`, a fingerprint kept in the guardrail folder, valid 600 seconds, used once). Otherwise it stops with the person-only message {src:.harness/engine/modules/task/task.py#L409-L413} {src:.harness/engine/core/approval.py#L29-L42}.

Then `running_board(root)` reads the port from `.harness/runtime/board-serve.json`, posts `/api/status` to it and accepts it only when the `root` in the answer is this copy. If a board runs, `already_running` asks it to open the browser through `/api/reopen` and nothing new starts. Otherwise the server binds, writes `board-serve.json` (`port`, `pid`, `started`) and removes it in the `finally` after Ctrl+C; a process killed hard leaves the file {src:.harness/engine/modules/task/boardserve.py#L2245-L2282}.

## Board internals: how the gate refuses an agent's request to the board's port

The gate learns the port from `board_serve_port(root)`, which reads `board-serve.json` and returns 0 when the file is missing or broken: the gate knows a port only while a board of this copy has written its file. `asks_board(ctx, text)` returns the port when `text` matches `(127.0.0.1|localhost|[::1]|0.0.0.0)\s*:\s*<port>\b`, case-insensitively, so `localhost:<port>`, `0.0.0.0:<port>`, the bracketed IPv6 form and spaces around the colon match too {src:.harness/engine/core/paths.py#L95-L105} {src:.harness/engine/modules/gate/handler.py#L580-L585}.

Two call sites. For the terminal, `check_terminal` runs it on the whole command string after the deny rules, so an address inside `bash -c '...'` is seen. For every other tool (web fetch, browser, MCP, edit tool), `_handle` runs it over the JSON of the whole call; `ask_user` and `askuserquestion` are exempt, because they only show a question to the person. The refusal text: the call goes to the board on port N, its buttons are the user's, do not call it, tell the user if something on the board should change {src:.harness/engine/modules/gate/handler.py#L148-L150} {src:.harness/engine/core/messages.en.json#L432-L432}.

What still passes the refusal: it reads text, so an address built at run time, or a port read from the file into a variable, is not seen. The next wall is the cookie: such a request is a POST with no pairing cookie, and every acting route answers 403 except the four free actions and the reads listed above. The agent has no command route either: the person-only rule in `gate.json` refuses its own `task approve-plan`, `confirm-req`, `approve-promote`, `recover`, `pause`, `resume`, `review ...`, `test runner`, `allow`, `autorun on`, `task board` (not `--once`), `approve-action`, `admin on` and `doctor --accept`, among others {src:.harness/policies/gate.json#L131-L137}. The third wall is the embedded browser, which is never paired.

## Board internals: the Enter screen and its checks

`/api/ready` (a POST, no cookie) calls `Ready.answer(paired)`, which builds five required lines in this order: `setup`, `paired`, `doctor`, `vscode`, `copilot`. Each has a `state`: `ok`, `wait` (comes by itself), `fail` (needs the person) or `check` (not known yet). A check that raises is a `fail` with the error name, never a failed request. `ready` is true only when all five are `ok`, so `wait` and `check` keep Enter off. The optional block "From the company" is built apart (`optional()`); a row of it can be red and still blocks nothing {src:.harness/engine/modules/task/ready.py#L650-L689}.

Setup: `setup_done` is true when `user.override.json` has `setup_done`, or the target override file exists, or any task folder exists; when false the page turns Enter into Get ready (`/setup?first=1`). Paired: the `paired` flag of the request {src:.harness/engine/modules/task/ready.py#L77-L86}.

Doctor. `run_doctor` runs `harness doctor` once in a child process (low priority, the whole tree ended at the deadline) with the deadline `board.doctor_seconds` (default 300, held between 30 and 1800). Only output lines starting `[ERROR]` count as errors; `[WARN]`, `[WARN:company]` and `[WARN:copies]` are counted as warnings and block nothing. A crash or timeout is `failed`. The first run starts before the browser opens; it runs again after 600 s when clean, after 1, 2, 5, then every 10 minutes while it fails, and at once on Check again (`/api/doctor-again`, paired) or when a configuration file changed. On every poll `doctor_line` also fails a clean doctor when a company tool pack clashes with a factory pack or a guardrail file differs from what was accepted {src:.harness/engine/modules/task/ready.py#L159-L186} {src:.harness/engine/modules/task/ready.py#L276-L324} {src:.harness/engine/modules/task/ready.py#L376-L406}.

VS Code and Copilot. The VS Code line is read from the link's cache: ready is `ok`; `starting`, `lost`, `error`, `cli-slow` are `wait`; any other reason is `fail`. When `ok`, `launchenv.carried` asks whether the connected VS Code was started with this copy's tool folders and CA bundle; if not, the line is `fail` (`env` or `unseen`) and the VS Code button restarts it. The Copilot line is `wait` while VS Code is not `ok`, `fail` when the host said `Provider ... not ready` or `Client is not connected`, `fail` when no model is enabled by the policy, else `ok` {src:.harness/engine/modules/task/ready.py#L326-L374}.

The screen is the page's work only: `enter.js` sets `app.inert = true` on the board under it and disables its button unless the last answer had `ready` (or the setup line asks for Get ready). The server has no "entered" state and `/api/ready` is the only caller of `Ready.answer`: the screen guides a person and is not access control (the cookie and typed codes are) {src:.harness/engine/modules/task/web/enter.js#L645-L662}.

## Board internals: the views, `--once`, and where a wait comes from

`harness task board --once` writes the static page `.workspace/reports/board.html`, `--refresh N` writes it again every N seconds, a person at a terminal gets the served board, and `harness task list --text` prints the rows as a table. The served page asks `/api/board` every `board.refresh_seconds` (default 3), keeps the view (Lobby or List) in `localStorage` as `harness.board.mode`, lists the newest `board.closed_shown` (50) closed tasks, and counts a task as at work only when its session's log was written within `board.active_seconds` (300) {src:.harness/engine/modules/task/commands.py#L199-L212} {src:.harness/engine/modules/task/web/board.js#L26-L56} {src:.harness/engine/modules/task/taskboard.py#L187-L204} {src:.harness/engine/modules/task/tasklife.py#L776-L787}.

What a task waits for is not stored: `tasklife.waiting` works it out from files and records, first match wins: the agent asks in a tool; a promote stopped halfway; a plan not approved or changed; a promote dry run not approved; checks that ran out; a delivered task; a written, unconfirmed requirement (full tier); held outside calls; a hand-over; a written-back result to commit; then the marks the Stop hook or an approval left. The board puts two waits from VS Code first: a command to allow, a question to answer {src:.harness/engine/modules/task/tasklife.py#L276-L338} {src:.harness/engine/modules/task/boardserve.py#L401-L420}.

## Board internals: the link thread `vslink.py` and why there is one

`VsLink` is one daemon thread (`vscode-link`) that owns the connection and a cache. The reasons are in the module docstrings: starting `code` takes a second or more (more on a work PC with a virus scan), the AHP connection is not thread safe, and a page request must never wait for or touch the host, so a page only reads the cache. `ahp.run_code` is called from this thread {src:.harness/engine/modules/task/vslink.py#L1-L20}.

Loop, `_run`: refuse any waiting job with `not-ready` when there is no connection; open (`find_code`, `code agent endpoints`, `choose`); on failure wait. `choose` takes the only endpoint; with several VS Code programs it keeps the one that has chats of this folder, and none or two is `NotReady("many")`, never a guess. Waits: 300 s for `no-cli` and `off`; otherwise a backoff of 3, 6, 12 ... up to 60 s, reset on success. When the board opens VS Code, `hurry()` looks every second for 60 s {src:.harness/engine/modules/task/vslink.py#L96-L119} {src:.harness/engine/modules/task/vslink.py#L503-L568}.

Inside a connection, `_serve` lists chats and models, then each turn (1 s) handles host notices and jobs, lists again every 180 s (every 2 s for up to 120 s while a chat the board just made is not listed yet), reads the models every 15 s, and looks at the tasks every 3 s or when marked dirty. `_look` reads the open tasks, adopts chats the board made, reads up to 3 unread chats per turn for their Copilot ids (newest first), decides the bindings and subscribes, only to: chats bound to an open task, chats the board made that wait for their task, the super agent chat, the newest 3 subagent chats of each bound chat and the chats of running subagent calls, plus the session of each bound chat for its `inputNeeded` list {src:.harness/engine/modules/task/vslink.py#L619-L647} {src:.harness/engine/modules/task/vslink.py#L1263-L1281} {src:.harness/engine/modules/task/vslink.py#L1412-L1443}.

Slow is not lost: a relist the host does not answer in time counts as slow, is asked again after 30 s, and only 3 in a row give the connection up; a closed connection is lost at once. On a loss `keep_shown` keeps what each row showed of its chat for 120 s with `kept: true`, so a task does not flash idle {src:.harness/engine/modules/task/vslink.py#L782-L803} {src:.harness/engine/modules/task/vslink.py#L530-L568}.

Off, and exceptions. `board.vscode: false` in the task policy makes the link `off` and the thread never starts; `HARNESS_VSCODE_CLI=off` makes `find_code` return None. A standalone `harness doctor` opens its own connection (`check_vscode`). Two paired routes start a process from the request thread: `/api/connections` step `open` and `/api/launch` (a company launch script, Windows) {src:.harness/engine/modules/task/vslink.py#L64-L66} {src:.harness/engine/doctor.py#L601-L625} {src:.harness/engine/modules/task/boardserve.py#L1036-L1050}.

## Board internals: the AHP client `core/ahp.py`

`find_code`: the file named by `HARNESS_VSCODE_CLI` when it exists (`off` returns None), then the standard install places, then `code` on PATH unless the path contains `remote-cli`. `run_code` runs it with a 25 s limit (`cli-slow` on timeout, `cli-failed` on a non-zero exit) and, for a VS Code it starts, the tool folders and CA bundle from `launchenv.extra` {src:.harness/engine/core/ahp.py#L34-L37}.

`read_endpoints` runs `code agent endpoints` and keeps `Endpoint(kind, path, pid, instance, token)`. The token sits in a private slot, is left out of `repr`, and `scrub` removes it from any text that is shown (the board's `ahp_scrub` reduces a host error to its class name). The transport is a unix socket (macOS, Linux) or a named pipe (Windows); the connection upgrades with `GET /?tkn=<token>`, waits for 101, then speaks masked WebSocket text frames with JSON-RPC 2.0, `PROTOCOL = "1.1.0"` {src:.harness/engine/core/ahp.py#L121-L163} {src:.harness/engine/core/ahp.py#L316-L346}.

Calls with a reply, each with a 20 s timeout: `initialize` (no `clientInfo`, so the host records the client as `vscode`), `subscribe`, `unsubscribe`, `listSessions` and `createSession` (called by `vslink._create`). `dispatchAction` is a notification, no reply. `disposeSession` is never called, because it deletes the chat's `events.jsonl`, and no function for it exists. A connection is used by one thread {src:.harness/engine/core/ahp.py#L385-L445}.

## Board internals: binding a chat to a task, `chatlink.py`

`chatlink.decide(entries, sessions, sdk)` returns for each open task a binding or None with a reason. Way 1, `how = "board"`: the board made the chat; `vslink.create` keeps what it made (and a stub for 120 s, since the host lists a chat only after its first turn), and when an open task of that name exists `_adopt` calls `chatlink.adopt`, which writes the binding into the task state at once. It stands while the chat exists and gives way only when `moved_on` finds a sure sign that another chat picked the task up: the task's session id is new since the binding (not `was`, not the board chat's own) and exactly one other chat carries it {src:.harness/engine/modules/task/chatlink.py#L1-L16} {src:.harness/engine/modules/task/chatlink.py#L38-L81} {src:.harness/engine/modules/task/vslink.py#L1283-L1320}.

Way 2, `how = "sdk"`: the task's `session_id` (from `task attach`) is compared with the `sdkSessionId` Copilot writes in the usage of a chat's turns (`ahp.sdk_ids`); the task is bound only when exactly one chat of this folder carries it. The thread reads at most 3 unread chats per turn, newest first, and a chat without an id again when it changed or every 5 s while it is busy {src:.harness/engine/core/ahp.py#L527-L541} {src:.harness/engine/modules/task/vslink.py#L1338-L1368}.

The task stays unbound, with a reason, rather than guess: `no-session` (no session id), `no-chat` (no chat has the id; a new chat has none until the model has answered once), `ambiguous` (two chats carry the id, or two open tasks share one session id and the session does not hold exactly one of them). `VsLink.check` shows `ambiguous` as `unsure` and every other reason as `unbound`; the board shows the text to copy. No route and no button binds a chat by hand {src:.harness/engine/modules/task/chatlink.py#L38-L72} {src:.harness/engine/modules/task/vslink.py#L428-L441}.

Unsettled. A task bound the board way whose session id is new since (not `was`, not among the chat's own ids) is `unsettled`: another chat may have taken it and has not been read, so `_recheck` refuses a send with `changed` until the chats are read. A pending chat of the board is let go after 3600 s without its task, or when a task of that name opens with a session id the chat does not carry. The binding is written into the task state as `chat: {session, chat, title, how, bound_at, sdk}` (way 1 also keeps `was`; `model` is the person's); `updated_at` stays, because a binding is not something the person did {src:.harness/engine/modules/task/chatlink.py#L89-L94} {src:.harness/engine/modules/task/chatlink.py#L105-L143}.

## Board internals: the ten actions on a linked chat and the state each needs

Each action is its own POST route (paired browser only), one `Board` method and one job kind for the thread. `NEEDS` in `vslink.py` names the chat state a kind needs; `VsLink.check` reads it from the cache and the thread checks it again. The chat state comes from the host's status bits: `input` (waits for a person), `busy`, `error`, `idle` {src:.harness/engine/modules/task/vslink.py#L140-L141}.

- **Send** (`/api/send`): needs idle; `chat/turnStarted` with the task's chosen model on the message.
- **Steer** (`/api/steer`): needs busy; `chat/pendingMessageSet` kind `steering`, into the running turn.
- **Queue** (`/api/queue`): needs busy; the same action with kind `queued`, the next turn after the running one. The page offers it only in steer mode.
- **Take back** (`/api/unqueue`): any state; refused `queue-gone` when the message is no longer queued, else removed (`chat/pendingMessageRemoved`) and its words return to the box.
- **Withdraw** (`/api/undo`): any state. A running turn is cancelled first (`chat/turnCancelled`) and the thread waits at most 12 s for it to end (`not-stopped` if not); with no turn, `no-turn`; else `chat/truncated` removes the last turn. The host cuts Copilot's own history, files the agent changed stay changed, and the text and file names return to the box.
- **Stop** (`/api/stop`): needs busy; `no-turn` when the chat shows no running turn.
- **Try again** (`/api/resume`): any state, but only when the last turn ended in an error part with `resumable: true` and nothing runs (`ahp.resumable_turn`), else `no-retry`; it sends `chat/turnResume`. A chat in the `error` state is not idle, so Send is refused there.
- **Compact** (`/api/compact`): needs idle; an ordinary `/compact` message with no model; the page asks for a confirm; its refusals have their own texts (`compact.refused.*`).
- **Allow or deny** (`/api/confirm`) and **Answer** (`/api/answer`): need `input` (a waiting subagent chat of the task counts). The page must name the item `id`, the `toolCallId` (or request id) and the `digest` of what it showed, else `ask.refused.shown`. The thread subscribes the session again, finds the item (else `ask-gone`), checks its kind, digest and key (else `ask-changed`), and only then dispatches {src:.harness/engine/modules/task/vslink.py#L994-L1068} {src:.harness/engine/modules/task/vslink.py#L1139-L1206} {src:.harness/engine/core/ahp.py#L656-L669}.

**Go on in a new chat** is not one of these jobs: it is `/api/skill` (step `act`) with the skill `harness-my-task` and the task's name; the thread makes a new chat (`createSession`, mode `interactive`, Allow all) and sends the message, and the board binds it at its next look. Only the page checks that the old chat is idle; the server checks that the link is on and ready {src:.harness/engine/modules/task/boardserve.py#L1186-L1216} {src:.harness/engine/modules/task/web/common.js#L182-L184}.

Send or Queue while the chat waits for the answer to a question turns into kind `say`: the thread reads the session again, skips the open questions of this chat, then sends the words as a steering message (a steer alone does not unblock a question). ## Board internals: the path of a chat action, and its refusals

Order. (1) The cookie. (2) `target` resolves the task and requires it open. (3) Text and files: empty or over 20,000 characters (`MAX_TEXT`), at most 10 files, 10 MB a file and 20 MB in all, each valid base64. (4) `VsLink.check` from the cache: `off`, `not-ready`, `unbound`, `unsure`, or `not-<state>`. (5) `dispatch` queues a `Job` and waits at most `JOB_WAIT` (25 s); at the end it sets `cancelled`, so a late thread does not send what the person was told failed, and raises `timeout`. (6) The thread runs `_recheck` and acts. (7) After the host was told, one line goes to `.task/sent.jsonl` (time, kind, chat, turn, the whole text, files by name and size) and one to the task history; a failure to write them does not undo the send {src:.harness/engine/modules/task/chatsend.py#L28-L35} {src:.harness/engine/modules/task/boardserve.py#L970-L980} {src:.harness/engine/modules/task/vslink.py#L443-L457}.

`_recheck(link, task, kind)` is the "read the host again just before the action" rule. It lists the chats again, works the binding out again from that list and the ids read so far, and compares with the binding the page showed. It refuses `unbound` or `unsure` without a sure binding, `changed` when the binding differs (`chatlink.same`) or is unsettled, and `not-idle`, `not-busy` or `not-input` when the chat's state now is not the one `NEEDS` names (a waiting subagent chat still counts for confirm and answer). A `relay` job (autorun's wake) takes idle or error. Only then does the thread act {src:.harness/engine/modules/task/vslink.py#L851-L878}.

A refused send, steer or queue raises `Fallback`: the page shows the reason and the text to copy into the chat; the other chat routes give a plain refusal. The reasons are keys `send.refused.*` (`off`, `not-ready`, `unbound`, `unsure`, `changed`, `not-idle`, `not-busy`, `not-input`, `no-turn`, `no-retry`, `queue-gone`, `ask-gone`, `ask-changed`, `confirm-waits`, `timeout`) {src:.harness/engine/modules/task/boardserve.py#L954-L955}.

The busy refusal is a separate rule and covers other buttons. `Board.idle(action, task)` looks again whether the agent is in the middle of a turn (`tasklife.at_work`: the task is open, held, not paused, waiting for no one, its session made a hook call within 300 s and has not stopped). VS Code's word wins: a bound chat that is `idle`, `error` or `input` counts as not at work; otherwise it raises `serve.busy`. It is used by `act` (every action except `review set`, `task allow`, `task link`, `test runner`, and except Off work and Back to work, which return earlier), by `close`, by the approval of held calls and by Start autorun. No chat route calls it: Send, Steer, Queue, Take back, Withdraw, Stop, Try again, Compact, Allow or deny and Answer rely on their own chat state. The page also dims its action buttons for a working task, except Archive, Steer and Stop {src:.harness/engine/modules/task/boardserve.py#L685-L696} {src:.harness/engine/modules/task/boardserve.py#L746-L760} {src:.harness/engine/modules/task/web/common.js#L199-L203}.

## Board internals: fixed message text, `chatsend.py`

Python writes every message; the page only previews it (`Board.message`, `chatsend.prepare`). The approval messages are fixed English templates: `go-req` "Requirement confirmed (REQ.md). Go on.", `go-plan` "Plan approved (PLAN.md). Go on with TODO.md.", `go-promote` "Promote (write-back repo) approved. Go on with the promote, then stop and report.", and the plain lines `go-recover` and `go-review`. A `go` send is allowed only for a wait in this list (else `nogo`); `template()` returns an empty string for any other wait and `prepare` refuses a kind it does not know. The approval code is in no template, and the tests assert that no template contains a brace, the word code, `[review]`, `[EN]` or `/compact` {src:.harness/engine/modules/task/chatsend.py#L43-L66} {src:.harness/engine/modules/task/boardserve.py#L957-L968} {src:.harness/tests/test_chatsend.py#L33-L47}.

What the person can add: notes (saved drafts and one typed note, one line each, after `Notes from the person:`), the reply language (`[ZH]` first when Chinese is chosen; `[EN]` only for a chat that replies in Chinese) and files. An answer, a steer, a queued message and `say` go as typed, so a person can still type `[review]=2` in their own words; the board never adds it {src:.harness/engine/modules/task/chatsend.py#L67-L72}.

Why no control mark goes out unless a button asked for it: every board message is dispatched with `origin: {kind: user}`, as a typed prompt, and the task hook sees it (a restore point is matched to that user turn). The hook reads `[review]=n` from a person's words and sets the task's number of independent checks, a paid setting (extra model calls). So no button or template carries it; the number is set on the task page (`review set` through `/api/act`, no code). The control marks the board does send: `[ZH]` and `[EN]` after a language choice, `/compact` (the Compact button), the slash command of a one-click skill (`skillsend.message`: a skill of this copy, one line, no control characters, at most 2,000 characters), `/harness-ask` (a read-only question to a task from the Super agent view) and `/harness-super` (the super agent chat's own mark). Autorun also sends `/compact`, at its Start and at a pit stop, through the `relay` job after the person switched autorun on, so "only the Compact button" is not the whole truth {src:.harness/engine/modules/task/vslink.py#L72-L90} {src:.harness/engine/modules/task/handler.py#L77-L93} {src:.harness/engine/modules/task/skillsend.py#L24-L42} {src:.harness/engine/modules/task/autorun_start.py#L4-L5}.

## Board internals: the stage ribbon, `taskstages.py`

`taskstages.of(root, task)` works the ribbon out from files and state each time; nothing is kept, so a task that starts over falls back by itself. It returns None for kind `qa`, for a task not started and for one that cannot be read. Kinds `rca`, `design`, `other`: `doing`, `done` (done = closed). Kinds `dev` and `kb`: `requirement`, `plan`, `developing`, `writeback`, `done`. Kind `test`: `guide`, one step per environment (`## <ENV>` headings of `TEST-GUIDE.md`, else DEV, IST, UAT), `done` {src:.harness/engine/modules/task/taskstages.py#L1-L17}.

The rule is `steps_of(names, finished, flags)`: the first step that is not finished is `now`, every step before it is `done`, and every later step is `todo`, even when its own condition is true. For `dev` and `kb`, `finished` is: requirement confirmed (or plan or promote already approved), plan approved, promote approved, promote done, promote done {src:.harness/engine/modules/task/taskstages.py#L46-L68}.

Fall-back. The plan counts as approved (`tasks.plan_approved`) only when the SHA-256 of `PLAN.md` equals the approved hash and the requirement digest kept with the approval equals the current one. That digest is a SHA-256 over the sections What to do, What not to do and Done when (either language), blanks ignored. So an edited plan sends Developing, Write-back and Done back to `todo`, and an edited requirement does the same to the plan. When a promote is done and the task is opened again, `archive_round` renames `DEV` to `DEV_r<n>` and the plan to `PLAN_r<n>.md`, resets the plan and `promote` and raises `round`, so Plan becomes the step now {src:.harness/engine/core/tasks.py#L109-L164} {src:.harness/engine/modules/task/task.py#L234-L251}.

Variants. A `dev` or `kb` task whose `DEV/` holds only `_manual/` work, with no promote approved, uses the apply ribbon (`by_hand`): requirement, plan, developing, apply, done; apply is done by a `run-record` event after the last `approve-plan` (or the close), and its label names the environments of those records (`Apply to DEV`). A test environment is done when its newest results file ends with `Verdict for <env>: PASS` outside code fences. Flags: `partial` on write-back when the promote stopped halfway; `failed` on an environment with a FAIL verdict; NEEDS MORE or no verdict sets no flag. The independent checks row gives one mark per check (`pass`, `run`, `fail`, `todo`), and each step gets its seconds from the history events that end it {src:.harness/engine/modules/task/taskstages.py#L70-L92} {src:.harness/engine/modules/task/taskstages.py#L188-L260}.

## Board internals: safe drawing of task files, `mdtree.py`

Task files are written by an agent, so `mdtree.parse` turns Markdown into a tree of a closed set of blocks (`h`, `p`, `ul`/`ol`, `code`, `quote`, `table`, `hr`) and spans (`text`, `code`, `b`, `i`, `s`, `a`, `br`, `img`), and the page builds every node itself. No HTML passes: a `<script>` is plain text in a `text` span. Lines that are only an HTML comment are dropped (not inside a fence); over 5,000 lines the result is marked `cut`; a document is cut at 400,000 bytes {src:.harness/engine/modules/task/mdtree.py#L1-L14} {src:.harness/engine/modules/task/taskdesk.py#L24-L24}.

Links: `safe_href` keeps a link only when it starts with `http:`, `https:` or `mailto:`, is an anchor, or is a path; any other scheme (`javascript:`, `data:`, `vbscript:`) makes the link plain label text. The page draws a clickable `a` for `http(s)` or `mailto` only, with `rel="noopener noreferrer"`. Pictures: an image is kept only with no scheme and not starting `//`; `resolve_images` and `task_path` allow only `.png`, `.jpg`, `.jpeg`, `.gif` and `.webp` (no SVG: it can carry a script) and refuse an absolute path, a drive letter, a NUL or a path that leaves the task folder. The route `/file/<task>/<path>` checks again (`taskdesk.image_file`): the same path test, no symbolic link on the way, the resolved file inside the task folder, a file, at most 8 MiB {src:.harness/engine/modules/task/mdtree.py#L35-L47} {src:.harness/engine/modules/task/web/desk.js#L253-L262} {src:.harness/engine/modules/task/mdtree.py#L315-L342} {src:.harness/engine/modules/task/taskdesk.py#L584-L609}.

The page: every script of `web/` builds nodes with `h()` and `textContent`; a search of `web/*.js` finds `innerHTML` only in a comment, and no `outerHTML`, `insertAdjacentHTML`, `eval`, `new Function` or `document.write`. The data of a page is one JSON blob with `<`, `>` and `&` escaped. The served page carries the Content-Security-Policy as a second wall; a saved HTML copy carries a stricter one (images from `data:` only, no connections). A fenced code block still gets a Run button that runs on the paired person's click, and `mdtree` removes no secret from a file's text {src:.harness/engine/modules/task/web/common.js#L1-L12} {src:.harness/engine/modules/task/taskhtml.py#L68-L70}.

## Board internals: health warnings and the records they read

The warnings are display only: nothing in the code reads them to stop or change a task. `health.check` returns the rules that fire for an open task and never raises; a missing or unreadable file gives no warning. Defaults, from `health` in the task policy: `stuck_minutes` 10, `repeat_commands` 3, `idle_turns` 4, `cost_ratio` 2.0, `context_percent` 70, `context_notice` 50 {src:.harness/engine/modules/task/health.py#L1-L33}.

Records: only the tail is read (256 KiB of the hook log, 512 KiB of Copilot's `events.jsonl`), cached per file until its size or time changes. From the hook log: tool events with their kind and, for a terminal call, `cmd`, the first 10 characters of a SHA-1 of the command with whitespace normalised. From Copilot's record: event types and times only, subagent rows skipped. No prompt, reply or thinking is read {src:.harness/engine/modules/task/health.py#L29-L34}.

Rules, checked only while the agent is at work (open, held, not paused, waiting for no one, and the row says working or Copilot's record has a turn open). `stuck`: the later of the last hook tool event and the last Copilot tool start or completion is at least `stuck_minutes` old. `repeat`: the last terminal calls, completed or failed, have the same hash, `repeat_commands` in a row; a completed edit or create resets the count and other tool kinds do not break the run. `idle`: main-agent model turns since the user's last message and after the last edit number at least `idle_turns` (subagent turns do not count) {src:.harness/engine/modules/task/health.py#L130-L139} {src:.harness/engine/modules/task/health.py#L188-L211}.

`cost` needs at least 3 closed tasks of the same kind with Credits from the brief (`MIN_PEERS`) and fires at `cost_ratio` times their median. The board's rows pass the peers, a task page calls `check` without them, so cost shows on the board and not on a task page. `context` is added by `with_context` from the link's context meter, for an open task whose chat is bound, so only a served board shows it; it fires above `context_percent`, and from `context_notice` the bar turns amber with no tag {src:.harness/engine/modules/task/health.py#L141-L178}.

## Board internals: the read-mostly rules and where each holds

Re-read before acting: for a chat action the thread's `_recheck` reads the host again just before the action; for allow, deny and answer `_respond` subscribes the session again and refuses `ask-gone` or `ask-changed`; a command confirmation cannot be replaced by free text (`confirm-waits`); a job the page gave up on is cancelled and never sent. The Super agent chat re-checks too: `Brain.turn` synchronises with the chat and rebuilds the digest from the rows when it sends, and a proposal is judged again against the rows at each read; it refuses with `asleep` (VS Code not linked), `limit` (the day's Credits reached `super.daily_credits`), `busy` or `error` {src:.harness/engine/modules/task/vslink.py#L1162-L1206} {src:.harness/engine/modules/task/superbrain.py#L415-L460}. The three-second refresh of the page is another thing: it redraws rows from the cache and acts on nothing.

Never start `code` from a request: a page request reads the cache, and `ahp.run_code` runs only on the link thread. The named exception is a person's click: **Open** and **Restart VS Code** make the thread run `code <folder>` (never `-r`) or quit and open VS Code, from a paired browser only; the Servers window and a Windows launch script start a process from the request, paired only. `disposeSession` is never called, so the board deletes no chat {src:.harness/engine/modules/task/vslink.py#L459-L466} {src:.harness/engine/modules/task/boardserve.py#L1847-L1873}.

Fails soft: pages read only the cache and never wait on the host; the `/api/super` endpoints catch errors and the page keeps what it shows; an unreadable record of the super chat's day gives a fresh one; a super chat turn that the chat never shows is given up after 180 s (`LOST_AFTER`). The Enter screen is the one place that does not fail soft: with no VS Code, or Copilot not connected, a new tab does not get in, while a tab already past it still reads and takes approvals but sends nothing {src:.harness/engine/modules/task/superbrain.py#L41-L41} {src:.harness/engine/modules/task/boardserve.py#L2113-L2137} {src:.harness/engine/modules/task/ready.py#L650-L689}.
