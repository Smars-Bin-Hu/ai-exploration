## Setup internals: how a new person starts, from Start Harness to the board

**Start Harness needs no `harness` on PATH.** `Start Harness.command` (macOS) and `Start Harness.cmd` (Windows) run `.harness/bin/harness task board` by relative path. Before that they only check that a Python name exists (`python3` or `python`; on Windows `python`, `python3` or `py`); they do not run it or read its version, and on Windows `where python` also finds the Microsoft Store stub. With none they print "Harness needs Python 3.9 or newer" {src:Start Harness.command#L1-L17} {src:Start Harness.cmd#L1-L12}.

**The launcher** `.harness/bin/harness` looks upward from the current folder for `.harness/engine/cli.py`, as git looks for `.git`; outside every copy it follows its own symlinks, and a plain copy of the script uses `$HARNESS_HOME` or stops. It `exec`s the first of `python3`, `python` that runs `-c ""`, else exits 127. `harness.cmd` searches the same way, steps past a `\WindowsApps\` `python.exe` (the Store stub) to the `py` launcher, and never tries `python3`. Neither checks the version; `doctor` does {src:.harness/bin/harness#L1-L44} {src:.harness/bin/harness.cmd#L1-L43}.

**One board per copy.** `serve` first asks `running_board`: the port in `.harness/runtime/board-serve.json` must answer `/api/status` with this copy's folder. If so, a second start prints that port and asks the running board to reopen the browser; otherwise it binds `127.0.0.1` on `board.port` of the `task` policy (default 8765), and a busy port fails with "port busy" unless a board of this copy started a moment earlier {src:.harness/engine/modules/task/commands.py#L92-L98} {src:.harness/engine/modules/task/boardserve.py#L119-L122} {src:.harness/engine/modules/task/boardserve.py#L2254-L2280} {src:.harness/engine/modules/task/boardserve.py#L2307-L2326}.

**The start order.** After binding, `sync_on_start` puts the company's content in place (it takes nothing back) and calls `integrity.accept_on_start`, which makes the accepted list of guardrail files when there is none or when the version in `registry.json` changed; a list for this version whose files do not match is left alone. A fault in either never stops the board. The child `doctor` starts before the browser is asked to open, and the browser opens `http://127.0.0.1:<port>/#pair=<code>`. The code is `secrets.token_urlsafe(12)`, in memory only; `pair` trades it for a session token once and clears it, so a link works a single time {src:.harness/engine/modules/task/boardserve.py#L2283-L2296} {src:.harness/engine/modules/task/boardserve.py#L2327-L2349} {src:.harness/engine/modules/task/boardserve.py#L361-L395} {src:.harness/engine/integrity.py#L200-L210}. The gate refuses the agent's `task board` (except `--once`) {src:.harness/policies/gate.json#L131-L137}.

## Setup internals: the short command, Set it up and Test it

**Set it up** is needed because every command the agent is told to run starts with `harness`. The board asks what a new terminal would see (`shortcmd.fresh_path`: a login shell, `$SHELL -lic`, 5 s, on macOS and Linux; the registry `Path` on Windows) and looks for `harness` there {src:.harness/engine/core/shortcmd.py#L16-L53}. The button runs a line that the engine builds (`command_for`) and runs itself (`install`, 20 s); a line from the page is never run, and only the paired browser reaches it. On Windows it copies `harness.cmd` to `%USERPROFILE%\bin` and appends that folder to the user `Path`. Elsewhere it links the launcher into `~/bin` or `~/.local/bin` when one is on the fresh PATH, else makes `~/bin` and appends an `export PATH` line to `~/.bashrc` or `~/.zshrc` {src:.harness/engine/core/shortcmd.py#L56-L69} {src:.harness/engine/core/shortcmd.py#L101-L109} {src:.harness/engine/modules/task/boardserve.py#L1160-L1165}. So the harness does change the PATH, but only when a person presses this button; `docs/01-quickstart.md` says the harness never changes environment variables, which describes the manual route {src:docs/01-quickstart.md#L54-L54}.

**Test it** runs `harness --version` as found on the fresh PATH, in this copy's folder, within 20 s (`RUN_WAIT`; a work computer starts programs slowly); exit code 0 is a pass. On Windows `try_short` also checks `python`: missing on the fresh PATH is "missing", and `python -c ""` that fails is "stub", because the hooks start `python` there {src:.harness/engine/core/shortcmd.py#L72-L98} {src:.harness/engine/core/setup.py#L334-L338}.

**The wait for VS Code.** When the board saw the command missing and then found, and the VS Code link is ready, `wait_reopen` remembers the link's drop count; the Enter screen's setup line stays "waiting" until the link has dropped once, that is, VS Code was closed and opened again, because terminals it already started keep the old PATH {src:.harness/engine/modules/task/boardserve.py#L1175-L1186} {src:.harness/engine/modules/task/ready.py#L566-L575}.

**The Enter screen's setup line.** Enter has five required lines: copy set up, browser paired, `doctor` without error, VS Code open, Copilot connected; the company's items never block {src:.harness/engine/modules/task/ready.py#L1-L8}. The setup line is red (reason `new`) until `setup_done` is true: `user.override.json` holds `setup_done: true`, or, for copies from before Get ready, `target.override.json` exists or any task folder does {src:.harness/engine/modules/task/ready.py#L77-L85}.

## Setup internals: how Get ready is laid out and what it writes

Get ready is the page `/setup`, answered by `/api/setup`, which refuses an unpaired browser; no agent runs {src:.harness/engine/modules/task/boardserve.py#L1961-L1967}. It has four cards. **1 The short command**: Set it up, Test it. **2 You** (required): name and language (locked when `HARNESS_LANGUAGE` is set). **3 From the company** (the only card tagged OPTIONAL): the knowledge base (keep, package zip, or folder), a read-only checklist, and the code repositories. **4 Local**: a read-only checklist and a closed "More" part with the Python install command and the paths the agent must not touch. The skill prefix is a box only when the knowledge base names none. The checklists (instructions, skills, standards, packs, connections, programs, CA bundle, MCP) only show facts; identities go to `.harness/.env` and the CA bundle to `.harness/certs/` through their own windows, and Get ready writes neither {src:.harness/engine/modules/task/web/setup.js#L296-L372} {src:.harness/engine/modules/task/web/setup.js#L651-L662} {src:.harness/engine/core/setup.py#L291-L331}.

**Checks before any write.** `Job.start` runs `setup.check`, which collects every error and raises one `ValueError`; with any error nothing is written. It tests the name and language, the repositories (a git folder, not this copy's own folder or its `knowledge-base/`, not shaped like a knowledge base), the install command length, the knowledge base mode and path, the skill prefix, a language that conflicts with `HARNESS_LANGUAGE`, and a stamp that no longer matches {src:.harness/engine/core/setup.py#L341-L388} {src:.harness/engine/core/setup.py#L84-L143} {src:.harness/engine/modules/task/setupjob.py#L154-L163}. The stamp, a hash of the fields the form shows, keeps what a terminal wrote meanwhile from being overwritten. `kept` raises on a broken override, which is therefore never overwritten. `write` replaces only the top-level keys a step owns and saves through `state.atomic_write` (temporary file, then `os.replace`) {src:.harness/engine/core/setup.py#L33-L52} {src:.harness/engine/core/setup.py#L216-L223} {src:.harness/engine/core/state.py#L129-L146}.

**The files and keys.** Three steps write three files ({src:.harness/engine/core/setup.py#L391-L454}):

- `user.override.json`: `name`, `skill_prefix`, and `language` unless forced. Later: `setup_done: true` after all steps pass, and `none` from the tick "We have none" (skills, standards; written at once) {src:.harness/engine/core/setup.py#L493-L501}.
- `target.override.json`: `repos_root` and `repos` (name to `{path, base_ref, refused_paths}`). Every `refused_paths` list that Get ready writes starts with `.git/**`. A repository on another branch than the policy's `base_ref` gets that branch as its own `base_ref`, because `doctor` stops on a missing base branch. Nothing chosen and nothing there before: nothing written. The git step adds `repos.kb = {path: knowledge-base, knowledge_base: true}` when the knowledge base is not registered.
- `tools.override.json`: `python.interpreter`, by `setdefault`, to the Python that runs the board (an existing value stays), and `python.install_command` when typed (removed when the box is emptied).

**Finish, seven steps.** `user`, `target`, `tools` (core) then `kb`, `git`, `sync`, `doctor` (`setupjob.py`) run in order on a thread. The first failing step stops the loop; the person fixes it and presses Finish again, and each step can be run again. `setup_done` is written only when all seven passed {src:.harness/engine/modules/task/setupjob.py#L88-L137} {src:.harness/engine/modules/task/setupjob.py#L169-L186}. `kb` puts a package or folder in place (a pull with news needs the person's tick; a copy over a non-empty `knowledge-base/` needs replace, and the old one moves to `.harness/runtime/kb-backup/`). `git`: `kbsetup.init` runs `git init` and a first commit. `sync`: `company.sync_after(remove=True)`. `doctor`: any `[ERROR]` fails the step.

**What is written outside override files.** Finish also writes `knowledge-base/` (with its own `.git`), the company's skills and instructions under `.github/`, and `connections.company.json` and `computer.company.json`. The comment "everything goes into the person's own `*.override.json`" is true of the three core steps only; the short command is a separate button {src:.harness/engine/core/setup.py#L1-L4} {src:.harness/engine/core/company.py#L1-L30}.

**Why override files.** The code shows these reasons. `.harness/policies/**` is a core guardrail path, so the gate refuses the agent's writes to the shipped policies and to the override files alike, while the board process, which the hook does not judge and which acts only for a paired browser, can write them. The accepted list skips `*.override.json` and `*.company.json` (`SKIP_POLICY`), so a person's setting does not look like a changed guardrail file and does not make the hook refuse. An upgrade replaces the shipped files and leaves overrides; only four overrides (`target`, `user`, `cli`, `tools`) are in `.gitignore`, and `reinstall --from` carries all `*.override.json` {src:.harness/engine/core/guardrails.py#L11-L19} {src:.harness/engine/integrity.py#L25-L29} {src:.gitignore#L10-L21} {src:.harness/engine/core/reinstall.py#L1-L13}.

## Setup internals: how policy layers merge in `config.py`

`config.load_policy(root, name)` reads `.harness/policies/<name>.json`, then `<name>.company.json`, then `<name>.override.json` if they exist, merging each onto the result with `deep_merge` (files read as UTF-8, BOM allowed). The person's file is last and wins {src:.harness/engine/core/config.py#L1-L24} {src:.harness/engine/core/config.py#L98-L110}. The rules of `deep_merge` {src:.harness/engine/core/config.py#L31-L50}:

- An override value that is not an object (number, string, boolean, `null`, array) replaces the base value whole; an array in a layer replaces the default array.
- Objects merge key by key, recursively; plain keys first, then append keys.
- A key written `"<key>+"` (longer than one character) appends its array to the array already there; with no base key it gives just the override's list; if either side is not an array, `OverrideError` is raised.
- No key can be deleted: `null` replaces the value, and `+` only adds.

The `tools` policy has more layers. The systems of installed tool packs are merged between the company layer and `tools.override.json`; after all layers each connection of a known type becomes a system, and a system written by hand with the same name wins. When a part cannot be built (a broken pack, connection list or list of knowledge bases) its programs go into one `broken-<part>` system and the gate holds every call of them, instead of letting them pass unjudged {src:.harness/engine/core/config.py#L83-L146}. The company layers the code produces are `connections.company.json` and `computer.company.json`, copied by `company sync`; the mechanism accepts any `<name>.company.json` beside a `<name>.json`. The release note that says `tools.company.json` is copied from `company/tools/systems.json` does not match the 1.8.3 code {src:.harness/engine/core/company.py#L46-L48} {src:docs/07-release-notes.md#L769-L769}. The company layer is a default, not a lock: the person's override comes after it.

## Setup internals: what an override cannot remove, what it can, and the gate's fallback

**What an override can do, with no floor:** replace `terminal.deny` and `terminal.ask` of `gate.json` (the schema only needs the three terminal lists to exist after the merge), shorten `git.approval_minutes` (minimum 1), replace `guardrail_paths` with a shorter array, replace `refused_paths`. `doctor` warns when a layer replaces a non-empty array and names the `key+` form {src:.harness/engine/modules/gate/policy.py#L28-L55} {src:.harness/engine/doctor.py#L433-L461}.

**What it cannot remove:**

- The seven core guardrail paths (`.github/hooks/**`, `.harness/policies/**`, `.harness/engine/**`, `.harness/bin/**`, `.harness/registry.json`, `.harness/runtime/**`, `.vscode/settings.json`): `guardrail_paths(policy)` puts them first whatever a layer says; the gate adds a missing one back, and `doctor` reports a dropped one as an error. The other seven shipped paths are guarded only because `gate.json` lists them {src:.harness/engine/core/guardrails.py#L9-L33} {src:.harness/engine/modules/gate/policy.py#L57-L74}.
- Any path with a `.git` segment, for the edit tools: `check_write` refuses it before `refused_paths` is looked at; in a terminal line the `GIT_FOLDER` pattern does the same, and `Compiled` drops the `.git/**` entry from per-repository rules because that floor covers it {src:.harness/engine/modules/gate/handler.py#L35-L44} {src:.harness/engine/modules/gate/policy.py#L14-L15} {src:.harness/engine/modules/gate/policy.py#L135-L144}.
- The folders outside the workspace that hold the accepted lists (`~/.copilot-harness`, and `HARNESS_INTEGRITY_DIR`) are in code only and refused in admin mode too; `.harness/runtime/**` stays closed in admin mode {src:.harness/engine/core/guardrails.py#L21-L61}.

**When a layer cannot be read.** Readers differ. `policy_or_empty` returns `{}` for callers that have defaults, and `doctor` reports the break. `targets.load` raises, and the gate then refuses edits and git or shell writes into any other git repository (`targetfault`) {src:.harness/engine/core/config.py#L149-L155} {src:.harness/engine/modules/gate/handler.py#L593-L598} {src:.harness/engine/modules/gate/handler.py#L804-L811}. For the gate's own policy, a failing merge or schema check makes the handler use `builtin.policy()`, a copy of the shipped `gate.json` with all 14 shipped paths and the shipped terminal rules, without the company and person layers. `fallback.refine` adds the strict fallback: an edit passes only inside the folder of the session's open task (none open: no write), a git command that writes is refused, a shell command that writes outside that folder is refused, and a path it cannot read counts as outside. An admin session gets the built-in rules only, so the file can be mended. {src:.harness/engine/modules/gate/handler.py#L789-L803} {src:.harness/engine/modules/gate/fallback.py#L1-L23} {src:.harness/engine/modules/gate/fallback.py#L141-L181}.

## Setup internals: what `harness doctor` checks, in run order

`doctor.run` calls the checks in a fixed order (`STEPS`) and prints `[OK]`, `[WARN]` or `[ERROR]` per line, then `{"errors": N}`; it returns 1 only when N is not 0, so warnings never change the exit code {src:.harness/engine/doctor.py#L1017-L1112}. In order:

1. **Python** 3.9 or later (ERROR if older). **Interpreter**: `python3` (`python` on Windows) is found and runs `-c "print(1)"` within 15 s (ERROR otherwise: a hook that cannot start makes Copilot refuse every call) {src:.harness/engine/doctor.py#L65-L93}.
2. **Short command**: not on PATH is an ERROR; the copy's own launcher or a byte-identical copy is OK; any other `harness` is a WARN (a copied `harness.cmd` does not follow upgrades) {src:.harness/engine/doctor.py#L160-L190}.
3. **Registry** unreadable: an ERROR that stops doctor at once, exit 1, no `{"errors": N}` line. {src:.harness/engine/doctor.py#L1040-L1046}
4. **Hook configuration**: one JSON file in `.github/hooks/`; every entry starts `launch.py`; `command` and `bash` start with `python3`, `windows` and `powershell` with `python`; every event the enabled modules need is configured (ERROR), an unneeded one is a WARN. `launch.py` and `hook.py` must compile {src:.harness/engine/doctor.py#L201-L286}.
5. **Hook activity** from the newest 20 session logs: no call, none in 7 days, a latest Local (legacy engine) session, or a slowest gate call of half the hook timeout (default 30 s) or more are WARNs {src:.harness/engine/doctor.py#L96-L158}. **Agents**: models of one agent in one series (ERROR when mixed) {src:.harness/engine/doctor.py#L894-L955}.
6. **Override layers** (below), **user** (unreadable policy, unknown language: ERROR; no name: WARN) {src:.harness/engine/doctor.py#L355-L422}. **Target repositories**: unreadable policy, missing folder, non-git path, no base branch: ERROR {src:.harness/engine/doctor.py#L815-L873}.
7. **Knowledge base**, **skills**, **company copies**: WARNs {src:.harness/engine/doctor.py#L522-L590} {src:.harness/engine/doctor.py#L647-L662}. **Tool packs**: a name clash, a faulty pack file or an unreadable connection list are ERRORs (the gate holds those programs); an unknown name in `use` or a missing program is a WARN {src:.harness/engine/doctor.py#L664-L708}.
8. **Guardrail files** against the accepted list, VS Code settings, standards, optional packages (`xlrd`, `pypdf`; also a WARN when the install command targets another Python), the `code` CLI, outside systems (malformed list ERROR, unreachable WARN), then **each module**: files exist, it imports (ERROR if enabled), its own `doctor` hook, its policy validates {src:.harness/engine/doctor.py#L601-L660} {src:.harness/engine/doctor.py#L710-L813} {src:.harness/engine/doctor.py#L288-L325}.

**Override layers.** `check_overrides` reads each `*.company.json` and `*.override.json` on its own against the bare default, not against the stack. A name containing `.company` or `.override` (an override of an override) or with no `<name>.json` is an ERROR, as is a layer that cannot be read or merged; replacing a non-empty array is a WARN. The shipped docs and message say "one layer", but the code has two since 1.7.1 {src:.harness/engine/doctor.py#L433-L461} {src:docs/03-configure.md#L28-L28}.

**What doctor does and does not do.** It writes no file except the integrity list under `--accept`, but it starts programs: Python, `git`, `code`, and the probes of connections and systems. The board runs it in a child with `HARNESS_DOCTOR_TOPICS=1`, which tags company warnings and skips the `code`, VS Code settings and probe checks the board makes itself {src:.harness/engine/doctor.py#L36-L60} {src:.harness/engine/doctor.py#L601-L612} {src:.harness/engine/doctor.py#L739-L769}. It does not check the `python.interpreter` pin, that `chat.useHooks` is on, or the quality of a skill.

## Setup internals: `doctor --accept` and the integrity list

`harness doctor --accept` first calls `approval.require_person`: stdin and stdout must be a terminal, or the command must run in the board's Terminal window, where the board gives each command a one-time code (`HARNESS_BOARD_PERSON`, kept only as a fingerprint in the lists' folder, valid 600 s, used once). The agent has no paired browser, so no code is made, and the gate also refuses the command on the agent's line {src:.harness/engine/core/approval.py#L22-L42} {src:.harness/engine/core/boardperson.py#L1-L40}. Then `integrity.accept` walks the watched files (all of `.harness/engine`, `.harness/bin`, `.github/hooks`, `.harness/toolpacks` except caches; `registry.json`; the `.json` files of `.harness/policies/` but not `*.override.json` or `*.company.json`) and writes size, time and SHA-256 of each, through a temporary file and `os.replace`, to `~/.copilot-harness/integrity/<16 hex>.json` (the hex is from the copy's folder path; `HARNESS_INTEGRITY_DIR` replaces the folder). If the folder cannot be written it prints the reason and exits 1. Otherwise it prints "Accepted these changes (n)" with up to five files when something differed, then the count, then runs the full check {src:.harness/engine/doctor.py#L1017-L1040} {src:.harness/engine/integrity.py#L23-L128}.

With no accepted list, an unreadable one, or a folder where none can be written, `doctor` gives only a WARN and the hook refuses nothing. With a list the files do not match, `doctor` gives an ERROR that says "upgrade" (another version in `registry.json`: start the board) or "changed" (same version: accept or restore). The hook compares at every tool call, prompt and session start except in an admin session; it refuses only on a tool call. The board's start does not replace a list for this version whose files do not match {src:.harness/engine/doctor.py#L973-L1003} {src:.harness/engine/hook.py#L312-L360}.

## Setup internals: why the Python is pinned, and what a command does on another Python

**The reason**, from the header of `pinpython.py` and the `tools.json` description: the `harness` command runs on the first `python3` of the PATH of whichever terminal starts it, so two terminals can run it on two Pythons (an Anaconda and a Homebrew Python on one Mac), and a package installed into one is not found by the other. The packages are the optional readers `xlrd` (old `.xls`) and `pypdf` (PDF text) that `task intake convert` uses; without them that kind of file is kept as it is. `python.interpreter` of the `tools` policy names one Python by full path {src:.harness/engine/core/pinpython.py#L1-L9} {src:.harness/policies/tools.json#L1-L13}.

**What a command does.** `cli.main` calls `restart_if_pinned` first, before arguments are parsed, so every `harness` command takes part (even `--version` and `doctor`), but only when called as the command (`argv is None`), not by a test. `named` reads `python.interpreter` through all layers and expands `~` and variables {src:.harness/engine/cli.py#L211-L214} {src:.harness/engine/core/pinpython.py#L24-L42}. Then:

- No Python named, or `HARNESS_PINNED_PYTHON` already set: stay.
- The named path is not an executable file: print "The Python named in tools.override.json (python.interpreter) is not there" to stderr and go on with the current Python.
- The `realpath` of the named Python equals the running one: stay.
- Otherwise set `HARNESS_PINNED_PYTHON=1` and run the named Python with the same arguments: `os.execve` on macOS and Linux, a child process with the same exit code on Windows.

An exception in `target` (a broken policy) is swallowed: a broken policy must not stop a command {src:.harness/engine/core/pinpython.py#L45-L60}. The board is started by this command, so it runs on the pinned Python.

**What sets the pin, and what ignores it.** Get ready's `tools` step sets it with `setdefault` to the Python that runs the board {src:.harness/engine/core/setup.py#L439-L454}. The hooks and launcher scripts are not pinned: the launcher starts the first working `python3`, and `cli.py` restarts when that differs, so a command may start two interpreters. `doctor` does not check the pin; the optional-packages check warns when the install command installs into another Python than the one running {src:.harness/engine/modules/task/intake.py#L100-L140}. By the code, and not separately tested: the guard variable is inherited by child processes, so a `harness` started from a pinned command does not restart again.

## Setup internals: upgrade in the same folder, what the board accepts and what it does not

**The board accepts a new version only at its own start, and only when the list's version differs.** `integrity.accept_on_start` runs from `sync_on_start` when the board starts. It reads the accepted list of this copy (`~/.copilot-harness/integrity/<16 hex>.json`, named from the copy's folder path). When there is no list, or the `harness` version stored in the list differs from the version in `registry.json`, it calls `accept` and returns `made`. When the version is the same and the files do not match, it returns `changed` and writes nothing; when they match it returns `kept`; on any exception it returns `none` and the board starts anyway {src:.harness/engine/integrity.py#L200-L210} {src:.harness/engine/integrity.py#L44-L48}. So unzipping a new version and starting the board is accepted, but unzipping the same version over a file that was changed (a repackaged copy, a hand edit) is not: the hook keeps refusing, and the way out is one of `harness doctor --accept` in the person's own terminal, the Accept button on the Enter screen's `doctor` row, or putting the files back from the zip {src:.harness/engine/integrity.py#L171-L183} {src:.harness/engine/modules/task/boardserve.py#L2007-L2020} {src:.harness/engine/modules/task/ready.py#L395-L406}. The button answers only the paired browser and lists the files before it accepts.

**What the hook does in between.** `hook.integrity_problem` calls `integrity.status` at every PreToolUse, UserPromptSubmit and SessionStart, except in an admin session. `status` says `upgrade` when the list's version differs from `registry.json`, `changed` when it is the same version. A PreToolUse call is then refused (message `hook.integrity.upgrade` says to start the board); a prompt or session start is let through with the same words added as context {src:.harness/engine/hook.py#L312-L328} {src:.harness/engine/hook.py#L342-L360} {src:.harness/engine/core/messages.en.json#L3897-L3898}.

**A board that is still running from the old version accepts nothing.** `serve` first calls `running_board`; when a board of this copy answers, it returns `already_running`, which prints the port and reopens the browser, and the function ends there, before `sync_on_start` and so before `accept_on_start` {src:.harness/engine/modules/task/boardserve.py#L2307-L2314} {src:.harness/engine/modules/task/boardserve.py#L2274-L2280}. The running process was started before the unzip and keeps its old code until it is stopped (by the code path, not separately tested), so a second start does not replace it. This is why the documented steps begin with closing the board and only then unzipping; if it was open during the unzip, restart it {src:docs/01-quickstart.md#L200-L200}.

**What `sync_on_start` does for the company's files.** Before `accept_on_start`, it calls `company.sync_after(root)` with `remove` false: the company's instructions and skills, and the skills of the tool packs, are copied from the knowledge base into `.github/` as Sync now would, but a skill that left the company content is not taken back. After an unzip that put the factory version of a file the company had changed, the company's version is therefore back when the board starts. A fault in the sync is swallowed so the board still starts; `doctor` reports it. Get ready's Finish calls `sync_after(remove=True)`, which does remove {src:.harness/engine/modules/task/boardserve.py#L2283-L2296} {src:.harness/engine/core/company.py#L310-L319}.

## Setup internals: `harness reinstall`, the source checks and what it carries

**The old copy is checked first.** `reinstall.source_of` accepts the `--from` path only when it is absolute, holds `.harness/registry.json`, is not this copy and is neither inside nor around it, and its version is not newer than this copy's version (numbers of the first three parts compared). The same version is allowed. {src:.harness/engine/core/reinstall.py#L61-L78}. Without `--apply` the command only lists and the agent may run it; with `--apply` it calls `approval.require_person`, so a terminal or the board's "Coming from an older copy?" window is needed {src:.harness/engine/core/reinstall.py#L300-L315}.

**What it carries, group by group.** `make_plan` carries tasks, reports and goals (each folder whole, unless this copy has one of that name); `runtime/` (every file this copy lacks); every `*.override.json`; `.harness/.env` and `.harness/certs/`; `knowledge-base/` (only when this copy's is absent or holds only `README.md` and `.gitkeep`); and the company's files, below. Anything already there is skipped and listed with a reason, so a run can be repeated {src:.harness/engine/core/reinstall.py#L116-L189} {src:.harness/engine/core/reinstall.py#L235-L246}. After the copy it runs `company.sync_after` (without remove) and the check that lists unreadable tasks and runs `doctor` {src:.harness/engine/core/reinstall.py#L327-L334}.

**Shipped files the company changed: two by git status, the skills by name.** `Plan.company` carries the two shipped files in `COMPANY_FILES` (`.harness/standards/code-standards.md` and `.github/instructions/knowledgebase.instructions.md`) only when `git status --porcelain` of the old copy lists them as changed. If the old copy is not a git repository, or git does not answer within 60 s, they are skipped with "not git". If this copy's file is byte-identical it is left; if this copy's git status also shows it changed, it is skipped as changed in both. The `domain-*` skills and the skills that start with the company's `skill_prefix` (read from the old copy's `user.override.json`, else this copy's) are carried by name from `.github/skills/` and not by git status, unless a folder of that name is already here {src:.harness/engine/core/reinstall.py#L191-L223} {src:.harness/engine/core/reinstall.py#L81-L91}. Every other changed file is only listed (`changed_in_old_not_copied`, the first 20 shown), with the person's own folders (`.workspace/`, `runtime/`, `toolpacks/`, `knowledge-base/`) left out of that list; the person decides about those files {src:.harness/engine/core/reinstall.py#L226-L232}.

**What it does not carry.** `runtime/capture/` (debug input, large, may hold code) and `runtime/board-serve.json` (the old process's port) are left out by `RUNTIME_LEFT_OUT`. The target repositories are outside the harness. The short command lives in PATH, not in the copy, and `doctor` says when it still points at the old copy {src:.harness/engine/core/reinstall.py#L1-L14}. The accepted list of guardrail files is not carried either: it is kept under the home folder, named from the new folder's path, so a new copy has none until its board first starts and `accept_on_start` makes one; before that `doctor` only warns and the hook refuses nothing {src:.harness/engine/integrity.py#L200-L210} {src:.harness/engine/doctor.py#L973-L1003}.

## Setup internals: how the board opens VS Code with the right environment

**What `launchenv` hands VS Code, and only at its start.** The agent's terminal commands and the hooks run in the editor's agent host, which has the environment VS Code was started with; a setting of the editor's own terminals does not reach them. So `launchenv.extra` builds the variables the board adds when it starts VS Code, and `vslink` runs `code <folder>` (no `-r`, so a window that already has the folder is brought forward) with that environment {src:.harness/engine/core/launchenv.py#L1-L14} {src:.harness/engine/core/launchenv.py#L237-L253} {src:.harness/engine/modules/task/vslink.py#L583-L588}. Two things are given: tool folders and the CA bundle. Identities are a third path, below.

**Tool folders.** `tool_folders` is the folders in `HARNESS_TOOL_PATH` of `.harness/.env` (those that still exist) plus the `bin/` of each active tool pack. `extra` puts them before the PATH VS Code would have, removing duplicates, and writes the variable under the name the platform uses (`Path` on Windows). `save_paths` accepts a folder only when it is absolute, exists and holds a program {src:.harness/engine/core/launchenv.py#L231-L253} {src:.harness/engine/core/launchenv.py#L152-L168}.

**The CA bundle.** `launchenv.make` writes `.harness/certs/ca-bundle.pem`. It starts from public roots (`base_roots`: the `certifi/cacert.pem` found under a tool folder's own Python, else this Python's `certifi`, else the file OpenSSL reads), adds every certificate of the chain this computer builds for the check address except the first, the site's own (PowerShell on Windows, `openssl s_client` elsewhere, through the proxy when there is one), and when the check fails adds the Mac system keychains' roots. The bundle is kept only if a TLS check against the same address and proxy passes with it; a failing trial file is deleted and the old bundle stays. On success `.harness/.env` gets `HARNESS_CA_BUNDLE`, `HARNESS_CA_HOST`, `HARNESS_CA_PROXY` and `HARNESS_CA_MADE`, and `extra` sets each variable of `TRUST_VARS` (`REQUESTS_CA_BUNDLE`) and those a tool pack asks for to the bundle's path {src:.harness/engine/core/launchenv.py#L574-L607} {src:.harness/engine/core/launchenv.py#L696-L761} {src:.harness/engine/core/launchenv.py#L249-L252}. A proxy that inspects TLS signs with the company's own CA, which the system trusts and a tool with its own roots does not; the bundle fixes that {src:.harness/engine/core/launchenv.py#L1-L14}.

**Why a running VS Code cannot pick them up.** The environment of a process is fixed when it is created. The code's comments say that `extra` is for a VS Code the board starts, that one that is open already keeps its own, and that a start that finds VS Code running gives it no environment {src:.harness/engine/core/ahp.py#L104-L106} {src:.harness/engine/core/launchenv.py#L510-L511}. The board therefore cannot add variables to an open VS Code; the only way is to quit it and open it again from the board. The code does not say what a running VS Code does with a later `code <folder>`; the Guide claims no mechanism beyond what the code's comments state.

**How the board checks whether the running VS Code has them.** `launchenv.carried` returns one of four states. `free`: this copy has nothing to carry (`needs` finds no tool folder and no bundle), so any VS Code will do. Otherwise it takes the pid of the editor's agent host from `code agent endpoints`. On macOS it reads the host's environment with `ps eww` and on Linux from `/proc/<pid>/environ`, and runs the same `lacking` the hook runs: a missing tool folder on PATH, or a trust variable that does not name the bundle, gives `missing` and lists what; none lacking gives `carried`. On Windows the environment is not read (that means reading another process's memory, which security tools watch for). There the board compares when it started VS Code (`mark_started`) with when that process was created (`process_started`, `GetProcessTimes` on a limited-information handle): created within `START_SLACK` (3 s) before the mark or later is `carried`, earlier is `missing`. A VS Code the board did not start, with no chat yet, is `unseen`: nothing proves either way, and the Enter screen then shows the line red and the button restarts it {src:.harness/engine/core/launchenv.py#L325-L328} {src:.harness/engine/core/launchenv.py#L342-L357} {src:.harness/engine/core/launchenv.py#L369-L432}. The hook adds a second proof: at SessionStart `note_seen` stores in `.harness/runtime/state/vscode-env.json` what the hook's own environment lacks, and `carried` uses it when it is newer than the process start {src:.harness/engine/modules/gate/handler.py#L601-L606} {src:.harness/engine/core/launchenv.py#L279-L306}.

**The Open button is refused for a VS Code that runs and has settings to carry.** In `/api/open`, unless the request says `anyway`, the board answers 409 with `serve.open.running_env` ("quit VS Code completely first, then press Open again") when `extra` is not empty, a VS Code is running and no chat or board start has proved the settings (`seen.ok` not true). With nothing to carry the button just opens. `anyway`, added in 1.7.29, lets the person open it regardless {src:.harness/engine/modules/task/boardserve.py#L1847-L1856} {src:.harness/engine/core/launchenv.py#L510-L522}.

**Restart is a polite quit, never a kill.** `/api/restart` answers only the paired browser. It refuses when the board runs inside a VS Code terminal, and (unless `anyway`) when an open task's agent or another chat is working. `vsrestart.Restart` then asks VS Code to quit: AppleScript `quit` on macOS, `taskkill` without `/F` on Windows, SIGTERM to `code` elsewhere. It waits `QUIT_WAIT` (30 s) for the process to end. If VS Code is still there (it asks about an unsaved file or a chat that still runs), it is not forced and not opened: the state becomes `failed` (`still-chat` or `still-open`, naming up to three chats), and the person answers VS Code and presses the button again. When it has gone, `open_vscode` marks the start and opens it again {src:.harness/engine/modules/task/boardserve.py#L1857-L1868} {src:.harness/engine/modules/task/vsrestart.py#L1-L30} {src:.harness/engine/modules/task/vsrestart.py#L88-L109}.

**Identities go through a separate path, `connections.launch`.** Plain open and restart with identities are different routes. "Open with identities" (`/api/connections`, step `open`) is refused while VS Code of this folder is open (`connections.open.running`: a VS Code that is open cannot take new identities), then calls `connections.launch`. `plan` decides which chosen identities this window holds itself (`direct`) and which are `wrap`ped: one Windows account per window (the `primary`, else the first), one value per environment variable (the first connection that wants it keeps it); a conflicting one is wrapped, and a chosen one with nothing saved is `missing`. `launch` merges `launchenv.extra` with the direct identities' variables and starts VS Code: for a Windows account through `netonly.start` (`CreateProcessWithLogonW`, network credentials only, Windows only), otherwise as a detached process with the merged environment {src:.harness/engine/modules/task/boardserve.py#L1041-L1052} {src:.harness/engine/core/connections.py#L1239-L1297} {src:.harness/engine/core/netonly.py#L1-L6}. A wrapped identity is reached by `harness as <alias> -- <command>`, which `run_as` runs only for a call of that server (exit 2 otherwise) {src:.harness/engine/core/connections.py#L1311-L1334}. Which identities a window holds is the person's choice, and the others are reached by `harness as`, so a missing identity never makes a VS Code "wrong": `needs` and `carried` count only tool folders and the bundle.

## Setup internals: why the harness never runs or guesses a package install

**The engine has no code path that runs an install.** The only use of `python.install_command` is to print it: `intake.optional_packages` fills `{package}` into the template for each optional package (`xlrd`, `pypdf`), `need_package` raises a `CommandError` that names the command, and `intake.setup` builds one command for everything missing. The error text says "Run this yourself (an agent cannot install packages)" and that the command must install into the Python the harness runs on {src:.harness/engine/modules/task/intake.py#L58-L80} {src:.harness/engine/modules/task/intake.py#L120-L132} {src:.harness/engine/core/messages.en.json#L818-L818}. `doctor`'s optional-package check only warns, so a missing optional package is not an emergency: the file stays as it is {src:.harness/engine/doctor.py#L627-L644}.

**The command is empty by default, and only a person writes it.** `policies/tools.json` ships `python.install_command` as an empty string. With none set the messages say that no command is set and that the harness "does not guess one": ask the platform team for the approved command, put it in `.harness/policies/tools.override.json` as `python.install_command` with `{package}` where the name goes, and run `task intake setup` {src:.harness/policies/tools.json#L4-L7} {src:.harness/engine/core/messages.en.json#L819-L824}. Policy files are guardrail paths, so the agent's edit tools cannot write that override; a person writes it directly or through Get ready's "More" part, whose Finish stores it with the `tools` step {src:.harness/engine/core/setup.py#L439-L454}.

**Why it does not guess.** Two reasons, one from the code's text and one from its design. The right command is company knowledge: a company may need an internal index, a proxy, a trusted host or other arguments, and a guessed `pip install` would reach the public index or an unapproved source; the message says some companies need extra arguments. And the command must install into the Python the harness runs on, which is why the pinned `python.interpreter` exists (see the section on the pinned Python) {src:.harness/engine/core/messages.en.json#L824-L824} {src:.harness/policies/tools.json#L3-L3}.

**What the gate does when the agent runs an install: it asks, it does not refuse.** The rule "it installs packages" (`pip`, `npm`, `pnpm`, `yarn`, `brew`, `apt`, `choco`, `winget`, `gem`, `cargo` followed by `install`, `add` or `i`; `go install`; `go get`; `npx`) is in the terminal `ask` list of `gate.json`, not in `deny`, and the built-in fallback policy carries the same rule {src:.harness/policies/gate.json#L146-L174} {src:.harness/engine/modules/gate/builtin.py#L183-L189}. `terminal._check` tests deny rules first and returns `("ask", why)` for the first ask rule that matches, so the agent's install raises Copilot's confirmation. A person's permission mode that skips confirmation, Allow all or Allow in this Session, gets past it. The `description` of `tools.json` and the harness docs say the gate "refuses package installs"; that overstates it, and the Guide follows the code {src:.harness/engine/modules/gate/terminal.py#L187-L205} {src:.harness/policies/tools.json#L3-L3}. What the harness does guarantee is that its own engine never runs an install.

## Setup internals: supported session types, Local sessions and `copilot -p`

**Only Copilot (SDK) sessions are supported.** The chat box of VS Code has a Session Target; the harness supports the sessions with Copilot picked, the `@github/copilot` engine. Claude and Codex sessions are not tested and are taken as not working {src:.harness/engine/adapters/copilot_vscode.py#L1-L9} {src:docs/05-design.md#L155-L161}. The board's link to VS Code works only with the `copilotcli` provider (`LOCAL_PROVIDER`): the chats the board creates and reads are those of GitHub Copilot, and other providers are not its own {src:.harness/engine/core/ahp.py#L41-L41}.

**In a Local session the hook runs, but a refusal has no effect.** The adapter `copilot_vscode.py` still parses the older Local payloads (`engine()` returns `legacy` for them, `cli` for an SDK payload). The gate and modules run and the call is logged with that engine, but `render` produces the SDK output format only, which a Local session cannot read, so a deny is not obeyed. No code path blocks a Local call {src:.harness/engine/adapters/copilot_vscode.py#L7-L8} {src:.harness/engine/adapters/copilot_vscode.py#L46-L61}. The docs give two reasons: the output format, and VS Code's statement that Local will be removed. `doctor` warns (`doctor.hook.local`) when the newest PreToolUse row of the recent logs is `legacy`, and says it is OK when it is `cli` {src:.harness/engine/doctor.py#L142-L146} {src:docs/05-design.md#L159-L159}.

**With `copilot -p` the hooks do not run and the harness has no effect.** The docs record that, measured, the hooks of the repository do not run under `copilot -p` (the command line with no window). The Copilot CLI adapter was removed in 1.0.3 because it was written from documentation and never verified; only `vscode` is left as a surface. Because no hook runs, no session log is written, so `doctor`, which reads the session logs, cannot see such a session {src:docs/05-design.md#L161-L161} {src:docs/07-release-notes.md#L3637-L3638} {src:.harness/engine/doctor.py#L106-L110}.

**`chat.useHooks` and the hook configuration.** The VS Code setting `chat.useHooks` does not reach Copilot (SDK) sessions: with it off in both the user and the workspace settings the hooks run all the same. `.github/hooks/harness.json` is read when the window starts, so a change needs Reload Window {src:docs/05-design.md#L172-L172}.
