This file holds the reasons behind the major steps of the harness from 1.0.0 to 1.8.3: what each step set out to fix, what the release notes and design documents say was learned, what was incompatible, and what still holds in 1.8.3. It is for "why did version X change Y" questions. Every version with its date and items is in the file 34 Version history; how a feature works today is in that feature's own file. The sources are the release notes `docs/07-release-notes.md` and the design documents `docs/05-design.md`, `docs/06-cost-optimization.md`, `docs/12-guardrails-and-gate.md` and `docs/13-tool-packs-and-mcp.md`; code is cited only where a statement is about 1.8.3.

## Version story: 1.0 shipped three Task Levels and the gate

Version 1.0.0 (2026-10-04) was the first official version, verified on macOS and Windows {src:docs/07-release-notes.md#L3684-L3747}.

- **Three Task Levels, picked by the person.** L1 quick answers, L2 medium tasks, L3 several agents together. Only the user could switch, by `/l2` or `[L2]` at the start of a prompt or by picking the orchestrator in the drop-down list. Searches under L1 had a limit by count. Under L2 a separate verifier agent could be switched on with `[verify]` {src:docs/07-release-notes.md#L3690-L3694}.
- **The gate.** Guardrail files cannot be changed; dangerous terminal commands are refused or need a person to confirm; the working tree of a target repository and any `.git` folder cannot be written directly; a git write command needs a person's approval in the terminal and `push` and the like are always refused; and when the same refusal keeps coming up the agent is told to stop retrying {src:docs/07-release-notes.md#L3695-L3702}.
- **Target repositories and promote.** Repositories are set up in `target.override.json` and the agent can only read them. Files are fetched from main into a work area; after the changes comes `--dry-run`, a person approves in the terminal, and the files are written to a new branch with nothing committed {src:docs/07-release-notes.md#L3703-L3708}.
- **The L2 task mode.** One agent writes `PLAN.md`, a person approves in the terminal, the agent writes only `DEV/` of the task folder, then promote; when the plan changes, the approval ends {src:docs/07-release-notes.md#L3709-L3713}.
- **L3.** An orchestrator dispatches, a builder works and a reviewer reviews, in a request folder; the plan needs a person's approval before the first round and a failed review means rework with a limit on rounds {src:docs/07-release-notes.md#L3714-L3718}.

Also in 1.0.0: admin mode, the log of every call, `doctor`, `eval check`, `.override.json` files and three skills {src:docs/07-release-notes.md#L3719-L3747}.

## Version story: what was learned from 1.0 and why the Levels were dropped

The lessons are in `docs/05-design.md`, "Why there are no Levels". L2 was the only level that got used; L1 and L3 went unused most of the time. The three-role L3 was no better than one agent on tasks with a clear requirement, at about 4.5 times the usage and about 6 times the time. Picking a level first every time was a needless step. And with two sets of rules side by side the agent was unsure and gave wrong explanations {src:docs/05-design.md#L57-L63}.

**The measurement** is in `docs/06-cost-optimization.md`, section 9: a simulated data engineering repository of 5 domains and 93 files, 4 tasks (adding a pipeline, adding a field across domains, renaming a pipeline with deleting files, fixing a formula where the requirement also asked for a change to a protected path). Each was done by the three-role setup with a knowledge base and by a single agent on a top model with no harness, and scored by the same static check script without running code {src:docs/06-cost-optimization.md#L84-L88}. Both passed 4 of 4 in one round; the three-role setup used about 456 AI credits and 16 minutes in total, the single agent about 101 credits and 3 minutes. Each task was run once, so the numbers show an order of magnitude and no more {src:docs/06-cost-optimization.md#L90-L97}.

**What the extra spend bought.** Mainly the independent check: once the builder missed two references across domains, and the reviewer found them and sent the work back with no person stepping in. That is why 1.1 kept only the independent check, as `[review]=n` switched on when wanted {src:docs/06-cost-optimization.md#L99-L100}. So the reviewer was kept on a measured case, not on reasoning alone. **What was not measured:** tasks with a vague requirement in a very large messy repository, and how `[review]` of 0, 1 and 2 differ on real tasks {src:docs/06-cost-optimization.md#L101}.

**What survives in 1.8.3.** Only the mark `[review]=n` is read. The old `[verify]`, `[No-Verify]` and `[L2]` mean nothing, and a test says so {src:.harness/tests/test_taskreview.py#L36-L38}. Of the 1.0 agents only the reviewer remains.

## Version story: the 1.0.x patches

- **1.0.1 (2026-10-10), the write scope.** Before, in the L2 mode only `PLAN.md` could be written before the plan was approved and only `DEV/` after. After, everything in the task folder can be written and only `DEV/` waits for the plan approval; `REQ/` and `REF/` cannot be written. Files at the root of `DEV/` no longer block `task promote`, and a `DEV/<name>/` that is not a configured repository is still refused, to guard against a mistyped name {src:docs/07-release-notes.md#L3663-L3683}.
- **1.0.2 (2026-10-10), getting started.** The short command `harness` became a required setup, and `doctor` reports an error when it is not on PATH. The user name (`user.json`) and a first-setup skill were added {src:docs/07-release-notes.md#L3640-L3662}.
- **1.0.3 (2026-10-10), two lessons from measuring Copilot.** Running with administrator rights (`sudo`, `runas`) and changing rights recursively or deleting containers, clusters or infrastructure (`chmod -R`, `docker rm`, `kubectl delete`, `terraform apply`) went from "you confirm" to refused outright, because it was measured that with the permission set to Allow all the confirmation box does not pop up and the command just runs; the docs then say the remaining "you confirm" commands are only a reminder. The adapter for the Copilot CLI was removed: it had been written from the documentation and never verified, and it was measured that under `copilot -p` the repository's hooks do not run. Local sessions were retired; only sessions with Copilot as the Session Target are supported {src:docs/07-release-notes.md#L3616-L3639}.

## Version story: 1.1 put everything at the centre of the task

The first sentence of the 1.1.0 note (2026-10-11): everything centres on the task; no Levels any more; one task is one folder; the work goes on after a change of session; the code counts the independent checks {src:docs/07-release-notes.md#L3559-L3562}. In place of the level, tasks are guarded by two things code decides: how much a mistake costs (judged from paths and commands) and which kind the task is, which sets the standard for done and the files the task needs {src:docs/05-design.md#L57-L76}.

**Added.** `task new`, `task open`, `task upgrade`, `task list`; seven kinds and three tiers; the handover file `TASK.md`; the requirement file `REQ.md`, which counts only after the person has read it; `[review]=n` checks counted by code; snapshots at the gates (plan approval, before every check, before the promote dry run), kept 14 days; the skills `/harness-my-task`, `/harness-quick-start` and `/harness-wondering` {src:docs/07-release-notes.md#L3565-L3584}.

**Changed.** A session with no task cannot call a subagent, and a session with a task can call only the reviewer, only after `task review start`. The checker was renamed reviewer (Sonnet, falling back to Haiku). Searches and tool calls no longer have a limit by count. `task close` leaves the folder where it is. `orchestration.json` became `task.json` and `l3_write_root` was removed from `gate.json` {src:docs/07-release-notes.md#L3585-L3598}. In 1.8.3 the first rule still holds in code: with no task open the task hook refuses every subagent except the mapper, so here the code does force a task {src:.harness/engine/modules/task/handler.py#L278-L291}.

**Retired, and what was not.** The whole L3 flow went: the commands `request`, `brief`, `attempt`, `dispatch`, `handoff`, `check`, `promote` and `report`, the orchestrator and builder agents, the request folder; also the Levels with `/l1` and `/l2`, the `verifier` agent, `task start` and the folder `.workspace/current_tasks/` {src:docs/07-release-notes.md#L3599-L3607}. Only the L3 `promote` was retired. The write-back of a task was kept: `task promote --dry-run`, the person's approval, then `task promote`. The 1.1.0 note itself says a dry run is refused without enough review passes, and in 1.8.3 `task promote` writes `DEV/` onto a new branch of each target repository {src:docs/07-release-notes.md#L3581} {src:.harness/engine/modules/task/commands.py#L1-L10}.

**What was incompatible.** The note says "This version has incompatible changes". They are the policy rename and changed fields, `l3_write_root` gone from `gate.json`, changed field names in `harness stats` and the session log (`level` gone, `verifier_verdicts` became `review_verdicts`, `budget_denials` gone), `task start` removed, and the old task folder no longer read with no migration command {src:docs/07-release-notes.md#L3585-L3615}. Five upgrade steps: run `harness doctor`; move an old task you want to go on with from `.workspace/current_tasks/` to `.workspace/sandbox/tasks/` by hand and run `task open`; rename `orchestration.override.json` to `task.override.json`, delete `task-levels.override.json` and any `l3_write_root` entry; take `/l1`, `/l2` and "task start first" out of prompt templates; and put the work of an L3 request in progress into `DEV/` of a new task by hand, since it cannot be carried on. Only task folders and the approval records inside them carry over {src:docs/07-release-notes.md#L3608-L3615}.

## Version story: 1.2, 1.3 and 1.4

**1.2.0 (2026-10-11), the task board and analysis.** The aim: one look shows which task waits for the person and where the time and usage of a task went; no incompatible changes {src:docs/07-release-notes.md#L3525-L3528}. `harness task report` writes a self-contained analysis page: working time against the time the agent waited for the person, the share of thinking, tools, subagents and confirmation clicks, one bar per prompt, time and usage per stage, context size, time per tool, and the verdict of every independent check. Usage is read from Copilot's own `events.jsonl`, falling back to the hook log (times only). `task list` sorts by how long a task has waited, `task board` writes `.workspace/reports/board.html`, a hook notes when the agent stopped and waits, `task pause` and `task resume` are person-only, and `/harness-task-report` runs only when typed {src:docs/07-release-notes.md#L3529-L3558}.

**1.3.0 (2026-10-12), knowledge base write-back, queue, mapreduce, autorun.** A knowledge base registered as a target with `"knowledge_base": true` is updated like code (fetch, change under `DEV/`, approve plan and write-back), except that it is written straight into its main branch, the harness commits once with only the files of this time, no branch is made, and the harness never pushes. `harness task queue` lists per repository which task holds it and who waits, and only reports. `/generic-mapreduce` hands a splittable job to read-only `mapper` subagents, at most 4 per run (`mapreduce.max_agents`), counted by a hook, only when the person types it. Autorun (beta) worked down `TODO.md` unwatched after plan approval, switched on only by the person with `harness task autorun on` and a typed code, needing an approved plan, unticked steps and `[review]=n`; a hook stopped it on done, plan changed, checks used up, refused 2 times, pushed on 20 times, 120 minutes, 3 rounds with no progress, the agent saying it cannot go on, or the person {src:docs/07-release-notes.md#L3495-L3524}. **1.3.1** was the first Windows measurement; among its fixes, an unfilled `REQ.md` confirmation line no longer makes an independent check fail for something the author cannot change {src:docs/07-release-notes.md#L3444-L3494}.

**1.4.0 (2026-10-13), the language setting.** One setting picks English or Chinese for what the harness prints and what the agent answers in; English is the default; docs, rules and skills are English only {src:docs/07-release-notes.md#L3401-L3404}. `language` in `.harness/policies/user.json` is `en` or `zh`, and the environment variable `HARNESS_LANGUAGE` wins. It covers CLI and hook output, the task file templates and the language the agent is told to answer in, which is one injected line, a request to the model that code cannot enforce. Every engine text is in `core/messages.en.json` and `core/messages.zh.json` with the same names, and a test fails when they differ, because a table can be tested while a second copy of prose drifts {src:docs/07-release-notes.md#L3407-L3414} {src:docs/05-design.md#L147-L153}. The incompatible point is the default: to keep Chinese, write `{"language": "zh"}` in `user.override.json` {src:docs/07-release-notes.md#L3418-L3443}.

## Version story: 1.5 made the knowledge base standard and beginner-friendly

The 1.5.0 note (2026-10-18): until now the harness left the knowledge base to the team and only plugged it in; from 1.5.0 it builds one with the person from their own code, in a standard form, and the agent leads {src:docs/07-release-notes.md#L2803-L2806}.

**The standard, 1.4.8 (2026-10-16).** Per domain: `domain.yaml` (scope, sources with the commit, entry points, boundaries, open questions), `architecture.md` (at most 300 lines), `objects/index.jsonl` (one line per object: stable id, repository and path, git sha of each source, card as `file#section`, a level of `verified`, `supported`, `inferred`, `unknown` or `conflict`), cards, `environment.md`, `tasks/`, `discovery/`, `skills/` and `exam.md`. Scripts enforce it with no model: `kb check` (fields, unique ids, card files and sections, levels, size limits) and `kb stale` (objects learned from files that changed since, by sha: `changed`, `gone`, `unstamped`) {src:docs/07-release-notes.md#L3282-L3295}. `kb cardcheck` (1.4.36) compares each card's Reads, Writes, Calls and Called by with the map; it catches a relation the model made up {src:docs/07-release-notes.md#L2883-L2893}. The reason in `docs/08-knowledge-base.md`: scripts do the structure and the model does the meaning {src:docs/08-knowledge-base.md#L9-L15}.

**The wizard and `kb status`, 1.5.0.** `/harness-rookie-new-knowledgebase` checks where the person stands, explains each step, asks only for what the person knows and leads through toolkit, map, audit, domains and each domain in batches. `kb status` works out how far the knowledge base is built from the files, never from what an agent remembers, and names the next step. The agent offers that step at a stop, once per session, while a registered knowledge base is not built and the task is not a `kb` task and not in autorun; `kb_offer: false` turns it off. The beginner skills were renamed with a `harness-rookie-` prefix {src:docs/07-release-notes.md#L2803-L2829}. Patches 1.5.1 to 1.5.4 came from the first full run in Copilot; 1.5.4 made a domain one task `learn-<domain>` with one plan approved once {src:docs/07-release-notes.md#L2757-L2802}.

**Evidence, fork and intake in the 1.5 line.** The reasoning is the same each time: material from the person must reach the agent in a form it cannot rewrite or get wrong.
- **1.5.28, `task test record`.** Results are written by script: each criterion judged with `--row`, the verdict worked out (any FAIL gives FAIL, else any NEEDS MORE, else PASS), a PASS row with no evidence refused, the person's words kept as given {src:docs/07-release-notes.md#L2498-L2511}. **1.5.41** adds screenshots copied to `TEST/evidence/<ENV>/` {src:docs/07-release-notes.md#L2321-L2335}.
- **1.5.37, `task fork`.** The next task starts from an old one: documents, `REQ/`, `REF/`, `RUNS/` and test notes are copied to `REF/from-<old>/` with `FORK.md`; approvals, checks, snapshots and `DEV/` stay behind {src:docs/07-release-notes.md#L2372-L2379}.
- **1.5.42, `task run record` and `INBOX/`.** The person gives run results on the task page, saved under `INBOX/<ENV>/`, which the agent can only read, because evidence the agent could edit would not be evidence {src:docs/07-release-notes.md#L2303-L2320} {src:docs/05-design.md#L208-L210}.
- **1.5.44, `task intake convert`.** A program with no AI turns Word into Markdown and Excel into CSV in `REQ/`, keeps the original in `REQ/originals/` and writes a report of what was left out; `paste` and `init` came with it. The Intake tab is 1.5.45; 1.5.46 adds the colour-loss notice and `task intake setup`; 1.5.47 makes `doctor` warn about missing `xlrd` or `pypdf` {src:docs/07-release-notes.md#L2277-L2292} {src:docs/07-release-notes.md#L2223-L2276}. Reason: a Word or Excel file is mostly layout, and a model reading it directly spends tokens on that and may drop a part silently {src:docs/05-design.md#L204-L206}.

## Version story: 1.6 rewrote how a person meets the harness

The 1.6 release note opens: "Version 1.6 rewrites how you meet and use the harness." The core is that the person talks to the agent on the task board, which is linked to VS Code, so the person starts a task, watches the agent live, replies, answers, allows and stops from the page; around that, setup left the chat too: double-click to start, set up in the browser, learn from the board step by step, and build the knowledge base with lessons and a window of its own {src:docs/07-release-notes.md#L1059-L1061}. The note's before and after table: Start was "put `harness` on PATH, then run a command", now double-click Start Harness; Set up was a skill in the chat then `*.override.json` by hand, now Get ready, a form in the browser with no agent; Learn was knowing which skill to type, now How can I help? with skills sorted by intent; Knowledge base was skills and command output, now steps in order and a Knowledge base window of cards; Daily work was answering in VS Code and reading on the page, now start, answer, steer and stop on the page {src:docs/07-release-notes.md#L1063-L1069}. The steps are 1.6.0 (2026-10-31) to 1.6.85, folded into one section at 1.6.86.

**The VS Code link** (first step 1.6.1) reads the agent host of VS Code through a socket on macOS and a named pipe on Windows, lists the chats of the folder and finds which chat belongs to which task by the Copilot session id; where it is not sure the task stays unlinked: nothing is guessed {src:docs/07-release-notes.md#L2015-L2033}. The board lists chats, streams the agent live, takes a reply, withdraws the last message, stops, allows or denies a command, answers a question, compacts, and starts a task with a first message shown before it is sent {src:docs/07-release-notes.md#L1073-L1081}. A chat made from the board is allow all and the gate still holds; `default` and `assisted` permissions were retired because with them the first command could wait in VS Code before the task existed and the board had nothing to show {src:docs/07-release-notes.md#L1533-L1549}.

**The safety rules of the link** are in `docs/05-design.md`: only a person triggers an action (every action is a POST from the paired browser, there is no command an agent can call, and the gate refuses an agent that sends a request to the board); a message goes out only when the chat is bound to the task for sure; the messages are fixed text; allow all makes the gate the only brake. The "VS Code required" rule is the Enter screen's: with no VS Code, or Copilot not connected, the person does not go in {src:docs/05-design.md#L184-L192}. The hook and gate code do not ask whether the board or VS Code runs, so the guardrails work with no board {src:.harness/engine/hook.py#L1-L15}.

**Start and setup.** `Start Harness.command` (macOS) and `Start Harness.cmd` (Windows) sit at the root; a second double-click opens the running board. Get ready runs no agent: it sets up the short command with one button and tests it as a new terminal would, asks for name, language, code repositories and knowledge base, and shows each step of Finish setup so a failed step can be run again. The short command is still required; Get ready only automates that step {src:docs/07-release-notes.md#L1082-L1094}. **Learning** moved onto the board: How can I help?, a window of all skills in three parts, and the Knowledge base window {src:docs/07-release-notes.md#L1095-L1111}.

**Incompatible and retired.** The harness needs VS Code (with it closed the Enter screen waits); each board must be paired again; the agent no longer closes a task that waits for the person's commit. Retired: the skill `harness-rookie-get-me-ready`, `default` and `assisted` permissions, Plan and Autopilot on the board, `depends_on` (`task queue` keeps the order), the old chat bar and dialogs {src:docs/07-release-notes.md#L1125-L1151}.

## Version story: 1.7.0 added the outside-system protocol and 1.7.12 the tool packs

**1.7.0 (2026-11-04).** A company lists the outside systems an agent may reach in `tools.override.json` under `systems`: how a call is recognised, the environment, what it does (`verbs`: read, write, destroy, exec) and what the gate decides (`rules`: allow, task, outbox, human, deny). A terminal command that calls a listed program becomes one action `{system, env, verb, target}`. Two floors hold whatever the company writes: a call no `verbs` pattern names is a write, and an environment no `env` pattern names is prod. With no rule: read allow, write outbox, exec human, destroy deny, prod only read. The harness shipped no system {src:docs/07-release-notes.md#L777-L783}. The reason is in `docs/12-guardrails-and-gate.md`: an agent goes wrong by what it reads, by wanting to finish and by slips, and it works with the person's account, so the gate makes sure it does not do in the person's name what the person did not want {src:docs/12-guardrails-and-gate.md#L5-L15}.

**The outbox and the log.** A call marked `outbox` (by default every write) is refused once and held; in a session with a task a draft `OUTBOX/<code>-<system>.md` records the action and the exact command, written only by the harness. The person runs `harness approve-action` in their own terminal and types the code; the same command may then run once, in the same session, within `git.approval_minutes` of `gate.json` (10), and a changed command needs a new code {src:docs/07-release-notes.md#L778-L779} {src:.harness/policies/gate.json#L184-L186}. Every call to a listed system leaves an `external` field in the session log (system, environment, verb, target, decision), also when it went through; results are never kept. Values of passwords and tokens in a refused command and its reason are replaced by `***` before the line is written, for the common spellings only {src:docs/07-release-notes.md#L780-L784}.

**1.7.12 (2026-11-06), tool packs.** One folder per outside tool: `toolpack.json`, connection types, gate rules, skills named after it. `harness toolpack add` installs one (the person, in their own terminal), or it sits in the knowledge base under `company/tools/packs/` and `company sync` installs it; its systems come after the company pack's and before the person's `tools.override.json`; `toolpack check` says whether its programs are found. The harness shipped no pack in 1.7.12; factory packs `ado`, `sqlserver` and `demotracker` came in 1.7.30 {src:docs/07-release-notes.md#L648-L653} {src:docs/07-release-notes.md#L401-L411}. Why packs and not only MCP: many companies switch MCP off by policy; an MCP server does not say which call is a read and which a write, so the editor's confirm is the only brake; and a server says what can be called but not when and in which order, which a pack's skills do {src:docs/13-tool-packs-and-mcp.md#L1-L23}.

## Version story: 1.7.38 made the gate fail closed

Version 1.7.38 (2026-11-09) is the largest note of the 1.7 line {src:docs/07-release-notes.md#L201-L323}.

**Fail closed for governed calls.** Before, when the engine could not be loaded, a guardrail module raised, or the session state could not be read, the hook printed `{}` and every call passed, a drop on PROD included. From 1.7.38 `hook.py` answers with the standard library alone: every terminal command and every write or edit tool is refused with one line saying what failed and that the user repairs it in their own terminal; reads and the tool that asks the user stay {src:docs/07-release-notes.md#L254}. A call to a program a tool pack governs is refused when a pack file is faulty {src:docs/07-release-notes.md#L231-L254}. The 1.1 design had chosen the opposite on purpose, because the hook runs before every tool call and a bug in it could stop all work {src:docs/05-design.md#L163-L165}. Only helpers (reminders, logs, what the board shows) still fail without stopping anything, and a fault in the task part refuses only subagent calls {src:docs/07-release-notes.md#L308}. The paragraph of `docs/05-design.md` on the hook failing itself still says local work passes then; the release note and `docs/12-guardrails-and-gate.md` say commands and writes are refused, and this file follows them {src:docs/12-guardrails-and-gate.md#L83-L88}.

**The incident behind "cannot tell is not a pass".** `docs/12-guardrails-and-gate.md` gives it: before 1.7.38 the gate read "cannot tell" as "not mine", and `sqlcmd -S 127.1,14332 -Q "DROP TABLE t"` ran because the server was spelled in a way the gate did not match. The release note adds that the red team of C13 found what the gate let through, and states the rule: a call to an outside system passes only when it is on the pass list and it reaches one connection the gate knows; what the gate cannot tell, including its own failures, it does not pass {src:docs/12-guardrails-and-gate.md#L61-L63} {src:docs/07-release-notes.md#L216}.

**`launch.py`.** `.github/hooks/harness.json` starts a small standard-library file that loads `hook.py` and, when that cannot load, answers in its place (commands and writes refused, reads allowed); before, a broken `hook.py` made the hook exit with no answer. `harness doctor` and the Enter screen say red for a start file that does not compile {src:docs/07-release-notes.md#L259}. Two cases stay with the platform, measured and not handled: a hook that cannot start counts as a refusal and every call fails, and a hook that times out (30 seconds) lets the call through without a notice {src:docs/05-design.md#L167-L170}. A hook configuration that cannot be read means no hook runs; `doctor` says ERROR and the harness cannot cover it {src:docs/12-guardrails-and-gate.md#L86}.

**The integrity list.** The guardrail files (engine, shipped policies, hooks, packs) are checked against a list the person accepted: made at the first start of the board, at the first start after an upgrade, by `harness doctor --accept` in the person's terminal, and when an admin session ends; kept in `~/.copilot-harness/integrity/`. A changed, new or missing file refuses the agent's commands and writes, and that folder is itself a guardrail path the agent cannot write, in admin mode either. It stops slips and plain tampering, not a process that runs as the person {src:docs/07-release-notes.md#L255}. Its gap: with no list accepted yet nothing checks the files, and `doctor` then warns {src:docs/07-release-notes.md#L307}.

**The three answers.** For a database call through a tool pack type: pass (what the gate can show to be a read), refuse (a short list each with the right way: `KILL`, `RESTORE`, `xp_cmdshell`, sqlcmd's `!!` and `:connect`) and ask (everything else, with the card saying why under **Why held**). An opened connection passes only the write list, prod passes reads only, and the refuse list is best effort; the final guarantee is the account's rights {src:docs/07-release-notes.md#L242}. Three and not two because a pass list alone would send every other call to the person, and a person who approves forty cards a day stops reading them. A refusal needs a right way: the first sample lists also refused `DROP`, `TRUNCATE` and strings run as SQL, ETL testing on DEV needs them, the agent stopped and the task stalled; so after the red-team rounds they were held on DEV and IST instead {src:docs/12-guardrails-and-gate.md#L23-L35} {src:docs/07-release-notes.md#L273}.

**Closing is acceptance.** The agent never asks "close the task?" and never runs `harness task close`; the gate refuses it with a line that says to deliver. A promote accepts a development task and the board closes it. Every other task, a look and a ticket chore included, ends with `harness task deliver` and shows **to accept**: **Accept and close** or **Not yet**. Until the person accepts, a follow-up stays in the same task {src:docs/07-release-notes.md#L212}. The old eight-character confirmation code (now six) and the second click after an approval were retired {src:docs/07-release-notes.md#L317-L319}.

## Version story: 1.8.0 to 1.8.3

**1.8.0 (2026-11-17), autorun rewritten.** The old autorun, the default agent doing every step pushed on by the Stop hook, was retired. Now the default agent only schedules, a `worker` subagent does one step per call in a fresh context, and the board keeps the run going {src:docs/07-release-notes.md#L58-L60}. The reason in `docs/05-design.md`: a fresh context per step so a long run does not fill one chat; three layers (scheduler, Stop hook, board relay); a step that cannot be settled is parked and asked at the end; the code, not a model, says when the run stops {src:docs/05-design.md#L111-L119}. Only the default agent of a task with autorun on can call the worker. A step that cannot be settled is marked `[?]` and its question goes to `QUESTIONS.md`; a call the gate holds is listed as `[held: ...]` and does not park the step; all questions are asked once at the end {src:docs/07-release-notes.md#L64-L65}. The Start form asks for scheduler model, worker model, compact percent, minutes and a spend limit, then the person types the code; Start sets Allow all, compacts if there is history and sends `/harness-autorun`; Claude models only, since with a GPT scheduler the Claude worker gets no file tools {src:docs/07-release-notes.md#L66} {src:docs/07-release-notes.md#L77}. The spend limit stops the run with `budget`. The board relay sends the next message 15 seconds after the chat stops, waits 60, 300 and 900 seconds after an error and stops after 3, and at the compact percent sends `/compact`; with no board there is no relay {src:docs/07-release-notes.md#L67-L70}.

**The stop rules differ from 1.3.0** (refused 2 times, 20 pushes, 120 minutes, 3 stalls, agent cannot go on). A gate refusal no longer stops the run, because the step is parked; `autorun.max_denies` and the `denied` reason are retired. `stalled` counts worker calls in a row with no progress and a parked step counts as progress; `steps` caps calls and relays together at the larger of 20 and `steps_per_todo` times the steps; `agent` is only for when going on would do harm; the default run time rose from 120 to 480 minutes {src:docs/07-release-notes.md#L78-L88}. In 1.8.3 `task.json` has `minutes` 480, `max_stalls` 3, `steps_per_todo` 3 and `stop_cap` 8 {src:.harness/policies/task.json#L32-L39}. In autorun the default agent writes only `TODO.md`, `TASK.md`, `LOG.md` and `QUESTIONS.md`, the worker the rest; there are three subagents (reviewer, mapper, worker); and the gate refuses every spelling of `task allow` to the agent, `--conn`, `--links` and `--off` included {src:docs/07-release-notes.md#L76} {src:docs/07-release-notes.md#L81-L83}.

**1.8.1 (2026-11-17), locks.** On a slow work computer calls of one session were refused as "the harness was busy", and two could write the same task file at once. Session and task locks became locks of the system, freed when the holding process ends; before, a lock older than 5 seconds was taken as left behind and removed, so a slow `harness task fetch` let a second one in and one fetch record was lost. A call now waits up to 20 seconds for a lock, not 7, under the hook's 30-second limit {src:docs/07-release-notes.md#L48-L56} {src:.harness/engine/core/state.py#L31-L32}.

**1.8.2 (2026-11-17).** A skill only the person can start (`disable-model-invocation: true`) could not be loaded by the agent, so the board's button ended with the agent asking the person to type it. Now the first message only opens the task, and when that turn is over the board sends `/<skill> <your words>` to the same chat, once {src:docs/07-release-notes.md#L40-L46}.

**1.8.3 (2026-11-18), the super agent.** A third view shows what waits for the person across all tasks as short messages with the board's own buttons. The board opens one Copilot chat a day with the `super` agent, which has read and search tools only and runs on Claude Haiku 5.5, limited by `super.daily_credits` (50 by default, `0` switches it off). A message that starts with `/harness-ask` makes one turn of a task read only: the gate refuses every write and write command. Proposal cards suggest archiving, pausing, autorun, review settings, a message to a task or a new task, and nothing happens until the person presses; the super agent is not a subagent and the gate keeps its chat to reading. When an agent asks a question and waits, the person may write their own words instead of picking an option {src:docs/07-release-notes.md#L13-L38}.
