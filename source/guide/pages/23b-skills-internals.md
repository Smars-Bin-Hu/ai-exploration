This file holds the code-level detail behind the feature file 23 Skills: the text-layer files and what each holds, how the harness chooses between code and text, what "one main source" means and what keeps it, what the hook injects into every prompt, skill name prefixes and upgrades, the company's prefix word, user-only skills, domain skills, `skillcheck.py`, the `board-*` keys, the files of `/generic-goal-driven`, and the language split with its two message tables. It is for "how does it work" and "where in the code" questions. Code locations are at harness version 1.8.3.

## Skills internals: the text-layer files and what each holds

The harness keeps its text rules in five kinds of file. All are text for the model; none blocks a call by itself.

`AGENTS.md` holds only the rules every agent must follow and the safety limits {src:AGENTS.md#L1-L5}. Its sections: what the repository is (decoupled from any knowledge base, `knowledge-base/` empty when shipped); language (shipped files in English only; what the agent says and writes for a task follows `language` in `user.json`); writing style (short sentences, no filler, do not write what the model already knows); where information goes (`.harness/INDEX.md` is the path index; detailed rules go in `copilot-instructions.md`, `.github/instructions/`, `.github/skills/` or `.harness/policies/`); and core limits {src:AGENTS.md#L7-L40}. The core limits: look at real files first; work happens in a task under `.workspace/sandbox/tasks/<task>/`, opened with `harness-my-task` when files are produced or changed (plain questions need none); with a task, write only inside the task folder, target-repository files change only by a promote the person approves, and `DEV/` is writable only after the person approves `PLAN.md`; only the person changes the confirmation line of `REQ.md`, switches independent checks on (`[review]=n`) and switches autorun on; there are three subagents (reviewer, worker, read-only mapper) and the super agent is not one; guardrail files change only in admin mode {src:AGENTS.md#L42-L64}. A list of "reviewer and mapper only" is out of date: `AGENTS.md` and the agents instruction file name three subagents, and `.github/agents/` holds four files, `mapper`, `reviewer`, `worker`, `super` {src:.github/instructions/agents.instructions.md#L34-L44}.

`.github/copilot-instructions.md` (25 lines) adds what applies while the agent runs: what to do after a refusal, that approvals are board buttons, and which git commands run or can never be approved {src:.github/copilot-instructions.md#L1-L25}.

`.github/instructions/*.instructions.md` are topic rules Copilot adds when a file matching their `applyTo` is involved. `agents` (`.github/agents/**/*.agent.md`): when a new agent is allowed, that every agent but the default is a subagent whose `user-invocable: false` does not stop a call (a hook decides), the three subagents and who may call each, the super agent, the `/harness-ask` turn, the models {src:.github/instructions/agents.instructions.md#L1-L53}. `workspace` (`.workspace/**`): the task folder, who writes which file, `DEV/`, `fetch` and `promote`, evidence runs, and that `goals/<id>/` is not writable while a task is open {src:.github/instructions/workspace.instructions.md#L6-L32}. `knowledgebase` (`knowledge-base/**`): how to read the knowledge base, the levels, keeping it true, the standard form {src:.github/instructions/knowledgebase.instructions.md#L1-L41}. `skills` (`.github/skills/**/SKILL.md`): progressive loading, prefixes, who starts a skill {src:.github/instructions/skills.instructions.md#L1-L42}. Skills are `.github/skills/<name>/SKILL.md`; agents are `.github/agents/*.agent.md`, whose body has no budget numbers {src:.github/instructions/agents.instructions.md#L25-L32}.

## Skills internals: "stop with code, teach with text" and how the line is chosen

What is certain (dangerous commands, writes out of bounds, a subagent called without checks, a write-back without enough passes) is enforced with hooks and the command line; what is not certain (is the requirement right, is the work good) is text and skills for the model, then checked by the independent reviewer {src:docs/05-design.md#L133-L137}. The code does not judge quality: it counts checks and passes from the record and the sha256 of the work {src:docs/05-design.md#L121-L127}.

There are four levels, the "ladder" in the course skill `harness-rookie-wondering`. S: text (instructions, skills, an agent body); the agent knows why and may not comply. C: the `harness` command does the file operations and checks preconditions; works in every runtime, guards only what goes through the command. H: a hook's deny or block; enforced at run time, depends on the platform. V: `doctor`, eval and log review; finds violations, cannot prevent them. The principle: start at S; go to C or H on repeated violations, on consequences that cannot be undone, or when breaking the rule would break another module's premise; where C will do, do not use H; every C or H rule keeps one sentence of S {src:.github/skills/harness-rookie-wondering/references/14-internals.md#L86-L97}.

Who chooses: a person, the maintainers, by design review after they see violations; no code computes it. The levels appear in code only as the `enforcement` list of each module in `registry.json` (the schema accepts `S`, `C`, `H`, `V`): `task` S, C, H; `gate` S, H; `observe` V; `evalcheck` V {src:.harness/engine/core/registry.py#L38-L38} {src:.harness/registry.json#L92-L111}. The H mark has one effect: `hook.py` treats modules marked H as guards. A guard that raises on a `PreToolUse` call makes the call not pass; any other module that raises has its state changes rolled back and no opinion. The `task` module is a guard only for subagent calls, so when it fails only those are refused {src:.harness/engine/hook.py#L55-L88}.

Text only: the language of the agent's answers, writing style, "look at the real files first", "confirm before you delete or overwrite" {src:AGENTS.md#L17-L31}. The gate is a guardrail, not a sandbox: a terminal command can write any path and the gate stops only the common spellings {src:docs/05-design.md#L220-L226}. Moved into code: the repeated-refusal breaker (the third identical deny in a session has its reason replaced by an order to stop; `circuit_breaker.repeat_limit` in `gate.json`, 0 turns it off) {src:.harness/engine/core/breaker.py#L19-L60} {src:.harness/policies/gate.json#L187-L189}; the subagent rules (reviewer only with a check open, mapper only after the person typed `/generic-mapreduce`, worker only in autorun) {src:.harness/engine/modules/task/handler.py#L278-L324}; and the check count from the record and sha256, with `[review]=n` read only from the person's own words, never from a skill's text {src:.harness/engine/modules/task/taskreview.py#L63-L66} {src:.harness/engine/adapters/copilot_vscode.py#L71-L85}.

## Skills internals: "a rule has one main source" and what keeps it

Each rule is written in full in one file; every other file holds a link and one sentence, never a copy; to change a rule, find its main source first {src:AGENTS.md#L39-L40}. The reason: with the same rule in three files a change misses one and the agent reads contradicting versions {src:docs/05-design.md#L139-L141}.

Each kind of thing has one home. Numbers (budgets, limits, minutes) live in `.harness/policies/*.json`, not in agent bodies {src:.github/instructions/agents.instructions.md#L32-L32}; a few modules keep a mirror default in code for a policy that cannot be read, such as `DEFAULTS` in `mapreduce.py` (4 agents, 60 minutes) and `DEFAULT_REPEAT_LIMIT` in `breaker.py` {src:.harness/engine/modules/task/mapreduce.py#L28-L28}. Every printed text has one source per language, `messages.en.json` and `messages.zh.json`; prose exists once, in English {src:docs/05-design.md#L147-L153}. The version has one source, `registry.json`; the path map one, `.harness/INDEX.md` {src:.harness/INDEX.md#L3-L4}. The company's `company/` folder in the knowledge base is the main source of company skills and instructions; the `.github/` copies are written and replaced by `company sync` {src:.harness/engine/core/company.py#L1-L19}.

What keeps sources and copies together is the maintainers' tests, which a copy in use does not run. `test_docs.py` checks that every relative doc link has a target, that every path in `INDEX.md` exists and every shipped `harness-*` skill is indexed (`generic-*` skills are not checked), that documented policy fields exist, and it pins a few sentences {src:.harness/tests/test_docs.py#L74-L113} {src:.harness/tests/test_docs.py#L149-L250}. `test_language.py` checks the message tables, `test_skillcheck.py` that every shipped skill has no error {src:.harness/tests/test_skillcheck.py#L132-L150}, and `doctor` reports a registry-listed file that is missing {src:.harness/engine/doctor.py#L190-L197}. Not kept: I found no test that compares prose between instruction files and docs, so a duplicated paragraph can drift unnoticed. One drift shows in code: `docs/10-skills.md` puts three skills under "You type these" that carry no flag (see the section on user-only skills) {src:docs/10-skills.md#L31-L35}.

## Skills internals: what the hook injects into every prompt

The task module answers `SessionStart` and every `UserPromptSubmit` with context built by `prompt_text` {src:.harness/engine/modules/task/handler.py#L162-L177}.

Admin session: only the admin rules (what it may change, what stays closed, no subagent or task, the session id) and the language rule; no session rule, no task entry rule, no task list {src:.harness/engine/modules/task/handler.py#L69-L74}.

Session with no task, in order: the session rule (the session id, to be used as written for `--session-id` of `task new` and `task open`, and "when a call is refused, do the next step the refusal gives") {src:.harness/engine/core/messages.en.json#L109-L109}; the language rule; `rules.task.entry` (when the person asks to produce or change files, or mentions an existing task, first open or pick up a task with `harness-my-task`; plain Q&A needs none; without a task no reviewer can be called; the mapper depends only on `/generic-mapreduce`; target-repository files are never changed directly) {src:.harness/engine/core/messages.en.json#L43-L43}; if the prompt has `[review]=n`, a line that a check needs a task, so open one first {src:.harness/engine/core/messages.en.json#L110-L110}; and the open tasks (up to five, newest first, "and more"), with the command to pick one up {src:.harness/engine/modules/task/handler.py#L129-L142}.

Session with a task: the session rule, the language rule, then the task text; the open-task list and `rules.task.entry` are not sent. The task text is the head (task, kind, tier, round) plus the next step; a requirement line when `REQ.md` exists; the check counts (`n`, passes, used, limit) when `n` is above 0, or a line that the person switched checks off; the edit-tool scope; the task's board address; one line naming the task's domain skills; and an autorun line when autorun is on {src:.harness/engine/modules/task/handler.py#L93-L126}.

Language line, every case: the language rule, plus a second line when a `[ZH]` or `[EN]` the person wrote earlier in the session differs from the setting {src:.harness/engine/modules/task/handler.py#L154-L159}. A subagent's first message gets nothing, since the hook returns no decision for a message from a subagent or for the engine's own continuation of a Stop {src:.harness/engine/modules/task/handler.py#L233-L238}; at `SubagentStart` the reviewer gets its package path, the mapper that it only reads, the worker its task and rule, each with the language rule {src:.harness/engine/modules/task/handler.py#L326-L344}. Other additions: the gate adds reminders of approved outside calls and connection lines {src:.harness/engine/modules/gate/handler.py#L490-L498}, and the engine a notice when a guardrail module could not run {src:.harness/engine/hook.py#L119-L121}.

Position: the code only returns `additionalContext`, and Copilot places it {src:.harness/engine/adapters/common.py#L137-L150}. `AGENTS.md` and `copilot-instructions.md` say "at the top"; the repository cannot prove it. VS Code's own prompt handler sometimes takes the one `additionalContext` place, so at `UserPromptTransformed` the engine checks whether the first line of its text is in what the model will get and, if not, appends the text at the end inside `<system_reminder>` tags, for a prompt under 120 seconds old {src:.harness/engine/core/state.py#L378-L394}.

## Skills internals: skill name prefixes and what each means for upgrades

The folder name and the `name` field must be equal, and the name has a prefix; only third-party skills have none {src:.github/instructions/skills.instructions.md#L15-L17}. `skillcheck.py` owns `harness-`, `generic-`, `domain-`, the company's word and the name of every installed tool pack {src:.harness/engine/core/skillcheck.py#L76-L86}.

`harness-<name>`: the harness's own, maintained upstream; the meaning side of a module (name matches `modules/<module>/`, underscores as hyphens) or a flow for using the harness. `generic-<name>`: a general skill, maintained upstream {src:.github/instructions/skills.instructions.md#L19-L22}. Both are in the package, so an in-place upgrade replaces them in the same way; a person's own change to one is lost and must be backed up first, and own work goes in the knowledge base or a prefixed skill (see the file 24 Setup, doctor and upgrade).

`<skill_prefix>-<name>` and `<skill_prefix>-<pack>-<name>`: the company's skills, in `.github/skills/`; the second is a tool pack's SOP and `company sync` makes it from the pack's `<pack>-<name>` {src:.github/instructions/skills.instructions.md#L27-L30}. The package has no skill of that name, so an in-place upgrade leaves them. `harness reinstall` into a new folder carries `<prefix>-*` and `domain-*` skills from the old copy's `.github/skills/` by folder name (the prefix read from the old copy's `user.override.json`, else this copy's) and skips a name that already exists {src:.harness/engine/core/reinstall.py#L196-L216}. `skillgroups.group` sorts a name into harness, pack or company by name alone {src:.harness/engine/core/skillgroups.py#L1-L37}.

`domain-<domain>-<skill>`: maintained by the team, kept in the knowledge base at `domains/<domain>/skills/<skill>/SKILL.md` {src:.github/instructions/skills.instructions.md#L23-L24}. The package carries no `knowledge-base/` folder, so an in-place upgrade never writes them; `reinstall` carries the knowledge base whole when the old one has team content and the new one is a placeholder {src:.harness/engine/core/reinstall.py#L182-L189}.

The checker: an error when `name` differs from the folder or a `domain-` name is not `domain-<domain>-<name>`; only a warning when the name has no owned prefix (fine for a third-party skill) {src:.harness/engine/core/skillcheck.py#L154-L165}. The company's word is one word of lowercase letters and digits and may not be `harness`, `generic` or `domain`; a failing word is not used and `doctor` says why {src:.harness/engine/core/skillcheck.py#L60-L73}. An installed tool pack's own name counts as an owned prefix for its skills.

## Skills internals: the company's prefix word, and what happens when two words differ

The word can be written in two places: `skill_prefix` in the person's `user.override.json` (policy `user`), and `skill_prefix` in `company/company.json` in the knowledge base, which is a file there, not a policy {src:.harness/engine/core/skillcheck.py#L32-L50}. The code reads them two ways, so the outcome depends on the operation.

`company sync` reads the word only from the person's policy. In `copies()`, before anything is copied: when the company content has skills or instruction files and the person's policy has no usable word, `company.no_prefix` stops the sync; when `company.json` has a word and the person's differs (ignoring case), `company.other_prefix` stops it. The stop comes before anything is copied, removed or written, tool-pack skills included, and the copies of the last good sync stay. When `company.json` has no word, the person's word alone is used; when the content has no skills or instruction files, no word is needed {src:.harness/engine/core/company.py#L164-L174} {src:.harness/engine/core/company.py#L259-L270}. The board's company window shows the same problem {src:.harness/engine/core/company.py#L364-L381}.

The checks use `effective_prefix`: the person's word, or when the policy has none, the word in `company.json`. So `skill check`, tool-pack skill names and the board's grouping use the person's word when both are set and differ, and `doctor` warns "The policy wins. Make them the same word" {src:.harness/engine/core/skillcheck.py#L37-L57} {src:.harness/engine/doctor.py#L575-L582}. In short: a difference is a warning for the checks, with the policy winning, and a stop for copying.

`company sync` also refuses single skills: a folder in `company/skills/` that does not start with `<word>-`, or whose check has errors, goes to `refused`, is not copied, and the command exits 1 {src:.harness/engine/core/company.py#L176-L184}.

## Skills internals: user-only skills and why each is one

Eight skills carry `disable-model-invocation: true`: `generic-goal-driven`, `generic-kb-toolkit-build`, `generic-mapreduce`, `generic-workflow-build`, `harness-agent-performance-review`, `harness-autorun`, `harness-vscode-updates`, `harness-task-report`. Copilot does not load them for the agent; only the person's `/<name>` or a board click does. The reasons: task report and performance review read logs and cost tokens; autorun changes how a task runs and only the person may switch it on; goal-driven is a whole way of working; mapreduce runs several subagents at once, several times the usage; workflow build and toolkit build write many files or code after the person approves a design; vscode-updates is for the harness owner {src:docs/10-skills.md#L56-L67}.

`docs/10-skills.md` also lists `harness-rookie-quick-start`, `harness-rookie-wondering` and `harness-reinstall` under "You type these", but none carries the flag, so Copilot may load them for the agent; the code makes only the eight user-only {src:docs/10-skills.md#L31-L35}.

A skill file that cannot be read counts as user-only: `skillsend.user_only` returns true on a read error, else true only when `disable-model-invocation` is `true` (trimmed, any case). It drives the 1.8.2 follow-up: a board task made for a user-only skill gets a first message that only opens the task, then `/<skill> <words>` once the turn ends; any other skill gets "Use the skill ..." {src:.harness/engine/modules/task/skillsend.py#L30-L37} {src:.harness/engine/modules/task/chatnew.py#L91-L96}. Copilot enforces the flag; the harness adds its own check only for `generic-mapreduce` (the hook reads the person's prompt and gives the session `max_agents` mapper calls for `minutes`; every other mapper call is refused) and for autorun (the gate refuses `task autorun on` from the agent) {src:.harness/engine/modules/task/mapreduce.py#L1-L12}. The agent could still read a user-only `SKILL.md` and follow it; the gate never blocks a read.

## Skills internals: domain skills and how they reach the agent

`domainskills.py` finds skills Copilot does not list. It looks in every knowledge base (`knowledge-base/` and any repository registered with `knowledge_base: true`); when the target policy cannot be read it silently falls back to `knowledge-base/` only {src:.harness/engine/core/targets.py#L225-L242}. `domains()` lists subfolders of `<knowledge base>/domains/` whose name matches `^[A-Za-z0-9][A-Za-z0-9_-]*$`; the first knowledge base that has a domain wins; `find()` matches a name in any case {src:.harness/engine/core/domainskills.py#L19-L58}. `skills()` reads every `skills/<skill>/SKILL.md` of the wanted domains and returns domain, name, description, start (`user-only` when the flag is `true`, else `agent`) and path {src:.harness/engine/core/domainskills.py#L69-L94}. Nothing is cached: folders are read anew at each call, so a skill added now is found at the next prompt.

`harness task set-domain <domain>...` (at least one name) calls `tasklife.set_domains`. Names match folders in any case, repeats are dropped, and an unknown name is refused with "No such domain" and the list of known domains; the exception is a task of kind `kb`, which may name a valid folder name not yet in the knowledge base, since the domain appears only after its write-back. A closed task is refused. The new list replaces the old one and is noted in the task's history {src:.harness/engine/modules/task/tasklife.py#L224-L252}. `task new --domain <d>` runs the same check before the task is made {src:.harness/engine/modules/task/commands.py#L76-L84}.

The injected line: `domain_hint` gives one line, "Domains of this task: ... Their skills: <names> ... run `skill list --domain <domain>` for when to use each, read its SKILL.md and follow it" {src:.harness/engine/modules/task/tasklife.py#L255-L263}. It carries skill names only, not descriptions or the user-only flag; the agent must run `harness skill list --domain <d>`, which prints name, description, start and path {src:.harness/engine/cli.py#L103-L105}. The line is empty when the task has no domain, no skills in them, or its domain folder is gone. An admin session and a session with no task never get it, since only the task text carries it {src:.harness/engine/modules/task/handler.py#L93-L126}. The rule not to follow a user-only domain skill is text only {src:.harness/engine/core/messages.en.json#L1155-L1155}. `skill check` with no argument also checks the domain skill folders; the board never lists them {src:.harness/engine/core/skillcheck.py#L225-L240}.

## Skills internals: what `skillcheck.py` checks

`skillcheck.check(folder, company)` returns `skill`, `errors` and `warnings` for one folder and reads files only. An error means Copilot cannot load the skill or a link is dead; a warning means it loads but will be found or used badly {src:.harness/engine/core/skillcheck.py#L132-L202}.

Errors: `SKILL.md` missing or unreadable, or no frontmatter (checking stops); a `board-*` value that is not allowed or an unknown `board-*` key; `name` missing, different from the folder, of invalid form, or a bad `domain-<domain>-<name>`; `description` missing, under 10 or over 1024 characters; body over 500 lines; a relative link (not in code, not a web address, not an anchor in the same file) that leads to no file {src:.harness/engine/core/skillcheck.py#L139-L193}.

Warnings: no owned prefix in the name; description over 600 characters or without a "when" word (`when`, `if the user`, `whenever`); for a skill with an owned prefix, `type` not `unit` or `workflow`, and `specificTo` missing or, for a domain skill, not the domain's name; body over 200 lines; no `Gotchas` heading; a mention of `.claude/`; a secret-like value (`api_key`, `secret`, `password`, `token` followed by 12 or more characters); a file in `references/`, `templates/`, `scripts/` or `assets/` that no text of the skill names {src:.harness/engine/core/skillcheck.py#L164-L222}.

`harness skill check [name or path ...]` exits 1 only when there is an error; a warning never changes the exit code {src:.harness/engine/cli.py#L90-L100}. With no argument it checks every folder in `.github/skills/` and every knowledge-base domain skill. `doctor` runs the same check for every skill and only warns: it lists a skill with an error, and a skill with an owned prefix that has only warnings, and leaves a third-party skill's warnings alone {src:.harness/engine/doctor.py#L575-L589}.

## Skills internals: the `board-*` keys and `skillboard.py`

The board keeps no list of skills. `skillboard.skills(root)` reads the frontmatter of `.github/skills/*/SKILL.md`, and a skill appears when `board-opens` has a valid value (`chat`, `task`, `reply`) {src:.harness/engine/core/skillboard.py#L1-L12} {src:.harness/engine/core/skillboard.py#L61-L84}. Without it the skill is not on the board, except a skill of an active tool pack, which is listed under its pack by name and description with no click to start. Domain skills are never on the board.

Keys, all optional, one line each, with the default when absent or wrong {src:.harness/engine/core/skillboard.py#L3-L28}: `board-opens` (no default; absent means off the board); `board-place` (a comma list of `ask`, `kb`, `task`, `all`; default `all` when `board-opens` is set); `board-kind` (a task kind the harness knows, used with `task`; default none); `board-cost` (`high` marks a costly skill; default not); `board-label` (default the folder name); `board-group` (`harness`, `kb`, `task`; default `task`); `board-order` (a whole number, small first; default 999, ties by name); `board-step` (`start`, `toolkit`, `domains`, `learn`, `keep`, the step of building a knowledge base; default none). The first sentence of `description`, cut at 200 characters at a word, is the skill's line; a company skill whose folder left `company/skills/` is marked `gone` and its copy stays.

`skillboard.problems(fields)` is what `skill check` turns into errors: a value outside the lists above, a non-numeric `board-order`, and any `board-` key not among the eight {src:.harness/engine/core/skillboard.py#L31-L50}. At run time the board is more forgiving: a bad value other than `board-opens` counts as not written and the default applies, so a hand-edited copy stays on the board; a bad `board-opens` takes the skill off it.

## Skills internals: `/generic-goal-driven`, its files, and why the gate is not changed

`generic-goal-driven` is user-only (`disable-model-invocation: true`, `board-opens: chat`) {src:.github/skills/generic-goal-driven/SKILL.md#L1-L13}. It keeps a long job as files in `.workspace/goals/<id>/`, ignored by git, that the agent reads and writes directly with its edit tools {src:.github/skills/generic-goal-driven/SKILL.md#L31-L33} {src:.gitignore#L34-L35}:

- `GOAL.md`: the central idea (goal, principles, scope, what is not done, overall acceptance), a "Decided" part, the change record at the end; changes only when a requirement or decision changes.
- `TODO.md`: the steps, each with a status, acceptance standard, result of the agent's own check, feedback. Five statuses only: `todo`, `doing`, `handed over`, `passed`, `cancelled`; step numbers are not reused.
- `NOW.md`: the progress pointer (current step, next step, which task is used); the first file a new session reads, about one screen.
- `LOG.md`: the change log, one entry per passed step, newest on top, never edited (a correction is a new entry).
- `accept/<step number>.md`: an acceptance guide, only for a complex step {src:.github/skills/generic-goal-driven/SKILL.md#L35-L45}.

Per step: set `doing` and write `NOW.md`; open one task per step that writes files; do it and check yourself; `harness task deliver` and stop, since the agent never closes a task and the person accepts it on the board; after the person closes the task, set `handed over` and write the acceptance; only when the person says "passed" in the conversation, add the `LOG.md` entry, set `passed` and point `NOW.md` at the next step {src:.github/skills/generic-goal-driven/SKILL.md#L53-L69} {src:.github/skills/generic-goal-driven/SKILL.md#L122-L122}. No code stops an agent that declares a pass itself; text has to hold it {src:docs/05-design.md#L214-L218}.

## Skills internals: the language setting, what code guarantees and what is a request

Code guarantees what the engine prints and writes: refusal reasons, injected rules, command answers and board texts come from two message tables, and new task files from a template folder per language. A request to the model is the language of its answers and the files it writes, told by an injected line it may not obey {src:docs/05-design.md#L147-L153}.

Which language: `messages.language()` reads once per process the environment variable `HARNESS_LANGUAGE`, else `language` of the `user` policy; the value must be `en` or `zh`, and anything else, a bad variable included, gives the default `en` {src:.harness/engine/core/messages.py#L18-L67}. `doctor` reports an error when `language` in the file is neither, and says whether the language came from the environment, the policy or the default {src:.harness/engine/doctor.py#L398-L403}. Policy texts carry their own reasons: every `why` of the terminal rules in `gate.json` is `{"en": ..., "zh": ...}`, and `messages.pick` takes the current language, then English, then the first value {src:.harness/engine/core/messages.py#L90-L95}.

The language rule says: answer in the setting's language; files you write (`TASK.md`, `REQ.md`, `LOG.md`, plans, prose in results) too; code, commands, paths and technical terms stay; when the user clearly asks for another language, do as the user says {src:.harness/engine/core/messages.en.json#L1092-L1092}. It is injected at every prompt, admin session included, and at the start of the reviewer, mapper and worker {src:.harness/engine/modules/task/handler.py#L154-L166}. `[ZH]` or `[EN]` is parsed by code: `reply_marker` takes the last one (any case) in the person's own words, not a skill's text, and saves it in the session's task-module state; when it differs from the setting, one more line says to reply in that language for the rest of the session, technical terms in English, files in the setting's language {src:.harness/engine/modules/task/handler.py#L145-L159} {src:.harness/engine/modules/task/handler.py#L249-L251}. Existing task files keep their language when the setting changes: they are written when made, from the template folder of the language then current (else a template placed right in the folder, else English), and the code that reads them finds its labels in either language {src:.harness/engine/modules/task/tasklife.py#L86-L99}. List punctuation is language aware: `messages.joined` uses the message `list.comma` (`, ` in English, the enumeration comma in Chinese) and `gap` is a space in English and nothing in Chinese {src:.harness/engine/core/messages.py#L98-L105}. Tests pin that the English table has no Chinese and that engine code and board web files have none outside the tables {src:.harness/tests/test_language.py#L72-L106}.

## Skills internals: the two message tables kept in step, and the confirmation line of `REQ.md`

Every printed text is a name in `core/messages.en.json` and `core/messages.zh.json`, fetched with `messages.text(key, **values)`, which never raises: the current language's table, else the other language's text, else the name itself; a table that cannot be read gives the name; a missing placeholder returns the unfilled template {src:.harness/engine/core/messages.py#L76-L87}. A message that names a button or tab writes `{@name}`; when the table is read, the mark is replaced, in two passes, by that message's text in the same language, so the words match the screen {src:.harness/engine/core/messages.py#L30-L48}.

`test_language.py`, run by the maintainers, keeps the tables in step; nothing at run time compares them. It checks: the same names in the same order; the same `{placeholders}` in both languages; every `{@name}` names a message and none is left unreplaced; no Chinese in the English table; no duplicate key; every message has a Chinese text; no Chinese in engine code outside the tables; and the task template folders hold the same five files with the same shape {src:.harness/tests/test_language.py#L43-L106} {src:.harness/tests/test_language.py#L230-L245}. `doctor` only checks that both files load as a non-empty JSON object, not that they match {src:.harness/engine/doctor.py#L272-L286}. A new message needs both files edited in one change; the test run finds a miss.

The confirmation line of `REQ.md` has the label `User confirmed` in English templates and `用户确认` in Chinese ones; the engine's Chinese labels are the only Chinese allowed in its code, in a short list the language test names {src:.harness/tests/test_language.py#L28-L36} {src:.harness/engine/modules/task/taskreview.py#L45-L47}. The reader, `taskreview.confirm_line_filled`, takes the first line anywhere in the file that contains the label (any case, no need to start the line); it is confirmed when what follows has `confirmed`, `已确认` or a date and has none of `not yet`, `not confirmed`, `还没确认`, `yyyy-mm-dd`, which the template line itself holds; `req_confirmed` also needs `REQ.md` unchanged since (the digest); no label gives `None` {src:.harness/engine/modules/task/taskreview.py#L88-L110}. Edge: `confirmed` also matches inside `unconfirmed`.

The writer, `fill_confirmation`, called by `task confirm-req` under the task lock, finds the first line shaped as a list item (`-` or `*`, optional bold, the label, a colon of either width) and rewrites what follows as the word plus today's date; the word follows the file's own label, `已确认` when the label has Chinese, else `confirmed`, whatever the setting is {src:.harness/engine/modules/task/task.py#L480-L480} {src:.harness/engine/modules/task/task.py#L601-L611}. If no line has that shape, the file is written back unchanged. `req_state` is `none` (no `REQ.md` or no label), `unwritten` (the template's first words, `<One or two paragraphs` or `<一两段`, are still there), `open`, `changed` or `confirmed`; `confirm-req` refuses `none` and `unwritten` with `req.missing` {src:.harness/engine/modules/task/task.py#L551-L598}.

`tasks.req_digest` hashes only the sections "What to do", "What not to do" and "Done when" (or `要做什么`, `不做什么`, `做完的标准`), blanks and line breaks ignored, so the confirmation line, sources, open questions and change record are outside it and a line added there undoes no approval; a file with none of those headings is hashed whole except lines holding the label {src:.harness/engine/core/tasks.py#L117-L149}. No code stops an agent from hand-editing the confirmation line with its edit tools; `AGENTS.md` and a test pin the sentence that only the person may {src:.harness/tests/test_docs.py#L102-L113}.
