This file holds the code-level detail behind the subagents of the harness at 1.8.3, which the Guide describes in three feature files: 31 How it is built (the agent files and the subagent rule), 17 Independent checks (the `reviewer`) and 20 Autorun (the `worker`); the `mapper` has no feature file and is described here and in 23 Skills. It is for "how does it work" and "where in the code" questions: which subagents exist, how a call is decided, how the mapper grant is counted, what the worker reads and may not write, how the question tool is refused, and how the core links a subagent's calls to its parent. The subagent rule is in `.harness/engine/modules/task/handler.py`, the mapper grant in `mapreduce.py` and the worker's checks in `autorun.py` of the same folder, and the session tracking in `.harness/engine/core/state.py`. The reviewer's state and package are in 17b Independent checks internals.

## Subagents internals: the agent files, as written

Four agent files are in `.github/agents/`; three are subagents the task hook can let through (`reviewer`, `mapper`, `worker`). The fourth, `super`, is the board's own chat agent, not a subagent of a task (see 21b Super agent internals) {src:.github/agents/super.agent.md#L1-L8}. All four have `agents: []` (no agent may be called from them) and `user-invocable: false`. Models: Claude Sonnet 5.5, Claude Haiku 5.5 and Claude Haiku 4.5 for the reviewer and the mapper; Claude Sonnet 5.5 only for the worker; Claude Haiku 5.5 only for `super` {src:.github/agents/reviewer.agent.md#L1-L8} {src:.github/agents/mapper.agent.md#L1-L8} {src:.github/agents/worker.agent.md#L1-L7}.

The tool lists differ. The `reviewer` has `tools: ['read', 'search', 'execute']`: it has the terminal, and what keeps it from changing anything is its text ("Do not: change any file, create a file, or run a command that writes a file") and the gate's general rules, not the list {src:.github/agents/reviewer.agent.md#L51-L57}. The `mapper` has `tools: ['read', 'search']`, so the platform gives it no terminal and no edit tool, and its text says it changes no file and runs no command {src:.github/agents/mapper.agent.md#L30-L34}. The `worker` file has no `tools` line; which tools VS Code then gives it is not shown in the repository, and what the worker may write is fixed by its text and the gate's rules (below) {src:.github/agents/worker.agent.md#L1-L7}.

Nothing in the harness code reads `user-invocable: false` or the skill key `disable-model-invocation`, and neither stops a subagent call by itself. The barrier is the task hook, which decides by the agent name in the call, read from the input key `agentName` or `agent_type` {src:.harness/engine/adapters/tool_kinds.json#L44-L50} {src:.harness/engine/adapters/common.py#L124-L129}.

## Subagents internals: why only three subagents, and the three things that justify one

The design document says dividing the work has no value in itself, and a second agent is worth it only when it buys one of three things: an independent point of view, parallel work, or working unattended {src:docs/05-design.md#L111-L113}. It names three subagents "only": the `reviewer` buys an independent view (it has not seen the author's reasoning); the `mapper` buys parallel work (read-only readers that each hand in a summary); the `worker` buys a fresh context for each step of an autorun, so a long run does not fill one chat {src:docs/05-design.md#L116-L117}. There is no dispatching agent, since whoever dispatches must understand the task, and all three are switched on by the user, as they cost money or hand over control {src:docs/05-design.md#L115} {src:docs/05-design.md#L118}.

The book chapter 2.3 adds a fourth reason, a hard limit on tools, and the Guide file 41 Ideas follows the book and lists four; the design document and the code have three. `docs/02-features.md` says "There are two only" for the subagents the user switches on, while the code has three; this file describes the code {src:docs/02-features.md#L112-L112}.

## Subagents internals: the subagent rule, the order of checks

The subagent rule is `on_subagent_call` in the task module, reached by `handle` for every PreToolUse whose tool kind is `subagent`; the kind comes from `tool_kinds.json`, which maps `Agent` and `runSubagent` to `subagent` {src:.harness/engine/modules/task/handler.py#L641-L642} {src:.harness/engine/adapters/tool_kinds.json#L17-L27}. Its checks run in this order {src:.harness/engine/modules/task/handler.py#L278-L300}:

1. The calling session is itself a subagent session (it has a `parent_session_id`): no opinion, the call passes. The platform does not nest subagents, and a subagent's tools are not this module's business.
2. The target name is read from the call; an empty name becomes the text "the general subagent", which fails every check below that lets a name through, so a call with no agent name is refused.
3. Admin mode is on: refused, with no subagent allowed.
4. The name is `mapper` (compared in lower case): decided by `mapreduce.on_call`, with no task needed (next sections).
5. The session holds no open task: refused, with the message that a task and `[review]=n` come first.
6. The name is `worker`: decided by `worker_call` in autorun (see "the worker").
7. Any other name than `reviewer`: refused, with the message that only the reviewer can be called with a task.
8. The task's `review.n` is 0, that is, checks were never switched on (`[review]=n` was not written by the person): refused.
9. No round is open (`taskreview.pending` finds none; a round is opened by `task review start`, which writes the package): refused. Otherwise the call passes.

So the `reviewer` needs a session with an open task, checks on and an open round; the `mapper` needs only a typed `/generic-mapreduce` grant; the `worker` needs a task in autorun and passes its checks; any other name is refused, in every session that is not itself a subagent session, while the hook works {src:.harness/engine/core/messages.en.json#L102-L103} {src:.harness/engine/core/messages.en.json#L111-L112}. The refusals are deny decisions of the task module with the fact kinds `subagent`, `task-subagent`, `mapreduce` or `autorun-call`.

One call is never seen by this rule: `search_code_subagent` is mapped to the tool kind `search`, not `subagent`, so the rule is not run for it {src:.harness/engine/adapters/tool_kinds.json#L28-L28}.

## Subagents internals: when the whole hook fails, a subagent call stays allowed

If the hook as a whole cannot decide, a subagent call is not refused: the engine cannot be imported, the session state cannot be locked (wait up to 20 s, then `TimeoutError`) or read, or a guardrail file is not as the person accepted it. `hook.py` then answers with the standard library only: it refuses terminal, edit and unknown tools and lets through tools that cannot run a command or change a file; its list `SAFE_TOOLS` includes `Agent` and `runSubagent`, so the call passes with none of the checks above and no mapper count {src:.harness/engine/hook.py#L170-L173} {src:.harness/engine/hook.py#L261-L309}.

If only the task module raises, the result is the opposite: `GUARDS_FOR` makes a failing task module refuse the subagent call while every other command and write goes on, judged by the other modules {src:.harness/engine/hook.py#L55-L87}. The question tool is not covered by that rule: when the task module raises on a question call, nothing refuses it.

## Subagents internals: `/generic-mapreduce` and what the skill does first

`/generic-mapreduce` is a skill with `disable-model-invocation: true`, so only a typed command loads it. It is text: it tells the agent what to do, and code gives and counts the calls (next section). It is for reading only: research with several unrelated directions, a scattered root-cause analysis, scattered reading of code or of the knowledge base, and brainstorming one question from several angles. It does no writing, and no task needs to be open {src:.github/skills/generic-mapreduce/SKILL.md#L20-L38}.

Before any mapper is sent, the skill's steps are, in order {src:.github/skills/generic-mapreduce/SKILL.md#L39-L66}:

1. **Judge whether it is worth it** (`references/worth-it.md`). It is worth it only when all three hold: no part needs another part's conclusions, every part needs a lot of reading, and only a summary of each part is needed. If not, the agent says why, suggests doing it itself, and stops until the person decides.
2. **Tell the person the cost and wait for a yes**: the parts (one sentence each, no more than the limit), that it is expensive (every mapper is its own session and reads from the start; by experience several times the usage of doing it alone), and how many it suggests, as few as will do.
3. **Only then send all the mappers in one reply**, so they run in parallel, each call message written from `templates/brief.md` (question, scope, what to hand in, length), with scopes that do not overlap; a mapper cannot see the conversation.
4. **Put it together** itself: mark a conclusion with no source as not verified, write both sides when summaries contradict, and tell the person about a part that came back "Brief lacks" or "Not found" instead of sending more.

Steps 1, 2 and 4 are the model following text; no code checks that step 2 happened. Code only counts the calls. The grant deliberately outlives the typed prompt: the person's "yes" in step 2 is a second prompt, and the calls come after it.

## Subagents internals: the mapper grant, from the typed prompt

The grant is made at UserPromptSubmit: in `on_user_prompt`, `mapreduce.asked(event.prompt)` decides and `mapreduce.grant(ctx)` writes {src:.harness/engine/modules/task/handler.py#L252-L253}. The handler returns earlier, with no grant, for a prompt with `from_subagent` set (a subagent's call message), a `continuation` prompt (the engine feeding a Stop block reason back), a prompt of an admin session, and a board question (`/harness-ask`) {src:.harness/engine/modules/task/handler.py#L233-L244}.

`asked(prompt)` is true when the prompt contains either mark: the XML tag `<skill-context name="generic-mapreduce">` that the Copilot SDK puts around a skill's text, or the engine's sentence `invoked the "/generic-mapreduce" skill`; or when the prompt, after leading spaces, starts with `/generic-mapreduce`. A mention in the middle of a sentence does not count {src:.harness/engine/modules/task/mapreduce.py#L25-L40}. Settings come from the policy `task.json`, key `mapreduce`, read through `config.whole`: `max_agents` defaults to 4 and `minutes` to 60; a value that is not a whole number falls back to the default; the policy schema requires `max_agents` of at least 0 and `minutes` of at least 1; `max_agents` 0 switches the mapper off {src:.harness/engine/modules/task/mapreduce.py#L43-L48} {src:.harness/engine/modules/task/policy.py#L40-L43} {src:.harness/engine/core/config.py#L158-L160}.

`grant` stores in the session state, under the task module, the key `mapreduce` with `limit` (max_agents), `used` 0 and `until` (now in UTC plus `minutes`) {src:.harness/engine/modules/task/mapreduce.py#L55-L59}. It replaces any earlier grant: typing `/generic-mapreduce` again resets the count to 0 and the clock to a full `minutes`.

## Subagents internals: how a mapper call is counted and expires

A mapper call is decided by `mapreduce.on_call`, once per call, at PreToolUse of the parent session {src:.harness/engine/modules/task/mapreduce.py#L75-L83}. `current(ctx)` returns the grant only if it exists, is a dictionary and `now` is not after `until`; a missing, malformed or expired grant returns None. With no live grant, the call is denied (not asked); with `used >= limit`, it is denied (used up). Otherwise `used` goes up by one and the call passes. A refused call costs nothing, because `used` is changed only on the passing branch {src:.harness/engine/modules/task/mapreduce.py#L62-L72}.

The count is safe against parallel calls because the whole hook run for a session happens inside `state.session()`, which holds the cross-process `state_lock` of that session's state file (wait up to 20 s) and writes the state back at the end {src:.harness/engine/hook.py#L111-L129} {src:.harness/engine/core/state.py#L206-L237}. Mappers called in one reply are several PreToolUse events of the same parent session, so each does its read, increment and write alone; the count is not taken at SubagentStart or SubagentStop, so the order in which mappers start or stop does not matter {src:.harness/engine/modules/task/mapreduce.py#L11-L12}. The grant ends when `used` reaches `limit` or when `until` has passed; `until` is fixed at the grant and calls do not extend it.

## Subagents internals: why mappers only read, and why there is no parallel writing

The harness offers parallel reading and no parallel changing of files, and the design says why: several agents writing the same files in parallel produce merges that hide decisions, and merging costs a lot, and the repositories the harness works on cannot be run, so there is no way to judge a merged result; the design notes name the condition to revisit it as a target repository that can run its tests locally {src:.github/skills/harness-rookie-wondering/references/10-subagents.md#L43-L45} {src:.github/skills/harness-rookie-wondering/references/15-design-choices.md#L58-L58} {src:docs/02-features.md#L128-L128}. The mapper's value is a summary with sources (file path and line) that the main agent can check, not a changed file; the skill says a mapper's summary is not fact, and a key conclusion's source lines are to be checked by the main agent {src:.github/skills/generic-mapreduce/SKILL.md#L76-L84}.

"Reads only" is enforced in layers, and only some are code. The tool list `['read', 'search']` of `mapper.agent.md` is applied by the platform, not by harness code. The mapper's text and the start context the hook gives it at SubagentStart ("read only, change no file, run no command") are text {src:.harness/engine/modules/task/handler.py#L328-L332}. In code, the gate refuses any subagent session an outside-system or tool-pack call that would need the person's leave, with nothing to approve {src:.harness/engine/modules/gate/handler.py#L282-L283} {src:.harness/engine/modules/gate/handler.py#L412-L413}. No hook rule says "the mapper may not edit a file": a plain file edit by a mapper session is stopped by the mapper not having an edit tool, not by the harness.

Nothing in code forbids two workers or two writers at once; "never in parallel" is a design and text rule. Among the subagents only the worker writes, only in autorun, one `TODO.md` step per call, and into the task folder (`DEV/`), never into a target repository: a promote, approved by the person, writes back {src:.github/agents/worker.agent.md#L19-L28}.

## Subagents internals: the worker, what it is told, reads and returns

The worker is called by the scheduler (the task's own agent) once per `TODO.md` step. Its decision is `worker_call`, which calls `autorun.on_subagent_call`; a refusal there is a deny with kind `autorun-call`, is not a gate refusal and does not end the run, and a call that passes opens a ledger line {src:.harness/engine/modules/task/handler.py#L316-L325}. `on_subagent_call` checks, in this order, under the task lock {src:.harness/engine/modules/task/autorun.py#L415-L450}: autorun is on (else refused: stop); no fact ends the run (`fact_reason`: the plan is no longer approved, the time `until` has passed, a handoff is open, the spend limit is reached, or the checks ran out; if one holds, the run is ended and the call refused) {src:.harness/engine/modules/task/autorun.py#L310-L331}; no pit stop waits; the model is one the task's worker list allows, and a model is passed at all when a default is set; and the last calls moved something (`calls_since_tick` below `max_stalls`, default 3; else the step is to be parked).

At SubagentStart the hook tells the worker its task and its rule, only when the task's autorun state is `on`; otherwise it adds nothing {src:.harness/engine/modules/task/handler.py#L333-L337}. The worker file says what it reads: the call message holds the step text and the task path, and the worker reads `TASK.md`, the section of `PLAN.md` the step names and the files the step names, and nothing else; when the step or the path is missing, it writes "Brief lacks: ..." and does its best {src:.github/agents/worker.agent.md#L13-L18}.

It returns one line, `DONE: <what> | files: <paths> | check: <result>`, plus, when something is open, `QUESTION: <question> | took: <the way it chose, or none>`; `took: none` means the step is not done. Code reads only little of it. At SubagentStop, `on_subagent_stop` takes the reply (payload key `response`, or `last_assistant_message`) and the stop reason (`stop_reason` or `stopReason`) and writes the `end` line of the run ledger `.task/autorun-run.jsonl` {src:.harness/engine/modules/task/handler.py#L582-L596}. `reply_result` finds the result: `failed` if the stop reason is one of error, failed, failure, aborted, cancelled, canceled or timeout; `parked` if a `QUESTION:` line has no `| took:` part, or its `took` is `none`; otherwise `done`. The `DONE:` line, its `files` and its `check` are not parsed. The `files` of the ledger come from the write hooks (`on_task_write` adds each task-folder path a worker session wrote) plus a comparison of file hashes before and after, so a terminal write is also found {src:.harness/engine/modules/task/autorun.py#L497-L539} {src:.harness/engine/modules/task/handler.py#L350-L364}.

## Subagents internals: what the worker may not write, and what the gate does when it does

The worker's text says: do not write `TODO.md`, `TASK.md`, `LOG.md` or `QUESTIONS.md`; do not change `PLAN.md` or the confirmation line of `REQ.md`; do not promote or call a subagent; decide no trade-off that changes the result; write no file from the terminal; never copy source files into `DEV/<repo>/`, because a promote writes back what is under it {src:.github/agents/worker.agent.md#L19-L35}. Code enforces only some of this. The gate's `check_task_write` applies to every session that holds a task, and a subagent session inherits its parent's task, so it applies to the worker: a path outside the task folder, or the folder `DEV` itself, is refused; `DEV/` opens only once the plan is approved; `REQ`, `REF` and `INBOX` are the person's; and the CLI-owned paths (`.task/`, the diff files, `REVIEW/`, `SNAPSHOT/`, `OUTBOX/`, `READ/`, `.workspace/reports/`) are refused to every agent {src:.harness/engine/modules/gate/handler.py#L64-L94} {src:.harness/policies/gate.json#L24-L34}. In a task in autorun the write split adds that the worker's edit of `TODO.md`, `TASK.md`, `LOG.md` or `QUESTIONS.md` is refused (the scheduler may write only those four) {src:.harness/engine/modules/gate/handler.py#L100-L109}.

Not refused by code: the worker writing `PLAN.md` or the confirmation line of `REQ.md`. A changed `PLAN.md` no longer matches `plan.approved_sha256`, so `plan_approved` is false and `fact_reason` returns `plan`, which ends the run at the next worker call {src:.harness/engine/core/tasks.py#L159-L164}. Promoting, calling a subagent and writing from the terminal are kept by text and by the platform: the subagent rule gives no opinion for a subagent session, and a write-back needs the person's code anyway.

A call of the worker that the gate refuses or holds is written into `QUESTIONS.md` as `[held: <tool>] <command or path> | took: held`. `park_worker_call` does this for any PreToolUse deny or ask in a subagent session of a task in autorun, except the kinds `autorun-write`, `task-scope` and `write-no-path`, which only add to the call's `denied` count; `took: held` is not `none`, so a held call does not park the step {src:.harness/engine/modules/gate/handler.py#L731-L755} {src:.harness/engine/core/autorunfiles.py#L141-L163}.

## Subagents internals: how the hook refuses the question tool for the worker and the scheduler

The question tool is `ask_user` (older recordings: `AskUserQuestion`), and `tool_kinds.json` maps both to the kind `ask` {src:.harness/engine/adapters/tool_kinds.json#L33-L34}. In `handle`, a PreToolUse of kind `ask` goes to `on_ask_call` first, and a refusal is returned at once {src:.harness/engine/modules/task/handler.py#L629-L633}. `on_ask_call` decides in this order {src:.harness/engine/modules/task/handler.py#L550-L565}: admin mode, or no open task, or a task whose autorun state is not `on`: no opinion (the question passes). Otherwise, if the session is a subagent session (it has a `parent_session_id`, the test `is_subagent_session`), the call is denied with the message `autorun.deny.ask_worker`, which tells the worker to end its reply with a `QUESTION: ... | took: ...` line. Otherwise, for the scheduler, if `autorun.open_steps_of` finds a step of `TODO.md` that is neither `[x]` nor `[?]`, the call is denied with `autorun.deny.ask`, which tells it to write the question into `QUESTIONS.md` and go on {src:.harness/engine/core/autorunfiles.py#L30-L53}. With no open step left, the question is let through, so the questions are asked together at the end.

No other module can loosen the refusal, because the hook merges decisions with deny above ask above allow {src:.harness/engine/core/events.py#L77-L93}. The deny carries the fact kind `autorun-ask`, which the circuit breaker skips, so a repeated refusal is never counted and never becomes a stop instruction {src:.harness/engine/core/breaker.py#L50-L51}. When a question is let through, `on_ask_call` records `ask_since` in the module state, and at the PostToolUse of the tool `note_ask_return` adds the waiting time back to the run's time limit (`add_wait` moves `until` out) when the wait is over 0 and at most 24 hours {src:.harness/engine/modules/task/handler.py#L568-L579} {src:.harness/engine/modules/task/autorun.py#L460-L460} {src:.harness/engine/modules/task/autorun.py#L542-L554}.

The worker's question is not refused in two cases. If the child session was never linked to its parent (see below), it has no task, so the first test finds none and the question passes. And if the task module itself raises on a question call, no rule refuses it: the failure rule covers only subagent calls, and the emergency answer lets the question tool through {src:.harness/engine/hook.py#L55-L55} {src:.harness/engine/hook.py#L170-L173}.

## Subagents internals: passing work by files, and what "a subagent has no state and cannot ask back" means

Agents do not pass messages to each other. The design document says: "Agents do not pass messages to each other; they all read and write the files of the task folder. A subagent has no state and cannot ask back." {src:docs/05-design.md#L119-L119} The phrase "subagents are synchronous and stateless" is not in the harness source (the Guide file 36 Design decisions uses it). The platform still gives each subagent one prompt in and one reply out; the harness keeps the real state in files, which a person can read too, so work can go on after a break.

For a call this means the message must carry the step text (or the question, scope and what to hand in) and the task path, and everything else must already be in readable files: `TASK.md`, `PLAN.md`, the files the step names. The hand-overs in code:

- **Reviewer.** Input is `REVIEW/round-NNN/package.md`, whose path the hook puts in its start context at SubagentStart when a round is open {src:.harness/engine/modules/task/handler.py#L338-L344}. The hook saves the reply as `verdict.md` and reads `VERDICT: PASS` or `FAIL` in the first three non-empty lines (`unknown` otherwise), at the PostToolUse of the parent's call in `on_review_done`, not at SubagentStop {src:.harness/engine/modules/task/handler.py#L391-L401} {src:.harness/engine/modules/task/taskreview.py#L69-L85}. With no package, its text says to write "Brief lacks: ..." and return FAIL {src:.github/agents/reviewer.agent.md#L15-L26}.
- **Mapper.** Input is Question, Scope and To hand in; it returns a summary with sources and the main agent merges; a missing item makes it write "Brief lacks: ..." and do its best {src:.github/agents/mapper.agent.md#L14-L22}.
- **Worker.** Input is the step and the task path; an open point comes back as `QUESTION: ... | took: ...` and the scheduler copies it into `QUESTIONS.md`; a gap in the brief becomes "Brief lacks: ...". The ledger `.task/autorun-run.jsonl` is written by hooks, and the gate's write split gives the scheduler four files and the worker the rest {src:.harness/engine/core/autorunfiles.py#L79-L89}.

Code checks the brief only loosely: the ledger `start` line finds the step by the first 60 characters of each step's text (`STEP_MATCH`) inside the call prompt, and with no match the line has no step number and the call is not refused {src:.harness/engine/modules/task/autorun.py#L463-L476}. The worker's model is part of the call and is checked against the task's allowed list and default.

## Subagents internals: how the core tracks subagent sessions

A subagent runs in a session of its own, with its own state file `.harness/runtime/state/vscode/<session>.json`, and the core links it to the parent by heuristics, because the SubagentStart payload has no agent id. Wiring: `SubagentStart` and `SubagentStop` are registered in `.github/hooks/harness.json` and in the task module's `events` in `registry.json`; core lists them in `TRACKED_EVENTS` (needed even if no module subscribes); and `harness doctor` reports an error for a needed event the hook configuration lacks {src:.github/hooks/harness.json#L76-L99} {src:.harness/registry.json#L91-L103} {src:.harness/engine/core/state.py#L48-L49} {src:.harness/engine/doctor.py#L242-L251}.

In the parent's session state, `subagents.active` lists the running subagents. `track_before` (before the modules run) appends at SubagentStart an entry `{agent_id: "<agent_type>@<time>", agent_type, at, awaiting_child: true}`: the id is made up from the agent type and the time, since the payload has none. At SubagentStop it removes the first entry with the same `agent_type`, since the payload reports the child's session id and not the made-up one; so two reviewers running at once leave one entry after both end. The parent's Stop empties the list, and SessionStart empties it and the pending prompts {src:.harness/engine/core/state.py#L262-L300}. Every hook call first prunes entries older than `SUBAGENT_ACTIVE_TTL_SECONDS` (1800 s) and pending prompts older than 300 s, so a missing SubagentStop does not leave entries behind {src:.harness/engine/core/state.py#L38-L41} {src:.harness/engine/core/state.py#L254-L259}.

The claim is made by `claim_child`, called in `process` for the first UserPromptSubmit of a session that has no state file yet {src:.harness/engine/hook.py#L100-L102}. It scans the 30 newest other state files (`CHILD_SCAN_FILES`), skips files not touched in the last 600 s, and keeps a parent only if it has an `awaiting_child` entry at most 10 s old (`CHILD_CLAIM_SECONDS`). Scoring: a parent whose `pending_prompts` (the call messages of allowed subagent calls, at most 8, kept by `track_after`) holds a message equal to the child's first prompt scores 2, any other waiting parent scores 1; the highest score wins, then the newest entry. The parent's first `awaiting_child` entry is marked claimed (`child_session_id` set), not necessarily the matching one, so two simultaneous starts can swap. The child's state then takes `parent_session_id` and the parent's `active_task`, so the child holds the same task, and its first prompt is marked `from_subagent` {src:.harness/engine/core/state.py#L303-L354} {src:.harness/engine/core/state.py#L357-L371} {src:.harness/engine/hook.py#L113-L115}.

From then on, in the child session, every later UserPromptSubmit is marked `from_subagent` and returns at once, and so never counts as the user (the engine feeds the SubagentStop block reason back as a prompt) {src:.harness/engine/core/state.py#L286-L291}. Admin mode is never on for a subagent session {src:.harness/engine/core/state.py#L246-L248}. If no parent is found, the child is an ordinary session with no parent and no task: no worker rule reaches it (no write split, no refused question, no task scope); the link rests on timing and on the call message, not on an id.

## Subagents internals: limits and points the code does not settle

- **The link between a child and its parent is heuristic**: it rests on timing and on the call message, not on an id.
- **"Reads only" is partly text.** The mapper has no terminal and no edit tool by its tool list (the platform); the reviewer has a terminal, kept to read-only commands by text alone {src:.github/agents/reviewer.agent.md#L27-L35}. The worker file has no tool list, so what tools the worker has is not shown by the repository.
- **Nothing in code forbids parallel workers or writers**, and the call message is not read by code except for the ledger's step match and the core's match of a child's first prompt.
