## Known limits: how to read this file

The harness is a governance layer around VS Code Copilot, not a sandbox: the agent runs as the person's own user, and the gate judges the text of each tool call before it runs, so a write the text does not show is not stopped {src:.harness/engine/modules/gate/terminal.py#L1-L5}. A known limit is a place where a protection described in another Guide file does not hold, or holds only because text asks the model or a person checks; every item here is gathered from the limits of the other files and checked against the code of version 1.8.3. Each item ends with the Guide file that has the details.

## Known limits: what the gate cannot see

- **The gate reads text.** A path built from variables at run time, a script the agent writes that changes a file other than a guardrail file, or a program that chooses by itself where to write is not seen; the check of a script that is run looks only for writes to guardrail paths, and only as best effort {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}. Details: 15 The gate and guardrails.
- **The terminal is not kept to the task folder.** A terminal command is refused when its text names a guardrail file, a harness-owned file, a `.git` folder or a target repository as a write target (in full, or after a `cd` on the same line; a target repository only by its full path); a terminal write anywhere else passes {src:.harness/engine/modules/gate/handler.py#L117-L139}. Details: 11 Task.
- **A terminal write into a target repository is refused only when the command spells the repository's full path.** The terminal rule for a target repository's working tree, a registered knowledge base included, is built from absolute paths only, and a `cd` to a relative folder stays relative; so `echo x > knowledge-base/domains/a/SKILL.md`, `cd knowledge-base && echo x > domains/a/SKILL.md` or `cp f knowledge-base/company/skills/s.md` passes, while the same write by the full path is refused {src:.harness/engine/modules/gate/policy.py#L149-L156} {src:.harness/engine/core/repo_paths.py#L143-L164} {src:.harness/engine/modules/gate/terminal.py#L67-L109}. Details: 16 Write-back.
- **Tools the harness has not recorded are not judged.** A tool whose name is not in `tool_kinds.json` gets the kind `other`: no path check and no terminal rules, only the tool-pack MCP check, the board-address check and the secrets check; that covers a file-writing MCP server no tool pack names, and an edit or terminal tool under a new name {src:.harness/engine/adapters/tool_kinds.json#L1-L4} {src:.harness/engine/modules/gate/handler.py#L776-L788}. Details: 15 The gate and guardrails.
- **An MCP tool a tool pack names is only asked about when it writes.** A write or run of a named MCP tool goes to Copilot's own confirmation (a destroy is refused), which does not show under Allow all; an MCP tool no pack names is left as it is {src:.harness/engine/modules/gate/handler.py#L317-L337}. Details: 19 Tool packs, connections and MCP.
- **Reads are not guarded.** The gate policy says it never blocks a read: the agent can read whatever the person's account can, except `.harness/.env` and the board's address. The `.env` refusal sees only the `filePath` and `path` keys of a tool's input and the text of a terminal command, and an MCP tool a pack names returns from the gate before that check {src:.harness/policies/gate.json#L3} {src:.harness/engine/modules/gate/handler.py#L633-L650} {src:.harness/engine/modules/gate/handler.py#L776-L788}. Details: 19 Tool packs, connections and MCP.
- **▶ Run and the board's Terminal window are not seen by the gate.** Both start a command from the board server, as the person; only the paired browser may use them, and the Run dialog warns that the gate does not check the command, also one the agent wrote, so the person's reading is the only check {src:.harness/engine/modules/task/taskrun.py#L1-L8} {src:.harness/engine/modules/task/boardterm.py#L1-L9} {src:.harness/engine/core/messages.en.json#L2005-L2009}. Details: 12 The board.
- **A hook that times out lets the call through.** The hook's timeout is 30 seconds, and Copilot passes a call whose hook did not answer in time, with no notice (measured, written in the design doc) {src:.github/hooks/harness.json#L12-L13} {src:docs/05-design.md#L167-L170}. Details: 24 Setup, doctor and upgrade.
- **Only Copilot (SDK) sessions in VS Code are covered.** The older Local sessions are not supported, `copilot -p` on the command line runs no hooks, and the adapter follows Copilot's undocumented payloads, which an update can change {src:.harness/engine/adapters/copilot_vscode.py#L1-L8} {src:docs/05-design.md#L160-L161}. Details: 31 How it is built.

## Known limits: the task folder and sessions

- **The task folder binds only a chat that holds an open task, and only its edit tools.** A chat with no task, or whose task is closed, is kept to no folder by the edit-tool check {src:.harness/engine/modules/gate/handler.py#L64-L72}. Details: 11 Task.
- **`DEV/` is closed before the plan is approved only to the edit tools of the chat that holds the task.** Its terminal commands and a chat with no task can write there; what the code guarantees is that nothing in `DEV/` is written back without an approved plan and an approved write-back {src:.harness/engine/modules/gate/handler.py#L64-L94} {src:.harness/engine/modules/task/task.py#L911-L944}. Details: 14 Plans and approvals.
- **The approval records are files.** They live in `.task/task.json`; the edit tools and a terminal command that names the file are refused, but a script the agent writes and runs is checked only for guardrail paths {src:.harness/policies/gate.json#L23-L33} {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}. Details: 14 Plans and approvals.
- **Opening a task does not release an earlier session that still holds it.** `task open` changes only the opening session's state {src:.harness/engine/modules/task/task.py#L154-L209}. Details: 11 Task.

## Known limits: permissions and Allow all

- **The ask rules are only a reminder.** Deleting files, network calls, installs, git history rewrites and `harness logs prune` go to Copilot's own confirmation, and the harness docs say no box shows when the chat's permission is Allow all {src:.harness/policies/gate.json#L146-L182} {src:docs/02-features.md#L50}. Details: 15 The gate and guardrails.
- **Every chat the board makes starts with Allow all, and Start autorun sets it.** New task, a one-click skill chat and "go on in a new chat" offer no other permission; Start autorun sets Allow all on the task's chat for the run {src:.harness/engine/modules/task/chatnew.py#L25-L26} {src:.harness/engine/modules/task/autorun_start.py#L1-L6}. Details: 12 The board.
- **The agent can delete the session logs.** `harness logs prune` has no person check and is only on the ask list, so in a chat under Allow all the agent's call runs {src:.harness/engine/modules/observe/commands.py#L30-L31} {src:.harness/policies/gate.json#L176-L181}. Details: 22 Cost and usage.
- **In autorun, a call the gate asks about is listed as held though it ran.** A worker's call that the gate answers with "ask" goes to `QUESTIONS.md` as held, while Allow all lets it run {src:.harness/engine/modules/gate/handler.py#L737-L760}. Details: 20 Autorun.
- **Admin mode opens the guardrails.** In a chat the person switched to admin mode, of the guardrail paths only `.harness/runtime/**`, the policy's `admin_locked_paths` and the integrity-list folder stay closed (command-line-owned files, `.git`, target repositories and the person-only commands stay closed as everywhere); the integrity check is skipped, and ending admin mode accepts the guardrail files as they are then {src:.harness/engine/core/guardrails.py#L21-L61} {src:.harness/engine/modules/gate/handler.py#L36-L61} {src:.harness/engine/hook.py#L312-L323}. Details: 11 Task.

## Known limits: repositories that are not set up as targets

- **Git writes need an approval only when target repositories are set up.** Without them only the ask list looks at git, so `git push` is asked about, not refused, and in a board-made chat under Allow all it runs; a write that names a `.git` folder is still refused {src:.harness/engine/modules/gate/handler.py#L815-L824} {src:.harness/policies/gate.json#L155-L160}. Details: 15 The gate and guardrails.
- **An unregistered `knowledge-base/` folder is not a target repository.** The gate's target refusal does not cover it, and a chat that holds no task can write it with its edit tools {src:.harness/engine/core/targets.py#L225-L242} {src:.harness/engine/modules/gate/handler.py#L64-L72}. Details: 18 Knowledge base.
- **With targets set up, the write-back is still not the only way in.** A terminal write by a relative path, a script, an alias or a path made at run time can write a repository unseen, and a git command the person approves with `approve-command` changes a repository without a write-back {src:.harness/engine/modules/gate/gitcmd.py#L1-L9} {src:.harness/engine/modules/gate/handler.py#L153-L162}. Details: 16 Write-back.
- **The write-back fetches and moves the base branch.** At a first fetch and at every dry run the harness runs `git fetch` and fast-forwards the base branch, although the design doc says there is no automatic fetch or pull {src:.harness/engine/modules/task/basesync.py#L52-L80} {src:docs/05-design.md#L224}. Details: 16 Write-back.

## Known limits: text rules that are not guarded

- **The text rules are not guardrail paths and not in the integrity list.** `AGENTS.md`, `.github/copilot-instructions.md`, `.github/instructions/`, `.github/skills/` and `.github/agents/` can be written by the edit tools of a chat with no task, and a direct terminal write to them is refused in no chat (only a script or inline code that writes `AGENTS.md` is refused, outside admin mode); the harness does not notice a change {src:.harness/policies/gate.json#L4-L19} {src:.harness/engine/integrity.py#L23-L26}. Details: 23 Skills.
- **Domain skills in a registered knowledge base are protected from the edit tools, and from the terminal only by full path.** In a knowledge base registered as a target repository, the usual setup, the edit tools of every chat are refused its domain skills and the sources in `company/skills/`, and so is a terminal command that names them by the repository's full path; a terminal write by a relative path (`echo … > knowledge-base/…`), a script or a path made at run time is not refused, so a write-back is not the only way they change. Only an unregistered `knowledge-base/` folder and the copies in `.github/skills/` are open to the edit tools as well {src:.harness/engine/modules/gate/handler.py#L50-L52} {src:.harness/engine/modules/gate/policy.py#L149-L156} {src:.harness/engine/core/targets.py#L225-L242}. Details: 23 Skills.
- **`AGENTS.md` is guarded against scripts only.** The script check refuses a script or inline code that writes `AGENTS.md`, but the edit tools of a chat with no task, and a terminal command that writes it directly, are not refused {src:.harness/engine/modules/gate/scriptcheck.py#L29} {src:.harness/engine/modules/gate/scriptcheck.py#L32-L47} {src:.harness/policies/gate.json#L4-L19}. Details: 15 The gate and guardrails.
- **The reviewer's agent file is not guarded.** Its tools, model list and instructions are not a guardrail path, not in the integrity list and not in the script check, so a terminal write can change them and only the person's review of the change would notice {src:.harness/engine/integrity.py#L23-L26} {src:.harness/engine/modules/gate/scriptcheck.py#L27-L29}. Details: 17 Independent checks.
- **A skill only the person may start rests on Copilot's flag.** The flag stops Copilot from loading the skill, not the agent from reading its `SKILL.md` and following it; six of the eight such skills have no code guard beyond it, and `harness task performance` is not person-only {src:.harness/policies/gate.json#L131-L137}. Details: 23 Skills.

## Known limits: approvals and person checks

- **The requirement's confirmation is a text line.** A "User confirmed" line the agent filled counts only before the person's first confirmation; deleting the line or `REQ.md` at any time means nothing to confirm, and the plan is then approved alone. The plan still needs the person's code {src:.harness/engine/modules/task/task.py#L551-L567} {src:.harness/engine/modules/task/taskreview.py#L88-L116}. Details: 13 Requirement and intake.
- **Some person-only commands ask no code.** `task review set`, `task allow`, `task test runner`, `task pause`, `task resume`, `task offwork` and `task onwork` check that a person runs them but ask no typed code, because the harness counts them as changes that can be undone {src:.harness/engine/modules/task/taskreview.py#L476-L480} {src:.harness/engine/modules/task/tasklife.py#L543-L548} {src:.harness/engine/modules/task/tasklife.py#L686-L742}. Details: 14 Plans and approvals.
- **A leading `--short` gets past the person-only text rules.** The gate's patterns expect the command right after `harness`, and the command line accepts the global flag `--short` before it, so `harness --short task close` is not refused by the gate; commands with their own check for a person at a terminal still refuse {src:.harness/policies/gate.json#L136} {src:.harness/policies/gate.json#L143} {src:.harness/engine/cli.py#L131-L132}. Details: 15b The gate and guardrails internals.
- **`task close` has no person check.** The agent is kept from closing a task only by the gate's text rule for `harness task close` and by the board's pairing {src:.harness/engine/modules/task/commands.py#L125-L134} {src:.harness/policies/gate.json#L138-L144}. Details: 14 Plans and approvals.
- **Some commands meant for the person are open to the agent.** `task intake convert`, `paste` and `init` are not person-only, and the terminal checks do not cover `REQ/`, `REF/` or `INBOX/`, so the person's folders are closed to the edit tools only; `reinstall --apply` has no gate rule and rests on its terminal test alone {src:.harness/engine/modules/task/commands.py#L318-L336} {src:.harness/engine/modules/gate/handler.py#L91-L93} {src:.harness/engine/core/reinstall.py#L300-L331}. Details: 13 Requirement and intake.
- **After the plan is approved, some outside calls need no further approval.** A call the company's policy marks `task`, and a write on a connection the person opened for the task, pass without the person seeing the code that runs {src:.harness/engine/modules/gate/handler.py#L287-L308}. Details: 14 Plans and approvals.
- **A code stops a swap, not a careless yes.** An approval compares the typed code with the digest of the files; it does not know whether the person read them {src:.harness/engine/core/approval.py#L50-L58}. Details: 16 Write-back.
- **A change to the "Done when" items does not undo a confirmed requirement or an approved plan.** The requirement digest stops at every heading, and the template puts the numbered Done when items under `###` sub-headings, so they are not in the digest; a change to What to do or What not to do does undo both {src:.harness/engine/core/tasks.py#L134-L149} {src:.harness/contracts/templates/task/en/REQ.md#L16-L31}. Details: 13b Requirement and intake internals.
- **A `medium` task does not wait for its requirement.** Only a `full` task (dev, test, kb) stands on a confirmed requirement; an RCA or design task goes on without one {src:.harness/engine/modules/task/taskdesk.py#L533-L535}. Details: 13 Requirement and intake.

## Known limits: the board

- **Reads and pause need no pairing.** Any program on the computer that sends the right host can read the pages, files, downloads and Live items and press pause or resume; the gate refuses only an agent call whose text names the board's address with the port {src:.harness/engine/modules/task/boardserve.py#L96} {src:.harness/engine/modules/task/boardserve.py#L1723-L1812} {src:.harness/engine/modules/gate/handler.py#L580-L584}. Details: 12 The board.
- **The embedded browser is known by its user agent.** VS Code's own browser is never paired because it sends `Electron`; any other browser tool is kept out only by having no pairing cookie {src:.harness/engine/modules/task/boardserve.py#L1709-L1721}. Details: 12 The board.
- **Many board actions are one paired click with no code.** Accept, Close, Archive, review set, test runner, linking a ticket, opening the linked items and closing a connection ask for the paired browser only, though the task policy's description says every button but pause and resume asks a typed code {src:.harness/engine/modules/task/boardserve.py#L670-L700} {src:.harness/engine/modules/task/boardserve.py#L775-L800} {src:.harness/policies/task.json#L3}. Details: 12 The board.
- **A ticket the person links on the board while the linked items are open is opened at once,** though the board's pop-up says a ticket linked later still waits; a ticket the agent links with `task link add` is not opened {src:.harness/engine/modules/task/tasklife.py#L612-L635} {src:.harness/engine/core/messages.en.json#L3867}. Details: 19 Tool packs, connections and MCP.

## Known limits: knowledge base

- **Any task with an approved plan can write a registered knowledge base.** The write-back does not check the task kind; that only `kb` tasks change it is an instruction {src:.harness/engine/modules/task/task.py#L911-L930} {src:.harness/engine/modules/task/promote_target.py#L164-L166}. Details: 18 Knowledge base.
- **The Commit button commits everything.** When Pack for colleagues finds uncommitted files, its Commit button runs `git add -A` and one commit of every change in the knowledge base, with a paired click and no code, without showing the content {src:.harness/engine/core/company.py#L555-L571} {src:.harness/engine/modules/task/boardserve.py#L2026-L2033}. Details: 18 Knowledge base.
- **`kb map` runs toolkit Python with no sandbox.** It loads the extractors as Python modules in its own process; with `--toolkit` it runs a toolkit from a task folder, which the agent may have written and no person has reviewed, although the map contract says a person has read that code {src:.harness/engine/core/kbextract.py#L36-L49} {src:.harness/engine/core/kbmap.py#L151-L160} {src:.harness/contracts/kb/map.md#L19}. Details: 18 Knowledge base.
- **The write-back does not run `kb check` or `kb cardcheck`.** A knowledge base change that breaks the standard form is written back; `doctor` only warns {src:.harness/engine/doctor.py#L559-L571}. Details: 18 Knowledge base.

## Known limits: outside systems

- **An opened connection comes back with the task.** Closing a task does not clear the connections and linked items the person opened for it; they are ignored while it is closed and in force again when the same task is opened again, a new round included {src:.harness/engine/modules/task/task.py#L174-L182}. Details: 19 Tool packs, connections and MCP.
- **`task allow --conn X --off` leaves a ticket board's linked items open.** For a connection that opens only linked items, `--on` opens the linked items, but `--off` only takes X off the list of opened connections, where it never was, and says "X is closed for this task"; `task allow --links --off` or Close on the linked-items row closes them {src:.harness/engine/modules/task/tasklife.py#L543-L595} {src:.harness/engine/core/messages.en.json#L3853}. Details: 19 Tool packs, connections and MCP.
- **A destroy can pass on SQL Server DEV and IST.** On an opened connection, `DROP TABLE` and `TRUNCATE TABLE`, which the sample type's write list names, pass; the CLI help and the tool-pack protocol still say a destroy is refused {src:.harness/engine/modules/gate/handler.py#L299-L306} {src:.harness/engine/modules/task/commands.py#L358} {src:.harness/contracts/toolpack/README.md#L125-L133}. Details: 19 Tool packs, connections and MCP.
- **The gate cannot read every call to an outside system.** A program name built at run time, a script changed after the check, a program a script finds by itself and remote execution are not seen; the protocol advises an operating-system sandbox for an agent that is not trusted {src:.harness/contracts/toolpack/README.md#L147-L158}. Details: 19 Tool packs, connections and MCP.
- **The refuse list is best effort, and `.harness/.env` is kept private by file rights only on macOS and Linux.** A spelling the refuse list misses is held, not refused; on Windows the file gets no restricted rights {src:.harness/contracts/toolpack/README.md#L111} {src:.harness/engine/core/connections.py#L290-L295}. Details: 19 Tool packs, connections and MCP.

## Known limits: autorun and cost

- **Autorun's spend limit is checked between calls.** The check runs at a call, so a call under way can pass the limit {src:.harness/engine/modules/task/autorun.py#L308-L327} {src:.harness/engine/modules/task/autorun_spend.py#L1-L5}. Details: 20 Autorun.
- **No spend limit holds when the spend cannot be read.** When Copilot's session record cannot be read, the run does not stop for `budget`; the run card only notes it {src:.harness/engine/modules/task/autorun.py#L288-L294} {src:.harness/engine/modules/task/autorun.py#L323-L327}. Details: 20 Autorun.
- **There is no total budget per task.** Nothing stops a task's own chat when its Credits pass a sum; the ⚠ tag only warns, and only once 3 closed tasks of the same kind exist to compare with {src:.harness/engine/modules/task/health.py#L141-L157}. Details: 22 Cost and usage.
- **Autorun's write split covers the edit tools only.** The scheduler is refused an edit tool's write outside its four files, but not a terminal write into `DEV/` {src:.harness/engine/modules/gate/handler.py#L64-L109}. Details: 20 Autorun.
- **A ticked step is the scheduler's word.** Code does not check the work; the run ledger's result is the worker's own reply {src:.harness/engine/core/autorunfiles.py#L15-L76}. Details: 20 Autorun.
- **The super agent's daily limit is checked before a turn,** so the turn that crosses it is still spent, and questions to tasks run in each task's own chat, outside the limit {src:.harness/engine/modules/task/superbrain.py#L415-L433} {src:.harness/engine/modules/task/superroute.py#L75-L128}. Details: 21 Super agent.

## Known limits: independent checks

- **The reviewer is the same model family.** The reviewer runs on a Claude model, as the main agent often does, and no policy makes them differ, so they may share blind spots; a PASS means a second reader found nothing {src:.harness/policies/agents.json#L1-L20} {src:.github/agents/reviewer.agent.md#L1-L7}. Details: 17 Independent checks.
- **A PASS's evidence is not checked.** The script checks the form of a FAIL's findings only {src:.harness/engine/modules/task/taskreview.py#L412-L436}. Details: 17 Independent checks.
- **The reviewer's terminal is kept to reads by text only.** It has the `execute` tool, and only its instructions say to run read-only commands; the message the agent sends it is not read by code {src:.github/agents/reviewer.agent.md#L7} {src:.github/agents/reviewer.agent.md#L33}. Details: 17 Independent checks.
- **Checks gate only the dry run of a write-back.** For a task whose result stays in its folder, the checks are a reminder {src:.harness/engine/modules/task/task.py#L911-L926}. Details: 17 Independent checks.

## Known limits: integrity of the guardrail files

- **The first board start after a version change accepts every watched file as it is,** without listing what differs from the shipped version {src:.harness/engine/integrity.py#L198-L210}. Details: 24 Setup, doctor and upgrade.
- **Before the board's first start there is no list,** so nothing is checked and `doctor` only warns {src:.harness/engine/integrity.py#L171-L183} {src:.harness/engine/doctor.py#L973-L998}. Details: 24 Setup, doctor and upgrade.
- **The list stops slips and plain tampering, not a process that runs as the same user,** which can rewrite the list as well {src:.harness/engine/integrity.py#L1-L9}. Details: 24 Setup, doctor and upgrade.

## Known limits: fixed recently

- **1.8.0: every spelling of `task allow` is the person's.** Since 1.7.38 the command took `--conn` and `--links`, but the gate's person-only rule matched only the old `--env`, so only the command's own person check stood between the agent and opening a connection for its task; the rule now matches every form {src:docs/07-release-notes.md#L83} {src:.harness/policies/gate.json#L136}. - **1.8.1: two calls can no longer write the same task file at once.** The session and task locks are the system's; before, a lock older than 5 seconds was removed, and a record could be lost {src:docs/07-release-notes.md#L54}. Details: 34 Version history.
- **1.7.38: a guardrail that cannot decide refuses.** When the engine cannot load, a guardrail module raises, or the state cannot be read, the hook refuses every terminal command and write; before, every call passed {src:docs/07-release-notes.md#L254} {src:.harness/engine/hook.py#L1-L15}. A gate policy that cannot be read no longer fails open either {src:docs/07-release-notes.md#L229}. Details: 15 The gate and guardrails.
- **1.7.38: the guardrail files are checked against a list the person accepted, and a script that is run is read** for writes to guardrail paths {src:docs/07-release-notes.md#L255} {src:docs/07-release-notes.md#L260}. Details: 24 Setup, doctor and upgrade.
