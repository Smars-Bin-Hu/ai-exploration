## Harness: what it is

The harness is a set of files and Python code that wraps the GitHub Copilot agent in VS Code so that a team can let it work on real code under rules. It does three things. A hook checks every tool call of the agent before it runs {src:.github/hooks/harness.json#L1-L113}. Work is done in tasks: a task is a folder with the requirement, the plan, the results and a state file; the agent is told by its rules to open one before it produces or changes files, and the code does not force it to {src:.harness/engine/core/tasks.py#L1-L8} {src:AGENTS.md#L46-L47}. A person approves the plan and every write-back to a code repository by typing a code, and confirms the requirement the same way; the requirement's confirmation is also a text line the agent can write {src:.harness/engine/core/approval.py#L1-L8} {src:.harness/engine/modules/task/taskreview.py#L88-L110}. The harness carries no business knowledge: the team plugs in its own knowledge base, skills and target repositories (the company code repositories the agent may change). The harness has no remote server: everything of it, the board's local web server included, runs on the person's computer, while the model runs in GitHub Copilot's service and the agent may call the outside systems the company connects {src:docs/00-overview.md#L161} {src:.harness/engine/modules/task/boardserve.py#L8-L9}. This Guide describes harness version 1.8.3.

The harness is not a sandbox. The agent runs as the person's own operating system user, and the gate reads the text of a command, so it guards against an agent's mistakes, not against an agent set on getting around it {src:.harness/engine/modules/gate/terminal.py#L1-L5}.

## Harness: the parts and how a piece of work flows through them

The harness has six parts. The **agent** is a Copilot chat in VS Code; it thinks and calls tools. The **hooks** are one Python entry point that VS Code runs at session start, at every prompt, before and after every tool call, when a subagent starts or stops, and when the agent stops; it runs the harness modules registered for that event: the gate, the task module and the observe module {src:.github/hooks/harness.json#L1-L113} {src:.harness/engine/hook.py#L1-L15} {src:.harness/registry.json#L91-L305}. The **gate** decides, before each tool call, whether a write or a command may run {src:.harness/engine/modules/gate/handler.py#L1-L14}. The **task folder** under `.workspace/sandbox/tasks/<task name>/` holds the work {src:.harness/engine/core/tasks.py#L19-L37}. The **`harness` command line** makes tasks, fetches files, writes back, and runs the approvals that only a person may run {src:.harness/engine/modules/task/task.py#L1-L10}. The **board** is a page served on this computer only (127.0.0.1) where a person follows every task and presses the buttons for approvals {src:.harness/engine/modules/task/boardserve.py#L1-L17}.

Three subagents work for the agent, each only where the code lets it: the `reviewer` (the independent check, only in a task whose checks are on), the `mapper` (reading in parallel, read only, only after the person starts `/generic-mapreduce`) and, since 1.8.0, the `worker` (one step of `TODO.md`, only in a task whose autorun is on); the task hook refuses every other subagent {src:.harness/engine/modules/task/handler.py#L278-L300} {src:AGENTS.md#L53}. Since 1.8.3 the board also has a **Super agent** view: what waits for the person across all tasks, with the board's own buttons, and a chat with a `super` agent that only reads and whose proposals do nothing until the person presses them {src:.harness/engine/modules/task/superbrain.py#L1-L13} {src:.harness/engine/modules/task/superact.py#L1-L7}. The file 21 Super agent explains it.

A development task flows like this. The person says what they want; the agent asks until it is clear and opens a task with `harness task new` {src:.github/skills/harness-my-task/SKILL.md#L29-L65}. The agent writes the requirement into `REQ.md`, and the person confirms it with a code, which fills the "User confirmed" line of `REQ.md` {src:.harness/engine/modules/task/task.py#L570-L612}. The agent reads the knowledge base and the code and writes `PLAN.md`; the person approves the plan with a code. For the chat that holds the task, the gate refuses the agent's edit tools any write under the task's `DEV/` folder until then; a chat that holds no task is not bound by this, but nothing reaches a repository without the write-back approval below {src:.harness/engine/modules/task/task.py#L428-L475} {src:.harness/engine/modules/gate/handler.py#L64-L94}. The agent copies the files to change into `DEV/` with `task fetch`, changes them, runs the independent checks when the person asked for them, and runs `task promote --dry-run`; the person approves the exact write-back with a code; the agent runs `task promote`, which writes the files to a new branch of each target repository without committing; a repository registered as a knowledge base instead gets the files committed once on its base branch {src:.harness/engine/modules/task/task.py#L911-L1024} {src:.harness/engine/modules/task/promote_target.py#L1-L14}. The board closes the task once the agent has stopped and nothing else waits; a commit still to be made does not keep it open, and the person commits the branch in the repository {src:.harness/engine/modules/task/accept.py#L184-L218}. A task whose result stays in the folder (a question, a root cause analysis, a design, a test) ends instead with the agent's summary (`task deliver`) and the person pressing **Accept and close** on the board {src:.harness/engine/modules/task/accept.py#L1-L11}. Once the plan is approved, the person may instead switch on autorun (rebuilt in 1.8.0): the agent only schedules, a `worker` subagent does each open step of `TODO.md` in a fresh context, a step that needs an answer is parked with its question in `QUESTIONS.md` for the end, and the run stops on facts, such as the spend limit the person picked or the time limit (480 minutes by default); nothing is written back on the way, and the write-back still waits for the person {src:.harness/engine/modules/task/autorun.py#L1-L23} {src:.harness/engine/modules/task/autorun.py#L44-L46}. The file 20 Autorun explains autorun. The file 11 Task explains each step; the harness tutorial "1 A day with the harness", in the OneDrive folder `3 Courses/Harness tutorials/`, shows the first steps on screen.

## Harness: what is enforced by code, what is asked of the model by text, and what is left to a person

The harness splits every rule three ways. Code (the hooks and the command line) enforces what must hold; text (`AGENTS.md`, `.github/instructions/`, skills and the lines the hook adds to every prompt) asks the model, which can ignore it; a person decides what cannot be taken back {src:AGENTS.md#L42-L64} {src:.harness/engine/modules/task/handler.py#L93-L126}. The pattern is the same in every row: code sets the gates a piece of work must pass, text tells the model how to get there, and a person holds the keys at each gate. The file 11 Task gives the same split for tasks in full.

## Harness: how a person uses it day to day

A person uses the harness in two places: the Copilot chat in VS Code, to talk to the agent, and the board in the browser, to follow tasks and approve {src:.harness/engine/modules/task/boardserve.py#L1-L17}. Day to day it takes five steps.

1. Start the board once: double-click **Start Harness**, or run `harness task board` in your own terminal, and keep it running. Open it in Chrome, Edge or Firefox, paired from the link the terminal prints {src:docs/01-quickstart.md#L20} {src:docs/01-quickstart.md#L87-L97}.
2. Say in one sentence what you want done and in which repository, in the chat or with **New task** on the board. The agent asks until it is clear, then opens a task {src:.harness/engine/modules/task/chatnew.py#L1-L8}. A skill only a person may start (`disable-model-invocation: true`) can be picked in the same window: the board opens the task with the first message, then sends `/<skill>` to that chat once (1.8.2) {src:.harness/engine/modules/task/chatnew.py#L91-L96}.
3. Drop requirement documents on the task's **Intake** tab; confirm the requirement the agent writes in `REQ.md` with **Confirm requirement** and the code the page shows {src:.harness/engine/modules/task/intake.py#L1-L10} {src:.harness/engine/modules/task/task.py#L570-L598}.
4. Approve the plan, then the write-back, each with a code, when the board says the task waits for you {src:.harness/engine/modules/task/tasklife.py#L276-L338}. Between the two, **Start autorun** on the task page lets the agent work down `TODO.md` alone (see the file 20 Autorun) {src:.harness/engine/modules/task/autorun_start.py#L1-L6}.
5. Commit the branch the write-back made (the board closes a written-back task without waiting for the commit); or, for a task that changes no repository, press **Accept and close** {src:.harness/engine/modules/task/accept.py#L1-L11} {src:.harness/engine/modules/task/accept.py#L186-L199}.

The harness tutorial "1 A day with the harness", in the OneDrive folder `3 Courses/Harness tutorials/`, shows steps 1 to 3 on screen; the tutorial "3 When the agent is stopped" shows what "waiting for you" on the board means when a call or command is held. The board's **Super agent** view (1.8.3) gathers what waits across all tasks in one place, with the same buttons; see the file 21 Super agent.

## Harness: the main safety guarantees and their exact scope

The guarantee that matters most is about target repositories: the harness writes code back to a target repository only in a version the person approved. `task promote` refuses unless the dry run and the person's approval are for the same plan digest, and that digest covers the branch, the base commit of each repository, and the sha256 of every file to write {src:.harness/engine/modules/task/task.py#L941-L944} {src:.harness/engine/modules/task/promote_target.py#L112-L116}. The write goes to a new branch and is never committed, except for a registered knowledge base, which gets one commit on its base branch {src:.harness/engine/modules/task/promote_target.py#L1-L14}. The harness itself writes a target repository only through `task promote`; a git command the person approves with `approve-command` can also write it {src:.harness/engine/modules/gate/handler.py#L153-L162}. The VS Code edit tools of every chat are refused inside a target repository's working tree, and a terminal command that names a path there in full, or by a relative path after a `cd` in the same command line (the terminal's real working folder is not used) as a write target is refused; a script, or a path made at run time, is not seen {src:.harness/engine/modules/gate/handler.py#L47-L52} {src:.harness/engine/modules/gate/policy.py#L149-L156} {src:.harness/engine/modules/gate/terminal.py#L65-L117} {src:.harness/engine/modules/gate/terminal.py#L1-L5}.

The other guarantees, each with its scope:

- **Approvals need a person.** The gate refuses, on the agent's command line, `task confirm-req`, `task approve-plan`, `task approve-promote`, `task recover`, `task review set`, `extend`, `waive` and `dismiss`, `task test runner`, `task pause`, `resume`, `offwork` and `onwork`, `task autorun on`, `task allow` (every spelling, since 1.8.0), `task board` (except `--once`), `approve-command`, `approve-action`, `admin on` and `doctor --accept`, read the way the shell reads them, so quotes and variables do not hide them {src:.harness/policies/gate.json#L131-L137} {src:.harness/engine/modules/gate/harnesscmd.py#L1-L8}. The commands also check for a person at their own terminal, and the board runs the same functions only from the paired browser's buttons; both ask for a code made from the sha256 of what is approved, and a file that changed after the person read it gets a new code {src:.harness/engine/core/approval.py#L17-L58} {src:.harness/engine/modules/task/boardserve.py#L11-L16}. The board's Terminal window, which the board vouches for with a one-time code, counts as the person too (1.7.39), but only for the commands that ask for no code: it gives no keyboard input to type one {src:.harness/engine/core/boardperson.py#L1-L10} {src:.harness/engine/core/approval.py#L50-L56}. The requirement is the exception: its confirmation is the "User confirmed" line of `REQ.md`, which the agent can write {src:.harness/engine/modules/task/taskreview.py#L88-L110}.
- **Closing a task is the person's.** The gate refuses `task close` on the agent's command line; the command itself has no person check, so a script the agent runs is not stopped from closing a task. A task closes when the person accepts it, presses **Close** or runs `task close` in their own terminal, or, for a development or knowledge base task, when the board sees the write-back done and nothing waiting {src:.harness/policies/gate.json#L138-L144} {src:.harness/engine/modules/task/accept.py#L167-L218}.
- **Guardrail files.** Outside admin mode, the engine, the policies, the hook files and the other guardrail paths are refused to the edit tools and to a terminal write that names them in full, or by a relative path after a `cd` in the same command line (the terminal's real working folder is not used); a script a command line runs is checked for writes to them as best effort {src:.harness/policies/gate.json#L4-L19} {src:.harness/engine/modules/gate/terminal.py#L65-L117} {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}. In a chat the person switched to admin mode (`admin on`), only `.harness/runtime/**`, the policy's `admin_locked_paths` and the folder of the integrity lists (`~/.copilot-harness`, or the folder `HARNESS_INTEGRITY_DIR` names) stay closed {src:.harness/engine/core/guardrails.py#L21-L61} {src:.harness/engine/modules/gate/policy.py#L113-L119} {src:.harness/engine/modules/gate/handler.py#L44-L46}. Once the person has accepted the files (the first start of the board), the hook compares the engine, `.harness/bin`, the hook files, the tool packs, `registry.json` and the shipped policies with that list before every call, and refuses every command and write while one differs; admin chats skip this check, and ending admin mode accepts the files as they are then {src:.harness/engine/integrity.py#L1-L5} {src:.harness/engine/integrity.py#L18-L26} {src:.harness/engine/hook.py#L312-L323} {src:.harness/engine/hook.py#L342-L360}.
- **The super agent and a question to a task only read** (1.8.3). In a session whose person's prompt started with `/harness-super`, and in a turn that starts with `/harness-ask` until the next normal prompt, the gate refuses every call except reading, searching and a fixed list of read-only harness commands (`task list`, `task status`, `task queue`, `task autorun status`, `task review status`, `target list`, `target show`); a mark it cannot read refuses the call. The board writes both openings {src:.harness/engine/modules/gate/superagent.py#L18-L31} {src:.harness/engine/modules/gate/superagent.py#L78-L89} {src:.harness/engine/modules/gate/askturn.py#L21-L53}. The super agent never presses a button: its proposals are cards of the board's own buttons, which act only when the person presses them {src:.harness/engine/modules/task/superact.py#L1-L7}.
- **Fail closed.** When the engine cannot load, the gate fails on a call, or the session state or the module registry cannot be read, the hook refuses every terminal command and every tool that may change a file, and still allows reads {src:.harness/engine/hook.py#L11-L15}. When the task module fails, only subagent calls are refused {src:.harness/engine/hook.py#L55}. A hook call that cannot get the session lock within 20 seconds gets the same answer as an engine that cannot load, with a message that the harness is busy; since 1.8.1 the locks are the operating system's, freed when the process that held one ends {src:.harness/engine/core/state.py#L29-L32} {src:.harness/engine/core/state.py#L172-L174} {src:.harness/engine/hook.py#L269-L278} {src:.harness/engine/hook.py#L308-L309}.
- **Task folder.** For a chat that holds an open task, the VS Code edit tools write only inside that task's folder (a chat with no task is not bound); `REQ/`, `REF/` and `INBOX/` are the person's and refused; `DEV/` opens when the plan is approved {src:.harness/engine/modules/gate/handler.py#L64-L94}.

## Harness: known limits

These limits come from the code of 1.8.3; each one narrows a guarantee of the section "Harness: the main safety guarantees and their exact scope".

- **The terminal is not confined to the task folder.** A terminal command is refused when it names a guardrail file, a harness-owned file, `.git` or a target repository folder in full, or by a relative path after a `cd` in the same command line (the terminal's real working folder is not used) as a write target, or when a script it runs is found to write a guardrail file; it is not refused for writing elsewhere {src:.harness/engine/modules/gate/handler.py#L117-L139} {src:.harness/engine/modules/gate/terminal.py#L65-L117}.
- **The task folder binds only a session that holds an open task.** A session with no task, or whose task is closed, is not kept to any folder by the edit-tool check {src:.harness/engine/modules/gate/handler.py#L64-L72}.
- **The requirement's confirmation is a line of text.** The code reads the "User confirmed" line of `REQ.md`, a file the agent may write; a missing `REQ.md`, or one with no such line, counts as nothing to confirm, and the plan is then approved alone {src:.harness/engine/modules/task/taskreview.py#L88-L110} {src:.harness/engine/modules/task/task.py#L551-L567} {src:.harness/engine/modules/task/task.py#L445-L449}. The plan approval still needs the person.
- **Only the tools the harness has recorded are checked.** A tool whose name is missing from `adapters/tool_kinds.json` gets the kind `other`: no write check and no terminal rules at all, only the tool-pack MCP check, the board-port check and the secrets check. That covers a file-writing MCP server a team adds that no tool pack names, and a terminal or edit tool under a name not recorded there {src:.harness/engine/adapters/tool_kinds.json#L1-L10} {src:.harness/engine/adapters/tool_kinds.json#L60} {src:.harness/engine/modules/gate/handler.py#L773-L788}.
- **Admin mode opens the guardrails.** In a chat the person switched to admin mode, only `.harness/runtime/**`, the policy's `admin_locked_paths` and the integrity-list folder (`~/.copilot-harness`, or `HARNESS_INTEGRITY_DIR`) stay closed; the integrity check is skipped, and ending admin mode accepts the guardrail files as they are then {src:.harness/engine/core/guardrails.py#L21-L61} {src:.harness/engine/hook.py#L312-L323} {src:.harness/engine/integrity.py#L1-L5}.
- **After the plan is approved, some outside calls pass without a further approval.** A call the company's policy marks `task` passes once the task's plan is approved, and writes on a connection the person opened for the task with `task allow` pass; neither checks the code the agent is about to run {src:.harness/engine/modules/gate/handler.py#L287-L308}.
- **The ask rules are only a reminder.** Commands on the ask list (deleting files, network, installs, git history rewrites) go to Copilot's own confirmation; the harness docs say no box shows when the chat's permission is Allow all. Every chat the board makes, with **New task**, a one-click chat with no task, or "go on in a new chat", starts with Allow all, the only permission the board offers, and **Start autorun** sets Allow all on the task's chat for the run; the person can change it for a task's chat later on the task page {src:.harness/policies/gate.json#L146-L182} {src:docs/02-features.md#L50} {src:.harness/engine/modules/task/chatnew.py#L25-L26} {src:.harness/engine/modules/task/skillsend.py#L50-L53} {src:.harness/engine/modules/task/boardserve.py#L1645-L1660} {src:.harness/engine/modules/task/autorun_start.py#L3}.
- **Git writes need approval only when target repositories are set up.** Without them, only the ask rules look at git, and `git push` is asked about, not refused; in a chat the board made, which starts with Allow all, no box shows, so the agent's `git push` runs. A terminal write that names a `.git` folder is still refused {src:.harness/engine/modules/gate/handler.py#L815-L824} {src:.harness/engine/modules/gate/handler.py#L124-L130} {src:.harness/policies/gate.json#L155-L160} {src:.harness/engine/modules/task/chatnew.py#L25-L26}.
- **The board runs the person's own commands without the gate.** **▶ Run** on a shell code block of a task page, and the board's Terminal window, start the command from the board server, which the gate does not see; only the paired browser may ask, and the Run dialog warns that the gate does not check the command, so the person's reading is the only check, also of a command the agent wrote {src:.harness/engine/modules/task/taskrun.py#L1-L8} {src:.harness/engine/modules/task/boardterm.py#L1-L9} {src:.harness/engine/core/messages.en.json#L2005-L2009}.

## Harness: how dangerous commands are blocked

Dangerous commands are blocked by the gate, a hook module that reads every terminal command before it runs and answers allow, ask or deny; a deny from any module wins over an ask, and an ask over an allow {src:.harness/engine/core/events.py#L77-L93}. The rules are in `.harness/policies/gate.json`, which is itself a guardrail file: refused to the agent's edit tools and named terminal writes, except in a chat the person switched to admin mode {src:.harness/policies/gate.json#L1-L23}.

The gate also refuses any call that reads the person's secrets file or prints a secret variable, and any request to the board's port {src:.harness/engine/modules/gate/handler.py#L633-L650} {src:.harness/engine/modules/gate/handler.py#L773-L777}. For a terminal command it applies these rules; the list groups them and is not the order in which the code checks them {src:.harness/engine/modules/gate/handler.py#L117-L167}:

- A write to a guardrail file (redirect, `tee`, `rm`, `mv`, `cp`, `sed -i`, `git checkout`, an inline `python -c` and others), to a harness-owned task file, into `.git`, or into a target repository's folder: denied {src:.harness/policies/gate.json#L35-L87}.
- A git command, when target repositories are set up: a read passes; a write is denied until the person approves that exact command with `harness approve-command` and its code, for one run within 10 minutes; `push`, `clean`, `filter-branch`, `filter-repo`, `update-ref`, `prune`, `reset --hard`, `branch -D` and any force are never approved {src:.harness/engine/modules/gate/gitcmd.py#L22-L37} {src:.harness/engine/modules/gate/gitcmd.py#L272-L282} {src:.harness/policies/gate.json#L184-L186}.
- A harness command only a person may run: denied {src:.harness/policies/gate.json#L131-L144}.
- A script the line runs that writes a guardrail file: denied, as best effort {src:.harness/engine/modules/gate/scriptcheck.py#L1-L11}.
- The deny list: recursive delete of the root, home or current folder; a download piped to a shell; formatting a disk; `sudo` and other administrator rights; recursive permission changes; `docker rm`, `kubectl delete`, `terraform apply` and `destroy` {src:.harness/policies/gate.json#L88-L130}. The same rules are applied to a command string given to `bash -c` or `pwsh -Command` {src:.harness/engine/modules/gate/handler.py#L140-L147}.
- A call to an outside system the company listed: judged by what it does {src:.harness/engine/modules/gate/handler.py#L151-L153}.
- The ask list: deleting files, rewriting git history, going on the network, installing packages, deleting session logs: Copilot asks the person {src:.harness/policies/gate.json#L146-L182}.

A refused command reaches the agent as a reason that says what to do instead; when the same refusal repeats, the reason tells it to stop retrying {src:.harness/policies/gate.json#L187-L189}. The gate reads text: what it cannot see is listed in the section "Harness: known limits".

## Harness: terms

- **Task**: one piece of work, kept as a folder under `.workspace/sandbox/tasks/<name>/` with a state file `.task/task.json`. See the file 11 Task.
- **Kind**: what a task is and what "done" means: `qa`, `rca`, `design`, `dev`, `test`, `kb` (knowledge base update), `other`.
- **Tier**: which files a task folder has: `light` (`TASK.md`), `medium` (adds `REQ.md`, `REQ/`, `REF/`, `LOG.md`), `full` (adds `TODO.md`, `DEV/`, `TEST/`).
- **Session**: one Copilot chat. A session holds at most one task at a time.
- **Gate**: the hook module that allows, asks about or refuses each write and command before it runs.
- **Guardrail files**: the files that hold the code rules (engine, policies, hook configuration and others, listed in `gate.json`); the agent's edit tools and terminal writes that name them are refused there, except in a chat the person switched to admin mode, where only `.harness/runtime/**`, the policy's `admin_locked_paths` and the integrity-list folder stay closed. The text rules (`AGENTS.md`, `.github/instructions/`, skills) are not guardrail files.
- **Target repository**: a company code repository the harness may write back to, set in `target.override.json`.
- **Write-back (promote)**: copying the approved files from the task's `DEV/` to a new branch of each target repository, uncommitted.
- **Approval code**: the first six characters, in capitals, of a sha256 of what is approved; the person types it.
- **Board**: the page served by `harness task board` on this computer, with every task, what it waits for, and the buttons.
- **Independent check**: a review by the separate `reviewer` subagent, switched on by the person with `[review]=n`.
- **Autorun**: a mode of a task, switched on by the person, in which the agent works down `TODO.md` through the `worker` subagent without stopping, until a fact ends the run. See the file 20 Autorun.
- **Super agent**: the board's chat that only reads (1.8.3): it sums up what waits across tasks and proposes actions the person presses. See the file 21 Super agent.
- **Tool pack**: a company's package that lets the agent call an outside system (a database, a ticket board) under the gate's rules.

## Harness: common questions

**Q: What is this harness, in one sentence?** It wraps the Copilot agent in VS Code so that every tool call is checked by a hook, work is kept in task folders, and a person approves the plan and the write-back with a typed code and confirms the requirement the same way, although the requirement's confirmation is also a text line in `REQ.md` the agent can write {src:.harness/engine/hook.py#L1-L15} {src:.harness/engine/core/approval.py#L1-L8} {src:.harness/engine/modules/task/taskreview.py#L88-L110}.

**Q: Is the workflow driven by a skill or by code?** By both: the skill `harness-my-task` and the hook's next-step text tell the agent the order of work, and code holds the gates between stages: for the chat that holds the task, `DEV/` closed to the edit tools until the plan is approved; the plan refused while the "User confirmed" line of `REQ.md` is not filled in, when `REQ.md` has that line (the line is text the agent can write); the write-back refused without an approved dry run of the same digest {src:.github/skills/harness-my-task/SKILL.md#L75-L99} {src:.harness/engine/modules/gate/handler.py#L86-L90} {src:.harness/engine/modules/task/task.py#L443-L451} {src:.harness/engine/modules/task/task.py#L941-L944}. The file 11 Task has the detail.

**Q: How are dangerous commands blocked?** The gate reads each terminal command against `.harness/policies/gate.json` before it runs: guardrail writes, `.git` writes, person-only commands and a deny list (`rm -rf /`, `curl | sh`, `sudo`, `terraform apply` and more) are refused, git writes wait for the person's code, and a few risky commands are asked about {src:.harness/engine/modules/gate/handler.py#L117-L167} {src:.harness/policies/gate.json#L88-L182}. It reads text, so it stops mistakes, not an agent set on getting round it.

**Q: Is it safe to let the agent work on our code?** The harness itself writes a target repository only through a write-back the person approved, to a new uncommitted branch (a registered knowledge base gets one commit on its base branch); a git command the person approves with `approve-command` can also write there {src:.harness/engine/modules/task/task.py#L941-L944} {src:.harness/engine/modules/task/promote_target.py#L1-L14} {src:.harness/engine/modules/gate/handler.py#L153-L162}. The agent's edit tools are refused inside a target repository, and so is a terminal command that names a path there in full, or by a relative path after a `cd` in the same line, as a write target {src:.harness/engine/modules/gate/handler.py#L47-L52} {src:.harness/engine/modules/gate/policy.py#L149-L156} {src:.harness/engine/modules/gate/terminal.py#L65-L117}. A script or a path made at run time is not seen: the gate reads text and is not a sandbox; see the section "Harness: known limits".

**Q: What does a person still have to do?** Say what they want, confirm the requirement, approve the plan and the write-back with a code, approve git writes and held calls to outside systems, switch autorun on and answer its questions, commit the branch, and accept or close a task that changes no repository (the agent is told never to close one, and the gate refuses `task close` on its command line) {src:.harness/policies/gate.json#L131-L144}.

**Q: What does the agent do alone?** It asks questions, opens the task, writes the requirement, the plan and the code in the task folder, fetches files, runs the independent checks, runs the dry run and, once approved, the write-back {src:.harness/engine/core/tasks.py#L1-L8}. With autorun on, it works down `TODO.md` through the worker without stopping, until a fact ends the run {src:.harness/engine/modules/task/autorun.py#L1-L23}.

**Q: Can the board's super agent approve or change anything?** No. Its chat may only read: the gate refuses every write and every harness command but a few read-only ones, and its proposals are cards of the board's own buttons that do nothing until the person presses them {src:.harness/engine/modules/gate/superagent.py#L78-L89} {src:.harness/engine/modules/task/superact.py#L1-L7}.

**Q: Can the agent change the harness's own rules?** The code rules, not through its edit tools or named terminal writes, outside admin mode: the engine, the policies and the hook files are guardrail paths, and once the person has accepted them, a changed one makes the hook refuse every command and write until the person accepts or restores it {src:.harness/policies/gate.json#L4-L19} {src:.harness/engine/integrity.py#L18-L26}. The text rules are not protected: `AGENTS.md`, `.github/copilot-instructions.md`, `.github/instructions/`, `.github/skills/` and `.github/agents/` are neither guardrail paths nor in the integrity list {src:.harness/engine/core/guardrails.py#L11-L19}. Before the first accept there is no list and no integrity check {src:.harness/engine/integrity.py#L171-L183}.
