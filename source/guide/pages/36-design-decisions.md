## Design decisions: status of this file

Draft distilled from the author's private design notes; to be reviewed before publishing.

This file lists the decisions that shaped the harness, most far-reaching first. Each decision says the problem, the options that were weighed, what was chosen and why, what it costs or what was changed later, and where it lives in the code at version 1.8.3. A decision that was reversed says so and names what replaced it. Ideas that were never built are in the last section, "Design decisions: considered and not built". The harness's own summary of its design is `docs/05-design.md` {src:docs/05-design.md#L55-L129}.

## Design decisions: work is a task, and a task is a folder

**Problem.** A Copilot chat is compacted as it fills and is lost when it ends, so a new chat did not know how far a piece of work had got; results that change no repository (a root cause analysis, a design) had no place to live; and a person running several chats could not see which one waited. **Options.** Keep the state in the chat; keep a request sandbox per role (the design of 1.0); or make one folder per piece of work. **Chosen.** One task, one folder under `.workspace/sandbox/tasks/<task name>/`, holding the handover note `TASK.md`, the requirement, the plan, the results, and a state file `.task/task.json` that harness code writes and the agent's edit tools may not. Experienced users already worked one folder and one chat per job, with the plan and the design inside it. A session and a task are kept apart and point at each other, so either can end without the other {src:.harness/engine/core/tasks.py#L1-L37} {src:docs/05-design.md#L101-L109}.

**Cost and later changes.** The folder is a sandbox only as far as the gate's rules hold it, not an operating-system boundary {src:docs/05-design.md#L97}. The stage a task is in is never stored: it is worked out from the files and the state each time, so a task whose requirement changed falls back to the right stage by itself {src:.harness/engine/modules/task/taskstages.py#L1-L15}. **Where it lives now.** `core/tasks.py` (kinds, tiers, paths), `modules/task/` (the commands and the hook) and the rule in `AGENTS.md` that work is done in tasks; the agent is told to open a task, and the code does not force it to {src:AGENTS.md#L46-L47}.

## Design decisions: guard by consequence, not by a level picked up front

**Problem.** Version 1.0 made the person pick a level, L1 to L3, before every piece of work, and one level bundled the budget, the checks, the record and the roles. **Options.** Keep the levels; keep them but let them govern only how strict the checks are; or drop them and guard by facts. **Chosen.** No levels since 1.1. Work is split by two things: how much a mistake costs, which code judges from paths and commands (reading and writing the task folder pass; changing a target repository goes through `DEV/` and two approvals; git and production need the person), and the kind of task, which sets what "done" means and which files the folder gets. The reasons were measured: only L2 was used, and the three-role L3 was no better on tasks with a clear requirement at about 4.5 times the usage and 6 times the time {src:docs/05-design.md#L57-L75}.

**Cost and later changes.** A person can no longer turn one dial for "be careful here"; each lever is switched apart (checks, autorun, connections). The old marks `/l1`, `[L2]` and `[verify]` were retired with the levels. **Where it lives now.** The kinds (`qa`, `rca`, `design`, `dev`, `test`, `kb`, `other`) and the tiers that set the files (`light`, `medium`, `full`) are in `core/tasks.py` {src:.harness/engine/core/tasks.py#L19-L23}; the consequence rules are the gate's {src:.harness/engine/modules/gate/handler.py#L1-L13}.

## Design decisions: the gate is a hook, and only a refusal is a boundary

**Problem.** A rule written in a prompt is a request the model may ignore. Copilot's own confirmations only ask, and "Allow in this Session", Allow all and Autopilot skip them. **Options.** Trust the instructions; use Copilot's approval prompts; or refuse in a hook before the call runs. **Chosen.** One hook entry point for every event, which hands each event to the modules registered for it and merges their answers, a deny winning over an ask and an ask over an allow. Only a deny is treated as a boundary; an ask is a reminder {src:.harness/engine/hook.py#L1-L15} {src:.harness/engine/core/events.py#L77-L93}. The hook was built on recorded payloads of real sessions, which showed that a deny holds under Allow all and Autopilot.

**Cost and later changes.** A hook that times out lets the call through without a word, so the gate must stay fast; the timeout is 30 seconds and `doctor` reports the gate's recent times {src:.github/hooks/harness.json#L1-L24} {src:docs/05-design.md#L167-L174}. The ask list still exists for deleting files, network calls and installs, and it is only a reminder in a chat set to Allow all {src:.harness/policies/gate.json#L146-L182}. **Where it lives now.** `.github/hooks/harness.json`, `.harness/engine/hook.py` and `modules/gate/`.

## Design decisions: a guardrail that cannot decide does not pass

**Problem.** A hook runs before every tool call, so a bug in it can stop all work; but a gate that lets a call through when it fails is no gate. **Options.** Fail open (a failing module has no opinion), which the 1.1 design chose and wrote into `AGENTS.md`; or fail closed. **Chosen, reversing the first design.** Since 1.7.38 a guardrail that cannot decide refuses: when the engine cannot load, the gate module raises on a call, the session state or the registry cannot be read, or a guardrail file is not what the person accepted, the hook answers with the standard library alone and refuses every terminal command and every tool that may change a file, while reads stay allowed {src:.harness/engine/hook.py#L11-L15} {src:.harness/engine/hook.py#L297-L310}. Before the change, a call to an outside system ran because the gate read "cannot tell" as "not mine" {src:docs/12-guardrails-and-gate.md#L61-L63}.

**Cost.** A broken setting now stops work until a person repairs it; the agent is told not to repair it or go round it {src:AGENTS.md#L55-L59}. Only helpers (reminders, logs, what the board shows) still fail open, and a failing task module refuses only subagent calls {src:.harness/engine/hook.py#L55} {src:.harness/engine/core/failopen.py#L1-L16}. A call that names a program a tool pack governs is refused with its own words {src:.harness/engine/modules/gate/failclosed.py#L1-L8}. **Where it lives now.** `hook.py` (`fail_closed`, `emergency`) and `modules/gate/failclosed.py`.

## Design decisions: stop with code, teach with text, leave the keys to a person

**Problem.** Every rule can be put in one of several places, and each place promises something different. **Options.** The design notes named a ladder of four levels: S (semantic: instructions and skills, which the model may not follow), C (the harness command line, which checks preconditions on every path through it), H (a hook, which the platform enforces) and V (checking afterwards: `doctor`, evals, logs, which finds but cannot prevent). **Chosen.** Start every rule at S; move it to C or H when logs show repeated breaches, when a breach cannot be undone, or when it breaks another module's premise; prefer C to H where C is enough, because C holds on every runtime; and keep one sentence of text for every coded rule, so a refusal tells the agent why and what to do next {src:docs/05-design.md#L133-L137}. What cannot be taken back is left to a person.

**Cost.** The workflow is two things at once: the skill and the hook's next-step line tell the agent the order of work, and code holds the gates between the stages; an architect has to read both to know what is guaranteed. **Where it lives now.** The text in `AGENTS.md` and the skills, the code in the gate and the task commands; each module lists its levels in the registry (see the section "Design decisions: every module says how it is enforced and when it may retire") {src:AGENTS.md#L42-L64}.

## Design decisions: a person approves with a code bound to what is approved

**Problem.** Two moves must never be the agent's: starting to change code, and writing the change into a repository. A dialog in the chat cannot guard them, because "Allow in this Session" turns it off. **Options.** Copilot's approval prompts; a one-time token; or a person typing, in a real terminal, a code made from a hash of the thing approved. **Chosen.** Two approvals, the plan and the write-back, each needing a person at a terminal (stdin and stdout are a TTY) or the paired board, and a code that is the first six characters, in capitals, of the sha256 of what is approved; a file changed after it was read gets a new code. The gate also refuses the approval commands on the agent's command line {src:.harness/engine/core/approval.py#L1-L8} {src:.harness/engine/core/approval.py#L14-L58} {src:.harness/policies/gate.json#L131-L144}. The confirmation of the requirement was added in front of the plan, and the same person check and typed code cover recovering a repository and extending, waiving or dismissing checks; a git write and a held outside call get their codes from a separate mechanism, `core/approvals.py` (the file 14b Plans and approvals internals) {src:.harness/engine/core/approvals.py#L1-L10}.

**Cost and later changes.** The requirement's confirmation is a text line in `REQ.md`, which the agent's edit tools can write; the plan approval still needs the person {src:.harness/engine/modules/task/taskreview.py#L88-L110}. The first design allowed the terminal only; the board's paired browser runs the same functions (see the section "Design decisions: the board is a page on this computer, not a manager agent"), and the requirement's old code of eight small characters gave way to the same six capitals in 1.7.38. **Where it lives now.** `core/approval.py`; `task approve-promote` and `task promote` check that the dry run and the approval are of the same digest {src:.harness/engine/modules/task/task.py#L941-L944} {src:.harness/engine/modules/task/task.py#L984-L1024}.

## Design decisions: the agent writes the requirement, and the person's words are not the requirement

**Problem.** An independent check and a new chat both need the requirement in writing. **Options.** A hook records the person's prompts and the command line saves them as the requirement (built in a first version of 1.1 and removed the same day, before release); or the agent writes its understanding and the person confirms it. **Chosen.** The agent writes `REQ.md` from the conversation and asks the person to confirm; when the requirement changes, the agent changes `REQ.md` first and notes the change; the person's own documents go into `REQ/`, which the agent may only read. A prompt leaves things out, and the requirement moves over several turns: the exact words are not the requirement, and storing them repeats what is already in the context {src:docs/05-design.md#L105-L109}.

**Cost.** The requirement is the agent's reading of the person, so its quality depends on the person reading it before confirming. The prompts are still kept, as a record rather than as the requirement: the task page shows up to 300 characters of each, and when a task closes its chat (the prompts and the agent's text, no thinking and no tool results) is saved in `.task/transcript.jsonl`, deleted 30 days after the task is archived {src:.harness/engine/modules/task/chatrounds.py#L1-L9} {src:.harness/engine/modules/task/taskarchive.py#L157-L161} {src:.harness/policies/task.json#L14-L24}. **Where it lives now.** The template `contracts/templates/task/en/REQ.md` with its "User confirmed" line {src:.harness/contracts/templates/task/en/REQ.md#L1-L42}, `task confirm-req` {src:.harness/engine/modules/task/task.py#L570-L612}, and the gate's refusal of the agent's edit tools in `REQ/`, `REF/` and `INBOX/` {src:docs/05-design.md#L208-L210}.

## Design decisions: changes are made on copies in DEV/ and written back to an uncommitted branch

**Problem.** The agent must never change a target repository directly, and target repositories can be large and may not run on a local machine. **Options.** Let the agent edit the working tree under a gate; copy the repository; or fetch only the files a plan changes into the task and write them back on approval. **Chosen.** `task fetch` copies the files to change, with their base version, into `DEV/<repository>/<path>`; the agent changes them there; `task promote --dry-run` makes the exact write-back; after the person's approval `task promote` writes the files onto a new branch of each repository and never commits, resets or switches branch: the person reviews and commits. Push and pull requests are always left to a person {src:.harness/engine/modules/task/promote_target.py#L1-L14} {src:docs/05-design.md#L200-L202}. The harness only brings the local base branch up to date: at the first fetch of a round and at every dry run it runs `git fetch` and moves the base branch forward when that is a fast-forward, and stops on local changes or a diverged branch {src:.harness/engine/modules/task/basesync.py#L1-L14}.

**Cost and later changes.** A failure halfway is not undone across repositories: the task is marked `partial` and the message gives the commands to put each repository back. A registered knowledge base is the one exception: it has one keeper, so its files are committed once on its base branch {src:.harness/engine/core/targets.py#L1-L10}. `task fetch --read` (1.7.42) copies code to read into `READ/`, never written back. **Where it lives now.** `modules/task/task.py` (fetch, dry run, promote) and `promote_target.py`; the gate refuses the agent's edit tools inside a target repository {src:.harness/engine/modules/gate/handler.py#L47-L52}.

## Design decisions: the gate guards writes, not reads

**Problem.** Every stop of the gate costs the agent time when it is wrong, and a mistake costs differently by kind of call: a read changes nothing, a write or a command can change a file, a repository or an outside system. **Options.** Judge reads and writes alike; or judge only what changes something, by what a mistake costs. **Chosen.** The gate guards writes and dangerous commands and never blocks a read of skills, instructions, the knowledge base or code. The design document sorts work by the cost of a mistake and puts read-only work in the row "Not stopped"; it also says that hurting normal work costs more than missing a stop, in its section on a hook that fails itself {src:docs/05-design.md#L69-L74} {src:docs/05-design.md#L165}. No document in the harness gives one sentence of reasoning for reads, so this reason is the Guide's reading of those two passages. The code only goes further for edit, create and terminal calls, and a write tool whose target the gate cannot read is refused, because the gate cannot tell what it would change {src:.harness/engine/modules/gate/handler.py#L787-L788} {src:.harness/engine/modules/gate/handler.py#L1-L13}.

**Cost and exceptions.** The reads the gate does refuse are of the person's secrets: the secrets file and printing a secret variable {src:.harness/engine/modules/gate/handler.py#L633-L650}. Since 1.8.3 a super agent chat and a question turn are kept to reading, the reverse case (see the section "Design decisions: the super agent only reads, and its proposals are the board's buttons"). **Where it lives now.** `modules/gate/handler.py`.

## Design decisions: one independent reviewer, role teams cut, handover by files

**Problem.** Splitting work across agents looked like a way to share a large task's context. Version 1.0 had an orchestrator, a builder, a reviewer and a verifier; a manager agent was planned to watch all tasks. **Options.** Keep role teams; or keep only the agents that buy something one agent cannot. **Chosen.** Splitting work has no value in itself: the dispatcher learned the task and did not do it, and the builder learned it again. A second agent is worth it only for an independent view, parallel reading, or a fresh context. The reviewer stays because it has not seen the author's reasoning and reads only the requirement, the work and the diff; its tools are read, search and execute, and it is told in text, not kept by its tool list, not to change anything. Agents do not pass messages: they read and write the files of the task, which a person can read too {src:docs/05-design.md#L111-L119} {src:.github/agents/reviewer.agent.md#L1-L12}.

**Cost and later changes.** The orchestrator and builder were deleted in 1.1, the verifier was merged into the reviewer, and the manager became the board. Later two subagents were added on the same test: the read-only `mapper` (parallel reading, only after the person types `/generic-mapreduce`, at most 4 in 60 minutes) and the `worker` (1.8.0, a fresh context per autorun step) {src:.harness/engine/modules/task/mapreduce.py#L1-L10} {src:.github/agents/worker.agent.md#L1-L12}. **Where it lives now.** The task hook decides every subagent call in code: none in admin mode; the `mapper` only within the calls a typed `/generic-mapreduce` granted (the one subagent that needs no task); otherwise only in a session that holds an open task, the `reviewer` only while a check round is open, the `worker` only while autorun is on; every other subagent is refused {src:.harness/engine/modules/task/handler.py#L278-L300} {src:.harness/engine/modules/task/handler.py#L316-L325} {src:.harness/engine/modules/task/mapreduce.py#L75-L83}. The person switches each one on: checks with `[review]=n`, autorun, `/generic-mapreduce` {src:AGENTS.md#L52-L53}. Only the command line writes a task's `REVIEW/` folder, where the hook stores the reviewer's verdict {src:.harness/policies/gate.json#L24-L34}.

## Design decisions: work it out from the files each time instead of storing state

**Problem.** A stored status goes stale when something it depends on changes, and someone has to remember to reset it. **Chosen.** What can be read from the files is worked out each time: a task's stage, from its files and state, so a task whose requirement changed falls back to the right stage by itself {src:.harness/engine/modules/task/taskstages.py#L1-L4}; the passes of the independent checks, counted from the rounds and the digest of the work as it is now {src:.harness/engine/modules/task/taskreview.py#L21-L22}; an approval, bound by its code to a sha256 of what was approved, so a plan counts as approved only while the plan and the requirement are what the person approved {src:.harness/engine/core/approval.py#L1-L8} {src:.harness/engine/core/tasks.py#L157-L162}; where the knowledge base build stands, from the files, never from what an agent remembers {src:.harness/engine/core/kbstatus.py#L1-L4}. The same care keeps the hook safe: everything its emergency answer needs is in `hook.py`, with the standard library only, so a broken engine cannot stop it from refusing {src:.harness/engine/hook.py#L11-L15}. **Cost.** Some marks are still stored in `task.json`, such as whether a task waits for the person, which the hook clears when the person answers {src:.harness/engine/modules/task/handler.py#L262-L263}; and the board, which re-reads files every few seconds, keeps what it worked out until a file changes {src:.harness/engine/modules/task/health.py#L13-L14}.

## Design decisions: checks are counted by code, and only the person sets how many

**Problem.** A check the agent says it ran is not a check, and an agent that checks more by itself spends the person's money. **Options.** "At most n checks, stop at the first pass"; checks switched on by task kind; or the person sets n and code counts passes. **Chosen.** The person sets n (`[review]=n` in a prompt, or the task page); the work must pass n checks in a row, each by a new reviewer, all on the work as it is now, counted again from the records and the sha256 of the work, so a change resets the count. A `task promote --dry-run` is refused until the passes are there or the person waives them. Checks are limited to n plus 2 extra before the person must allow more {src:.harness/engine/modules/task/taskreview.py#L1-L21} {src:.harness/policies/task.json#L9-L12} {src:docs/05-design.md#L121-L129}.

**Cost.** A reviewer may judge wrong; a failure with no valid finding is given back up to a limit, and the person can dismiss a check. Whether the reviewer itself judges well has not been measured (see the last section). **Where it lives now.** `modules/task/taskreview.py`, `reviewcheck.py` and the hook, which stores the reviewer's answer as `REVIEW/round-NNN/verdict.md`.

## Design decisions: count budgets were cut, and spend limits came back only where nobody watches

**Problem.** Cost control. Version 1.0 capped searches and tool calls per level. **Options.** Count caps; a spend budget on every task; or no cap. **Chosen in 1.1.** No count caps: the model regulates itself, a cap stopped it on simple tasks, and money is saved by choosing the model {src:docs/05-design.md#L220-L222}. **Later change.** Where no person is watching, a cap on spend came back, in Credits as Copilot records them: an autorun run stops at the spend limit the person picks when switching it on, counting the subagents' spend too (1.8.0); the super agent chat stops at 50 Credits a day by default (1.8.3) {src:.harness/engine/modules/task/autorun_spend.py#L1-L5} {src:.harness/engine/modules/task/superbrain.py#L13-L14}.

**Cost.** A task a person drives by hand has no budget; the board's health tag warns when a task's Credits run far above the median of its kind. **Where it lives now.** `.harness/policies/task.json` (`super.daily_credits`; the run's own limit is in `.task/autorun.json`) {src:.harness/policies/task.json#L21-L37}.

## Design decisions: the board is a page on this computer, not a manager agent

**Problem.** A person runs a few tasks at once and must see which one waits. **Options.** A manager agent, read-only or dispatching; a thin VS Code extension; a `task list --watch` terminal; or a web page served on the person's computer. **Chosen.** No manager agent: a Copilot agent runs only when someone sends a message, so it cannot watch; a read-only one only retells a table and can retell it wrong; a dispatching one cannot work, as a subagent has no state and cannot ask back {src:docs/05-design.md#L119-L119}. What a task waits for is told by code, from facts {src:.harness/engine/modules/task/tasklife.py#L276-L282}. The board, started by a person with `harness task board`, listens on 127.0.0.1 only, checks Host and Origin, needs a header on every POST, and pairs one browser: a random one-time code, kept in memory, traded for a session cookie {src:.harness/engine/modules/task/boardserve.py#L1-L17}.

**Cost and later changes.** The 1.1 notes had ruled out a board; it came with 1.5 and 1.6, and approvals moved onto it, each with the same preview and code as the terminal. Its Terminal window counts as the person for commands that ask no code (1.7.39) {src:.harness/engine/core/boardperson.py#L1-L10}; **▶ Run** and that window run commands the gate does not see. **Where it lives now.** `modules/task/boardserve.py` and the gate's refusal of an agent's request to the board's port.

## Design decisions: the board drives the VS Code chats, and only a person triggers it

**Problem.** After an approval the person had to go back to the right chat and type "go on". **Options.** Leave it to the person; or have the board talk to the chats. **Chosen.** Since 1.6 the board talks to VS Code's own agent host (WebSocket and JSON-RPC, standard library only); the connection token stays in memory and is never logged. Every action is a paired POST with fixed text; a message goes out only when the chat is bound to the task for sure, and otherwise the board gives the text to copy {src:.harness/engine/core/ahp.py#L1-L14} {src:docs/05-design.md#L184-L192}.

**Cost and later changes.** Chats the board makes start with Allow all, so the gate is the only brake there {src:docs/05-design.md#L191}. The one exception to "only a person triggers it" is autorun: once a person has switched it on, the board wakes the agent, compacts the chat at 70% of its window and retries after errors {src:.harness/engine/modules/task/autorun_relay.py#L1-L12}. **Where it lives now.** `core/ahp.py`, `modules/task/vslink.py`, `chatlink.py` and `chatsend.py`.

## Design decisions: autorun is a mode, with a scheduler and a worker per step

**Problem.** Long, well-planned work should run while the person is away, and one chat fills up over many steps. **Options.** A thin orchestrator agent (rejected in 1.1: the dispatcher does not know the task); the default agent doing every step and the Stop hook pushing it on (the first autorun); or the task's own agent calling a subagent per step. **Chosen in 1.8.0, replacing the first autorun.** Autorun is a mode of a task that only a person switches on, once the plan is approved and checks are on. The default agent only schedules and keeps `TODO.md`, `TASK.md`, `LOG.md` and `QUESTIONS.md`; the `worker` does one step in a fresh context; a step that needs an answer is parked and asked at the end; nothing is written back on the way. Code, not a model, says when the run stops: done, plan changed, checks ran out, budget, steps, time (480 minutes), stalled, error, agent or person {src:.harness/engine/modules/task/autorun.py#L1-L23} {src:.harness/engine/modules/gate/handler.py#L97-L109}.

**Cost.** A run spends unattended up to its limit; the person reads the questions and one diff at the end. The Stop hook and the board relay are second and third layers when the agent stops early. **Where it lives now.** `modules/task/autorun.py` and its `autorun_*` files; the run's record is written by code to `.task/autorun-run.jsonl`, because `LOG.md` is written by the agent.

## Design decisions: the super agent only reads, and its proposals are the board's buttons

**Problem.** With many tasks, the person wants one place to see what waits and to ask in words. **Options.** The manager agent rejected in 1.1; or a chat that talks but cannot act. **Chosen (1.8.1 to 1.8.3).** The board's Super agent view lists what waits from code alone; behind it, one chat a day with a cheap model gets a short digest written by code and answers questions. The gate keeps that chat to reading, searching and a fixed list of read-only harness commands, knowing the chat by its first message `/harness-super`. The agent never acts: an answer may end with a block that the board turns into cards of its own buttons, checked against the board's rows, which act only when the person presses them, with a code where the board asks for one {src:.harness/engine/modules/gate/superagent.py#L1-L31} {src:.harness/engine/modules/task/superact.py#L1-L7} {src:.harness/engine/modules/task/superbrain.py#L1-L13}.

**Cost.** The chat costs Credits, capped per day, and a proposal is only as good as the digest. **Where it lives now.** `modules/task/super*.py`, `modules/gate/superagent.py` and `.github/agents/super.agent.md`.

## Design decisions: the knowledge base and the company's content live outside the harness

**Problem.** Agents need business knowledge, but a shared harness must stay free of any one team's knowledge, and an upgrade must not collide with a team's changes. **Options.** Ship knowledge with the harness; serve it through an MCP server or retrieval; or let the team bring its own repository. **Chosen.** The harness ships `knowledge-base/` empty and does general things only {src:AGENTS.md#L9-L15}. The team's knowledge base is a git repository of its own, read by an index first, registered as a target with `knowledge_base: true` {src:.harness/engine/core/targets.py#L1-L10}. Its `company/` folder carries the team's skills, instructions, connections, standards and tool packs: `company sync` copies the first three into place, and the rest are read where they lie; settings layer as the shipped policy, then `*.company.json`, then the person's `*.override.json` {src:.harness/engine/core/company.py#L1-L16} {src:.harness/engine/core/config.py#L1-L6}.

**Cost.** Without a knowledge base the agent reads code and answers worse. Updating the knowledge base from a git folder runs `git fetch` and `merge --ff-only` once the person agrees to the list of changes {src:.harness/engine/core/company.py#L750-L798}. The harness records which knowledge base files each call read, never their content {src:.harness/engine/core/kbreads.py#L1-L9}. **Where it lives now.** `core/targets.py`, `core/company.py`, the `kb` commands and `knowledgebase.instructions.md`.

## Design decisions: outside systems go through tool packs, connections and a pass list

**Problem.** Agents began to call databases, ticket boards and pipelines from the terminal. VS Code already has the tools and the dialogs; it does not know what a call does, in which environment, or for which task. **Options.** Build an MCP server per system; list dangerous commands; or one protocol that turns every call into an action `{system, env, verb, target}`. **Chosen.** One protocol; the company lists its systems. A call to a listed system that no rule names counts as a write, and an environment no rule names counts as prod; by default a read passes, a write waits in the outbox for the person's code, a run is the person's, a destroy is refused, and on prod only a read passes. The gate says what may pass rather than chasing what to stop {src:.harness/engine/modules/gate/external.py#L1-L15} {src:.harness/engine/core/systems.py#L36-L38} {src:.harness/engine/core/outbox.py#L1-L8} {src:docs/12-guardrails-and-gate.md#L19-L23}.

**Later changes.** A tool pack (1.7.12) bundles a system's program, connection types, rules and skills; connections (1.7.17) hold the fields, and identities stay in `.harness/.env`, which the gate refuses the agent {src:.harness/engine/core/connections.py#L1-L12}. The first protocol shipped no system; since 1.7.30 a few factory packs ship as samples and the company turns them on {src:.harness/engine/core/toolpacks.py#L1-L24}. **Where it lives now.** `modules/gate/external.py`, `core/toolpacks.py`, `core/connections.py`.

## Design decisions: cost comes from Copilot's own records

**Problem.** A hook does not see tokens or Credits, and what an agent says it spent is not a record. **Options.** Count in the hook; read Copilot's OpenTelemetry export (the 1.1 decision); or read Copilot's session record. **Chosen.** For cost, the report reads Copilot's own `events.jsonl` of each session and takes numbers, times and names only, never a tool argument or a result (the Live tab and a task's saved chat read the prompts and the agent's text from the same file); the format is undocumented, so the reader never raises and falls back to the hook log {src:.harness/engine/core/copilot_events.py#L1-L11}. The harness holds no prices: Credits are shown as Copilot records them.

**Cost and later changes.** The OpenTelemetry plan was not built; the session record replaced it. A change in Copilot's file format can blank the numbers until the reader is fixed. **Where it lives now.** `core/copilot_events.py`, the task report and Agent Performance Review; the switch is `report.copilot_events` in `policies/task.json` {src:.harness/policies/task.json#L21-L31}.

## Design decisions: guardrail files are checked against what the person accepted

**Problem.** The rules live in files on the same disk the agent writes. **Options.** Path rules only; or path rules plus a check that the files are as the person accepted them. **Chosen.** Outside admin mode the gate refuses the engine, policies and hook files to the edit tools and to named terminal writes. Since 1.7.38 the files are also listed with size, time and SHA-256 when the person accepts them, the list kept in the person's home, and the hook refuses commands and writes while one differs {src:.harness/engine/integrity.py#L1-L9}. Extending the harness needs admin mode, a switch the person sets per session: the hook does not carry the main agent's name, so rights follow the session, not the agent {src:docs/05-design.md#L194-L198}.

**Cost.** A process of the same user can change the list as well; this stops slips and plain tampering, not a determined agent. The text rules (`AGENTS.md`, skills) are not in the list. **Where it lives now.** `integrity.py`, `core/guardrails.py`, `admin on` in `modules/gate/commands.py` {src:.harness/engine/modules/gate/commands.py#L1-L9}.

## Design decisions: locks belong to the operating system

**Problem.** The hook, the command line and the board write the same session and task state. A lock older than 5 seconds used to be taken over, and on a slow computer (one whose antivirus scans every file read) two writers then got in at once. **Options.** A lock file with a timestamp; or a lock the operating system holds for the process. **Chosen in 1.8.1.** An operating-system lock on a file in the system's temp folder, named by a hash of the locked path; it is freed when the holding process ends and a slow holder is never taken over; a call waits up to 20 seconds {src:.harness/engine/core/state.py#L25-L30} {src:.harness/engine/core/state.py#L170-L174}.

**Cost.** A hook call that cannot get its lock in 20 seconds cannot decide, so it is refused with a message that the harness is busy {src:.harness/engine/hook.py#L297-L310}. **Where it lives now.** `core/state.py`.

## Design decisions: one platform, measured, behind an adapter

**Problem.** Agent platforms change monthly, and a hook that guesses tool names guards nothing. **Options.** Support several runtimes; or one. **Chosen.** Only Copilot (SDK) sessions in VS Code; Local sessions, Claude and Codex sessions are not supported, and `copilot -p` runs no repository hooks {src:docs/05-design.md#L155-L161}. Hook logic is written against recorded payloads kept as test fixtures, and the differences of the runtime stay in one adapter {src:.harness/engine/adapters/copilot_vscode.py#L1-L8}. Beyond the hooks themselves, which VS Code still marks Preview, features are not built on preview or experimental settings (per-agent hooks, `context: fork`) {src:.github/skills/harness-vscode-updates/SKILL.md#L52}.

**Cost.** A tool name not recorded in `tool_kinds.json` gets the kind `other` and no write check. **Where it lives now.** `.harness/engine/adapters/` and `.harness/eval/fixtures/hooks/`.

## Design decisions: every module says how it is enforced and when it may retire

**Problem.** Rules written to make up for a weaker model become a burden once the model improves, and nobody remembers why a rule exists. **Options.** Add features freely; or admit each against fixed questions. **Chosen.** A new design must say what failure it prevents, which platform fact it depends on, which enforcement level is enough and why a lower one is not, where it belongs, and when it can be removed. The registry records, for each module (`task`, `gate`, `observe`, `evalcheck`), its events, its enforcement levels and a `retire_when` sentence; the limits a team may tune (checks, the mapper, autorun, the super agent's daily spend) are in `policies/task.json`, not in skills {src:.harness/registry.json#L91-L106} {src:.harness/registry.json#L220} {src:.harness/registry.json#L285} {src:.harness/policies/task.json#L9-L39}. The layers that tell a model how to work are expected to age first; the gates, the approvals and the write-back are not.

**Cost.** The admission questions are a habit of the project, not code. **Where it lives now.** `.harness/registry.json`; a rule has one main source, and other files link to it {src:AGENTS.md#L36-L40}.

## Design decisions: considered and not built

- **A cheap judging model in the hook** for classification, routing and escalation: those judgments are made by code or are not allowed by the platform; the ladder "code first, a cheap model only for frequent judgments code cannot make, the main model last" stays.
- **Changing the model or reasoning effort during a task**: a hook cannot; the person picks the model, and the board sends one with its messages.
- **An MCP server or vector search over the knowledge base**: an index and instructions to read by it were enough, and managed computers may block self-built MCP servers.
- **Operating-system isolation** (a container): outside the harness's scope {src:docs/05-design.md#L223}.
- **Several agents writing the same files in parallel**, and agents messaging each other: merges hide decisions, and the repositories cannot be run to check the result; the mapper reads only.
- **Measuring the reviewer** on labelled samples and running each eval several times: listed as gaps; a numbers-only record of closed tasks exists, a benchmark does not {src:.harness/engine/core/evalrecord.py#L1-L14}.
- **A goal as a parent of tasks**: `/generic-goal-driven` keeps files only, with no commands {src:docs/05-design.md#L212-L218}.
- **A tool pack program that asks the harness before each write**: the docs name it as the next step {src:docs/12-guardrails-and-gate.md#L179-L184}.
