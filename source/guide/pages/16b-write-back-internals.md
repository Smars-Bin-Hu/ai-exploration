This file holds the code-level detail behind the feature file 16 Write-back: how target repositories are registered and what fetch, `task diff`, the dry run, `task promote`, `task recover`, `task queue` and the commit message do in the code of harness 1.8.3, which checks run in which order and what happens when one fails. It is for "how does it work" and "where in the code" questions. The code is in `.harness/engine/modules/task/` (`task.py`, `promote_target.py`, `basesync.py`, `common.py`, `taskqueue.py`, `commitmsg.py`) and `.harness/engine/core/targets.py`.

## Write-back internals: what a target repository is and how it is registered

A target repository is a git repository outside the harness folder that a task reads from and writes back into. It is described by the policy `target.json` (`core/targets.py`) with the keys `repos_root`, `repos`, `base_ref`, `refused_paths` and `git_timeout_seconds`; the schema requires the first four and allows no other top-level key {src:.harness/engine/core/targets.py#L1-L13} {src:.harness/engine/core/targets.py#L36-L54}. The shipped file has `repos_root` empty, `repos` empty, `base_ref` `main`, `refused_paths` `[".git/**"]` and `git_timeout_seconds` 30 {src:.harness/policies/target.json#L1-L9}. With `repos_root` and `repos` both empty, `Targets.configured` is false: there is no target repository, a task is created without `target_mode`, and `task fetch` stops with "no target repositories" {src:.harness/engine/core/targets.py#L139} {src:.harness/engine/modules/task/common.py#L174-L178}.

## Write-back internals: repos_root, repos.<name> and base_ref

`repos_root` is a folder; `targets.load` makes each of its direct subfolders a target when the name matches `^[A-Za-z0-9][A-Za-z0-9_.-]*$` and the folder has a `.git` entry. The target is named after the folder and takes the global `base_ref` and `refused_paths`; a `repos_root` that is not a folder is listed as a problem, not raised {src:.harness/engine/core/targets.py#L29} {src:.harness/engine/core/targets.py#L116-L124}.

`repos` maps a name to an entry with the optional keys `path`, `base_ref`, `refused_paths` and `knowledge_base`, and no others. An entry with a `path` registers a repository elsewhere: a relative path is taken from the harness folder, and a path that is not a git repository is listed as a problem and skipped. An entry with no `path` holds settings for a repository `repos_root` already found; for a name not found it is a problem ("no path"). The entry's `base_ref` and `refused_paths` replace the global values for that repository only. A name in `repos` must match the same pattern, or `validate_policy` raises {src:.harness/engine/core/targets.py#L86-L95} {src:.harness/engine/core/targets.py#L125-L138}. Problems found while loading are kept in `Targets.problems`, which `harness doctor` lists; the repository is then not a target {src:.harness/engine/doctor.py#L833-L836}.

`base_ref` is the branch a task reads files from and a write-back branches from (default `main`). It must exist in the local repository: `ref_commit` returns an empty string for a missing branch, the first fetch then stops with "no such branch" and a dry run lists "no branch" as a problem. The harness reads the local branch, not the remote one {src:.harness/engine/core/targets.py#L362-L365} {src:.harness/engine/modules/task/common.py#L195-L199} {src:.harness/engine/modules/task/promote_target.py#L154-L157}.

## Write-back internals: refused_paths and where each place enforces it

`refused_paths` are git-style globs relative to a repository (`repo_paths.glob_regex`; an unusable glob makes the policy invalid). A repository's own list replaces the global list; it does not add to it {src:.harness/engine/core/targets.py#L91-L95} {src:.harness/engine/core/targets.py#L137}. Three places enforce them:

- **Promote.** `plan_files` checks every file against the code constant `ALWAYS_REFUSED` (`.git/**`) plus the repository's list, so `.git/**` is refused in a write-back whatever the configured list says {src:.harness/engine/modules/task/promote_target.py#L35} {src:.harness/engine/modules/task/promote_target.py#L176-L179}.
- **Fetch and delete.** `check_target_output` tests only the repository's own list, not the constant, and refuses the fetch or delete of a matching path {src:.harness/engine/modules/task/common.py#L242-L250}.
- **The gate.** The gate turns each repository's list (without `.git/**`) into patterns for the agent's edit tools and for terminal commands that name an absolute path in the repository; a write into any `.git` folder is refused by its own rule. These gate rules exist only when target repositories are configured {src:.harness/engine/modules/gate/policy.py#L135-L148} {src:.harness/engine/modules/gate/policy.py#L186-L193}.

## Write-back internals: layers of the target policy and the setup form

A policy is read in layers: the shipped `target.json`, then `target.company.json` (the company pack), then the person's `target.override.json`, which wins. Objects merge key by key, any other value in an override replaces the default (an array is replaced as a whole), and a key written `"<key>+"` appends to the default array {src:.harness/engine/core/config.py#L1-L5} {src:.harness/engine/core/config.py#L98-L110}.

The **Get ready** form on the board writes the person's layer through `setup.steps`: `repos_root`, one `repos` entry with a `path` for each single repository outside the folder, and a `refused_paths` list for every repository that has rules, always starting with `.git/**`. When a repository's checked-out branch is not the common `base_ref` and the common branch does not exist there, it writes that repository's own `base_ref`. It does not write `knowledge_base`: an entry that has it is kept as it is, and the flag is set by hand in `target.override.json` {src:.harness/engine/core/setup.py#L204-L206} {src:.harness/engine/core/setup.py#L399-L437}.

## Write-back internals: task fetch, what it reads and why it uses git

`harness task fetch <repository>/<path>...` (`task.fetch`, then `common.copy_from_target`) brings files into the task as the committed base branch has them, never from the working tree. It lists files with `git ls-tree -r -z <commit> -- <path>` and reads each with `git cat-file blob <blob>`, so the bytes are exactly what git stores, with no line-ending conversion {src:.harness/engine/modules/task/common.py#L164-L239} {src:.harness/engine/core/targets.py#L270-L288}. A dirty working tree, uncommitted work or another checked-out branch of the person therefore cannot leak into the task. A spec is a file or a folder (every tracked file under it); one call takes at most `fetch.max_files` files (200) {src:.harness/engine/modules/task/common.py#L215-L216} {src:.harness/policies/task.json#L4-L6}. Only regular files (git mode `100644` or `100755`) are fetched: a symlink or submodule found in a folder spec is skipped, and one named exactly is an error {src:.harness/engine/modules/task/common.py#L203-L214}.

The first read of a repository in a round fixes its commit: `copy_from_target` looks in `data["targets"]` of `.task/task.json`; when the repository is not there it runs the base sync, reads the commit of `base_ref` and stores `{path, base_ref, base_commit}`. Every later fetch, `--read` included, uses that `base_commit`, so every read in the round shows the same lines {src:.harness/engine/modules/task/common.py#L179-L202}. A new round clears `targets`, so the next round pins again {src:.harness/engine/modules/task/task.py#L251}. `task fetch <file> --rebase` pins again, once per repository in the call, and takes the file as the base branch has it now, dropping what was changed in `DEV/` {src:.harness/engine/modules/task/task.py#L629}. An error of the base sync is raised before the commit is stored, so no `base_commit` is recorded and nothing is copied {src:.harness/engine/modules/task/common.py#L190-L197}.

Each fetched file is written to `.task/base/<repository>/<path>` (the base copy, written only by the command line), recorded as `{blob, base_commit}` under `<repository>/<path>` in `target_files`, and copied to `DEV/<repository>/<path>`. When that file already exists in `DEV/` and differs from the base copy, it is kept and listed under `kept`, unless `--overwrite` or `--rebase` was given; fetching a file also removes it from `deletes` {src:.harness/engine/modules/task/task.py#L646-L659} {src:.harness/engine/modules/task/common.py#L217-L239}. A fetch that fetched or kept something turns a `dry_run` promote state back to `none`, which drops the plan digest and its approval. Preconditions, under the task lock: the task is open, its plan is approved, and the promote state is neither `done` nor `partial` {src:.harness/engine/modules/task/task.py#L635-L639}. `--read` needs no plan, copies to `READ/` and does not record `target_files`, so promote never sees it; `_manual/` fetch (`--from`) reads no repository {src:.harness/engine/modules/task/task.py#L676-L741}.

## Write-back internals: basesync, how the base branch is brought up to its remote

`basesync.sync` brings the local base branch up to the remote before a read, by fast-forward only. It runs at the first read of a repository in a round (a fetch, `--read` included) and at every `promote --dry-run`; the real `promote` and `approve-promote` do not run it {src:.harness/engine/modules/task/basesync.py#L1-L15} {src:.harness/engine/modules/task/common.py#L191-L194} {src:.harness/engine/modules/task/task.py#L925} {src:.harness/engine/modules/task/task.py#L994}. In order:

1. **Which remote.** The remote of the base branch's upstream when it exists, else `origin`, else the only remote, else none. With none, nothing is done {src:.harness/engine/modules/task/basesync.py#L32-L40}.
2. **Fetch.** `git fetch --quiet <remote> <base_ref>` with the timeout `max(git_timeout_seconds, 120)`. When it fails (offline, no access) the state is `offline`, a note says so and the local branch is used: not a stop, so a stale `main` is possible {src:.harness/engine/modules/task/basesync.py#L25} {src:.harness/engine/modules/task/basesync.py#L56-L61}.
3. **Compare the commits.** Equal: `current`. The remote commit is an ancestor of the local one: `ahead`, the local branch is left alone with a note. Neither is an ancestor of the other: it stops with `sync.diverged` {src:.harness/engine/modules/task/basesync.py#L62-L71}.
4. **Move forward, only when the local branch is an ancestor of the remote one.** If the base branch is checked out it must be clean (untracked files count) or it stops with `sync.dirty`, then `git merge --ff-only`. If it is not checked out (another branch, detached HEAD) the code runs `git update-ref refs/heads/<base_ref> <new> <old>`, a compare-and-swap on the old value that leaves the working tree alone. A failing merge or `update-ref`, including one lost to a concurrent move, stops it with `sync.failed` {src:.harness/engine/modules/task/basesync.py#L72-L81}.

A stop is a `CommandError` and moves nothing. In a fetch it aborts the call with no `base_commit` recorded; in a dry run it becomes a problem of that repository, so the plan is refused and that repository's files are not checked {src:.harness/engine/modules/task/promote_target.py#L147-L152}. The code decides to stop; what to do about a dirty or diverged branch is the person's.

## Write-back internals: task diff and CHANGES.diff

`harness task diff` is a real command (`task.diff`): it writes `<task>/CHANGES.diff`, overwriting it each time, by comparing the files in `DEV/` with the base copies in `.task/base/` made at fetch time. It contacts no git or repository and takes no lock {src:.harness/engine/modules/task/task.py#L828-L838} {src:.harness/engine/modules/task/commands.py#L270}. `changes` walks `DEV/` (skipping `.git`, `node_modules`, the top-level `_deleted/` and `*.patch`) and writes a header line with the task and round, then per changed file `diff --git a/<key> b/<key>` and a unified diff with 3 lines of context. A new file is shown against `/dev/null` with every line as `+`; a non-UTF-8 file gets a "binary" note; a file marked with `task delete` is shown as `deleted file` with every base line as `-`; unchanged files are left out {src:.harness/engine/modules/task/task.py#L771-L825}.

The agent gets back a summary, not the diff: `files` (path, action, added, removed, changed files only), `unchanged` (a count), `diff_file` and a `next` hint that the reviewer can read the file with `REQ/` and `PLAN.md` {src:.harness/engine/modules/task/task.py#L835-L838}. `CHANGES.diff`, `CHANGES_r*.diff` and `PROMOTE-PLAN.diff` are in `cli_owned_paths` of `gate.json`: the agent's edit tools and terminal writes are refused there {src:.harness/policies/gate.json#L24-L34}. When a promoted task is opened again, `keep_diff` saves the round's diff as `CHANGES_r<n>.diff` before the base copies are deleted {src:.harness/engine/modules/task/task.py#L221-L231}. `CHANGES.diff` compares with the fetched copies; `PROMOTE-PLAN.diff` compares with what the base branch holds at the dry run.

## Write-back internals: the dry run, its preconditions and what the agent gets back

`harness task promote --dry-run` (`task.run_promote`) runs under the task lock and refuses in this order: the task is not open; the task's own plan is not approved (`require_plan`: the approval of the plan before the work, not of the write-back, which comes after the dry run); the promote state is `done` or `partial` (it names the recover command); the independent checks the person switched on are not satisfied (`taskreview.require`) {src:.harness/engine/modules/task/task.py#L911-L925} {src:.harness/engine/modules/task/taskreview.py#L563-L568}. Then `make_plan` builds the plan with the base sync on. It sorts `DEV/`: files directly in `DEV/` belong to no repository and are listed as `not_promoted`; files in `DEV/_manual/` as `by_hand`; a file byte-identical to its base copy as `untouched`, left out so its repository is not checked; a file both changed and marked for deletion is a clash. With nothing left it says there is nothing to promote and why {src:.harness/engine/modules/task/task.py#L864-L902}.

When the plan passes, the dry run takes a snapshot of the task and stores `{state: "dry_run", plan_sha256, at}` in `promote` (with `direct: true` when a knowledge base is in the plan). When the old record's approved digest equals the new digest, the approval is kept; otherwise it is gone. It writes `PROMOTE-PLAN.diff` and returns the plan with all diff text stripped (`common.shown` removes `diff` and `source` from each file and `files` from each repository): `task`, `round`, `branch`, `plan_sha256`, `repos` (name, path, `base_ref`, `base_commit`, `current_branch`), `files` (path, action, added, removed, sha256), `snapshot`, `base_sync` notes, `not_promoted`, `by_hand`, `untouched`, `approved`, `review_file` and `next` {src:.harness/engine/modules/task/task.py#L926-L940} {src:.harness/engine/modules/task/common.py#L253-L264}. The `next` text, sent to the agent by code, says: when the plan is approved already, run `task promote`; otherwise give the person the link to the review file (not the diff), who presses **Approve promote** and types the code, and only then run `task promote` {src:.harness/engine/core/messages.en.json#L721-L722}.

`PROMOTE-PLAN.diff` (`write_review`, `full_patch`) starts with `# task <task>, round <n>, branch <branch>`, then a line `# repository <name>: <base_ref> at <base_commit>` per repository, then per non-`unchanged` file a `diff --git` block with 3 lines of context against the base-branch blob the plan recorded; a delete shows every base line as `-`, a create is against `/dev/null` {src:.harness/engine/modules/task/promote_target.py#L229-L265}. The dry run is not wholly write-free for the repositories: its base sync runs `git fetch` and may fast-forward the local base branch. Besides that it only reads blobs and trees {src:.harness/engine/modules/task/promote_target.py#L119-L127}.

## Write-back internals: the checks of plan_files, repository by repository

`promote_target.plan_files` checks every repository and file and writes nothing. It collects every problem, raises one `CommandError` that lists them all, and returns `(repos, files)` only when everything passes {src:.harness/engine/modules/task/promote_target.py#L119-L127} {src:.harness/engine/modules/task/promote_target.py#L219-L223}. The order:

1. **Branch name,** once for the plan: set, and matching `^feature/[A-Za-z0-9_]{1,60}$` (no `-`, `.` or `/`); the hint is `task set-branch` {src:.harness/engine/core/targets.py#L31} {src:.harness/engine/modules/task/promote_target.py#L129-L132}.
2. **Group by repository,** sorted by name. The first path segment must be a configured target repository and be followed by a path {src:.harness/engine/modules/task/promote_target.py#L133-L143}.
3. **Sync (dry run only).** An error becomes a problem of that repository, and its files are not checked {src:.harness/engine/modules/task/promote_target.py#L147-L152}.
4. **Look** with two git processes (`targets.look`): base commit, checked-out branch, uncommitted paths, local branches. No base commit is a problem {src:.harness/engine/core/targets.py#L394-L423}.
5. **Dirty tree.** Any uncommitted path, untracked files included, is a problem; up to 6 paths are listed, with the hint to commit, stash or discard. When the repository is on a branch a done promote of another task wrote and nobody committed, the text names that task {src:.harness/engine/modules/task/promote_target.py#L159-L163}.
6. **Branch free.** For an ordinary repository the branch name must not be among the local branches (the remote is not looked at). A knowledge base gets `direct_problems` instead {src:.harness/engine/modules/task/promote_target.py#L164-L167}.
7. **Each file:** `refused_paths`, then `_file_problem`. A repository whose files all turn out `unchanged` is skipped with a note, even when its tree is dirty or its branch name is taken, because nothing is written there {src:.harness/engine/modules/task/promote_target.py#L207-L209}.
8. **Order.** Ordinary repositories by name, knowledge bases last {src:.harness/engine/modules/task/promote_target.py#L216-L218}.

These checks run again at the real `task promote` and at `approve-promote` (both call `make_plan` without sync), and `task promote` refuses unless the fresh digest equals the dry run's and the approved one {src:.harness/engine/modules/task/task.py#L941-L944} {src:.harness/engine/modules/task/task.py#L994-L997}.

`_file_problem` compares one file with the base commit's tree, read once with `git ls-tree -r -t` and kept for the process {src:.harness/engine/modules/task/promote_target.py#L59-L92} {src:.harness/engine/core/targets.py#L291-L339}. A file is a problem when: its path is a folder on the base branch; it is there but not a regular file (symlink, submodule); it is there but was never fetched (hint: fetch it first); its base blob is not the one recorded at fetch (hint: `task fetch <file> --rebase`; the harness does not merge); it was fetched but is gone from the base branch; or it is new and a parent path component is a file or link there, or differs from an existing folder or neighbour only in letter case. A delete of a file not on the base branch is refused; a modify whose bytes equal the base blob becomes `unchanged` {src:.harness/engine/modules/task/promote_target.py#L190-L206}.

## Write-back internals: the plan digest and the approval

`plan_digest` is a sha256 over a JSON list of the branch name, `[name, base_commit]` of every repository (with `"direct"` added for a knowledge base only, so the digest of every other plan stayed the same) and `[path, action, sha256]` of every file {src:.harness/engine/modules/task/promote_target.py#L112-L116}. The code a person types is its first 6 characters in capitals, compared without regard to case {src:.harness/engine/core/approval.py#L17-L25} {src:.harness/engine/core/approval.py#L50-L58}. `approve-promote` (`task.approve_promote`) requires a person, picks the task whose promote is `dry_run` and not approved, builds the plan again and refuses when its digest differs from the stored one, rewrites `PROMOTE-PLAN.diff`, shows the screen and asks for the code {src:.harness/engine/modules/task/task.py#L984-L1014}. It then looks at the plan once more under the lock only when the code came more than `RECHECK_AFTER` = 3.0 seconds after the first look (a person reading in a terminal; a code typed at once on the board reuses the first result); if the digest differs it refuses, otherwise it stores `approved_plan_sha256` and `approved_at` and sets the waiting reason `go-promote`, so the board sends the agent its "go on" {src:.harness/engine/modules/task/task.py#L1015-L1024} {src:.harness/engine/modules/task/task.py#L42}. A fetch, `task delete` or `task set-branch` that changes a `dry_run` state resets it to `none` and with it the approval {src:.harness/engine/modules/task/task.py#L765-L766} {src:.harness/engine/modules/task/task.py#L330-L332}.

## Write-back internals: what task promote writes, in order

`task.run_promote` without `--dry-run` refuses unless the state is `dry_run` with a digest equal to the freshly built plan and the approved digest equals it too. It then calls `promote_target.run_result` {src:.harness/engine/modules/task/task.py#L941-L957} {src:.harness/engine/modules/task/promote_target.py#L455-L493}:

1. **Backup (`save_dev`).** Before any repository is touched it writes into `DEV/`: the base content of every deleted file under `_deleted/`, every changed file not already at its place, and the whole change as `DEV/<task name>.patch` (`<task name>_r<n>.patch` from round 2). If the backup fails the run stops with `promote.backup.failed` before any repository is touched, and the promote state stays `dry_run`, not `partial` {src:.harness/engine/modules/task/promote_target.py#L268-L284} {src:.harness/engine/modules/task/task.py#L82-L92}.
2. **Per repository, in plan order (`write_repo`).** For an ordinary repository: `git switch -c <branch> <base_ref>`, which leaves the repository checked out on the new branch. For each file other than `unchanged`: the destination must resolve inside the repository; the file is appended to `written` before the write, so a half-written file is undone like a finished one; a delete unlinks the file, removes folders that lost their last file and verifies it is gone; a create or modify copies the bytes and checks the written file's sha256 against the approved one {src:.harness/engine/modules/task/promote_target.py#L389-L431}.
3. **No commit and no `git add`** in an ordinary repository: the person reviews the branch and commits. A knowledge base is the exception (its own section).
4. **Result.** The `done` record keeps the digests, the approval time, the branch, per repository the path, base commit and original branch (and `commit` for a knowledge base), the files and the backup paths. The answer to the agent (`promoted_text`) says which repositories wait for a commit on which branch; for a knowledge base that it was written into `base_ref` and committed, and "nothing to push" when it has no remote; the `COMMIT-MESSAGE.md` text and the test offer only when an ordinary repository was also written {src:.harness/engine/modules/task/promote_target.py#L479-L493} {src:.harness/engine/modules/task/task.py#L960-L981}.

## Write-back internals: a write that stops halfway (partial)

Any `OSError`, `TargetError` or `CommandError` while writing a repository stops the whole run at once; later repositories are untouched. `run_result` asks git whether the branch was made (`switch -c` may have worked before the failure) and returns `partial_record` {src:.harness/engine/modules/task/promote_target.py#L464-L477}. The record holds `state: "partial"`, `recover_command`, the plan digest, the branch, `error`, `repos_done`, `repo_failed`, `repos_untouched`, `recovery` (command lines), `recovery_steps` (the steps as data) and the backup paths. `run_promote` stores it, writes the event `promote-partial` and raises an error telling what is done, what failed, what is untouched, where the backup is and the recovery commands, and that after recovery the agent runs the dry run again and does not close the task itself {src:.harness/engine/modules/task/promote_target.py#L496-L538} {src:.harness/engine/modules/task/task.py#L948-L957}.

`recovery_steps` records per repository: `git restore -- <modified and deleted files>`, `git clean -f -- <created files>` (each with the sha256 promote wrote, so a later edit can be told apart), then, when a branch was made, `git switch <original branch>` (the base branch when the original was a detached HEAD) and `git branch -d <branch>`. Repositories already done get the same steps for all their files. A committed knowledge base gets only `git revert --no-edit <commit>`; one that failed before its commit gets `restore` and `clean`, no branch steps {src:.harness/engine/modules/task/promote_target.py#L298-L319}.

While the state is `partial` the code refuses `task promote` and the dry run, `task fetch`, `task set-branch`, `task open`, `task close` and archiving; the task page's waiting reason is `recover`; the task is out of the promote queue; and autorun cannot be switched on {src:.harness/engine/modules/task/task.py#L328-L329} {src:.harness/engine/modules/task/task.py#L355-L356} {src:.harness/engine/modules/task/taskarchive.py#L70-L71} {src:.harness/engine/modules/task/taskqueue.py#L68-L69} {src:.harness/engine/modules/task/autorun.py#L138-L139}. The agent is told to ask the person to run `task recover` and not to close the task.

## Write-back internals: task recover

`task recover` (`task.recover`) is the person's command: `approval.require_person` refuses it from the agent's command line, and the gate refuses it there too. It refuses when the state is not `partial` or when the record lacks the digest, the branch or `recovery_steps` {src:.harness/engine/modules/task/task.py#L1027-L1038}. It shows a screen of the commands, listing first the files a person edited since promote wrote them (`edits_at_risk`), and asks for the code (the first 6 characters of the plan digest) {src:.harness/engine/modules/task/task.py#L1039-L1046}. `edits_at_risk` finds, in a repository still on the promote branch, a file that is neither what promote wrote nor what git holds; it is run again after the code, and every such file is copied to `<task>/REF/recovered-<time>/<repository>/<path>` before any step runs {src:.harness/engine/modules/task/promote_target.py#L322-L347} {src:.harness/engine/modules/task/task.py#L1047-L1050}.

`run_recovery` runs the steps repository by repository. In a repository that is no longer on the promote branch (for a knowledge base: on its base branch) the `restore`, `clean`, `switch` and `revert` steps are skipped with a note, because the person may have edits of their own; `branch -d` is skipped when the branch does not exist, and `-d` makes git refuse a branch with commits no other branch has. A failed step skips the rest of that repository's steps, not other repositories' {src:.harness/engine/modules/task/promote_target.py#L350-L386}. Each command is printed as `done`, `skipped` or `failed`. On a failure the record stays `partial` and `recover` can be run again. On success the promote state becomes `{state: "none", recovered_at}`: the approval is gone, so a new dry run and a new approval are needed; the branch name stays, the backups in `DEV/` are not touched, and the board tells the agent to retry {src:.harness/engine/modules/task/task.py#L1051-L1061}.

## Write-back internals: the knowledge base, committed by the harness

A repository is a knowledge base when its `repos` entry has `knowledge_base: true`; `Repo.knowledge_base` carries it, and the plan and its digest carry `direct: true` {src:.harness/engine/core/targets.py#L138} {src:.harness/engine/modules/task/promote_target.py#L212-L215}. In the plan checks it is not asked whether the branch name is free; instead `direct_problems` requires that it is checked out on its `base_ref` and that git config has both `user.name` and `user.email` (the last value wins, so an empty name in the repository beats a global one) {src:.harness/engine/modules/task/promote_target.py#L95-L109}. A clean working tree is still required; the file checks, the typed approval and the backup in `DEV/` are the same.

In `write_repo` a knowledge base gets no branch. Just before writing it checks again that the checked-out branch is still `base_ref`, that `base_ref` still points at the approved base commit and that the tree is clean (`promote.kb.changed`, `promote.kb.dirty`); a failure ends in `partial` {src:.harness/engine/modules/task/promote_target.py#L405-L409}. It writes the files, then `commit_direct` runs `git add -A -- <written paths>` (which stages deletes too) and `git commit -q -m <message> -- <written paths>`, so the commit holds those files and nothing else, with the author from that repository's git config. When either fails, `git reset -q -- <paths>` unstages and the run is `partial`; on success the commit id is stored as `commit` {src:.harness/engine/modules/task/promote_target.py#L429-L443}. The message is `harness task <task name>: <n> file(s)`, a blank line and "Written by `task promote` after the person approved plan <12 characters of the digest> (round <n>)" {src:.harness/engine/modules/task/promote_target.py#L450-L452}. A knowledge base is written last. No review step follows: the approval of the plan is the review.

Recovery differs: a committed knowledge base is undone with `git revert --no-edit <commit>` (a new commit), only while on its base branch, so the feature file's line that `task recover` puts uncommitted files back is only half right for it. After success the harness does not push; with no remote it does not even say to {src:.harness/engine/modules/task/task.py#L960-L981}.

## Write-back internals: task queue, a report and not a scheduler

`harness task queue` (`taskqueue.queue`) is a read-only report, not a scheduler: nothing forces the first task in line to go first {src:.harness/engine/modules/task/taskqueue.py#L1-L10} {src:.harness/engine/modules/task/commands.py#L203-L204}. It lists open tasks that have files for a known target repository (a folder under `DEV/` holding a file, or a path in `deletes`) and whose promote state is not `done` or `partial`. The stage is `approved` (state `dry_run`, approved digest equal to the plan digest), `asked` (`dry_run`, not approved) or `working` (otherwise); the order is by stage in that order, then time (approval, dry run or last update), then name {src:.harness/engine/modules/task/taskqueue.py#L26-L96}. Per repository it reads git (`dirty_paths`, `current_branch`) and reports the branch, whether it is clean, up to 5 uncommitted paths, the tasks waiting, `held_by` and a `next` advice. `held_by` is the newest task whose promote is `done` on the repository's current branch with no `commit` recorded (closed tasks count), looked up only when the tree is not clean {src:.harness/engine/modules/task/taskqueue.py#L99-L107} {src:.harness/engine/modules/task/taskqueue.py#L133-L176}.

The waiting comes only from the dirty-tree rule of `plan_files`: a promote leaves its files uncommitted on the new branch, so the next task's dry run into the same repository is refused, naming the holder, until the person commits or discards {src:.harness/engine/modules/task/promote_target.py#L159-L163}. There is no lock between tasks, so two promotes into repositories that are clean at that moment are not stopped by the queue. After another task's work reaches the base branch, a file fetched earlier fails the base-blob check and needs `--rebase` {src:.harness/engine/modules/task/promote_target.py#L74-L75}. A knowledge base is committed straight on its base branch, so its record has a `commit` and it is never `held_by` {src:.harness/engine/modules/task/taskqueue.py#L104}.

## Write-back internals: rounds

The round number is `data["round"]` in `task.json`, starting at 1. A new round starts only when the person has the task opened again with `task open` after a `done` promote: `attach` calls `archive_round`; a promote, or the board closing the task, does not start one. With `partial`, `task open` is refused {src:.harness/engine/modules/task/task.py#L174-L183}. `archive_round` renames `DEV/` to `DEV_r<n>/`, saves `CHANGES_r<n>.diff`, deletes the base copies, renames `PLAN.md` to `PLAN_r<n>.md`, appends a record to `rounds`, and resets: `round` plus one, `targets`, `target_files`, `manual_files`, `deletes` and `plan` emptied, `promote` to `none`, `branch` emptied {src:.harness/engine/modules/task/task.py#L234-L251}. So a new round needs a new plan approval and pins the base commit again.

In later rounds the default branch is `feature/<name>_r<n>` and the patch is `<task name>_r<n>.patch` {src:.harness/engine/modules/task/task.py#L62-L72} {src:.harness/engine/modules/task/task.py#L856-L857}. Autorun cannot be switched on for a task whose promote is `done` or `partial` {src:.harness/engine/modules/task/autorun.py#L138-L139}. A rewind point of an earlier round is refused {src:.harness/engine/modules/task/rewind.py#L212-L221}. On the task page an earlier round opens read-only, and `DEV_r<n>` cannot be edited {src:.harness/engine/modules/task/taskdesk.py#L478-L500} {src:.harness/engine/modules/task/taskfileedit.py#L67-L70}. A task with no target repository has `target_mode` false and has no promote to start a round from.

## Write-back internals: COMMIT-MESSAGE.md, who writes it and what the page adds

The agent writes `COMMIT-MESSAGE.md` in the task folder, asked by text: the answer of `task promote` tells it to write a subject of at most 72 characters, a blank line and the body, one `## <repository>` section per repository when there are several, and not the `Co-authored-by` line {src:.harness/engine/core/messages.en.json#L1981}. The trailer is added when the page builds the text, not in the file: `commitmsg.compose` removes a `Co-authored-by` line equal to the configured one that the agent wrote and puts it back once (inside the agent's trailer block when it ended with one, else after a blank line). `commit.coauthor` in `task.json` sets the name (default `GitHub Copilot Coding Agents`); an empty string leaves the line out {src:.harness/engine/modules/task/commitmsg.py#L31-L55} {src:.harness/policies/task.json#L80-L82}. For several repositories `sections` finds `## <repository>` headings naming a repository the write-back wrote; the lines before the first `##` heading are the start of every repository's message, then comes that repository's section; with no matching section every repository gets the whole text {src:.harness/engine/modules/task/commitmsg.py#L71-L94}. `view` builds the messages only when the promote is `done` and a repository has no `commit` recorded {src:.harness/engine/modules/task/commitmsg.py#L115-L143}.

The Changes tab's commands do not read the message from the file: they embed the finished text and pipe it to `git commit -F -`. For macOS and Linux: `cd '<path>'`, `git switch '<branch>'`, then `git add -A && git commit -F - <<'EOF'` with the message (the marker grows when a line of the message equals it); for PowerShell: `Set-Location`, `git switch`, `git add -A`, a single-quoted here-string piped to `git commit -F -` with UTF-8 set {src:.harness/engine/modules/task/commitmsg.py#L97-L112}. The reason, from the module header: a message with a backtick or `$` pasted into `git commit -m "..."` lost words to the shell, and a quoted here-document runs nothing in it {src:.harness/engine/modules/task/commitmsg.py#L1-L13}. The file lives in the task folder, not the repository, and lacks the trailer, so the page composes the text; the person can edit the file on the Files tab. The Stop hook only reminds: `write_back_stop` blocks the agent's stop once per session when the promote is `done` and a step is unticked or there is no non-empty `COMMIT-MESSAGE.md`; not in autorun {src:.harness/engine/modules/task/handler.py#L438-L459}.

## Write-back internals: why there is no automatic rollback, push, PR or pull

The design document gives one line: no automatic push, PR, fetch or pull, because outward actions are always done by a person; no automatic rollback across repositories, because on a failure partway the harness stops, says what was done and a person recovers {src:docs/05-design.md#L224-L225} {src:.harness/engine/modules/task/promote_target.py#L13-L14}. The code supports this. Separate repositories have no atomic step, so no rollback could be all-or-nothing; the recovery steps are destructive and would run on a state the harness cannot know, which is why `task recover` shows a screen, needs a typed code and skips a repository the person moved. The code instead checks everything first, backs up first, stops at the first failure, asks git for the failed repository's state, records the exact steps with digests and keeps the task blocked until a person recovers {src:.harness/engine/modules/task/promote_target.py#L455-L538}.

The harness does run `git fetch` and a fast-forward in the base sync, at a first fetch of a repository in a round and at every dry run, never at the real `task promote`; it stops on a dirty or diverged branch and uses the local branch when the remote is unreachable {src:.harness/engine/modules/task/basesync.py#L1-L15}. A person-started setup job for the harness's own knowledge-base folder can run `git pull --ff-only` (`company.folder_update`); it is not part of a promote {src:.harness/engine/modules/task/setupjob.py#L97-L103} {src:.harness/engine/core/company.py#L728}.

What the agent may run itself, when target repositories are configured: `gitcmd._git` sorts every git command. Only a fixed read-only set (`status`, `diff`, `log`, `show`, `ls-tree`, `cat-file` and the like) passes; `git fetch` and `git pull` are not in it, so they wait for the person's `approve-command` and its code, and `curl`, `ssh` and other network programs are on the ask list of `gate.json`. `git push`, `git clean`, `git update-ref`, `git reset --hard`, `git branch -D`, every force option and `gh pr` are never approved: there is no code to approve them. This holds only when a target repository is configured, and the gate is a net of patterns, not a sandbox {src:.harness/engine/modules/gate/gitcmd.py#L22-L50} {src:.harness/engine/modules/gate/gitcmd.py#L253-L289} {src:.harness/policies/gate.json#L161-L167}.

## Write-back internals: limits

- **The queue is advice.** `task queue` reports and `plan_files` refuses a dirty tree; no lock stops two promotes started at the same time into repositories that are clean at that moment {src:.harness/engine/modules/task/taskqueue.py#L1-L10}.
- **Branch existence is local.** The branch-free check reads local branches; a same-named branch on the remote is not seen {src:.harness/engine/modules/task/promote_target.py#L166-L167}.
- **The base sync reads the network.** With a slow remote the dry run may wait the fetch timeout (at least 120 seconds) for each repository {src:.harness/engine/modules/task/basesync.py#L25-L61}.
