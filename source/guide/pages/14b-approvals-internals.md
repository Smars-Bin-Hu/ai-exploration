This file holds the code-level detail behind the feature file "14 Plans and approvals". Use it for "how does it work" and "where in the code" questions: how the approval code is made and checked, which digest each approval uses, how the person check and the board's one-time pass work, how the board reuses the terminal command, how a git write and a call to an outside system are approved and stored, what happens when the content changes after the code was shown, and where the plan's approval is tested. The feature file says what a person approves and why.

## Approvals internals: three pieces of code, and which approval uses which

The word approval covers three separate pieces of code in harness 1.8.3, and `core/approval.py` is only the first. It is not the one function behind every person approval.

**`core/approval.py`: the person check and the typed code.** It holds `terminal_person`, `require_person`, `is_person`, `code_of` and `ask`. The commands that ask a typed code from it are `task confirm-req`, `task approve-plan`, `task approve-promote`, `task recover`, `task review extend`, `task review waive`, `task review dismiss`, `task autorun on` and `admin on`; the task commands, `task autorun on` included, reach it through the helpers `person()` and `typed()` of `modules/task/task.py`, and `admin on` calls `require_person` and `ask` directly {src:.harness/engine/core/approval.py#L17-L58} {src:.harness/engine/modules/task/task.py#L409-L420} {src:.harness/engine/modules/task/taskreview.py#L497-L548} {src:.harness/engine/modules/task/autorun.py#L206-L241} {src:.harness/engine/modules/gate/commands.py#L95-L117}.

**`core/approvals.py`: the stored tickets of a git write and of a call to an outside system.** The gate makes the code when it refuses the command (`_code`: the first six capitals of a sha256 over the session id, the command with white space collapsed, and the time of the request), and the person types it into `approve-command` or `approve-action`. These two commands use only `approval.terminal_person()` from `core/approval.py` for the person check, and read the typed code with plain `input()`; `code_of` and `ask` are not used for them. The file `modules/gate/approvals.py` only re-exports `core/approvals.py` {src:.harness/engine/core/approvals.py#L1-L6} {src:.harness/engine/core/approvals.py#L93-L94} {src:.harness/engine/modules/gate/commands.py#L37-L61} {src:.harness/engine/core/outbox.py#L269-L302} {src:.harness/engine/modules/gate/approvals.py#L1-L8}.

**Person-only commands with no code.** `task pause`, `task resume`, `task offwork`, `task onwork`, `task allow`, `task test runner`, `task review set`, `task board --serve`, `doctor --accept`, `toolpack add`, `toolpack remove`, `reinstall --apply`, `company update --apply` and `tools mcp` (when it allows or blocks) call `require_person(..., typed=False)` or its task wrapper: they check for a person and ask no code {src:.harness/engine/modules/task/tasklife.py#L548} {src:.harness/engine/modules/task/tasklife.py#L686} {src:.harness/engine/modules/task/tasklife.py#L708} {src:.harness/engine/modules/task/tasklife.py#L723} {src:.harness/engine/modules/task/tasklife.py#L742} {src:.harness/engine/modules/task/testrecord.py#L195} {src:.harness/engine/modules/task/taskreview.py#L480} {src:.harness/engine/modules/task/boardserve.py#L2310} {src:.harness/engine/doctor.py#L1019-L1021} {src:.harness/engine/cli.py#L119-L126} {src:.harness/engine/core/reinstall.py#L304} {src:.harness/engine/core/company.py#L806} {src:.harness/engine/modules/gate/commands.py#L321}.

## Approvals internals: the person check, `terminal_person` and `require_person`

`terminal_person()` in `core/approval.py` answers True when `sys.stdin.isatty()` and `sys.stdout.isatty()` are both true; if either is not a terminal it asks `boardperson.use()`, which is True only inside a command the board's Terminal window started with a valid one-time pass (see the section on the pass) {src:.harness/engine/core/approval.py#L28-L34}. It tests the streams of the process and nothing else: a process whose stdin and stdout are both a terminal passes whoever started it, so the gate's refusal of the person-only commands on the agent's command line (file 15 The gate and guardrails) is the other layer. A pipe, a redirected output or a script has no terminal and is refused.

`require_person(command, interactive=None, typed=True)` raises `Refused` when the person test fails. `interactive=None` means "ask `terminal_person()`"; the real CLI always passes None, and a value is passed only by tests and by the board (True) {src:.harness/engine/core/approval.py#L37-L42}. The message depends on `typed`: `approval.person_only.typed` says the command is for the user by hand "with a typed code"; `approval.person_only` says the same without the code, for the commands that ask none. `is_person()` is the same test without raising; `task board` uses it to start the served board by default, and `task close` and the other commands behind `guarded()` use it to know that a person, not the agent, is typing {src:.harness/engine/core/approval.py#L45-L47} {src:.harness/engine/modules/task/commands.py#L92-L98}.

In `modules/task/task.py` the helper `person(command, interactive, typed)` turns `Refused` into `CommandError`, and `typed(question, digest, refusal, reader)` does the same for `approval.ask`; each approval command calls `person()` first, before it reads any file of the task {src:.harness/engine/modules/task/task.py#L409-L420}.

## Approvals internals: the typed code, `code_of` and `ask`

`code_of(digest)` is `digest[:CODE_LENGTH].upper()` with `CODE_LENGTH = 6`: six capital hexadecimal characters, the same length and look as a held call's code. Before 1.7.38 the requirement's code was eight small characters; that old form is not accepted any more {src:.harness/engine/core/approval.py#L17-L25}.

`ask(question, digest, refusal, reader=None)` shows the question with the code in it, in the form "<question>, type <code> (anything else cancels): ", reads one answer with `reader` (default `input`), strips it, and compares `answer.upper()` with the code; an answer that differs raises `Refused(refusal)`, a text of the calling command ("plan.refused" and the like). Because of `.upper()` the person may type small letters {src:.harness/engine/core/approval.py#L50-L58}. The code is not a secret: it is printed in the question. What typing it proves is that a process with a terminal, or the board's page, answered this prompt, and that the digest the calling command computed when it asked is the digest in the answer.

If the command reaches `input()` and the stream is at end of file, `ask` raises `Refused` with the text `approval.no_input`: "the board's Terminal window has no keyboard behind it. Use the button on the board, or run it in your own terminal" {src:.harness/engine/core/approval.py#L53-L56} {src:.harness/engine/core/messages.en.json#L523}.

The screen before the question is kept short on purpose: each command prints a header, the name and the line count of the file to read in the editor, and what the approval opens, and never the content of the file. `approve_plan`, for instance, prints `plan.screen.file` with the number of lines and the path of `PLAN.md`; the plan itself is read in the editor {src:.harness/engine/core/approval.py#L1-L8} {src:.harness/engine/modules/task/task.py#L451-L458}.

## Approvals internals: which digest each approval uses

Each command passes its own digest to `ask`; the first six capitals of it are the code. What a person must read is the thing the digest covers.

- **`task confirm-req`:** the sha256 of the whole text of `REQ.md` as read (`hashlib.sha256(text.encode("utf-8"))`): the confirmation line, the sources and the notes count too, so any byte changes the code. After a correct code and the re-check, `fill_confirmation` writes "confirmed <date>" on the confirmation line (`User confirmed`, or the Chinese form) and stores `req.confirmed_sha256`, which is the normalised requirement digest of `tasks.req_digest` {src:.harness/engine/modules/task/task.py#L570-L612}.
- **`task approve-plan`, requirement already confirmed (or no confirmation line):** `tasks.plan_digest`, the sha256 of the raw bytes of `PLAN.md`; an empty string when the file is missing, which stops the command. A whitespace-only edit to `PLAN.md` changes the code and also un-approves a plan that was approved {src:.harness/engine/core/tasks.py#L109-L114} {src:.harness/engine/modules/task/task.py#L428-L459}.
- **`task approve-plan --with-req`, requirement written but not confirmed or changed since (`open` or `changed`):** `plan_digest_with(req_text, plan_digest)`, the sha256 of the hex sha256 of the whole `REQ.md` text followed by the plan digest: one code for both files as they are now. Without `--with-req` the command refuses in these two states, and in the state `unwritten` (the template is still empty) it refuses either way; the state `none` (no `REQ.md`, or no confirmation line) approves the plan alone {src:.harness/engine/modules/task/task.py#L423-L425} {src:.harness/engine/modules/task/task.py#L440-L451} {src:.harness/engine/modules/task/task.py#L551-L567}.
- **`task approve-promote`:** `plan_sha256` of a fresh `make_plan`, which `promote_target.plan_digest` computes as the sha256 of the JSON of the branch name, each repository's name and base commit (plus a "direct" mark for a knowledge base repository) and, for each file, its path, action and sha256. It must equal the `plan_sha256` stored by the last dry run, else the command refuses with `promote.approve.changed` {src:.harness/engine/modules/task/promote_target.py#L112-L116} {src:.harness/engine/modules/task/task.py#L984-L1014}.
- **`task recover`:** the `plan_sha256` of the failed write-back, stored in `promote` {src:.harness/engine/modules/task/task.py#L1027-L1046}.
- **`task review extend` and `waive`:** the digest of the task's results (`tasksnap.results_digest`, one sha256 over the path and file digest of every result file); `dismiss`: the digest kept for that check round. With no digest the code is `000000` {src:.harness/engine/modules/task/taskreview.py#L496-L548} {src:.harness/engine/modules/task/tasksnap.py#L81-L90}.
- **`task autorun on`:** `code_source`, the sha256 of the task folder name, the round, the plan digest and the text of every `TODO.md` step, joined by new lines {src:.harness/engine/modules/task/autorun.py#L143-L145}.
- **`admin on`:** the sha256 of "admin", the surface and the session id; it is bound to a session, not to a file {src:.harness/engine/modules/gate/commands.py#L115}.

The requirement has two digests. The code of `confirm-req` is over the whole text. The digest that decides whether an approved plan still holds is `tasks.req_digest`, over the three sections "What to do", "What not to do" and "Done when" with blanks and line breaks ignored; a file with none of those sections counts as a whole except the confirmation line {src:.harness/engine/core/tasks.py#L122-L149}. So a whitespace-only edit to `PLAN.md` changes the plan's code and its approval, while a whitespace-only edit to `REQ.md` changes the code typed for `confirm-req` but not the requirement digest, and lets an approved plan stand.

## Approvals internals: how a change after the code was shown is refused

`core/approval.py` does not compare file contents. `ask` only compares what was typed with the code of the digest that the calling command passed when it asked. The refusal "the content changed" is made by the callers: they compute the digest before the question, and after a right code they take the task's lock and compute it again {src:.harness/engine/core/approval.py#L50-L58}.

The lock is `locked(root, task)`: it locks `task.json`, yields the data and writes it back only if the block ends without an exception, so a refusal raised inside it saves nothing {src:.harness/engine/modules/task/task.py#L82-L92}. Per command:

- **`approve_plan`:** after `typed`, under the lock it recomputes `tasks.plan_digest` and refuses with `plan.changed` if it differs from the digest asked; with the requirement unconfirmed it also reads `REQ.md` again and refuses with `req.changed` if the text differs. Only then it stores `plan = {approved_sha256, approved_at, req_sha256}` (the requirement digest it was approved for), a history line, and the mark `waiting = go-plan`; the snapshot of the gate "plan" is taken after the lock is released {src:.harness/engine/modules/task/task.py#L459-L475}.
- **`confirm_req`:** under the lock it reads `REQ.md` again and refuses with `req.changed` if its sha256 differs from the one asked {src:.harness/engine/modules/task/task.py#L587-L595}.
- **`approve_promote`:** the second look is a new `make_plan` under the lock, made only when more than `RECHECK_AFTER = 3.0` seconds (monotonic clock) have passed since the plan was first computed (1.7.43: a code typed on the board comes at once, the person having read the plan in the preview); in both cases the plan digest must also equal the dry run's stored one, else `promote.changed`. It then stores `approved_plan_sha256` and `approved_at` and the mark `go-promote` {src:.harness/engine/modules/task/task.py#L42} {src:.harness/engine/modules/task/task.py#L1015-L1024}.
- **`task promote`:** at the write it recomputes the plan and refuses unless the dry run's `plan_sha256` and `approved_plan_sha256` both equal it (`promote.no_dry_run`, `promote.not_approved`) {src:.harness/engine/modules/task/task.py#L941-L944}.
- **`recover`:** no digest check after the code; it looks at `edits_at_risk` again, because the person read the screen for a while, and copies hand-edited files to `REF/recovered-<time>/` before it restores {src:.harness/engine/modules/task/task.py#L1046-L1052}.
- **`review waive`:** under the lock it compares `tasksnap.results_digest` with the one asked (`review.waive.changed`); `dismiss` checks that the round still counts; `extend` has no second look {src:.harness/engine/modules/task/taskreview.py#L522-L524} {src:.harness/engine/modules/task/taskreview.py#L549-L552}.
- **`autorun on`:** under the lock it recomputes `code_source` and the autorun requirements and refuses with `autorun.changed` if either changed {src:.harness/engine/modules/task/autorun.py#L242-L245}.
- **`approve-action` (outside calls):** the files the line names are pinned at approval and compared with what the person saw in View; see the section on outside calls.

## Approvals internals: the board Terminal window's one-time pass (`boardperson`)

The board's Terminal window starts commands through a pipe with stdin set to `/dev/null`, so a harness command typed there has no terminal and would fail the person test. `core/boardperson.py` lets the board vouch for the command instead: for each line that runs `harness` or `cli.py`, `boardterm` calls `boardperson.issue()` and puts the returned token in the environment variable `HARNESS_BOARD_PERSON` of that one process {src:.harness/engine/modules/task/boardterm.py#L67-L73} {src:.harness/engine/modules/task/boardterm.py#L139-L143} {src:.harness/engine/modules/task/boardterm.py#L141}.

`issue()` makes `secrets.token_urlsafe(32)` and stores only its sha256 as a file name in `person/` inside the folder of the guardrail lists (`integrity.home_dir()`: `HARNESS_INTEGRITY_DIR`, else `~/.copilot-harness/integrity`), with the content `{"until": now + 600}`; `SECONDS = 600`. Passes that ran out are deleted at each issue. When the folder cannot be written it returns an empty token and the command then runs as before, refused where a person is needed {src:.harness/engine/core/boardperson.py#L22-L58}.

`use()` is called by `terminal_person()` the first time a command asks whether a person runs it. It removes the variable from the process environment (so programs the command starts do not inherit it), looks up the fingerprint file, reads `until`, deletes the file, and answers True only if the pass has not run out. A second call in the same process answers True from the module flag `_used`; a second command with the same token finds no file and answers False. When the command ends, `boardterm.wait_end` calls `boardperson.drop`, used or not {src:.harness/engine/core/boardperson.py#L61-L90} {src:.harness/engine/modules/task/boardterm.py#L181-L186}.

The pass stands for a person's presence, not for a keyboard: a command that then asks for a typed code gets end of file from `input()`. `ask` turns that into the refusal `approval.no_input` {src:.harness/engine/core/approval.py#L53-L56}. `approve-command` and `approve-action` call `input()` directly with no handler for end of file: in this window they pass the person check, then fail at the prompt, and nothing is approved (read from the code; not run). So from the board's Terminal window the person-only commands that ask no code run, and those that ask a code do not {src:.harness/engine/modules/gate/commands.py#L57-L60} {src:.harness/engine/core/outbox.py#L292-L298}.

An agent gets no pass: the board makes one only for a command typed in its Terminal window, which only a paired browser may ask for (`/api/term`), and the agent cannot write the fingerprint, since `person/` lies in the guarded home folder. The module says itself that a process of the same user that builds the path at run time can still reach the folder: it raises the bar, it is not a sandbox {src:.harness/engine/modules/task/boardterm.py#L1-L9} {src:.harness/engine/core/boardperson.py#L1-L10} {src:.harness/engine/core/guardrails.py#L46-L62}.

## Approvals internals: the board's approval path, `preview` and `act`

The served board (`task board --serve`) lets a paired browser run the same functions as the terminal commands. `Board.act` in `modules/task/boardserve.py` does this with a table, `runner(root, action, task)`, from the action name to the terminal command's own function: `approve-plan`, `confirm-req`, `approve-promote`, `review extend`, `review waive`, `review dismiss`, `recover` and `approve-action`. `approve-plan` with `with_req` is wrapped to pass `with_req=True`, and `approve-action` with the files the card showed is wrapped to pass `seen` {src:.harness/engine/modules/task/boardserve.py#L145-L157} {src:.harness/engine/modules/task/boardserve.py#L809-L815}. The board's `review extend` always asks for two more checks (`taskreview.extend(root, task, 2)`).

Before `act` runs, the request passes these checks, in this order {src:.harness/engine/modules/task/boardserve.py#L1814-L1818} {src:.harness/engine/modules/task/boardserve.py#L2230-L2240} {src:.harness/engine/modules/task/boardserve.py#L746-L758}:

1. **The request itself (`do_POST`):** the `Host` header must be `127.0.0.1:<port>` or `localhost:<port>`; an `Origin` header, when sent, must be `http://` plus one of those; and the header `X-Harness-Board: 1` must be present. Else the answer is 403. The server listens on 127.0.0.1 only {src:.harness/engine/modules/task/boardserve.py#L2320} {src:.harness/engine/modules/task/boardserve.py#L1673-L1674} {src:.harness/engine/modules/task/boardserve.py#L1706-L1707}.
2. **The paired browser (`/api/act`):** for every action except `FREE` (`pause`, `resume`, `offwork`, `onwork`), `board.paired(token)` must be true, where the token is the session cookie.
3. **The allowed-actions list:** `action in self.actions`, the `board.actions` list of the task policy; otherwise `serve.action.off`.
4. **`idle()`,** for every action except the settings (`review set`, `task allow`, `task link`, `test runner`): see the section on the busy refusal.
5. **The shared function itself,** which checks the person (True, passed as `interactive`), then the digest again: for `approve-promote` it runs `make_plan` again, for `approve-action` it compares the digests of the files seen with the files now.

**Pairing.** At start the board makes a random code (`secrets.token_urlsafe(12)`) held in memory only; `/api/pair` trades it, once, for a session token set as a cookie `HttpOnly; SameSite=Strict` and the code is emptied. `board.paired` tests the cookie against the set of tokens in memory. When the server stops, they are gone {src:.harness/engine/modules/task/boardserve.py#L386-L399} {src:.harness/engine/modules/task/boardserve.py#L1828-L1835}.

**VS Code's built-in browser is never paired.** The user agent of an Electron app (the pattern `\bElectron/\d`) marks a request as embedded; `/api/pair` refuses it before the code is used up, and `token()` returns an empty token for every request from such an agent, so it cannot hold a session. The reason in the code: the agent can drive that browser with its browser tools, and so it must never be able to press a person's button there {src:.harness/engine/modules/task/boardserve.py#L271} {src:.harness/engine/modules/task/boardserve.py#L1709-L1721} {src:.harness/engine/modules/task/boardserve.py#L1829-L1830}. The gate also refuses a terminal command of the agent that names the board's port (`asks_board`, read from `board-serve.json`) {src:.harness/engine/modules/gate/handler.py#L580-L585}.

**Preview, then act.** With `step = preview` the function is called with `reader` set to a function that raises `Preview(asked)` with the prompt text, `interactive=True`, and `out` a string buffer; the board answers `{"screen": [the non-empty lines printed], "ask": <the question with the code in it>}`. If the function ends without asking for a code, the answer is `serve.preview.none`. With `step = act` the function is called again with `reader` returning the code the person typed on the page. Nothing is kept between the two calls: the digest is computed afresh in each, so a file that changed in between has another code and the typed one is refused, as in the terminal {src:.harness/engine/modules/task/boardserve.py#L137-L142} {src:.harness/engine/modules/task/boardserve.py#L816-L834}. The code is shown to the person in the preview, so on the board too it binds the yes to the version shown; it does not hide the code from anyone.

A preview is not free of side effects. The preview of `approve-promote` runs `make_plan`, which reads the base branches of the target repositories with git, and `write_review`, which rewrites `PROMOTE-PLAN.diff` in the task folder {src:.harness/engine/modules/task/task.py#L994-L998} {src:.harness/engine/modules/task/task.py#L864-L908}.

**What does not use `/api/act`.** `autorun on` raises `serve.autorun.form` there: it starts from its own endpoint `/api/autorun/on`, with the models, the spend limit and the Start order, which checks the allowed list and `idle()` and then calls `autorun.turn_on` with the typed code and `interactive=True` {src:.harness/engine/modules/task/boardserve.py#L807-L808} {src:.harness/engine/modules/task/boardserve.py#L1375-L1398}. Several held calls approved with one code go through `Board.batch`. `review set`, `task allow`, `task link`, `test runner`, `dismiss action`, `close` and `accept` take no code; `task allow` turning a connection on needs the code of a held call that offers it {src:.harness/engine/modules/task/boardserve.py#L713-L744} {src:.harness/engine/modules/task/boardserve.py#L774-L806}.

**After a decision.** For `confirm-req`, `approve-plan` and `approve-promote` (`WAKING`) the board starts a background thread, `wake_go`, which sends the agent its "go on" message if the task's waiting mark is one of the `go-*` marks; with `no_wake` on `approve-plan` it sends nothing and records `approve-plan-nowake` in the task's history {src:.harness/engine/modules/task/boardserve.py#L842-L852} {src:.harness/engine/modules/task/boardserve.py#L868-L879}.

## Approvals internals: the refusal while the agent is in the middle of a turn

A person at a terminal is refused while the agent is at work, unless `--force` is given. `guarded(command, call)` in `modules/task/commands.py` wraps `task approve-plan`, `confirm-req`, `approve-promote`, `recover` and `task review set`, `extend`, `waive` and `dismiss`: when `approval.is_person()` and not `--force`, it reads the task and calls `tasklife.require_idle`, which raises `task.busy` if `at_work` is true {src:.harness/engine/modules/task/commands.py#L106-L122} {src:.harness/engine/modules/task/commands.py#L233-L276}. `task pause`, `task autorun on` and `task close` check the same with their own `--force` {src:.harness/engine/modules/task/tasklife.py#L808-L811} {src:.harness/engine/modules/task/commands.py#L125-L133}.

`at_work(root, data)` is True when the task is open, not paused, has no `waiting` mark and no hand-over, is held by its session, that session made a hook call within the active window (`board.active_seconds` of the task policy, default `ACTIVE_SECONDS = 300`, read from the mtime of the session log) or a subagent runs, the agent is not waiting in `harness wait --approval` on a held call, and the task is not marked cancelled {src:.harness/engine/modules/task/tasklife.py#L776-L805} {src:.harness/policies/task.json#L46}.

The board repeats the test in `Board.idle(action, task)` before any action except the settings: if `at_work` is true it asks the link cache of VS Code about the bound chat; a chat whose state is `idle`, `error` or `input` counts as not at work (VS Code's word wins over the hook log, and the function returns True so a later check can say so); any other state raises `serve.busy`. So the board and the terminal both wait for the agent to stop, except that `--force` exists only for a person at a terminal. The terminal commands `approve-command`, `approve-action` and `admin on` have no such test; on the board `approve-action` goes through `idle()`, and an agent that sits in `harness wait --approval` on the call is not counted as at work {src:.harness/engine/modules/task/boardserve.py#L97} {src:.harness/engine/modules/task/boardserve.py#L194} {src:.harness/engine/modules/task/boardserve.py#L685-L695}. The docstring of `at_work` says the approvals do not need the agent to be idle, because each is bound to a digest; the commands above nevertheless refuse (a mismatch between comment and code) {src:.harness/engine/modules/task/tasklife.py#L793-L796}.

## Approvals internals: every action that needs a person

The gate's rule `person-only` in `gate.json` refuses these on the agent's command line, read the way the shell reads them (`harnesscmd.py`): `task approve-plan`, `confirm-req`, `approve-promote`, `recover`, `pause`, `resume`, `offwork`, `onwork`, `autorun on`, `review set`, `extend`, `waive`, `dismiss`, `test runner`, `allow`, `task board` (not with `--once`), `approve-command`, `approve-action`, `admin on` and `doctor --accept`; a second rule refuses `task close` {src:.harness/policies/gate.json#L131-L144} {src:.harness/engine/modules/gate/harnesscmd.py#L1-L8}. The table below says how each decision is made. "Code" means a typed code.

- **Confirm the requirement:** person check and code; board button **Confirm requirement**; board policy name `confirm-req`.
- **Approve the plan:** person check and code; board **Approve plan**; `approve-plan`.
- **Approve the write-back (promote):** person check and code; board **Approve promote**; `approve-promote`.
- **Recover a failed write-back:** person check and code; on the board by default: `recover` is in the default `board.actions` and in the `runner` table, though the description text of `task.json` says it stays in the terminal {src:.harness/policies/task.json#L50-L70} {src:.harness/engine/modules/task/boardserve.py#L122} {src:.harness/engine/modules/task/boardserve.py#L154}.
- **More checks, waive, dismiss a check (`task review extend`, `waive`, `dismiss`):** person check and code; they run from the board (Review tab) as well, although their help text says "terminal only" {src:.harness/engine/modules/task/commands.py#L236-L246} {src:.harness/engine/modules/task/boardserve.py#L151-L153}.
- **Number of checks (`task review set`):** person check, no code; board check chips; `act` handles it without a code {src:.harness/engine/modules/task/boardserve.py#L799-L802}.
- **Autorun on:** person check and code; board **Start** form, not `/api/act`; terminal `task autorun on`.
- **A git write (`approve-command`):** person check and the ticket code; no board button, not in the `runner` table or the default actions; terminal only; works from a terminal, and its prompt fails in the board's Terminal window.
- **A call to an outside system (`approve-action`):** person check and ticket code; board **Approve** on a card, single or in a batch; **Do not approve** (`dismiss action`) needs the paired browser and no code.
- **Admin mode (`admin on`):** person check and code; no board button; refused for a subagent session, for a session that holds a task and for an unknown session {src:.harness/engine/modules/gate/commands.py#L84-L119}.
- **Person-only, no code:** `task pause`, `resume`, `offwork`, `onwork`, `task allow`, `task test runner`, `task board --serve`, `doctor --accept`, `toolpack add`, `toolpack remove`, `reinstall --apply`, `company update --apply`, `tools mcp`. The gate rule names `task pause`, `resume`, `offwork`, `onwork`, `allow`, `test runner`, `task board` and `doctor --accept`; its pattern does not name `toolpack add`, `toolpack remove`, `reinstall --apply`, `company update --apply` or `tools mcp`, so for those the only person check is the one in the command {src:.harness/policies/gate.json#L133-L136}.
- **Accept and close, or close a task:** no person check in `task close`; the gate refuses `task close` on the agent's command line, and the board's **Close** and **Accept and close** need the paired browser and no code {src:.harness/engine/modules/task/boardserve.py#L697-L711}.

Terminal approvals are also refused while the agent is in the middle of a turn (the section on the busy refusal), unless `--force` is given.

## Approvals internals: git writes and `approve-command`

The gate looks at git commands in a terminal call only when target repositories are set up (`guard_git` is true when the target list is found and configured); without them only the ask list of `gate.json` looks at git {src:.harness/engine/modules/gate/handler.py#L824} {src:.harness/policies/gate.json#L146-L160}. Within `check_terminal`, after the checks of guardrail paths, CLI-owned paths, `.git` folders and target trees, `gitcmd.classify(command)` returns `none`, `approve` or `never` {src:.harness/engine/modules/gate/handler.py#L117-L132}.

**How a line is read.** `classify` splits the line with a quote-aware splitter (`;`, `&`, `|`, parentheses, backticks and new lines separate commands; a backslash and new line is joined first), looks for `git` after wrappers (`sudo`, `env`, `nohup`, `time`, `xargs`, `timeout` and the like), environment settings and numbers, and reads shell command strings inside `bash -c`, `pwsh -Command`, `cmd /c` and the like down to `MAX_DEPTH = 3`. A command string nested deeper that still names git or gh gives `approve` (reason `deep`); inline code of `python -c`, `node -e` and the like that names git gives `approve` (`inline`). The result is the strictest: when one command of the line is `never`, the whole line is `never`, even if another part is an approvable write. The code says in its docstring that this is a net, not a sandbox {src:.harness/engine/modules/gate/gitcmd.py#L1-L9} {src:.harness/engine/modules/gate/gitcmd.py#L299-L341}.

**What is a read.** A fixed set of subcommands (`status`, `diff`, `log`, `show`, `blame`, `rev-parse`, `ls-files` and the like) and `branch`, `tag`, `stash`, `remote`, `config`, `worktree`, `reflog` and `submodule` only in their listing forms. A read still asks for approval when it has an `--output` or `-o` option, a `grep` that opens a pager, a `GIT_*` environment variable, or the options `-c`, `--config-env` or `--exec-path` (`exotic`). A subcommand that contains `$` or `%` or starts with a non-word character (`unclear`), and everything not clearly a read, is a write and needs approval {src:.harness/engine/modules/gate/gitcmd.py#L25-L29} {src:.harness/engine/modules/gate/gitcmd.py#L221-L289}.

**Never approved, exactly.** The order of checks in `_git` is: `git clean` is first excused when its first argument is `--dry-run` or a short-option group containing `n` (it then only lists); then these are never approved: `git push`, `git clean`, `git filter-branch`, `git filter-repo`, `git update-ref`, `git prune`; `git reset` with `--hard`; `git gc` with an argument starting `--prune`; `git reflog expire` and `git reflog delete`; `git branch -D`; and any force. Force is `--force`, `--discard-changes`, `--force=...`, `--force-with-lease...` or `--force-if-includes...` on any subcommand, and a short option group containing a lowercase `f` (`-f`, `-fd`) only for `add`, `checkout`, `switch`, `branch`, `tag`, `mv`, `rm`, `fetch`, `pull`, `worktree`, `submodule`, `clean` and `push`: `-f` of `config` and the capital `-F` of `commit`, `tag` and `config` are not force. A `gh` command whose first word is `pr` is never approved too {src:.harness/engine/modules/gate/gitcmd.py#L30-L37} {src:.harness/engine/modules/gate/gitcmd.py#L49-L50} {src:.harness/engine/modules/gate/gitcmd.py#L212-L218} {src:.harness/engine/modules/gate/gitcmd.py#L253-L296}. For a never command the gate denies with `gate.git.never`: it can never be approved, do not retry with another spelling, the user runs it in their own terminal {src:.harness/engine/modules/gate/handler.py#L130-L132} {src:.harness/engine/core/messages.en.json#L483}.

**How an approvable write is approved.** For a verdict `approve` the gate first calls `approvals.consume(root, session_id, command, minutes)`: an `approved` entry with the same session id and the same command (white-space runs collapsed to one space, `collapse`) is marked `used` and the command runs once. A different session or a different spelling finds no entry. With none, `approvals.request` records a `pending` entry and returns its code, and the gate denies with a text that hands the agent the whole command and the code and tells it to ask the user to run `approve-command`, read the command, type the code, and then run the same command once within the time limit. The same command in the same session keeps its code while it waits {src:.harness/engine/modules/gate/handler.py#L154-L162} {src:.harness/engine/core/approvals.py#L103-L133} {src:.harness/engine/core/approvals.py#L150-L166} {src:.harness/engine/core/messages.en.json#L484}.

**`approve-command`.** `gate/commands.approve` requires `terminal_person()`; lists every pending, alive entry of every session (number, session id, surface, time asked, the whole command); reads one answer; and calls `approvals.approve(root, answer, minutes)`, which finds the pending entry whose code equals the answer (stripped, upper-cased), sets `state = approved` and starts the clock. No entry for the answer, or an empty answer, gives `gate.approve.refused`. Nothing but the command text is pinned: no file content is. The person sees the full command in the list; the approval holds for that string only {src:.harness/engine/modules/gate/commands.py#L37-L61} {src:.harness/engine/core/approvals.py#L186-L203}.

**How long it lasts.** `minutes` is `git.approval_minutes` of the gate policy, default 10 (`DEFAULT_MINUTES`). The clock starts at the moment of approval (`at = now`); a pending request itself stays `PENDING_HOURS = 24` hours from the request, because the person may be away. An approval that was not used by then is dead (`_alive`) {src:.harness/engine/core/approvals.py#L24-L36} {src:.harness/engine/core/approvals.py#L50-L55} {src:.harness/policies/gate.json#L184-L186}.

## Approvals internals: calls to outside systems and `approve-action`

A held call (a command the company's rules mark `outbox`) goes through `check_external` in the gate and the same store with the file `action-approvals.json`. The same steps apply as for git: `consume` an `approved` entry of this session for exactly this command, and only if the files the line names are unchanged since the person approved; otherwise `merge_into_waiting` or `approvals.request` records a pending entry with `extra` (system, environment, verb, target, task, working folder, why it waits), writes a draft `OUTBOX/<code>-<system>.md` into the task, and denies with the code. A subagent's held write, and any held or human call while autorun is on, is refused with no code: nobody is there to approve it {src:.harness/engine/modules/gate/handler.py#L405-L433} {src:.harness/engine/core/outbox.py#L108-L118}.

`outbox.approve_action` (terminal: `approve-action`; board: the `approve-action` action) requires a person, lists the pending calls of all sessions, reads the code, and pins the files with `pinfiles.pins`: the files inside the task folder or a target repository that the command names, at most `MAX_FILES = 12`, each as a sha256 (a file over 8 MB by its first bytes and size). The board passes `seen`, the files and digests the card showed when the person pressed View; when those differ from the files now, it raises `FileChanged` and nothing is approved {src:.harness/engine/core/outbox.py#L269-L302} {src:.harness/engine/core/pinfiles.py#L1-L20}. The approval then lets that command, in that session, run once within the time limit while the pinned files still hold the same content.

Several calls of one task can be approved with one code: `batch_code` is the first six capitals of a sha256 over a secret of the board process (`batch_salt`, new at each board start) and the code, session and command of every ticked call, in the order of their codes. A call that changed, one left out, one added, or a restarted board gives another code. `approve_batch` approves each call as if alone, needs that every call naming files was viewed and unchanged, and approves nothing unless all hold; at most `BATCH_MAX = 60` calls of one task {src:.harness/engine/core/outbox.py#L337-L342} {src:.harness/engine/core/outbox.py#L372-L409} {src:.harness/engine/modules/task/boardserve.py#L292}.

## Approvals internals: the approval files `git-approvals.json` and `action-approvals.json`

Pending and given approvals live in two files in `.harness/runtime/`: `git-approvals.json` for git writes and `action-approvals.json` for outside calls. Each holds `{"entries": [...]}` and is written by `atomic_write` (a temporary file, then a replace, so a reader never sees half a file) under `state_lock`, a lock across processes {src:.harness/engine/core/approvals.py#L19-L20} {src:.harness/engine/core/approvals.py#L84-L85} {src:.harness/engine/core/state.py#L129-L143} {src:.harness/engine/core/state.py#L206-L220}.

**Entry fields.** Always: `code`, `surface`, `session_id`, `command` (white space collapsed), `state`, `at` (the time of the last change of state, in seconds, used for the lifetime) and `created_at`. Added over time: `approved_at`, `used_at`, `dismissed_at` with `reason` and `note`, `opened_at`, `files` (the pins, dropped once used), `wait` (the agent's `harness wait --approval`: `running` with the last beat, `timeout` or `gone`), `told` (how the agent learned of the decision), `offers`, `opened_offers`, `opened_for`; entries of outside calls also carry the `extra` the gate gave (`system`, `env`, `verb`, `target`, `task`, `cwd`, and `zone` where relevant) {src:.harness/engine/core/approvals.py#L103-L133} {src:.harness/engine/core/approvals.py#L186-L281} {src:.harness/engine/core/outbox.py#L108-L118}.

**States.** `pending` (the gate wrote it), `approved` (the person's command or the board's button wrote it), `used` (the gate's `consume` ran the command once; a stub stays so a waiting `harness wait` learns the call has run), `dismissed` (the person said no, or the task closed; a stub with the reason), `opened` (the person opened the connections from the card; the agent is to run the call again, which `settle` then removes) {src:.harness/engine/core/approvals.py#L58} {src:.harness/engine/core/approvals.py#L150-L166} {src:.harness/engine/core/approvals.py#L206-L221}.

**Limits.** The file keeps at most `MAX_ENTRIES = 50` entries, and when it trims it never drops `pending`, `approved` or `opened` ones. A task may have at most `MAX_PENDING = 200` waiting calls (a session without a task has the same count), and `MAX_PENDING_ALL = 2000` in all; past that, `request` raises `TooManyWaiting` and the new call is refused, never an older one dropped {src:.harness/engine/core/approvals.py#L21-L27} {src:.harness/engine/core/approvals.py#L61-L81}.

**Why the agent cannot write them.** `.harness/runtime/**` is in the `guardrail_paths` and in the `admin_locked_paths` of `gate.json`: the agent's edit tools and the terminal's write patterns are refused there, in the person's admin session too. A script the agent runs is read by `scriptcheck`, which refuses one that writes to a guardrail path; this is best effort, and a path built at run time from pieces passes. The gate guards only writes: the agent can read the files {src:.harness/policies/gate.json#L3-L5} {src:.harness/policies/gate.json#L13-L23} {src:.harness/engine/modules/gate/scriptcheck.py#L1-L12}. Writing the files is not the same as approving: approving still needs a terminal, or a one-time pass or a paired browser; and the person's proof of the pass sits in a separate guarded folder, `person/` of the home folder of the guardrail lists {src:.harness/engine/core/boardperson.py#L27-L32}.

**A damaged file.** `_read` returns an empty list when the file cannot be read or parsed, so a damaged file means no approvals: nothing passes by accident; the next write replaces the file {src:.harness/engine/core/approvals.py#L39-L47}. A process of the same user that does not run through the gate is not stopped; the layer is a net, not a sandbox {src:.harness/engine/modules/gate/gitcmd.py#L7-L9}.

## Approvals internals: how the gate knows `PLAN.md` is the approved version

The plan's approval is kept in `.task/task.json` of the task as `plan = {approved_sha256, approved_at, req_sha256}`; the requirement's in `req = {confirmed_sha256, confirmed_at}`; the write-back's in `promote = {state, plan_sha256, approved_plan_sha256, approved_at}` {src:.harness/engine/modules/task/task.py#L469-L471} {src:.harness/engine/modules/task/task.py#L611} {src:.harness/engine/modules/task/task.py#L1020-L1021}. The file `.task/**` is CLI-owned in `gate.json`: edit tools and terminal writes that name it are refused, so the stored digest cannot be forged that way {src:.harness/policies/gate.json#L24-L26}.

`tasks.plan_approved(root, task, data)` answers True only when the task state exists, `PLAN.md` exists (a missing file has an empty digest: not approved), the stored `approved_sha256` equals the sha256 of the bytes of `PLAN.md` now, and the plan was not approved for another requirement (`plan_req_changed`: a stored `req_sha256` that differs from `tasks.req_digest` now; an approval from before this field was kept has none and cannot lapse that way). Nothing resets the approval: it is a comparison made fresh each time {src:.harness/engine/core/tasks.py#L109-L114} {src:.harness/engine/core/tasks.py#L152-L164}.

Where the test is made:

- **The gate, at every write of the edit tools:** `check_task_write` runs for a session that holds an open task; for each path under `<task>/DEV/` (including `DEV/_manual/`) it calls the test and, when the plan is not approved, denies with `task_plan_first`, or `task_plan_req` when the plan was approved for a requirement that is another one now. It is not a test made only when the code is typed. Writes to the task folder itself, the `DEV` folder as a name, and anywhere outside the task folder are refused regardless; `REQ/`, `REF/` and `INBOX/` are the person's {src:.harness/engine/modules/gate/handler.py#L64-L94} {src:.harness/engine/core/tasks.py#L37}.
- **The CLI:** `task fetch` (also `fetch --from` into `DEV/_manual`), `task delete`, `task promote` (a dry run too) and `task approve-promote` call `require_plan` and refuse with the next step; `task fetch --read` copies into `READ/`, which promote never sees, and needs no plan. Autorun cannot be turned on without an approved plan, and a running autorun stops with the reason `plan` when it lapses {src:.harness/engine/modules/task/task.py#L404-L406} {src:.harness/engine/modules/task/task.py#L637} {src:.harness/engine/modules/task/task.py#L676-L679} {src:.harness/engine/modules/task/task.py#L725} {src:.harness/engine/modules/task/task.py#L750} {src:.harness/engine/modules/task/task.py#L915} {src:.harness/engine/modules/task/task.py#L993} {src:.harness/engine/modules/task/autorun.py#L125-L140}.

**What `DEV/` is before the plan is approved.** The folder `DEV/` is created empty when a task is opened (`task open`, in `attach`) only if its tier is `full`; the code makes none for `light` and `medium`. Until the plan is approved the edit tools of the chat that holds the task cannot write under it; its terminal commands are not kept out by this rule (see the feature file's limits) {src:.harness/engine/modules/task/task.py#L205-L206} {src:.harness/engine/modules/task/tasklife.py#L39-L45}. After a rewind that puts an older `PLAN.md` back, the approval waits again: the rewind does not rewind the task state, and the stored digest no longer matches {src:.harness/engine/modules/task/rewind.py#L1-L12}.

## Approvals internals: what the board shows as waiting, and why an approval card disappears

The board computes what a task waits on from facts, in `tasklife.waiting`, and does not rely only on a mark that a message can clear. In order: the agent waits in the tool that asks the person (`asking`); a failed promote (`recover`); a plan file that exists and is not approved (`plan`, with the time of the file's last change; not for a `test` task); a write-back with `promote.state == dry_run` and no `approved_plan_sha256` (`promote`); checks that ran out (`review`); a delivered task to accept; a `full` task whose requirement is written and not confirmed (`req`); a held call (`outbox`); a hand-over; a written-back task to commit; and last the marks the hooks and the commands left {src:.harness/engine/modules/task/tasklife.py#L276-L334}. So the waiting for a plan or a write-back is recomputed each time; it is not cleared by a prompt.

The marks are `go-req`, `go-plan`, `go-promote`, `go-recover` and `go-review` (`GO_MARKS`): the approval commands write `waiting = {why: go-*}` when the person approved and nobody told the agent {src:.harness/engine/modules/task/tasklife.py#L273} {src:.harness/engine/modules/task/task.py#L471} {src:.harness/engine/modules/task/task.py#L1023}. The task hook clears the mark: on every normal user prompt (`on_user_prompt`) a task with a `waiting` or `deliver` mark gets `mark_waiting(ctx, data, False)`, which removes it {src:.harness/engine/modules/task/handler.py#L262-L263} {src:.harness/engine/modules/task/handler.py#L486-L499}. A person typing a question straight into the chat, without `/harness-ask`, sends a normal prompt: the card "tell the agent to go on" for an approval already given is gone, and that turn is not read-only, so the agent may even edit `PLAN.md`, which makes the approval lapse by itself.

The route that spares the card is the marker `/harness-ask` at the start of a message (the Super agent view and its routing add it): the gate's `askturn` makes that turn read-only, and the task hook returns before it clears anything ("no wait or delivery cleared, no resume, no restore point, no new count") {src:.harness/engine/core/askmark.py#L6-L11} {src:.harness/engine/modules/gate/askturn.py#L1-L40} {src:.harness/engine/modules/task/handler.py#L239-L244}.

## Approvals internals: snapshots at the gates, `SNAPSHOT/`

`tasksnap.take(root, task, gate)` copies the task's result files to `SNAPSHOT/<gate>-<UTC time>/files/` and writes `manifest.json` with the gate, the time, the task, one sha256 for the whole result and the path, sha256, size and `copied` flag of each file; the folder name is `<gate>-YYYYMMDD-HHMMSS`, with `-2`, `-3` appended when it exists. It is taken at three moments: when the plan is approved (`plan`), before each independent check (`review-NNN`), and at a promote dry run (`promote`) {src:.harness/engine/modules/task/tasksnap.py#L97-L119} {src:.harness/engine/modules/task/task.py#L474} {src:.harness/engine/modules/task/taskreview.py#L394} {src:.harness/engine/modules/task/task.py#L927}.

Which files count: all files of the task folder except `.task/`, the person's folders (`REQ/`, `REF/`, `INBOX/`), `SNAPSHOT/`, `REVIEW/`, `_deleted`, `READ/`, `OUT/`, earlier rounds (`DEV_r1/`, `PLAN_r1.md`), and at the top level `TASK.md`, `TODO.md`, `LOG.md`, `QUESTIONS.md`, `PROMOTE-PLAN.diff`, `COMMIT-MESSAGE.md` and the like; a file over `max_file_mb` (default 5) is listed and not copied. ## Approvals internals: what binding to content buys, in code

The approval of a plan or a write-back is bound to a digest, not to a time or a session. In code this means: the approval is stored in the task's state, so any chat or session sees it; nothing expires it; a change of the file un-approves it because every test compares the stored digest with the file as it is now; and the gate repeats the test at every write into `DEV/`, so the approval does not rest on the moment the code was typed {src:.harness/engine/core/tasks.py#L159-L164} {src:.harness/engine/modules/gate/handler.py#L73-L90}. A rewind that restores an older `PLAN.md` makes the plan wait again, as `rewind.py` says: the task's state is not rewound, and the approval is bound to contents {src:.harness/engine/modules/task/rewind.py#L10-L11}.

A time limit exists only where there is no digest of the thing: a git write and an outside call, which are bound to the exact command text, the session and `git.approval_minutes`, and, for an outside call, to the pinned files as the person viewed them; a batch code also depends on the board process's secret {src:.harness/engine/core/approvals.py#L24-L36} {src:.harness/engine/core/outbox.py#L337-L342}. The design leaves the screen without content on purpose: the code is shown to the person and the person reads the plan or the diff in the editor.

## Approvals internals: limits, and where the Guide's sources disagree with the code

- **The code is not a secret and not proof of reading.** It is printed in the question, and the gate tells the agent a git or outside call's code; a person who types it without reading is not stopped. The code stops a swap of the content, not a careless yes {src:.harness/engine/core/approval.py#L50-L58} {src:.harness/engine/core/messages.en.json#L484}.
- **Not a sandbox.** The person check tests streams or a pass; the stores are files in the user's own account; a same-user process that does not run through the gate can write them. The modules say so in their own words {src:.harness/engine/core/boardperson.py#L8-L9} {src:.harness/engine/modules/gate/gitcmd.py#L7-L9}.
- **The mid-turn refusal exists in code although `at_work` says approvals do not need it.** `guarded()` wraps the approval commands {src:.harness/engine/modules/task/commands.py#L106-L117} {src:.harness/engine/modules/task/tasklife.py#L793-L796}.
- **Recover on the board.** The description in `task.json` says `recover` stays in the terminal; the default `board.actions` list and the `runner` table include it {src:.harness/policies/task.json#L50-L70} {src:.harness/engine/modules/task/boardserve.py#L154}.
- **`core/approval.py` names three commands in its docstring** (`approve-plan`, `approve-promote`, `recover`); the code behind it serves the others of the list in the first section {src:.harness/engine/core/approval.py#L1-L8}.
