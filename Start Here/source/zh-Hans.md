## 第 2 页 · 共鸣 · AI 在团队里落不了地，难在哪里

假如今天让你把一个真实的 intake 交给 Copilot，从读需求一直做到更新工单。你会怎么做？

我猜大概率是这样：第一步，花半个小时去找相关的代码，一段一段粘贴给 Copilot，再加上一堆代码功能的介绍、需求的背景，写一长串要做的事（to do list）和 Don't，然后祈求它能 100% 完成这个任务。第二步，它写完了，你自己登上 DEV 的 server 跑测试、查数据。第三步，你自己打开 Azure DevOps 更新工单。第四步。。。你还得一行一行地看它写的代码，因为你不敢信它。

1. **AI 只会写代码，剩下的活还是我的。** 跑测试、查数据、看 pipeline 的报错、更新工单、查 incident，这些占了一个任务大半的时间，AI 一样都碰不到。
2. **它不懂我们的 domain，教它比自己干还慢。** 每开一个新 chat，代码流、程序入口、表之间的关系、有哪些坑，全都要从头讲一遍。“我知道直接改哪里，它还要我教。等我把 prompt 写完，活我自己早干完了。”
3. **不敢放手。** 它会不会 push、删表、连错环境？它说“全部测试通过”，你一跑，全是红的。它道个歉：“对不起，是我的疏忽。” 你能怎么办？下次还得自己盯着。
4. **老板问不出答案。** “我们用 Copilot 到底省了多少时间？一个任务花了多少钱？卡在哪里？” 没人答得上来。值不值得在团队里推广，只能凭感觉。

每一条都不大，但每一条都在折损团队用 AI 的信心。最后大家退回舒适区：代码自己写，AI 当一个会思考的 Google。心里还有一个说不出口的担心：要是全交给 AI，那人干什么？

AI 依旧是一个聊天机器人。

【图：一个任务的全部工作排成一排（读需求、找代码、写代码、跑测试、查数据、更新工单、看 pipeline、检查结果），只有“写代码”一格是 AI 的，其余都标着“你”】

## 第 3 页 · 结论和根因 · 缺的不是更聪明的模型，是两种能力

很多人的第一反应是模型不够聪明：换 Opus，把 thinking 开到最高。账单涨了，问题还在。我这几个月的结论是：团队用 AI 不自信、焦虑，是因为缺了两种能力，而这两种能力都不在模型里。

- **纵向能力：agent 能干多少活、懂多少。** 它懂我们的 domain 知识，能读懂需求；它能更新工单、查 pipeline 的报错；它能去 DEV 和 IST 跑测试、查数据；出了 incident，它能查出原因。它管的是第 1、2 条。
- **横向能力：agent 用起来有多安心、多舒服。** 不用写长 prompt；它动手之前要你批准计划，写外部系统之前要你批准；有围栏拦住错误的操作；有第二个 agent 独立检查；任务的进度和花费看得见、查得到。它管的是第 3、4 条。

这两种能力在模型外面那一层：它能连到什么、能读到什么、谁来管它、谁来查它。业界把这一层叫 harness，有一个说法：Agent = Model + Harness。

至于人干什么：人不再每一步都亲手做，而是做只有人能做的决定：定目标、回答它的问题、批准计划、批准结果。

【图：纵横坐标。纵轴“能干多少活、懂多少”，横轴“用起来多安心、多舒服”。左下：Chat AI（只写代码，你来贴）；左上：只有 agent（干得多，但你得盯着每一步）；右上：agent + harness（接住整个任务，又让你放心）】

## 第 4 页 · 解决方案 · 我的 harness 把这两种能力装进 Copilot

我做了一套 harness，装在 GitHub Copilot 外面。模型还是那个模型，变的是它能干的活、懂的东西，和管它、查它的那一层。后面每一页讲一个功能，截图都来自真实的看板。

【图：对照图，三列：难点 → 能力 → harness 的功能】
- 只会写代码 → 纵向 → 读写工单和 pipeline、查出原因、在 DEV 和 IST 上跑测试
- 不懂 domain → 纵向 → 懂我们的 domain 和需求
- 不敢放手 → 横向 → 两次批准、写外部系统前等你批准、围栏、独立检查
- 老板问不出答案 → 横向 → 看板、可审计
- 写 prompt 太慢 → 横向 → 新建任务

## 第 5 页 · 纵向 · 懂我们的 domain 和需求

- **解决什么**：agent 不懂我们的 domain，每开一个新 chat 都要重新讲一遍；读需求也只能照字面理解，需求里的坑要等写完代码才发现。
- **怎么做到**：agent 把一个 domain 学一次，存成知识库：每个对象一张小卡片，写它是干什么的、有什么规则、用到了谁、坑在哪里。脚本算出结构，模型写含义。读需求的时候，它拿需求对着知识库查一遍，把说不清、对不上的地方列出来问你。
- **关键性质**：每张卡都记着它是从哪个版本的代码读来的，代码改了，过期的卡能列出来重新学。业务给的 Word、Excel 由程序转成文本，不花 token。
- **你能拿它做什么**：新人、新 chat、新 agent 都从同一份知识开始，不用你再讲一遍；需求里的问题在写代码之前就列出来，你直接拿去和 business 沟通。

## 第 6 页 · 纵向 · 读写工单和 pipeline

- **解决什么**：工单和 pipeline 都在 Azure DevOps 上，agent 碰不到。读工单、贴结果、看 pipeline，还得你自己去。
- **怎么做到**：harness 用 tool pack 把 Azure DevOps 包成一个固定的程序和一组 skill。agent 直接调用，不用自己拼命令：读工单、读评论和历史、看 pipeline 的运行和日志、看测试结果；写评论、改字段、建工单、关联工单。看板上统一配置连接和登录，每个系统一行：状态、用哪个身份、上次检查的时间。
- **关键性质**：没有删除；没关联到这个任务的工单，写不进去；每次写都等你批准（见横向）。很多公司关掉了 MCP，tool pack 走的是编辑器本来就允许的终端，公司电脑上也能用。
- **你能拿它做什么**：开任务时关联工单，agent 自己读需求，做完自己把结果写回工单。

## 第 7 页 · 纵向 · pipeline 挂了，它自己查出原因

- **解决什么**：pipeline 挂了、出了 incident，人要自己翻日志、对 commit，一查就是半天。
- **怎么做到**：agent 自己读 pipeline 的运行记录、日志和这次的提交，把结论写成一份 RCA：看到了什么；证据，每一条都指向跑出它的那条命令；原因；怎么验证的；下一步。
- **关键性质**：查原因的任务只读，不改任何东西；每条证据都能复查，不是 agent 一句“我觉得”。
- **你能拿它做什么**：把 RCA 直接发给同事或者附到工单上；接着把它 fork 成修复任务，结论和材料一起带过去。

## 第 8 页 · 纵向 · 在 DEV 和 IST 上跑测试、查数据

- **解决什么**：代码写完了，测试还得你自己登 server 跑，数据还得你自己查、自己对。
- **怎么做到**：agent 在终端里用 `sqlcmd` 连到 DEV 和 IST 的数据库，跑测试、查数据，每条命令和返回的结果都记在任务里。
- **关键性质**：只读的查询直接跑；改数据的语句，要你先给这个任务打开 DEV 或 IST 的连接才能跑。QAT 默认不打开，PROD 永远不打开。
- **你能拿它做什么**：让 agent 自己跑完测试、核对完数据，再把结果交给你看。

## 第 9 页 · 横向 · 不用写长 prompt：新建任务

- **解决什么**：开一个任务，要写一大段 prompt 交代背景、规则和步骤，比自己干还慢。
- **怎么做到**：新任务从看板上的一张表开始：名字、任务类型、知识库、关联的工单、要做什么、模型和思考强度。看板替你写好第一条消息发给 agent。每个任务是一个文件夹，需求、计划、进度都是文件，不是聊天记录。
- **关键性质**：流程和规则在 harness 里，不在你的 prompt 里；任务类型决定它走多重的流程，问答轻，开发重。随时开一个新 chat，任务从上次停下的地方接着做。
- **你能拿它做什么**：只填只有你知道的东西，几句话开一个任务。

## 第 10 页 · 横向 · 两次批准：计划和写回

- **解决什么**：AI 一上来就写代码，改了哪里你事后才知道；写进代码库之前也没人把关。
- **怎么做到**：agent 只能写自己的任务文件夹；你批准计划之前，它连任务里放代码的地方都写不进去。代码做完，写回代码库之前要你再批准一次。
- **关键性质**：批准是看板上的按钮，要输入一个绑定这份计划的代码，计划改了就要重新批准；只有和你终端配对的浏览器能按，agent 按不了。写回只建分支，不 commit，也不 push。
- **你能拿它做什么**：动手之前看清它要改什么，写回之前看清它改了什么。

## 第 11 页 · 横向 · 写外部系统之前，先等你批准

- **解决什么**：敢让 agent 读工单，不敢让它写：怕它写错工单、写错内容。
- **怎么做到**：agent 对外部系统的每一次写，都先被拦下来，变成看板上的一张卡：写到哪个工单、写什么、要写进去的原文。
- **关键性质**：你输入卡上的代码再按 Approve，这次批准只对这一条命令有效，10 分钟内有效；agent 自己批准不了。
- **你能拿它做什么**：放心让 agent 写工单，最后一步由你来按。

【截图：等你批准的卡，和批准后的绿卡】

## 第 12 页 · 横向 · 围栏（Guardrails）

- **解决什么**：怕它 push、reset、删文件、改错仓库，甚至改掉管它的规则。在 prompt 里写“不要”拦不住。
- **怎么做到**：agent 的每一次工具调用，执行之前都先过同一个检查程序（gate）。危险的 git 命令、直接改目标仓库、改 gate 自己的规则、计划批准前写代码，都被代码拒绝，并写明原因。
- **关键性质**：拦人的是代码，不是 prompt 里的一句话。每一次拦截都有记录，算进报告。
- **你能拿它做什么**：放心给 agent 更大的权限去干活，不用担心它越界。

【截图：5 次被拒的调用，每次都有原因】

## 第 13 页 · 横向 · 独立检查（Independent review）

- **解决什么**：agent 检查自己的活，总是给自己打高分：“全部测试通过”，一跑全红。
- **怎么做到**：做完的工作交给另一个 reviewer agent。它没看过作者的思路，只看需求、结果和改动；它没有编辑工具；每条意见都要指到文件和行；第一行写 PASS 或 FAIL。
- **关键性质**：要连续通过几次，你在任务页上选（关，或者 1 到 5），只有你能开；通过的次数由代码数，不是 agent 自己报。每多一轮多一份花费，看板会提醒你。
- **你能拿它做什么**：把“它说做完了”变成“另一个 agent 按需求查过了”。

【截图：Review 结果：一次 FAIL（指到文件和行），两次 PASS】

## 第 14 页 · 横向 · 看板：所有任务一眼看清

- **解决什么**：开了好几个 chat、好几个任务，不知道哪个在干活、哪个在等你、等了多久。
- **怎么做到**：所有没关闭的任务都在一个看板上：每个任务在干什么、在等你什么、等了多久。agent 一停下来，hook 就记下“在等你”，不用你一个 session 一个 session 地去翻。
- **关键性质**：看板上的状态来自 harness 自己的记录，不是 agent 说的。
- **你能拿它做什么**：每天打开看板，先处理等你的那几件；一个按钮就能在新 chat 里接着做。

【截图：看板列表：4 个任务、谁在等你、等了多久】

## 第 15 页 · 横向 · 可审计（Auditability）

- **解决什么**：很多团队不知道一个复杂的 AI 任务，时间和钱到底花在了哪里。
- **怎么做到**：harness 基于 Copilot 的 session 记录和自己的 hook 日志，统计每个环节的时间、token 和 Credits 开支、工具调用和被拦下的调用、independent check 的结果。
- **关键性质**：报告全部由代码生成，不是 agent 的总结；看报告不花 token。
- **你能拿它做什么**：每份报告都可以存成 HTML，给团队分享，或者向 leader 汇报。
- **背后还有什么**：`/harness-task-report` 可以替你读报告，再翻 agent 的思考和工具调用历史，找出它在哪里走了弯路：是工具写得不好，规则没说清，还是上下文没加载对。这样才能对症改 harness。【另一个 skill 由你后续补上】

## 英文时要先定的词

- “落不了地”：use AI in real work，不用 land。
- “纵向能力 / 横向能力”：Vertical ability / Horizontal ability（你定的名字）。
- “围栏”：guardrail。“写回”：write the code back to the repository（不用 promote）。
- 环境：测试在 DEV 和 IST；QAT 是用户测的；PROD 只有 incident 才看。
